Reports refold gap and store currency at the source

A stored fold version nobody read made every reporting change non-retroactive — and a lowercase currency code proved it by withholding an entire production briefing

Executive Summary

Two follow-ups from enabling weekly reporting on production Wigclub, where a stale fold silently withheld every total on the newly enabled surface.

The refold gap. reportDay rows stored a foldVersion and reportDirtyDay declared a fold_version_bump reason, but nothing ever produced that reason and nothing ever compared a stored row's version against REPORTS_FOLD_VERSION. Any change to what foldDay computes was therefore silently non-retroactive, and bumping the constant did nothing at all. This change bumps the version 1 → 2 and adds reports/foldVersionRepair, a bounded store-scoped idempotent pass that marks stale days dirty for the existing sweeper, plus a read-only stale count.

The currency source. stores.create inserted the caller's currency verbatim, which is how production ended up with ghs against POS facts carrying GHS. The fold read two currencies, flagged the day mixedCurrency, and weekly completeness turned that into mixed_currency — for which the Weekly UI withholds every figure. This change normalizes on write through the existing shared helper and adds a dry-run-first migration for rows already stored.

Nine files, +397 source lines, one commit off main. Four of the nine files are new modules and their tests; the remaining edits are three lines of behavior and two lines of test-lock maintenance.

Problem and Context

The visible failure was severe and misleading: on production Wigclub, the just-enabled Weekly briefing rendered no numbers. Every total read Unavailable. The mechanism is a fail-closed control behaving exactly as designed on a false premise.

Daily Close stamps its close_snapshot report facts with store.currency. That field held ghs; POS facts held GHS. The day fold compared the raw strings, concluded the day contained two currencies, set flags.mixedCurrency, and excluded the offending facts. Weekly completeness checks that flag first, ahead of allocation and fold-coverage reasons, and returns mixed_currency. The Weekly presentation layer lists mixed_currency among the reasons that withhold all totals.

Worth stating precisely, because it bounds the incident: only close_snapshot facts were affected, and those never contribute to sales totals. Revenue was never wrong. The damage was purely that the surface refused to show anything.

Fixing the comparison inside foldDay was necessary but, on its own, inert — which is how the second and more durable defect was found. The affected days had already been folded. Nothing would recompute them. And the mechanism that was supposed to handle exactly this case did not exist.

Mental Model

Think of foldVersion as a receipt stapled to each materialized day: this row was produced by computation version N. A receipt is only useful if somebody reads it. Before this change, Athena wrote the receipt and never looked at it, and the schema even declared the word for what to do when the receipt is out of date — fold_version_bump — without anything ever saying it.

The circuit was described but never energized:

Before
  foldDay changes  ->  REPORTS_FOLD_VERSION bumped  ->  (nothing)
  reportDay.foldVersion       written, never read
  reason "fold_version_bump"  declared, never produced
  Already-folded days keep their old values forever.

After
  foldDay changes  ->  REPORTS_FOLD_VERSION bumped
       ->  foldVersionRepair.markStaleFoldVersionDays (per store, bounded, opt-in autoContinue)
       ->  reportDirtyDay { reason: "fold_version_bump" }
       ->  existing Reports sweeper  ->  refold with its own caps and retries
       ->  reportDay stamped with the current version

The second defect has the same shape one layer down. A value that must satisfy an invariant was accepted un-normalized at the write boundary, so every downstream comparison had to remember to normalize. Fix the writer, then run a bounded idempotent pass over what the old writer left behind.

Before and After

  • Before: bumping REPORTS_FOLD_VERSION had no observable effect anywhere. After: the bump is the signal, and markStaleFoldVersionDays is the mechanism that turns it into queued work.
  • Before: fold_version_bump was a schema literal with zero producers. After: it is produced by exactly one bounded maintenance path.
  • Before: stores.create stored the caller's currency string verbatim. After: it routes through the existing shared normalizeCurrencyCode, so a lowercase or padded code cannot be stored again.
  • Before: rows already holding ghs had no repair path. After: backfillStoreCurrencyCase normalizes them, dry-run by default, with a read-only verifier.
  • Unchanged: the sweeper remains the single fold authority. Nothing in this change refolds a day inline.

Layer-by-Layer Mechanics

1. The version constant

shared/reportsContract.ts moves REPORTS_FOLD_VERSION from 1 to 2, with a doc block recording what version 2 changes, that mixedCurrency feeds weekly completeness and withholds every total, and — explicitly — that a bump refolds nothing on its own and the repair must be run per store. The normalizeCurrencyCode helper itself is untouched.

2. The repair pass

reports/foldVersionRepair.ts exposes markStaleFoldVersionDays (an internalMutation) and countStaleFoldVersionDays (an internalQuery), each fronting a plain ctx-taking core so the logic is directly testable. Pages come from reportDay via by_storeId_operatingDate scoped to one store, with a default page of 25 and a hard cap of 100.

Staleness is day.foldVersion !== REPORTS_FOLD_VERSION — not <, so a row stamped by a newer version also counts. The predicate is applied in memory over each bounded page, because reportDay's only index is by_storeId_operatingDate. That is a deliberate trade recorded in the source: adding an index to serve a one-shot maintenance path would tax every fold write forever, and the scan is bounded and non-recurring.

3. Marking, not refolding

For each stale day the pass looks up any existing reportDirtyDay mark. If one exists it writes nothing at all and counts the day as already queued. That is deliberate: the sweeper drains oldest-markedAt first, so refreshing recency would push an already-waiting day to the back of the queue and delay a pending close_accepted fold behind a bulk version repair; patching reason would erase that more specific cause; and inserting would duplicate the queue row and fold the day twice. Only when no mark exists does it insert reason: "fold_version_bump".

Both halves matter. Overwriting the reason would erase a more specific pending cause such as close_accepted, and the day refolds either way, so there is nothing to gain. Inserting a second mark would duplicate the queue row and make the sweeper fold the day twice. This deliberately diverges from the sweeper's own newest-reason-wins upsert, because a maintenance pass has no claim to be the most informative reason on the queue.

4. The currency write boundary

inventory/stores.ts normalizes in create. The tests exercise the real mutation through convexTest across ghs, padded " ghs ", Usd, empty string, and whitespace-only, asserting GHS/GHS/USD/GHS/GHS, plus an already-canonical USD passthrough.

5. The migration

migrations/backfillStoreCurrencyCase.ts pages the store table and patches rows where normalizeCurrencyCode(currency) !== currency — a predicate shared with the verifier, which is what makes the pass idempotent by construction. dryRun defaults to true: only an explicit dryRun: false writes, and an omitted value stays a dry run across an entire autoContinue chain. In dry-run mode it still counts mismatches, so the operator sees the blast radius before committing to it.

Uppercasing stored values in place was cleared by a consumer audit first: the currency symbol formatter already keys on uppercase and looks up via .toUpperCase() (so lowercase was the fragile case, not the safe one), every currency equality comparison normalizes both sides, and currency appears in no Convex index, no .eq() filter, no URL, no filename, and no cache key.

6. Continuation

Both maintenance paths take the same opt-in autoContinue as the existing Reports migrations. When set and the page is not done, the batch self-schedules the next page with ctx.scheduler.runAfter(0, ...), forwarding the cursor and running totals. The mutations return per-batch counts alongside a cumulative totals object, so one fire-and-forget call replaces one invocation per page. Without autoContinue they never self-schedule — asserted directly in both test files.

The reference implementation for this shape is convex/migrations/backfillReportFactObservedAt.ts, whose header comment defines autoContinue and whose deployment-ordering comment is the repo's de facto runbook for paged maintenance: run the pass dry first, run it to completion, then page the read-only verifier until it reports zero. There is no runbook document and no cron entry for any of these passes; the contract lives in code comments, and both new modules follow it deliberately.

Failure Boundaries

  • The bump is inert until someone runs the repair. No cron invokes markStaleFoldVersionDays and no read path compares stored versions. Every existing reportDay in every store is now version-stale and keeps serving its stored flags until an operator runs the pass per store and per environment. This is stated in the contract doc block; it is an operational dependency, not self-healing.
  • Repair does not reorder the sweeper queue. The sweeper drains marks oldest-markedAt first. An earlier draft refreshed markedAt on a pre-existing mark, which preserved the reason but pushed that day to the back of the queue and could delay a pending close_accepted fold behind a repair run. The pass now writes nothing when a day is already queued, so queue position is preserved; a regression test asserts both markedAt and reason are untouched, and fails if the patch is reinstated. Backlog volume is still unthrottled: marking a long history enqueues work that competes with live folds.
  • A large backlog drains ahead of live folds. Marking a long history inserts many marks older than subsequent live day_open marks, and oldest-first draining processes the backlog first. Nothing throttles the marking side, so a store with a long history has a multi-tick tail.
  • Non-allowlisted stores queue work that will not drain. The sweeper skips marks for stores outside the read allowlist and leaves them in place, so countStaleFoldVersionDays keeps reporting non-zero. That reading is indistinguishable from "queue still draining".
  • The count query is per-page only. It returns no running totals and cannot self-schedule, so answering "is this store clean?" means paging every cursor by hand — asymmetric with the mutation's totals.
  • Scan cost tracks total days, not stale days, because staleness is an in-memory filter. Bounded and one-shot, and explicitly justified in the source.
  • Only create normalizes. Currency was normalized at the store-creation boundary; a future update path that writes currency without normalizing could reintroduce a non-canonical value.
  • A genuinely foreign currency still fails closed. Version 2 canonicalizes letter case; it does not merge distinct currency codes. ghs versus GHS is one currency, USD versus GHS is still mixed.

What Intentionally Did Not Change

  • The sweeper remains the single fold authority. Repair marks; it never folds inline, so caps, failure handling, and retries stay in one place.
  • foldDay is untouched by this commit — it already normalized each fact's currency before comparing. The fix at the source is stores.create only.
  • No index was added to reportDay. A one-shot maintenance path does not justify a permanent write-path cost.
  • No cron entry was added. Repair is an explicit operator action, not a background behavior.
  • The public surface is unchanged. The new module registers two internal-only functions and adds nothing readable from the client.
  • The exact-equality public-surface assertion in queries.test.ts was not loosened. The new registrations tripped it; the fix was to extend the internal-only list, keeping the assertion exact.

Next-Time Guidance

  • A stored version stamp is an obligation. If a row records the computation version that produced it, some path must compare that stamp to the current one and enqueue repair. A stamp with no reader is worse than no stamp, because it looks like the problem is handled.
  • A declared enum literal with no producer is an unfinished feature. When adding a reason, status, or kind union member, grep for its producer before considering the schema done.
  • When changing what a fold or projection computes, ship the retroactivity plan in the same change: bump the version and name the maintenance call that must run, per store and per environment.
  • Never accept a clean dev environment as evidence about a staleness bug. Dev with rebuilt tables has no stale rows to find, so it cannot reproduce the failure and cannot confirm the fix.
  • Normalize operator-entered values at the write boundary, not at each comparison site. Every un-normalized comparison is a future defect waiting for a second writer.
  • Before rewriting a stored field in place, audit its consumers for index terms, .eq() filters, URLs, filenames, and cache keys. In-place normalization is safe only when nothing derives a key from the old form.
  • Make maintenance passes bounded, store-scoped, idempotent, dry-run-first, and autoContinue-capable, matching the existing migrations, so a production run is one call.
  • When a new registration trips an exact-equality surface lock, extend the allowed list. Loosening the assertion to a subset check destroys the only thing the test was protecting.
