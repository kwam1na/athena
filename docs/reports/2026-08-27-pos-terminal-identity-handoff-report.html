Executive summary

This candidate adds a manager-approved way to transfer one active POS drawer from a lost browser terminal identity to its replacement without inventing a second register session.

The original cloud session remains canonical. The replacement opening amount is retained as a physical cash observation, eligible completed-sale and sale-clear history is replayed through the ordinary projector, terminal authority moves with a revision bump, current browser review rows receive a recovery command, and later uploads use the installed mapping normally.

Why this was needed

Clearing browser identity and registering the same device again creates a new terminal scope. If the original cloud drawer is still active, the replacement browser records a duplicate local open and its later sales cannot infer a cross-terminal register-session mapping.

The review queue is correct to stop: guessing across terminal identities could attach sales to the wrong drawer. The missing capability was an explicit, audited handoff where a manager attests the identity replacement and the stored store, register, duplicate-open, count, and mapping evidence is consistent.

Mental model: change the key, not the cash history

Think of the cloud register session as the ledger for one physical drawer and the browser terminal id as the key currently allowed to operate it. Losing the browser identity means replacing the key; it does not mean opening another drawer.

The handoff therefore preserves the original opening float and the pre-handoff expected-cash baseline in audit metadata, records the replacement count as evidence, applies ordinary sale cash deltas, then changes the authority owner.

Before and after

Before: replacement identity → duplicate open conflict → sales without a terminal-scoped session mapping → manager review items → old terminal still owns the cloud drawer.

After: manager approval → execution-time drawer reread → strict preflight → durable mapping → duplicate open rejected as count evidence → eligible sales replayed in sequence → conflicts settled → authority transferred → old identity marked lost → exact local-review cleanup queued for the replacement browser.

What changed and what did not

The replacement terminal detail page exposes the action only when its public, return-validated read model proves the drawer is eligible. The cash-controls mutation validates the canonical session, approved source terminal, replacement terminal, replacement register number, local drawer id, duplicate-open blocker, physical count, mapping state, and every current review kind before writing.

It deliberately does not relax cross-terminal inference globally, create a second cloud session, replace the original opening float, add non-cash payments to expected cash, delete sync evidence, or alter ordinary non-handoff review behavior.

  • Caller review IDs do not select handoff work.
  • The mutation rereads current needs-review conflicts and drawer events for the exact replacement local drawer.
  • A 501-row sentinel fails closed when either bounded evidence read is incomplete.
  • At most 20 pending completed-sale or sale-clear events and 100 total sale or service lines may replay in one transaction.
  • Inline approval proofs are validated before preflight and consumed only after preflight succeeds.
  • Any post-write projection drift throws so Convex rolls the whole transaction back.
  • The approving proof and manager ids are persisted in the operational audit.
  • A terminal recovery command names the exact repaired event ids and requires a fresh zero-review heartbeat before production completion.

Failure boundaries

The command refuses automatic or rejected actions, stale approval for a different source terminal, inactive or closing drawers, missing or mismatched terminals, a wrong replacement register, mismatched count/open evidence, an existing mapping to another session, malformed history, unsupported review kinds, more than 500 evidence rows, more than 20 replay events, or more than 100 total sale or service lines.

Once mutation begins, a sale that cannot project is an exception rather than a returned command error. That distinction is intentional: throwing preserves all-or-nothing behavior for the mapping, sales, conflict resolution, authority transfer, terminal retirement, and audit record.

  • Operational assumption: the manager is attesting that the old and replacement identities represent the same physical drawer; browser continuity and old-terminal inactivity are not independently proven by this command.
  • A failed preflight does not consume an inline approval proof or mutate drawer state.

How to extend or operate this safely

  • Use this path only when a manager can attest browser-identity replacement of one physical drawer and the stored evidence is consistent.
  • Do not pre-mark the old terminal lost; the handoff validates that it still owns an active session and retires it transactionally.
  • Treat review IDs from the UI as stale by default and reread authoritative pending state at execution.
  • Keep unsupported conflict kinds outside the handoff rather than widening manager approval implicitly.
  • After deployment, invoke the handoff with exact terminal and local drawer identifiers, then verify session owner, expected cash, mapping authority, resolved conflicts, old-terminal status, operational audit metadata, recovery-command acknowledgement, and a fresh zero-local-review runtime heartbeat.
