Executive summary

Athena is migrating its delivery machinery to a managed product that lives in another repository. Before anything cuts over, the product needs to run beside the existing machinery long enough to be measured against it. This change makes that side-by-side window safe to open.

It adds three things: activation metadata declaring the window is shadow-only and holds no delivery authority, a milestone measurement artifact that will hold one entry per shadow delivery, and a read-only guard that enforces four positions — the posture stays shadow, the vendored agent tooling keeps every tracked byte, the managed product's workflow projection appears only inside managed delivery worktrees, and a shadow run counts as evidence only when the product's own binding — never the agent that ran — says the run consumed it.

bun run pr:athena is untouched and remains the only delivery authority. Nothing here can block, reroute, or weaken an ordinary delivery.

The problem

The managed product materializes a run-pinned copy of its workflow text into the worktree a delivery runs in. That is how a managed run gets its instructions. Three things can go wrong while the old and new systems coexist, and each fails in a different direction.

Wrong place. If that projection lands at the repository root, every ordinary delivery — which still runs on the vendored generation — suddenly has a second, untracked source of agent instructions sitting beside the real one. Nobody asked for that, and nobody would notice.

Wrong method. The obvious way to stop the old tooling from being found is to move or edit its files. Do that and the shadow window has quietly become a cutover: there is no removal gate left to pass, and no cheap way back.

Wrong witness. A shadow delivery only measures the new product if the run actually used the new product's workflow text. The only party that can honestly report that is the one that wrote the bytes. Asking the agent whether it used them measures a claim, not a run — and the whole point of the milestone is to compare real behaviour against a frozen manual baseline.

Mental model

Think of a scaffold erected around a building that is still open for business.

  • The building is the vendored tooling. Every ordinary delivery still walks through its front door. Not one brick may move until the scaffold has proven itself.
  • The scaffold is the managed projection. It is erected only in the specific rooms set aside for the trial — managed delivery worktrees — and it is invisible from everywhere else.
  • The guard is the site inspector. It checks four things and refuses to check anything it cannot actually see: is this still a trial, are the bricks untouched, is the scaffold only in the trial rooms, and — crucially — who signed the worksheet.

The signature matters most. The workers on the scaffold cannot sign their own worksheets; the sign-off comes from the scaffold itself, in the form of a marker the product stamps into the projection when it erects it.

Before and after

Before this change.

  • Athena's delivery authority was mapped into a declarative policy document and compared read-only against a frozen pre-cutover oracle (the companion half of this ticket).
  • Nothing said where the managed product could install, where its projection could land, or what made a shadow run admissible evidence. A shadow delivery could have been run — and its results would have been unfalsifiable.

After this change.

  • The window is declared: shadow installation mode, delivery authority none, bun run pr:athena named as the comparison authority, and installation paths restricted to disposable directories that are never the operator's real host configuration.
  • The projection's permitted location is declared and checkable: only inside a managed delivery worktree.
  • The vendored discovery layout is pinned by digest, so a tracked byte cannot move before the cutover's removal gate without failing the guard.
  • The milestone's admission rule exists and is enforced: a delivery counts only on an affirmative record whose source is the product's binding.

What changed, and what deliberately did not

Changed.

  • Added the activation metadata, the milestone gate record, the guard, its suite, and a solution note. Five new files; no existing behaviour edited.
  • Generated Graphify artifacts refreshed by the repository's own pre-commit generator, as for any source change.

Deliberately not changed.

  • pr:athena and every script it chains. No package script was added either: the guard is invoked directly, exactly like the companion policy-projection sensor, so the delivery gate's command graph is byte-identical.
  • The vendored discovery layout. Not a file moved, not a symlink retargeted. That is the property the guard exists to defend, so changing it here would have been self-defeating.
  • Exclusivity is not asserted as blocking. Both graded hosts can add the run-pinned discovery root but cannot scope discovery to it, so coexisting ambient discovery is recorded as a non-blocking observation. Claiming otherwise would have been a claim the hosts cannot deliver — and the guard rejects an activation that makes it.
  • The repository's own skills living beside the exposure symlinks are outside the pinned layout. Including them would have made every unrelated skill edit fail the guard.

Failure boundaries

What this guard does not claim, stated plainly so a later reader does not over-trust it:

  • It does not prevent a projection from being materialized in the wrong place; it detects one that is there. Placement is the product's responsibility.
  • It does not make discovery exclusive. During the shadow window the vendored generation remains discoverable inside managed worktrees too. That is tolerable only because the window holds no authority.
  • It observes the tree it is invoked in, not every worktree on the machine. The scoping rule is a per-invocation assertion.
  • An affirmative consumption record proves the projection's bytes were materialized for that delivery and fence. It is not a proof that the model read them.

Guidance for next time

  • When a migration needs to run beside the thing it replaces, spend the effort on the admission rule before the measurement. A milestone that cannot say which runs count will be argued about rather than decided.
  • Source evidence from the component that produced the effect, not from the component being evaluated. Here that is one line of policy — the record's source must be the binding — and it is what keeps the eventual improvement claim honest.
  • Pin the bytes you promise not to touch. A digest turns "we did not change it" from a claim into a check, and turns changing it into a deliberate two-place edit.
  • Scope a pin to exactly what you mean. Pinning a whole directory because it is convenient makes the guard fail on unrelated work, and a guard people routinely re-pin protects nothing.
  • Do not assert a capability the graded host does not have. Recording a downgrade with its reason is stronger than an aspirational claim, because it tells the next reader exactly what has to change for the claim to become true.

Comprehension quiz

Eight of ten to pass.

  1. Why is a shadow delivery excluded from the comparison set when the agent itself reports that it consumed the run-pinned projection?

    1. Agent reports arrive too late in the run to be recorded.
    2. The agent is the component being evaluated, so its own claim cannot establish that the evaluation happened.
    3. Agent reports are not machine-readable.
    4. The milestone only accepts records written after merge.

    The milestone exists to measure the managed product. A record produced by the thing under measurement measures a claim rather than a run, so only the binding's own marker is admissible.

  2. Where may the run-pinned projection appear during the shadow window?

    1. Anywhere inside the repository, as long as it is untracked.
    2. At the repository root only.
    3. Inside a managed delivery worktree only.
    4. In any worktree that has the product installed.

    The repository root and every non-managed worktree keep the vendored generation authoritative, so a projection outside a managed delivery worktree is a finding.

  3. Why is the exclusivity assertion non-blocking during this window?

    1. Because exclusivity is expensive to check on every run.
    2. Because both graded hosts can only add the run-pinned discovery root, and coexisting discovery cannot corrupt an authority the window does not hold.
    3. Because the vendored generation is already disabled.
    4. Because the milestone does not measure discovery.

    Neither graded host can scope discovery to one root. Since the shadow window holds no delivery authority, coexistence is recorded as an observation rather than asserted away.

  4. What happens if the activation metadata declares a blocking exclusivity position?

    1. The guard upgrades its checks to match.
    2. Nothing; the field is advisory.
    3. The guard reports a finding, because the proving host is graded exclusivity-ungraded and cannot deliver that position.
    4. The guard falls back to the vendored generation.

    A claim the graded host cannot support is worse than no claim, so the guard refuses an activation that makes one.

  5. What exactly is covered by the pinned vendored-discovery-layout digest?

    1. Every file under the repository's agent directories.
    2. The tracked vendored generation tree plus the exposure symlinks that point into it — and nothing else.
    3. Only the active generation pointer.
    4. The whole repository tree.

    Repository-owned skills living beside the exposure symlinks are deliberately excluded; including them would fail the guard on unrelated skill edits.

  6. Why is suppression described as model-external and byte-neutral?

    1. Because the model is asked not to read the vendored files.
    2. Because the binding writes host discovery configuration inside the managed worktree, and no tracked byte of the vendored layout is moved or edited.
    3. Because the vendored files are deleted and restored per run.
    4. Because discovery is disabled entirely during the window.

    Suppression lives in configuration the binding owns, not in the repository's tracked content, which is what keeps the window reversible.

  7. A record says the source is the binding and affirmative is false. What should happen?

    1. A finding, because every shadow run must consume the projection.
    2. No finding, but the delivery is excluded from the comparison set — an honest negative is not a defect.
    3. The delivery counts, since the source is trusted.
    4. The guard rewrites the record.

    Absent, negative, and agent-supplied records all fail to admit the delivery; only the agent-supplied one is additionally a defect.

  8. Why does the milestone gate record live outside every execution grant's writable paths?

    1. To keep the repository's directory listing tidy.
    2. Because it is generated and would be overwritten.
    3. So a session cannot author or edit its own milestone measurement.
    4. Because it is too large for a tracked path.

    It is a measurement artifact, not a journal, and its value depends on the measured party being unable to write it.

  9. How does the suite prove the layout pin is live rather than self-satisfying?

    1. It compares the constant to itself.
    2. It recomputes the digest from git and asserts it equals the pin, and separately drives the guard with a different observed digest to prove drift is reported.
    3. It reruns the guard twice and compares outputs.
    4. It checks the file's modification time.

    One test grounds the pin in the repository's real tracked state; another proves a mismatch is actually surfaced.

  10. What must happen before the shadow-delivery gate can be scored?

    1. The vendored generation must be removed.
    2. The host must be graded exclusivity-capable.
    3. Shadow deliveries matching the baseline's mix and count must be run, each carrying an affirmative binding-sourced consumption record.
    4. The policy document must grant merge authority.

    An incomplete comparison set is reported as an observation, and the gate's improvement comparison cannot be made until the set is complete and admissible.
