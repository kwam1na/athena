Executive summary

After a trusted one-time enrollment from the reviewer’s iPhone, documentation waivers require a user-verified assertion from that sole passkey. Enrollment additionally requires a one-time secret chosen and configured outside agent runtimes. Agents retain full ability to prepare and dispatch a request, but GitHub credentials, a PTY, and possession of the approval URL do not provide approval authority.

The assertion is short-lived, single-use, and bound to the exact repository, pull request, head, base, merge base, deliverable tree, finding codes, and reason. The protected GitHub Environment remains a second review layer, not the proof of human presence. WebAuthn verifies a platform authenticator and user verification; it does not cryptographically attest the Apple device make.

Why the prior boundary was insufficient

A GitHub Environment approval proves that an authorized account approved a job. It does not prove a human was present when an agent can use that account’s token or call the same API. Likewise, hiding an Actions-write token behind a CLI only hides a capability; it does not narrow it.

The required boundary is an authentication ceremony that performs local user verification and signs the exact server challenge without exposing the private credential to the agent runtime.

Mental model

Think of the workflow as a sealed envelope. The agent may fill in the candidate details and deliver the envelope. Convex creates a one-time seal for exactly those details. Face ID unlocks the reviewer’s passkey on the iPhone and produces the seal. GitHub and CI then verify that the sealed envelope, relay run, issuer run, and live pull request still describe the same candidate.

request != approval
agent -> candidate request
iPhone Face ID -> user-verified passkey assertion
relay -> immutable artifact
issuer + CI -> exact-candidate and provenance verification

Before and after

Before: the dispatcher entered a protected GitHub Environment and a repository reviewer approved the job. An agent holding that reviewer’s GitHub credential could potentially reproduce the approval API call.

After: the unprivileged relay first waits for a candidate-bound WebAuthn assertion from the enrolled iPhone passkey. Only an approved request can dispatch the issuer. The issuer consumes the approval once, verifies the immutable relay artifact, and still passes through the protected Environment as defense in depth.

What changed and what did not

  • Added one-time authenticated passkey enrollment for the configured reviewer.
  • Added a public tokenized approval page; the token locates a request but cannot approve it.
  • Added Convex challenge, credential, approval, expiry, counter, and consumption storage.
  • Added a default-branch relay with narrow job-scoped Actions permission and immutable typed artifact.
  • Upgraded waiver attestations to schema v4 with relay and passkey provenance.
  • Kept local waivers, ordinary documentation satisfaction, exact finding coverage, and candidate drift checks unchanged.
  • Kept the protected GitHub Environment as an additional reviewer checkpoint.

Failure boundaries

  • The path fails closed until production configuration, backend deployment, and first trusted iPhone enrollment are complete.
  • The first enrollment is a sensitive bootstrap ceremony: it requires the configured Athena reviewer identity plus a separately held one-time secret, and the bootstrap hash is removed afterward.
  • WebAuthn enforces platform attachment and user verification but does not prove the authenticator is Apple hardware; using the intended iPhone is an operational requirement.
  • There is deliberately no self-service replacement or recovery fallback after enrollment.
  • The pending authentication expires after 15 minutes; successful Face ID opens a separate 10-minute issuer-consumption window.
  • Consumption is idempotent only for the same exact candidate, so transient publication retries reuse the same receipt without authorizing different work; any candidate, base, finding, workflow, actor, or artifact drift rejects the waiver.

Human operating procedure

  • Choose a one-time enrollment secret outside agent runtimes and configure only its lowercase SHA-256 digest in Convex production.
  • After production deploy, sign in to Athena on the reviewer’s iPhone and open the organization settings passkey page.
  • Enter the one-time secret and enroll with Face ID; Athena stores the public credential only, then the bootstrap hash should be removed.
  • For a waiver, let a human or agent run the waiver request command and open the approval URL from the workflow summary on the iPhone.
  • Verify every displayed candidate field, finding code, and reason, then approve with Face ID.
  • Complete the separate GitHub Environment review when the protected issuer requests it.
  • If the candidate changes or the request expires, prepare and approve a new request.
