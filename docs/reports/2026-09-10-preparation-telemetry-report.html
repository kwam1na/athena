Why the extra field matters

A successful preparation previously looked the same in durable telemetry whether checks ran or were reused. Terminal text exposed the difference, but later readers could not recover it safely from a command’s success or requested flags.

V26-1888 came from the Athena cutover’s review. The original receipt and ownership behavior was correct; this follow-up adds the missing durable observation.

The decision travels with its receipt check

The product makes the reuse decision where it validates the receipt. Its successful completion carries that decision into the run export. Athena reads the exported answer.

Telemetry describes what was observed. The existing candidate, base, policy, workspace, wiring and ownership checks continue to govern reuse and admission.

Ordinary prepare always runs checks. Only an explicit --refresh-record-neutral request evaluates reuse. The request is not proof: a reusable receipt and unchanged preparation fingerprint must survive the existing candidate, base, policy, wiring, workspace and ownership checks.

From terminal clue to durable field

Before: prepare executed or reused checks, emitted terminal narration, and recorded a generic successful command completion.

After: the installed 0.4.0 runtime returns a structured preparation object; successful version-2 command completion retains it; the existing export transports it; the Athena scorecard copies the latest retained CLI preparation completion.

prepare → command.completed.payload.preparation → product run export → metrics.deliveryRun.preparation

The reported preparation states

  • executed / ordinary: an ordinary preparation ran its configured checks.
  • reused / validation-equivalent: the existing strict receipt validation permitted reuse.
  • executed / receipt-not-reusable: refresh could not reuse the retained receipt, so checks ran.
  • executed / preparation-fingerprint-changed: the preparation fingerprint changed, so checks ran.
  • null: the latest retained matching completion has no preparation detail; its execution/reuse status is unknown.

Absence stays unknown

Failed or interrupted preparations do not receive a successful preparation object. When their completion is retained, it replaces the older completion and fieldless detail yields null. If the newer completion append is lost, the scorecard can only report the latest retained older completion.

Version-1 journals retain their frozen grammar. Older version-2 records and successful completions can also lack the optional field. None is relabeled as executed. The schema rejects the field on unsuccessful or non-prepare completions and rejects contradictory status/reason pairs.

Overlapping attempts retain the existing ownership rules: a newer attempt can supersede an older receipt, and a failed or interrupted command cannot report successful reuse.

The first real adopter gate exposed a compatibility gap: progress events now occur between the saved gate context and its completion. Athena now skips only declared version-2 progress observations, then requires the latest remaining event before the gate to be its athena-gate context. A real intervening command, a newer context, an unsuccessful or non-CLI gate, or a stale validation digest still prevents attribution.

Observation writes are best effort. If appending a completion fails, telemetry cannot reveal that missing completion. The scorecard reports the latest retained completion, which may be older; if that record has no detail it returns null. Missing telemetry never changes command authority.

How to read future runs

  • Read the latest retained event whose actor is cli, kind is command.completed, and command is prepare. Later executor, other-command or other-kind events cannot replace it.
  • Copy checks and reason together; do not infer reuse from flags or elapsed time.
  • Treat null as unknown: no retained matching completion or no field on the latest match. It does not prove that no newer command ran.
  • Verify the installed archive and runtime digests before relying on a new product field.
