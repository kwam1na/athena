Making the payment verification lane usable at production volume

The report source verifier had a green test suite and could not return a verdict on a real store. When it did speak, it called GH₵3,960 of untouched payment data a mismatch. Both defects were arithmetic against production row counts, and no test could have found either.

Executive Summary

Athena's report source verifier recomputes each day's metrics from primary tables and compares them against what the fold persisted. It was complete, it was tested, and the suite was green. Then it was run against production for the first time, and it failed in two ways at once.

It could not return a verdict. verifyCurrentWeekAgainstSources on the production Wigclub store returned { outcome: "incomplete", reason: "source_cap_exceeded" } — not a pass, not a mismatch, nothing. Every per-day run for 2026-07-27..08-02 returned the same. The payment allocation scan read a 90-day window under a 500-document cap; that window on production holds 1,050 rows, about 12 allocations a day. One over-wide read was costing the entire lane.

And when it did speak, it lied by omission. An incomplete lane fell back to an expected of 0, and the diff builder dutifully compared that zero to the real folded total: { field: "paymentsCollectedMinor", expected: 0, actual: 396000 } with matches: false. Monitoring output that reads as corrupted payment data when nothing had been checked. This is the more dangerous of the two bugs, because it makes a capacity limit and a genuine data discrepancy byte-identical — so a real finding would be dismissed as noise.

The fix is two independently bounded index reads with their ceiling arithmetic recorded beside the constants, and a third result state: unverifiedFields. Three files, 570 insertions against 52 deletions, one commit off main. The gate counts 305 considerable source lines — tests excluded — against a 150-line solution-note threshold and a 300-line report threshold.

The sales lane, throughout all of this, was verifying clean on production on all seven days.

Problem and Context

The verifier exists because a reporting pipeline that only checks itself proves nothing. Its rule, inherited from the read-optimized redesign, is verify against sources, not against the pipeline: recompute the day from posTransaction, paymentAllocation, adjustments, storefront orders and service cases, then diff that against the projection.

Every source scan is bounded, because an unbounded read in Convex is a production incident waiting for a busy store. The payment lane's bound had already been fixed once: an earlier change (766bfe61) introduced PAYMENT_VOID_LOOKBACK_MS and replaced a lifetime scan with the date-bounded window [startAt - 90d, endAt]. That was correct and necessary.

The 90 days are not arbitrary. paymentAllocation is indexed on recordedAt only, but a row contributes to a day at two instants: its original event at recordedAt, and — when voided with a server timestamp — its reversal at voidedAt. A row voided today may have been recorded months ago. To catch that, the scan reached back.

Bounding a read is not the same as sizing it. A 90-day window under a 500-document ceiling is an unstated claim that the store does fewer than about 5.5 allocations a day. Nobody wrote that claim down, and nobody checked it. Production does twelve. So the lane went incomplete on day one of real use, on every day, permanently — even though the rows the period actually needed numbered in the dozens.

The second defect was waiting behind the first, and would have stayed invisible if the first had never fired. There was no way to say "unknown". The verifier had exactly two answers — agreed and differs — so an expectation that could not be established had nowhere to go but differs, against whatever the zero-value happened to be.

Mental Model

Two ideas carry the change. The first is about reads:

One read cannot answer two questions with different volumes. The old scan was asking two things at once:

"What allocations belong to this period?"        ~30 rows   (common, essential)
"Was an older allocation voided during it?"    ~1,050 rows (rare, cheap to lose)

Under one ceiling, the rare question gets to veto the essential one. Split them and each gets a bound proportional to its own volume — and, more importantly, its own failure mode. Running out of in-period rows costs the day. Running out of lookback rows costs only the ability to spot a historical void.

The second idea is about outputs. A verifier needs three states, not two:

StateMeansWhere it appears
agreedChecked, and the source matched the projectionabsent from differences
differsChecked, and they disagreedifferences / paymentDifferences
unverifiedNot checked. No claim is made.unverifiedFields — and nowhere else

Collapsing the third into the second is what produced expected: 0. matches now means precisely "everything checked agreed", so matches: true with a non-empty unverifiedFields is partial verification, not a clean bill of health. Alerting must read both.

Before and After

  • Before: one scan, [startAt - 90d, endAt], ceiling VERIFY_MAX_DOCS_PER_DOMAIN (500). After: two half-open scans on by_storeId_recordedAt with ceilings of 5,000 and 3,000, derived from a measured rate and documented beside the constants.
  • Before: exhausting the read made the whole payment posture unreadable. After: exhausting the lookback ceiling degrades only reversal detection; the in-period posture still verifies.
  • Before: an incomplete lane produced expected: 0 and a false difference. After: the affected fields are withdrawn from comparison and named on unverifiedFields.
  • Before: matches required paymentPosture.outcome === "complete", so "we could not check" read as "it is wrong". After: matches is !truncated && differences.length === 0 && paymentDifferences.length === 0.
  • Before: one day with an incomplete payment lane returned incomplete for the entire week — six clean lanes discarded to say nothing about one. After: the week verifies and unions the withheld field names.
  • Before: weekly reasons included payment_source_incomplete and invalid_payment_allocation. After: both unreachable, and removed from the union. (Repo-wide grep: zero remaining references in source.)
  • Unchanged: the sales, adjustment, storefront and service lanes; PAYMENT_VOID_LOOKBACK_MS at 90 days and its documented blind spot; the persisted schema. Nothing in this commit is stored — unverifiedFields is a return-shape addition only.

Layer-by-Layer Mechanics

1. The two reads

const inPeriodAllocations = await ctx.db
  .query("paymentAllocation")
  .withIndex("by_storeId_recordedAt", (q) =>
    q.eq("storeId", storeId).gte("recordedAt", startAt).lte("recordedAt", endAt),
  )
  .take(VERIFY_MAX_PAYMENT_ALLOCATIONS_IN_PERIOD + 1);   // 5_000

const reversalLookbackProbe = await ctx.db
  .query("paymentAllocation")
  .withIndex("by_storeId_recordedAt", (q) =>
    q.eq("storeId", storeId)
      .gte("recordedAt", startAt - PAYMENT_VOID_LOOKBACK_MS)
      .lt("recordedAt", startAt),
  )
  .order("desc")
  .take(VERIFY_MAX_PAYMENT_REVERSAL_LOOKBACK_DOCS + 1);  // 3_000

The lookback is newest-first. That is not a stylistic choice: a row voided during the period is far likelier to have been recorded recently, so when this read caps out, the rows it keeps are the ones most likely to matter. The two ranges are half-open against each other (.lt("recordedAt", startAt)), so nothing is counted twice. Rows from the lookback contribute only their reversal — their original event belongs to an earlier day by construction — so that loop opens with if (allocation.status !== "voided") continue;.

Only inPeriodCapExceeded sets truncated. Neither read collects.

2. The ceiling arithmetic, written down

The numbers are documented next to the constants, which is the part that would otherwise rot into folklore:

ReadExpected volumeCeilingHeadroom
In-period~30 rows (one operating day ±18h of slack ≈ 2.5 days, at 12/day)5,000~2,000/day — ~165x measured, 10x the old 500 cap
Reversal lookback~1,080 rows (90 days at 12/day)3,000~33/day — ~2.8x measured

The lookback ceiling is deliberately the tighter of the two, because exhausting it is a soft degradation rather than a lost day. Worst-case read budget for the payment lane, per day: (5,000 + 1) + (3,000 + 1) index-backed documents. Measured in practice: about thirty.

3. The seven fields, and why one of them survives

VerifyUnverifiedField names every field whose source-side expectation can be unknown rather than wrong. All seven are payment-side, because the payment lane is the only one that can be withheld while the rest of the day still verifies: three metrics (paymentsCollectedMinor, paymentsRefundedMinor, paymentAllocatedMinor) and four posture fields (paymentUnsettledMinor, paymentAllocationCoverage, paymentAllocationOmittedMinor, paymentHasInvalidAllocation).

if (posture.outcome === "incomplete") {
  return [...VERIFY_PAYMENT_METRIC_KEYS, ...VERIFY_PAYMENT_POSTURE_FIELDS];  // all 7
}
if (posture.reversalLookback.outcome === "incomplete") {
  return [
    ...VERIFY_PAYMENT_METRIC_KEYS.filter((f) => f !== "paymentsCollectedMinor"),
    ...VERIFY_PAYMENT_POSTURE_FIELDS,
  ];                                                                          // 6
}
return [];

The two degradations are deliberately unequal, and the asymmetry is the most interesting line of reasoning in the change. In-period collection cannot be moved by an unseen historical void. A void of a pre-window row lands as a reversal: it adds to paymentsRefundedMinor and subtracts from paymentAllocatedMinor. It never touches what was collected inside the period. So an exhausted lookback withholds refunds, allocation and every posture field derived from them — but paymentsCollectedMinor stays verified. Withholding it too would have been the easy, symmetrical, and strictly less useful choice.

4. Withheld before diffing, not filtered after

const unverifiedFields = unverifiedPaymentFields(paymentPosture);
const unverified = new Set<string>(unverifiedFields);
const differences = diffMetrics(expected, foldedMetrics(day)).filter(
  (difference) => !unverified.has(difference.field),
);

A withheld field is never a candidate for disagreement. Six channels apply the filter: the day's differences and paymentDifferences; the weekly includedDifferences, outsideScheduleDifferences and the two payment equivalents; the accepted-baseline comparison; and the amendment comparison. That last one carries its own reasoning — an amendment is a claim that the week moved, and a field nobody checked has not moved.

5. The week stops sinking

verifyCurrentWeekWithCtx used to return early with incomplete the moment any day's payment posture failed. It now keeps iterating all seven dates and unions the withheld names into one set, so daysChecked: 7 with outcome: "verified" and a populated unverifiedFields is now reachable where the old code returned nothing usable.

6. The deviation: pagination was not available

The brief called for pagination on the in-period lane. Convex permits only one .paginate() per function execution, and this lane runs seven times inside a single verifyCurrentWeekAgainstSources — so pagination was structurally unavailable, not merely awkward. convex-test enforces the rule in the mock rather than letting it pass locally and fail in a deployed backend (node_modules/convex-test/dist/index.js:951):

"Only a single paginated query (`.paginate()`) is allowed per function
 execution. Calling `.paginate()` more than once in a single Convex function
 fails at runtime in a deployed backend."

A single bounded .take(ceiling + 1) is used instead. Anyone planning to paginate a per-day read inside a per-week aggregate in Convex will meet this wall; the workable answer is a well-sized bounded read with the arithmetic written down.

Failure Boundaries

  • In-period allocations exceed 5,000. An honest incomplete: a partial in-period read is a lower bound, never a total that happens to agree. It sets truncated, which forces matches: false, and withholds all seven payment fields. Asserted by refuses a period that exceeds the in-period allocation ceiling.
  • Pre-period allocations exceed 3,000. reversalLookback = { outcome: "incomplete", reason: "lookback_cap_exceeded" }. truncated stays false, the in-period posture still verifies, six of seven fields are withheld. Asserted by degrades only reversal detection when the lookback bound is exhausted.
  • The boundary is narrower than the headline. It is the lookback cap that is isolated from the in-period posture, not the lookback lane as a whole. A pre-window row carrying voided_refund_unsupported or legacy_void_missing_timestamp still sets paymentIncompleteReason and so still degrades the in-period posture to incomplete. That is correct — those are unrepresentable facts, not a capacity limit — but worth knowing before reading the reversal lane as fully independent.
  • A void older than 90 days. Still invisible, deliberately and unchanged. Documented in the module as a known blind spot: bounded staleness, not unbounded drift.
  • A genuine payment mismatch. Still reported. When the lane completes, unverifiedFields is empty and nothing is filtered — asserted directly by still reports a genuine payment mismatch when the lane completes, which expects expected: 9_000 against actual: 396_000 and matches: false. Withholding must not become silencing, and only that test proves it does not.
  • matches: true read alone. This is the one boundary the code cannot close for you. It means "everything checked agreed", and with a non-empty unverifiedFields it is partial verification. The type carries the warning at the declaration site, but any consumer that ignores the list will draw a false conclusion.
  • Nothing reads the new field yet. unverifiedFields has no consumer outside verify.ts and its two test files — no dashboard, alert, or UI branches on it. Until one does, the unchecked/wrong distinction lives in the return shape and not in anything an operator sees.

What Intentionally Did Not Change

  • VERIFY_MAX_DOCS_PER_DOMAIN is still 500, and still governs the completed-transaction, voided-transaction, adjustment, storefront-order and service-case scans. Raising it to cover the payment lane's worst case would have loosened four unrelated bounds to fix one. Those four bounds have not been measured against production either — they were not the lane that failed, which is not evidence they are sized right.
  • PAYMENT_VOID_LOOKBACK_MS stays at 90 days. Only its role narrowed: it now governs the reversal read alone, and its doc comment was rewritten to say so.
  • The sales lane. It was already verifying clean against production, and the whole point of the split is that the payment lane's capacity problem was never the sales lane's problem.
  • The schema and the persisted contract. This commit touches three files and stores nothing new.
  • The posture-level "invalid_allocation" reason and the weekly-fold "payment_invalid_allocation". Different enums from the two that were removed, and untouched.

Next-Time Guidance

  • A green test suite does not establish that a tool works at production scale. Run it against production. Both defects here were arithmetic against real row counts, and every test passed the entire time. For any read-bounded tool, a production dry run is a delivery step, not a follow-up.
  • Never choose a cap without measuring the volume it must clear, and record the measurement, the date, the store and the derivation beside the constant. A cap with no recorded arithmetic is indistinguishable from a guess.
  • Treat a window and a ceiling as one decision. [startAt - 90d, endAt] under 500 docs is a claim about allocations per day; write that claim down and check it. Widening a range means re-deriving the ceiling, and vice versa.
  • A verifier whose failure mode is indistinguishable from a finding is worse than no verifier. The cost is not the false alarm — it is that the next genuine mismatch arrives in the same shape and gets dismissed.
  • Never fall back to a sentinel in a comparison path. expected: 0 is an assertion that the source side is zero. If a value cannot be computed, withhold the field; do not invent one and compare it.
  • Withhold before comparing, not after. Filtering a computed difference list leaves every future channel free to reintroduce the bug — six needed the filter here, and a seventh added later must not have to remember.
  • When one lane of a multi-lane check degrades, degrade that lane. Discarding six clean results to say nothing about one is a worse answer than a partial result with named gaps.
  • Ask what a degradation can actually move. The unequal withholding came from reasoning about causality, not from picking the safe symmetrical answer. Symmetry is often a sign nobody worked it out.
  • Size a regression test like the defect. A ceiling test that seeds ten rows tests nothing about the ceiling; if that means a 60s timeout, set one and say why in the file.
  • To extend this area: the next honest step is a consumer that renders unverifiedFields distinctly from differences, and a production measurement of the five domains still reading under the unexamined 500 cap.

Comprehension quiz

Pass required: 8 of 10.

  1. The payment allocation scan was already date-bounded by an earlier fix. Why did it still fail on production?

    1. The index by_storeId_recordedAt was missing, so the read fell back to a table scan
    2. The bound was applied to voidedAt rather than recordedAt
    3. A 90-day window under a 500-document ceiling is an unstated claim that the store does under ~5.5 allocations a day; production does ~12, so the window held 1,050 rows

    Bounding a read is not the same as sizing it. The window and the ceiling are one decision, and nobody had checked the claim the pair was making.

  2. Why two new ceilings instead of simply raising VERIFY_MAX_DOCS_PER_DOMAIN?

    1. Convex enforces a hard per-query document limit that 500 was already near
    2. One read was answering two questions with very different volumes and very different costs on failure; the shared cap would also have loosened four unrelated scans
    3. The per-domain constant is generated and cannot be edited by hand

    In-period is ~30 rows and essential; the lookback is ~1,080 rows and rare. Under one ceiling the rare question vetoes the essential one.

  3. Why is the reversal lookback read newest-first (.order("desc"))?

    1. A row voided during the period is far likelier to be recent, so if the read caps out it keeps the rows most likely to matter
    2. Descending index reads are cheaper in Convex than ascending ones
    3. It guarantees the lookback and in-period ranges cannot overlap

    Non-overlap comes from the half-open bound .lt("recordedAt", startAt), not from the ordering. The ordering is about which rows survive truncation.

  4. An exhausted reversal lookback withholds six of the seven payment fields, keeping paymentsCollectedMinor verified. Why that one?

    1. It is the only field the weekly projection persists, so it must always be comparable
    2. It is derived from posTransaction rather than from paymentAllocation, so the lookback is irrelevant to it
    3. A void of a pre-window row lands as a reversal — it moves refunds and allocation but can never change what was collected inside the period

    The asymmetry comes from reasoning about causality rather than choosing the safe symmetrical answer. Symmetry here would have been strictly less useful.

  5. What does matches: true with a non-empty unverifiedFields mean?

    1. The day verified cleanly; unverifiedFields is advisory metadata about read cost
    2. Partial verification — everything checked agreed, but the named fields were never compared, and alerting must read both
    3. An internal inconsistency that should never occur and indicates a verifier bug

    This is the one boundary the code cannot close for you. The type carries the warning at its declaration, but a consumer that reads matches alone will draw a false conclusion.

  6. The old output was { field: "paymentsCollectedMinor", expected: 0, actual: 396000 } with matches: false. Why was this called the more dangerous of the two defects?

    1. Nothing had been checked, yet the output was byte-identical to a genuine discrepancy — so a real finding would later be dismissed as a known false alarm
    2. The fallback zero was written back into the projection, corrupting the stored day
    3. It masked the capacity problem, delaying discovery of the cap

    A verifier whose failure mode is indistinguishable from a finding is worse than no verifier. The cost is the credibility of every future alert, not the single false one.

  7. The brief asked for pagination on the in-period lane. Why was a bounded .take(ceiling + 1) used instead?

    1. Pagination cursors cannot be used inside a QueryCtx helper function
    2. Pagination would have been correct but was deferred to a follow-up for time
    3. Convex allows only one .paginate() per function execution, and this lane runs seven times inside one verifyCurrentWeekAgainstSources

    convex-test enforces the rule in the mock rather than letting it pass locally and fail in a deployed backend. Anyone paginating a per-day read inside a per-week aggregate will hit this.

  8. Which pair of tests, taken together, proves the withholding mechanism is safe?

    1. The two ceiling tests — one for the in-period bound, one for the lookback bound
    2. withholds payment fields rather than diffing them against a fallback 0 together with still reports a genuine payment mismatch when the lane completes
    3. The weekly rename test together with detects a void landing in-period against an older allocation

    The first shows unchecked fields are withheld; the second shows withholding did not become silencing. Either alone would be consistent with a broken verifier.

  9. A full local suite run shows 1–2 failures in usePosLocalSyncRuntime.test.ts at around 5000ms. How should this be read?

    1. The known load flake — the file passes 96/96 in isolation and different tests fail on different runs; separately, the three new ceiling tests carry explicit 60_000 timeouts for the same load reason
    2. A regression introduced by the new large allocation fixtures competing for the same workers
    3. Proof the 60s timeouts were set too high and are starving other suites

    The 60s timeouts exist because the ceiling tests seed thousands of allocations to exercise the real bounds and outran the 5s default under contention. A ceiling test that seeds ten rows tests nothing about the ceiling.

    2. Only the 90-day blind spot remains, and it is scheduled for removal in the next slice
    3. No consumer reads unverifiedFields yet, and five other source domains still read under the unmeasured 500 cap — and the change is a delivery candidate at 8033dcce, not merged, not deployed
