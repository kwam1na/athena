Executive summary

This delivery installs a shrink-only backend dependency guard (U1) that snapshots the current Convex backend dependency graph and fails only on new violations while protecting the inventoryLedger and agentHarness kernels from importing product domains.

The guard resolves imports to the real files the runtime loads, finds dependency cycles via Tarjan's algorithm, and compares cycles and kernel-boundary edges against a committed baseline of exact identities. Baseline drift fails until regeneration contracts it; a removed edge can never pay for a new violation elsewhere. The check refuses to pass an empty scan and refuses to absorb a new violation into the baseline.

The check runs as `bun run dependency:check:backend`, is wired into the harness `convex-backend-adjacent` validation surface, and is deterministic. All harness tests pass, the mechanical gate (lint + typecheck) passes, and the change is sensor/guardrail only — no runtime behavior changed.

Problem

Athena's Convex backend has grown to ~245K lines across 199 tables and 617 admitted operations. Over time, implicit dependency cycles formed between modules, making changes risky and harder to reason about.

The inventoryLedger kernel (which owns inventory valuation, costing, and stock movement logic) imports product domains like operations, reports, cashControls, and storeTime. The agentHarness kernel (which owns agent lifecycle, completion, evidence, and runtime contracts) has similar unwanted coupling.

Without a structural guardrail, new cycles could form silently, and product-domain churn could destabilize the core transaction kernels that encode Athena's strongest business invariants.

A first implementation attempt shipped a baseline claiming 0 cycles, but that was a false snapshot: imports were resolved to extensionless paths while graph nodes carried `.ts`/`.tsx` extensions, so no edges ever formed and cycle detection was inert. This delivery corrects the graph identity so the guard sees the real runtime graph.

Mental model

Think of the backend as a directed graph of imports. Some modules are kernels — they encode core invariants and must remain stable. Other modules are product domains — they implement features and churn more rapidly.

The guard draws a line: every file inside a kernel may import platform primitives (convex/values, convex/server, generated schemas) and its own kernel-internal helpers, but NOT product domains. Product domains may import kernels (that's the normal dependency direction).

A baseline captures today's cycles and grandfathered violations. The rule is shrink-only: the baseline can only contract over time as we refactor cycles away, and any removal from the baseline is drift until it is explicitly regenerated. This is not a layering rewrite — it's a ratchet that prevents regression while allowing intentional improvement.

Before vs after

Before: No structural guard existed. inventoryLedger/effects.ts imported convex/operations/inventoryMovements and convex/operations/skuActivity; inventoryLedger/corrections.ts imported convex/operationAdmission, convex/platform/operationAdmission, convex/reports/access, and convex/storeTime/operatingPeriods; inventoryLedger/commerceEffects.ts imported convex/storeTime/operatingPeriods. These 7 edges are grandfathered as known violations in the baseline.

After: A deterministic check (`scripts/convex-backend-dependency-check.ts`) scans the Convex source tree, resolves imports to concrete files (including extensionless specifiers), builds the graph, finds SCCs via Tarjan's algorithm, detects kernel-boundary violations, and compares against the committed baseline (`scripts/convex-backend-dependency-baseline.json`). It blocks on: (1) new dependency cycles, (2) new kernel violations (forbidden or not-allowed imports), (3) baseline drift (removed cycles or removed kernel edges without regeneration), and (4) empty scans (cannot prove green).

The baseline now captures the 4 real cycles and the 7 grandfathered inventoryLedger kernel violations. The violations will be addressed by downstream units (U18 schema composition, U20 POS projector split, U21 catalog import split, U22 cash-controls consolidation) that extract the offending logic into leaf helpers or platform modules.

Next-time workflow

To add a new protected kernel: add an entry to PROTECTED_KERNELS in convex-backend-dependency-check.ts with root, allowedImports, forbiddenImports, and excludedPaths. Every file under the root is checked — no name-based exemption.

If a new cycle is detected: refactor to break it (move shared logic to a leaf helper or platform module) rather than updating the baseline. Use --update-baseline only after intentional cycle removal.

If a kernel violation is detected: the imported logic belongs in a leaf helper (legal imports only) or a shared platform module. Do not add product domains to allowedImports — forbidden prefixes take precedence over allowed entries by design.

Removed cycle or kernel edge without regeneration is baseline drift and fails the check; regeneration is the only way the baseline changes, and it only ever contracts it.

Downstream units that will reduce baseline violations: U18 (schema composition), U20 (POS projector split), U21 (catalog import split), U22 (cash-controls consolidation).

The baseline file (scripts/convex-backend-dependency-baseline.json) is the contract — it should only shrink over time.
