Executive Summary

Athena's delivery harness is fail-closed on purpose. When it blocks, the operator cannot weaken the sensor, cannot auto-repair a semantic failure, and in most cases cannot waive. That makes the failure message the only remediation channel the harness has - and until this change, that channel was free-form prose that every command invented for itself.

This batch makes the blocker a first-class typed object. A fail-closed condition is now constructed at the boundary that detects it, carrying a stable machine code, a discriminated source, sanitized detail, and a non-empty tuple of typed remediations. Executable repairs are argument arrays, not shell strings. Terminal output and structured events are two renderers over that same object, so the two views cannot prescribe different repairs.

Every package-script-reachable harness CLI was migrated onto a shared boundary runner, and an inventory sensor now fails the build when a reachable harness command drifts off the contract. The durable guidance in docs/harness.md, the architecture doc, the registry solution note, and the execute skill was rewritten to match.

The Problem

The harness protects four kinds of trust - navigation, validation, review, and runtime - and its governing rule is that it may refresh files but never silently push repaired evidence past review. Every escape hatch is deliberately expensive. So when the gate says no, the operator's entire path forward is whatever the message happens to say.

That message had no contract. Three separate weaknesses compounded:

  • Two parallel remediation projections. The gate decision carried both a findings array, where each finding had a free-form remediation string, and a separately computed remediation object with machine and human string lists. Nothing kept them consistent, so the terminal could tell an operator one thing while the structured record said another.
  • Bespoke printing per command. Each CLI wrapped itself in its own try/catch, printing its own prefix - [harness:review] BLOCKED:, [pre-push] BLOCKED:, [pr:athena] Preparation blocked: - and some paths dropped remediation entirely while logging only code and message.
  • Shell strings inside prose. Provider-failure and candidate-drift paths built inline literals with commands embedded in the sentence, so automation could only recover the repair by parsing human text.

The Mental Model

Think of a blocker the way you think of a typed exception rather than a printed string.

The old model was print-at-the-point-of-failure: whichever code noticed the problem also decided how it looked, so presentation was scattered across every command and could not be inspected by anything downstream.

The new model splits detection from presentation, mirroring the ownership boundary the harness already applied to policy. The rule the architecture doc now states is that the source that detects a block constructs the blocker; the orchestrator may aggregate blockers and deduplicate remediation ids, but it does not rewrite their ownership, cause, or prescribed repair.

  • The owning boundary answers what is wrong and how to fix it, because only it knows.
  • The orchestrator answers which blockers happened together, and nothing more.
  • The renderer answers how this looks right now - bounded text for a human, a versioned envelope for a machine.
  • Remediation is guidance, not authorization. Nothing in this contract executes a repair on the operator's behalf.

Before And After

The same failure - a stale generated validation-map path owned by the app registry - travelled a very different route before and after.

  • Before: harness:review noticed the drift, formatted a sentence naming the registry file, and printed it with its own prefix. The gate decision separately recorded a findings entry plus two string remediation lists. An operator read the sentence; automation read the strings; nothing guaranteed they agreed.
  • After: the registry boundary calls createHarnessBlocker with a stable code, source of kind gate/obligation/provider/preparation/candidate/command, and typed remediations. formatHarnessBlockers renders bounded terminal guidance; serializeHarnessBlockers emits the versioned envelope. Both read the same object.
  • Before: gate-decision events were schema v1 with decision.findings and decision.remediation.machine/human. After: schema v2 carries blockers exclusively in a blockerEnvelope, and the delivery-run reader explicitly rejects an event that still carries the legacy fields.
  • Before: waiver eligibility inspected resolution.findings. After: it inspects resolution.blockers, matching the same code values against the same WAIVABLE_FINDING_CODES allowlist, so waiver semantics are unchanged.

How The Contract Works

A HarnessBlocker is a code, a source, a summary, optional details, and a non-empty remediation tuple. The non-emptiness is structural, not a runtime assert: NonEmptyTuple<T> is readonly [T, ...T[]], so an empty remediation list fails to type-check at the call site. The same trick types command arguments, so a command remediation cannot carry an empty argv.

The source is a discriminated union whose ids are borrowed from the authoritative registries rather than restated - a gate source takes HarnessGateId, an obligation source HarnessObligationId, a provider source HarnessProviderId, all imported from harness-gate-registry.ts. Because nothing in the repo typechecks scripts/, the union alone would be a convention rather than a gate, so the constructor also rejects at runtime any source no registry owns.

Remediations come in four kinds. command and retry carry argument arrays and are meant to be run as rendered. manual_action and code_change describe work a human must do deliberately, which is exactly where guidance that is not directly executable belongs. Stable kebab-case remediation ids let one command report several blockers while printing a shared repair only once, in first-seen order.

createHarnessBlocker({
  code: "review_evidence_missing",
  source: { kind: "obligation", id: "review.green" },
  summary: "The qualifying candidate has no fresh approved final-green review evidence.",
  remediations: [
    {
      id: "complete-final-green-review",
      kind: "manual_action",
      summary: "Run the approved review workflow for this candidate, or deliberately accept the offered human waiver.",
    },
  ],
});

Failure Boundaries

The contract is deliberate about the difference between an expected block and a genuine crash.

  • Expected non-zero result: runHarnessCliBoundary turns a non-zero return into a harness_command_failed blocker with a rerun command remediation, preserving the original exit code.
  • Known block: a thrown HarnessBlockedError carries its blockers, which are rendered once at the boundary and exit 1.
  • Unexpected exception: createHarnessInternalErrorBlocker maps any other throw to the stable code harness_internal_error, strips control characters, redacts common secret shapes, and always supplies a reproduction command plus an inspect-the-retained-log action. The execute skill now states plainly that this blocker is diagnostic, not self-repair authority.
  • Output is bounded, not unbounded: details are capped per blocker and the joined terminal output is capped overall, while the structured envelope and the retained pre-push log keep the complete sanitized detail.
  • Admission renders decision blockers itself and suppresses the boundary's synthetic blocker, so a blocked gate does not print two competing explanations.

What Changed, And What Did Not

Changed: the contract, the delivery spine, every reachable secondary harness CLI, the gate-decision event schema, and the durable guidance.

  • Added the typed contract and the shared renderers, plus the CLI boundary runner that every migrated command now uses.
  • Migrated the spine - candidate preparation, gate admission and obligations, provider failures, candidate drift, and the pre-push handoff - and then the secondary commands: audit, behavior, check, contract-preflight, generate, inferential-review, janitor, mechanical-check, review, review-evidence, runtime-trends, scorecard, self-review, test, and the documentation waiver command.
  • Moved gate-decision events to schema v2 with an exclusive blockerEnvelope, renamed the ledger's findingCodes to blockerCodes, and made the delivery-run reader reject legacy decision shapes outright.
  • Added the inventory sensor that discovers harness CLIs reachable through package scripts and fails on unregistered commands or a boundary that prints, exits, or throws outside the shared runner.
  • Unchanged on purpose: exit codes, waiver policy and its allowlist semantics, event correlation checks, hook byte and line caps, validation policy, and every successful-path output. The migration was diagnostics-only - it changes how the harness explains a refusal, never what it refuses.

What Review Caught

The three failures below share one shape, and it is the durable lesson of this delivery: a guarantee that lives beside the constructor instead of inside it is documentation, not enforcement.

All three passed the original test suite. None were caught by types. Each was found by a reviewer reading the contract's claims against its code.

A second review pass over the fixes found the sharpest instance of the same shape: the consistency guard added in the first round threw from inside the renderer, which the CLI boundary calls from within its own catch handler. The check meant to protect guidance would have destroyed all of it. Enforcement must not run inside the failure path it protects, so rendering became total and the invariant moved to the static sensor.

  • The sanitizer existed, was tested, and was correct - and ran on one of thirty paths. The constructor called its cleaning function and discarded the return value.
  • The output bound was off-by-one safe and well tested, but truncated from the end, which is where the remediation lived. Correct arithmetic, wrong thing truncated.
  • The enforcement sensor was thorough about the files it could see, and the file it could not see was the delivery spine. A sensor keyed on a naming convention measures the convention, not the boundary.
  • The second round also found the first round's own blind spot: the internal-error fix was applied to the two commands the review named, while harness:review, harness:test and harness:behavior kept the same defect. Fixing what was reported is not the same as fixing what was wrong.
  • A later round found the same shape a third time: two blocked exits built a typed blocker, persisted it to the decision event, and never rendered it. Constructing a blocker is not the same as delivering one - the event and the operator's screen are two separate obligations.

Next-Time Guidance

When you add a fail-closed path to the harness, the contract now tells you where the work goes.

  • Construct the blocker at the boundary that detects the condition, using createHarnessBlocker. Do not add a second free-form error convention, and do not let the orchestrator restate someone else's cause.
  • Take source ids from the registries. If a new obligation or provider appears, its id flows into the source union automatically, and a mistyped id is a compile error.
  • Put executable repairs in command or retry as argument arrays. If the fix needs judgment, it is a manual_action or a code_change - not a sentence with a command buried in it.
  • Register a new harness CLI in the inventory the same day you add it. The allowlist is a migration boundary, not permission for a new unstructured blocker.
  • If you add a blocker code to an already-waivable obligation, add it to WAIVABLE_FINDING_CODES too. Waivability is all-or-nothing across a blocked resolution, so an unlisted code silently makes the whole waiver unofferable.
  • When remediation guidance for the documentation policies changes, update scripts/delivery-documentation-check.test.ts - that note names it as the owning test.
  • As an operator: identify the blocker by code and source, run command and retry argv as rendered, perform manual_action and code_change deliberately, and resolve aggregated blockers as a set before rerunning the authoritative command.

Comprehension quiz

Pass required: 8 of 10.

  1. Why does a fail-closed harness need its failure messages to be a typed contract rather than prose?

    1. Because prose is slower to render in a terminal
    2. Because the operator cannot weaken the sensor, auto-repair a semantic failure, or usually waive - so the message is the only remediation channel there is
    3. Because CI systems cannot display multi-line text
    4. Because typed messages are required for internationalization

    Every escape hatch is deliberately expensive. When the gate refuses, whatever the message says is the operator's entire path forward, which is why it needed a contract.

  2. A blocker is detected inside a provider check. Who constructs it, and who decides how it is displayed?

    1. The orchestrator constructs and displays it, since it has the most context
    2. The provider constructs it; the renderer at the output boundary decides display; the orchestrator may aggregate and deduplicate but never rewrites cause or repair
    3. The renderer constructs it from the provider's exit code
    4. Whichever layer catches the error first does both

    Detection and presentation are separate boundaries. The owning source knows what is wrong and how to fix it; the orchestrator only knows which blockers co-occurred.

  3. Why are remediation commands stored as argument arrays rather than shell strings?

    1. Argument arrays serialize to smaller JSON
    2. So automation can inspect or execute the repair without parsing human output, and so nothing is ever assembled into an injectable shell string
    3. Because the terminal cannot render quotes correctly
    4. Because shell strings are not valid in TypeScript

    The array is the machine representation. Quoting happens only at the moment a human is shown the command, and the array is never joined for execution.

  4. The original createHarnessBlocker called its sanitizing helper on every summary. Why did secrets still reach the terminal?

    1. The helper's regex was wrong
    2. The helper returned a cleaned string and the constructor discarded it, returning the caller's object unmodified
    3. Sanitization ran after rendering
    4. The helper only ran in development builds

    Validation and normalization were conflated. The value was checked and thrown away, so the guarantee held only where redaction happened to be applied by hand - the internal-error path.

  5. What was wrong with bounding the rendered output by truncating the joined string at the end?

    1. It could split a multi-byte character
    2. Remediation was appended last, so verbose blockers pushed the guidance off the end - removing exactly what the contract exists to deliver
    3. The bound was off by one
    4. It made output non-deterministic

    The arithmetic was correct; the priority was not. Guidance now claims its budget before the diagnostic body, and a test proves every remediation id survives a tight bound.

  6. Why did the enforcement sensor report zero findings while the delivery orchestrator sat entirely outside the contract?

    1. The orchestrator was on an explicit exemption list
    2. Discovery keyed on the harness- filename prefix, and scripts/pr-athena-delivery-run.ts does not have it, so the file was structurally unreportable
    3. The sensor only ran in CI
    4. The orchestrator had no import.meta.main boundary

    A sensor keyed on a naming convention measures the convention rather than the boundary. Registration is now the mechanism and discovery is the drift alarm over it.

  7. harness:check found a stale generated doc and threw a bare Error. What did the operator see, and why does it matter?

    1. A clear stale-docs message; it does not matter
    2. harness_internal_error with generic reproduce-and-inspect guidance, replacing the registry-source remediation that this exact failure motivated
    3. A silent exit 0
    4. A TypeScript compile error

    The CLI boundary maps any unrecognized throw to the internal-error blocker, which is reserved for genuinely unexpected exceptions. Expected policy failures must carry their own code and repair.

  8. Two blockers carry a remediation with the same id but differently worded summaries. What now happens?

    1. Both are printed in order
    2. It throws, because a shared id is a claim that the repair is the same and the renderer prints it only once
    3. The longer summary wins
    4. They are merged into one combined summary

    Dedupe by id is lossy by design, so id reuse has to mean identical guidance. Divergence used to silently keep whichever phrasing appeared first.

  9. What is the honest limit of the static enforcement sensor?

    1. It cannot read TypeScript at all
    2. A new CLI that is neither harness--prefixed nor registered is invisible to it; that gap is covered only by the runtime source guard in createHarnessBlocker
    3. It cannot detect console.error
    4. It only works on committed files

    The limit is documented rather than implied, which is what V26-1223 asked for: where static discovery cannot cover dynamic blockers, require registration and state the boundary.

  10. What is the correct reading of a harness_internal_error blocker's details?

    1. A shell command to run as-is
    2. Diagnostic context - inspect the retained log and use the named reproduction command; it is not self-repair authority
    3. Proof the gate should be bypassed
    4. A list of files to delete

    Remediation throughout this contract is guidance, not authorization. The internal-error path especially: its details are sanitized exception text, not an instruction.
