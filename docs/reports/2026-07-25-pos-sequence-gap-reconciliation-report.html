POS Upload-Sequence Gap Reconciliation And Owed Daily-Close Sweep

A burned upload sequence — a number allocated to an event that never became durable — parked every later POS event behind a predecessor that could never arrive, wedging terminals permanently and stranding a store day's books open. This delivery adds durable gap state, a pure escalation policy, a cloud reconciliation sweep, terminal-side blocker diagnosis, and an owed daily-close sweep.

Executive Summary

POS terminals upload offline events under a per-cursor uploadSequence, and the server only ever projects acceptedThroughSequence + 1. Everything ahead of that is parked as held/out_of_order until its predecessor arrives. That rule keeps offline POS history in causal order and is correct as long as every allocated sequence eventually shows up — but a sequence can be burned: purged by ledger maintenance, lost to a torn write, or rejected client-side after its number was already allocated. The successors then wait on a predecessor that no longer exists anywhere, and the terminal wedges permanently.

This delivery gives the system a way out. Ingest records durable gap state on the cursor; a pure policy module decides when waiting has become pointless; a new cron drives a probe-then-bounded-skip ladder; and the terminal now diagnoses why it is held instead of guessing. Every skip records a manager-visible conflict naming the exact sequences that were stepped over. A companion sweep, owedDailyCloseSweep, removes the eligibility-window cliff that let this wedge strand a store day’s books open permanently.

Problem And Context

When a sequence is burned, no component was empowered to conclude “that number is never coming.” Sales and register closes stayed local forever while the scheduler looped the same held batch behind exponential backoff. The only exit was a human noticing a sync_stuck alert and invoking support tooling.

The terminal made this worse by guessing. It learned only that its batch was blocked, not by what, so it assumed a stuck needs_review precursor and drove a review-inclusive drain — a no-op whenever the real cause is a missing upload sequence.

The wedge then took out an unrelated subsystem. runConfiguredDailyOperationsAutomation closes a store day inside a roughly four-hour eligibility window. On 2026-07-24 a wedged terminal held the register-close event, so the day carried a register_session blocker through all five eligibility runs — and the wedge cleared 76 minutes after the last one. Nothing ever revisited the day, so the books stayed open permanently and only a support-invoked mutation could finish them.

Mental Model

Think of the cursor as a ticket-window queue that serves strictly in numbered order. Normally that is exactly what you want: it guarantees a refund never gets processed before the sale it refunds. But if ticket 47 is destroyed on the way to the window, the queue does not stall for a moment — it stalls forever, and everyone holding 48 and up waits on a person who will never arrive.

The fix is not to abandon ordering. It is to give the window an escalation procedure: notice that 47 has been missing a while, page the person holding it, and only after they either confirm they lost it or fail to answer for a full day, call 48 — while writing down, publicly, that 47 was skipped. That written record is what turns a silent hole into something a manager can investigate.

Before And After

  • Before: a burned upload sequence wedged a terminal indefinitely; the only exit was a human reading a sync_stuck alert.
  • After: reconcilePosLocalSyncSequenceGaps runs every 15 minutes in prod and drives an automated observe → probe → skip ladder off durable cursor state.
  • Before: the terminal knew only that it was held, and guessed the cause was a stuck needs_review precursor.
  • After: diagnoseHeldSyncBlocker compares the awaited sequence against the local ledger and reports heldBlockerKind plus heldBehindMissingUploadSequence on the heartbeat.
  • Before: a skipped sequence would have been an invisible hole in history.
  • After: every skip records a sequence_gap_skipped conflict naming each stepped-over sequence, surfaced to managers in RegisterSessionView.
  • Before: a blocker outliving the ~4h daily-close eligibility window stranded the day open permanently.
  • After: owedDailyCloseSweep derives the owed-day set from dailyClose rows and revisits each until it closes or is escalated.
  • Before: usePrint could double-print, and could call print() into a window already being torn down (“The provided callback is no longer runnable”).
  • After: a single runPrint path guarded by hasPrinted/isClosing serves both the load handler and the slow-load fallback.

Layer Breakdown

Policy (pure). convex/pos/application/sync/sequenceGapPolicy.ts decides from durable gap state alone — no clock, no database — so the escalation ladder is unit-testable and every threshold is readable in one place: SEQUENCE_GAP_PROBE_AFTER_MS (15 min), SEQUENCE_GAP_MIN_OBSERVATIONS_BEFORE_PROBE (2), SEQUENCE_GAP_SKIP_AFTER_UNANSWERED_MS (24 h), and SEQUENCE_GAP_MAX_SKIP_SPAN (5).

State. posLocalSyncCursor gains an optional gap object (missing sequence, first/last observed, observation count, probe id and time). ingestLocalEvents writes it when a gap is observed and clears it the moment the cursor reaches the awaited sequence; LocalSyncIngestionRepository grows getSequenceGap and a required gap argument on updateAcceptedThroughSequence so no call site can forget to clear it.

I/O. reconcileSequenceGaps.ts gathers terminal evidence, asks the policy, then probes, skips, or leaves the gap alone. It is bounded: 20 cursors per sweep, 50 held successors re-projected per skip.

Terminal. src/lib/pos/infrastructure/local/syncGapDiagnosis.ts produces a HeldSyncBlocker; usePosLocalSyncRuntime reports it on the heartbeat via the posTerminalRuntimeSyncValidator fields.

Operations. convex/operations/owedDailyCloseSweep.ts derives owed days and delegates each to the existing runHistoricEodAutoCloseForDate, which already carries the idempotency key, schedule-range resolution, quarantine rules, and historical currentness mode. Three helpers in dailyOperationsAutomation.ts were exported to support it.

Failure Boundaries

  • Positive assertions are never overridden. awaiting_local_upload and awaiting_review are the terminal stating it still holds the awaited event; the policy must not skip past either. Only missing_locally evidence or an unanswered-probe timeout permits a skip.
  • Bounded skip span. More than 5 consecutive sequences means something structural (a ledger reset, a restored backup, a cursor pointed at the wrong session) and escalates rather than writing history past it.
  • No silent skips. A skip that fails to record its sequence_gap_skipped conflict would defeat the entire safety argument — the conflict is the safety story, not a nicety.
  • Owed days are derived, never stored. dailyClose rows remain the sole authority; a parallel owed-days table could drift, and drift in an accounting ledger is worse than the original bug.
  • The sweep cannot force a close. A day closes only when the decision adapter judges it eligible; a real cash variance or pending approval keeps it open indefinitely and escalates past the staleness threshold.
  • Lookback is bounded. The sweep reaches back far enough to cover a long weekend plus a holiday; a backlog older than that is systemic and wants a human.

Next-Time Guidance

Any protocol that allocates a sequence number before the payload is durable needs a documented, automated answer to “what if this number never arrives?” Strict ordering without a reconciliation path converts one lost event into permanent, unbounded data loss.

When a client can only observe that it is blocked, give it enough information to determine why before it acts — a remediation driven by a guessed cause is a no-op at best. And whenever an automation runs inside a time window, ask what happens if the blocker clears one minute after the last run; if the answer is “nothing, ever,” the window is a cliff and wants a sweep.

Comprehension quiz

Pass required: 8 of 10.

  1. What is a “burned” upload sequence?

    1. A sequence number the server rejected as malformed.
    2. A sequence number reused by two terminals at once.
    3. A number that was allocated to an event which then never became durable, so it can never arrive.
    4. A sequence number above the cursor's maximum value.

    The event is purged, lost to a torn write, or rejected client-side after its number was allocated — permanently consuming that slot.

  2. Why does one burned sequence wedge a terminal indefinitely rather than briefly?

    1. The server only projects acceptedThroughSequence + 1, so every successor is parked forever behind a predecessor that will never arrive.
    2. The terminal deletes its local ledger on the first held response.
    3. Exponential backoff eventually exceeds the cron interval.
    4. The cursor resets to zero and replays from the beginning.

    Strict in-order projection is correct only if every allocated sequence eventually shows up; when one cannot, the queue stalls permanently.

  3. What is the escalation ladder the gap policy follows?

    1. Skip immediately, then notify.
    2. Alert a human, then wait for manual resolution.
    3. Reset the cursor, then replay all events.
    4. Observe, probe the terminal, then skip only on evidence or timeout.

    Deliberately slow to skip and fast to close: skipping is the last resort.

  4. Why is sequenceGapPolicy.ts written as a pure module with no clock and no database access?

    1. Convex forbids database reads inside policy files.
    2. So the escalation ladder is unit-testable and every threshold is readable in one place.
    3. To let it run on the terminal instead of the cloud.
    4. To avoid counting toward the delivery diff fingerprint.

    It decides from durable gap state alone, which keeps the thresholds honest and testable.

  5. What makes skipping a hole safe rather than silent data loss?

    1. Skipped sequences are re-requested from the terminal afterward.
    2. Only sequences confirmed empty by the server are ever skipped.
    3. Every skip records a sequence_gap_skipped conflict naming each stepped-over sequence, so a lost sale surfaces as a drawer discrepancy for a manager.
    4. Skips are reversible for 24 hours.

    The conflict is the safety story — it converts a silent hole into a specific thing a human can investigate.

  6. Which terminal blocker kinds must reconciliation never skip past?

    1. awaiting_local_upload and awaiting_review, because both are the terminal positively asserting it still holds the awaited event.
    2. missing_locally, because the terminal may be wrong.
    3. none, because it carries no information.
    4. All of them — skips are only ever driven by probe timeouts.

    A positive assertion that the event still exists outranks the timer; only missing_locally or an unanswered-probe timeout permits a skip.

  7. Why does SEQUENCE_GAP_MAX_SKIP_SPAN cap a single reconciliation at 5 consecutive sequences?

    1. To stay inside Convex mutation size limits.
    2. A handful of burned numbers is the known failure mode; a long contiguous run means something structural is wrong and a human should look before history is written past it.
    3. Because conflicts can only reference five sequences.
    4. To keep the sweep under its 20-cursor budget.

    A ledger reset, restored backup, or misaimed cursor produces a long run — a fundamentally different problem than a burned number.

  8. What did the terminal previously get wrong about being held, and what fixed it?

    1. It ignored held responses entirely; now it retries them.
    2. It retried too aggressively; now it backs off.
    3. It knew only that it was held and guessed the cause was a stuck needs_review precursor; diagnoseHeldSyncBlocker checks the awaited sequence against the local ledger instead.
    4. It reported the wrong terminal id; the heartbeat now carries the cursor id.

    The guessed cause drove a review-inclusive drain, which is a no-op when the real blocker is a missing sequence.

  9. Why is the owed-day set for owedDailyCloseSweep derived rather than stored in its own table?

    1. dailyClose rows are already the authority on which days are closed, and a parallel table could drift from them — drift in an accounting ledger is worse than the original bug.
    2. Convex does not support additional tables in this schema.
    3. A stored set would be too large to query within limits.
    4. It was derived only to avoid a schema migration and should be stored later.

    Deriving keeps a single source of truth for closed days.

  10. What general lesson should you carry to the next time-windowed automation?

    1. Widen the window until blockers cannot outlive it.
    2. Force the action once the window closes, regardless of blockers.
    3. Store the pending work in a dedicated table so it is never lost.
    4. Ask what happens if the blocker clears one minute after the last run — if the answer is “nothing, ever,” the window is a cliff and needs a companion sweep.

    The sweep reframes the question from “is now the right time?” to “what is still owed, and is it possible now?”
