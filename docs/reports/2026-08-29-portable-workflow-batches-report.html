Executive summary

Athena now exposes the five remaining portable workflows from the already qualified core-v1 generation to Codex and Claude Code. The migration is intentionally small: four dependency workflows move first, then the deliver-work entry point moves after them.

The batch record is bound to the accepted shadow comparison and successful kernel canary. The prior Athena deliver-work bundle is retained by content digest, and a disposable rehearsal proves that the entry point can be restored and the newly introduced workflows removed after the portable source is unavailable.

Athena repository policy does not move. Harness evidence, merge gates, review, telemetry, reporting, deployment, generated artifacts, pull-request rules, domain rules, and the full policy-authorized Linear surface remain local overlays.

Why batch migration needed another boundary

The shadow phase proved observational parity without authority. The canary then proved one reversible authority switch. Completing the migration still needed a bounded answer to three questions: which workflows move, in what dependency order, and what exact state is restored if the entry point or its dependencies regress.

Moving every generated workflow in one step would obscure those answers. Creating a new lifecycle or telemetry system would also duplicate infrastructure that already qualified the release. The delivery therefore records only the missing batch facts and reuses the existing release, canary, baseline, and delivery telemetry.

Mental model: replace the tools before the doorway

Think of deliver-work as a doorway and the planning, execution, review, and compounding workflows as the tools behind it. The first batch puts the qualified tools in place. The second batch switches the doorway to the portable entry point.

Rollback walks backward. Restore the old doorway first, then remove the newly introduced tools. This keeps the repository usable at each boundary and avoids inventing predecessors for workflows that did not exist in Athena before the migration.

Before and after

Before: only the portable kernel canary was authoritative. Athena still owned deliver-work, and the four portable dependency workflows were not exposed under the two host discovery roots.

After: both hosts resolve the same five remaining workflow bodies from the managed core-v1 generation. The prior Codex deliver-work body and metadata are retained exactly. The accepted characterization documents remain unchanged and are reconstructed through verified predecessor projection.

How admission and rollback work

  • The manifest names two ordered batches, exact workflow digests, both exposed hosts, the accepted release, the shadow comparison, the kernel canary prerequisite, and every baseline disposition.
  • The current-batch sensor verifies the strict manifest, accepted canary, exact workflow bodies, host links, classification inventory, and retained entry-point predecessor.
  • The baseline projection verifies only the strict record, predecessor bytes, and exact links it ignores. Full current-authority admission remains the separate batch check.
  • The rollback rehearsal copies the active workflows and predecessor into a disposable root, deletes the managed current generation, restores the prior entry point, removes the primitive exposures, and checks an unrelated sentinel byte-for-byte.
  • The characterization sensor still validates the original 31 assertions, 24 closure members, 7 scenarios, and 145 residual files.

What changed and what stayed local

Changed: five relative host links, one exact two-batch manifest, one retained predecessor bundle, one focused adoption sensor with rollback rehearsal, and the existing baseline projection needed to reconstruct the former deliver-work paths.

Stayed local: Athena’s track workflow and full Linear operations; repository discovery and policy precedence; harness and review evidence; pr:athena authority; telemetry and reporting; deployment policy; generated-artifact obligations; pull-request rules; and domain-specific constraints.

Failure boundaries

  • A changed manifest, workflow body, host target, classification disposition, predecessor file, accepted canary, or shadow identity fails current batch admission.
  • A malformed exposure cannot be hidden from residual discovery because the projection verifies every ignored link first.
  • An unresolved shadow or canary mismatch blocks the batch through the accepted canary prerequisite.
  • Rollback does not need the original release archive or source checkout; the retained predecessor is the only restoration input.
  • Qualification fixture hygiene does not become a production issue-count limit or reduce Linear operations.

Validation and finish line

Current evidence: 75 focused portable adoption, canary, and baseline tests pass; the batch and canary checks pass their source-independent rollback rehearsals; the accepted baseline remains green; the final root harness passes 1,698 tests with zero failures; Graphify is rebuilt and fresh.

Independent correctness review found no issues. Independent simplicity review identified one coupling and four small duplicates; the projection was narrowed and the duplicate marker, hashing, policy proxy, and stale fixture names were removed. The full pr:athena gate, hosted checks, merge, and root alignment remain pending. Deployment is deliberately omitted because this delivery changes repository infrastructure, not the application runtime.

Operating guidance

  • Keep the exact release, accepted shadow, and successful canary as prerequisites for any later exposure change.
  • Put dependencies in place before switching an entry point; roll back the entry point before dependencies.
  • Retain only real predecessor bytes. Remove newly introduced exposures instead of fabricating historical versions.
  • Keep current adoption checks separate from immutable characterization reconstruction.
  • Do not move Athena policy or constrain host-native Linear capability as a side effect of portable workflow reuse.
