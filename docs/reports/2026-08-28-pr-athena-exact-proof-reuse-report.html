Executive summary

This candidate lets a repeated bun run pr:athena invocation reuse the repository's existing validation proof only when the exact staged delivery identity and every observed authority input still agree. The command remains the final authority; reuse is an admission result of that command, not a shortcut around it.

A reusable result skips the five merge-grade phases and reports proof_reused in memory. It does not overwrite the authoritative full-run latest or history ledgers. Every missing, stale, malformed, contradictory, unreadable, or changed input names the reason and runs the normal full gate.

Why repeated validation needed a safe fast path

Athena already records a Git-private proof after a successful full delivery gate, and pre-push can reuse it. Running pr:athena again on the same prepared candidate nevertheless repeated the expensive phases because the proof evaluator's default clean-worktree posture did not admit the staged-index state that pr:athena itself validates.

The useful outcome is not generic caching. It is narrowly avoiding duplicated work when the repository can prove that the candidate, base, validation wiring, proof bytes, and authoritative ledger still describe the same accepted delivery.

Mental model: a boarding pass checked against the manifest

The stored proof is a boarding pass, not permission to fly. pr:athena is the gate agent. Before admitting reuse, it checks the pass against the current passenger identity and the authoritative flight manifest: the exact tree and base, validation wiring, proof bytes, five-phase delivery ledger, and gate decisions.

If every observed identity agrees, the gate agent records that the current admission reused an already completed inspection. If any identity is absent or disagrees, the boarding pass is not trusted and the full inspection runs.

  • Proof evaluator: verifies the current candidate and stored proof contract.
  • Authoritative ledger: proves the complete gate actually ran and passed.
  • pr:athena wrapper: owns the reuse or full-run admission decision.
  • Existing telemetry: distinguishes proof reuse without creating another evidence plane.

Before and after

Before: pre-push could reuse a valid clean-worktree proof, but a repeated pr:athena invocation always ran prepare, preflight, validate, record-proof, and scorecard again.

After: pr:athena calls the same evaluator in an explicit staged-index mode. It independently corroborates the reusable proof against one canonical completed ledger. A match skips the phases; every other status falls through to the unchanged full gate. Pre-push keeps its clean-only default.

How reuse is admitted

First, the wrapper reads the current deliverable fingerprint and authoritative latest-ledger bytes. The shared evaluator then checks the staged candidate, base, Bun version, command wiring, validation fingerprint, and stored proof shape. Review-loop evidence remains best-effort telemetry and does not authorize reuse.

Second, the evaluator makes one final concurrent observation of candidate identity, exact proof bytes, and ledger stability. It performs no later awaited work before returning. This closes the earlier serial race windows without claiming an atomic filesystem snapshot.

Third, the wrapper requires a canonical passing ledger with the exact ordered prepare, preflight, validate, record-proof, and scorecard spans; recomputed summary and duplicate metadata; and matching admitted gate events. Only then does it return proof_reused and skip commands.

If full fallback runs, failed phases clear the old proof. Prior malformed latest or baseline files cannot strand recovery, and only a complete five-phase pass can become the next scorecard baseline.

Failure boundaries

  • Missing or unsupported proof: run the full gate and report why reuse was unavailable.
  • Tree, base, Bun, command, or validation-wiring drift: reject reuse and run the full gate.
  • Incomplete, contradictory, stale, or unreadable authoritative ledger: reject reuse and run the full gate.
  • Candidate, proof, or ledger change visible during the final observation: return stale and run the full gate.
  • Fallback phase failure: clear stored proof so a later retry cannot reuse evidence for a failed run.
  • Malformed latest content is non-authoritative and can be overwritten by a successful full run. A malformed baseline reads as missing on that run; on the following full run, the prior healthy latest ledger can be promoted as the baseline.
  • Concurrent filesystem observation is not atomic; eliminating the remaining external-writer boundary would require locking or a new atomic authority source, intentionally outside this delivery.

What changed and what intentionally did not

Changed: pr:athena can admit exact staged proof reuse; proof_reused is accepted by delivery telemetry; authoritative-ledger corroboration and baseline recovery are stricter; and operator output names reuse or the fallback reason.

Unchanged: pr:athena remains the final authority; the full phase order and commands are unchanged; pre-push stays clean-only by default; no reusable result overwrites full-run latest/history evidence; no new cache, receipt, proof format, telemetry plane, deployment behavior, or Linear capability constraint was introduced.

How to extend or debug this safely

  • Keep one shared proof evaluator; add new invalidation inputs there instead of creating another cache contract.
  • Treat reusable as an admission result only after corroborating the complete authoritative ledger.
  • Keep pre-push's clean-only default distinct from pr:athena's explicit staged-index mode.
  • When fallback behaves unexpectedly, inspect the named proof status, latest ledger, baseline, and final candidate identity before changing policy.
  • Preserve the last complete full-run ledger when reuse succeeds; a zero-command reuse result is not replacement evidence.
  • Prefer fail-closed fallback over locks, new orchestration, or generalized cache infrastructure unless a future measured need changes the contract.
