Executive summary

Athena now has a reusable obligation layer in front of expensive harness gates. The first adoption guards the heavy pr:athena validation provider: qualifying agent work needs final-green review evidence for the exact prepared candidate, while documentation currentness remains an always-on live fact.

The guard distinguishes evidence, human waiver, CI delegation, non-applicability, live facts, and blocks. It owns the heavy command list, so admission is an enforced boundary rather than advice followed by a discoverable shell tail.

Merge-gate verification also exposed two shared-demo fixture assertions whose hard-coded historical date aged outside the fixture's three-week window. Their clocks are now pinned in the tests, preserving production behavior while keeping the coverage deterministic.

Why instructions were not enough

The workflow already told agents to review before running pr:athena, but nothing prevented an agent from starting merge-grade validation first. A committed marker would only move the weakness: it could be stale after an edit or rebase, copied between worktrees, and could not honestly say whether review passed, a human waived it, or CI owned it.

The failure was therefore an admission-model gap, not a missing reminder. The harness needed to know which exact candidate was crossing which gate, which obligations applied, and which provenance was allowed to resolve each one.

Mental model: a passport checked at the machine room

Think of preparation as issuing a passport for one exact Git tree and base. Review providers can stamp that passport only after their final complete green pass. The gate registry says which stamps or live inspections are required. The admission wrapper is the guard standing beside the expensive machinery, not a sign in the hallway.

A human waiver and repository CI delegation are different travel documents. They can authorize a narrow route, but neither is relabeled as a review stamp. Any candidate change produces a different passport.

prepare candidate -> evaluate obligations -> persist decision -> final stable capture -> spawn heavy provider

Before and after

Before: skill prose owned ordering; pr:athena:validate-provider exposed the heavy shell chain; proof identity existed only for later pre-push reuse; caller posture and review provenance were not part of admission.

After: one preparation wrapper publishes a candidate receipt; a typed registry and pure evaluator resolve obligations; approved review workflows issue candidate-bound evidence; one effectful wrapper evaluates documentation once, records the decision, rechecks the candidate, and directly owns every heavy command.

  • Agents: qualifying work requires fresh approved review evidence and never receives a human prompt.
  • Interactive humans: may deliberately acknowledge only the review obligation after deterministic facts are green.
  • CI: delegates review only for the exact Athena PR Tests workflow, harness-validation job, pull_request event, and athena-pr-tests policy.
  • Small non-sensitive work: records review.green as not_applicable rather than pretending review passed.

How a candidate reaches validation

Stable capture keeps the complete tree identity separate from activation filtering. baseTipSha identifies the current base-ref tip used for freshness, while diffBaseSha identifies the merge base used for activation and review scope. Tests, generated artifacts, and lockfiles may be excluded from the 50-line projection, yet changing any of them still invalidates historical evidence because treeSha changes.

Review sensitivity is registry metadata, not a second path list. Every validation scenario has an immutable ID and explicit reviewSensitive boolean, and generated validation maps expose the same fields for agents and audits.

Records live under a Git-private worktree path. Their IDs derive from semantic identity and publication uses atomic create-if-absent, so repeated providers converge. Malformed neighboring records block when no separately valid existential-provider record satisfies the obligation; contradictory fresh records always block.

Failure boundaries

  • Unstaged, untracked, missing-base, or racing Git state is unprepared or ambiguous; it never becomes a zero-risk projection.
  • Missing, stale, corrupt, wrong-provider, non-green, or unresolved-actionable evidence cannot authorize an agent.
  • A valid existential provider record can satisfy review without a malformed neighbor hiding it; contradictory fresh records block.
  • Documentation findings aggregate with review findings and prevent a human prompt until universal facts are repaired.
  • Prompt decline, EOF, candidate drift, provider failure, or post-provider drift leaves no reusable human waiver.
  • Telemetry persistence failure cannot turn a block into admission, and an admitted run fails closed before heavy work when its decision cannot be recorded.
  • The final candidate capture is adjacent to the first heavy spawn; a race starts zero heavy commands.

What changed and what did not

Changed: preparation became receipt-bearing; gate policy became typed and reusable; review providers gained final-manifest evidence; actor context and worktree-local records became first-class; the heavy provider moved behind one admission wrapper; gate decisions entered the delivery ledger; registry generation and audit now cover stable scenario IDs and sensitivity.

Intentionally unchanged: the standalone delivery:documentation-check policy and human-readable failure contract; the later post-validation harness review and merge-ready review loop; clean and staged-index proof support; the pr:athena phase order; tests/generated/lockfiles being excluded only from the line-count activation branch; raw internal commands remaining private implementation details rather than new public gates.

How to extend this posture

  • Add a stable gate and obligation definition instead of inserting gate-specific branches into admission.
  • Choose activation and allowed resolution kinds explicitly; do not normalize missing metadata into policy.
  • Use live facts for deterministic current checks and candidate-bound records for historical judgment.
  • Keep the pure evaluator effect-free and make the consuming wrapper own the guarded commands.
  • After any review fix, run pr:athena:prepare and repeat the complete evidence-bearing review before recording evidence.
  • Update package routing, CI authorization, registry audits, generated maps, validation fingerprints, focused tests, and docs as one contract.
