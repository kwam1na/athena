What this delivers

Anonymous shoppers could read Athena's internal catalogue columns two different ways: the public HTTP routes answered with whole Convex documents, and nine catalogue queries were still admitted to the public actor, so a Convex client could ask for the same documents directly. This delivery closes both doors in one branch.

The HTTP routes now apply a drop-only projection — public_catalog.v1 — after the read, so a cache hit and a cache miss are projected identically. The nine query definitions are flipped to deny the public actor, which is safe because every anonymous route already calls an internal sibling. The two tickets ship together because both regenerate the same admission-checker documents.

Why a spread is a leak

The catalogue handlers built their responses by spreading Convex documents — { ...product }, { ...sku } — and adding enrichment on top. That means the response contract was "whatever is currently in the table". Every column an operator feature added to productSchema or productSkuSchema reached the public internet the day it landed, with nothing in the type system or the tests to notice, because the leak is the absence of a step rather than the presence of a wrong one.

What actually went out: unitCost, netPrice, barcode, barcodeAutoGenerated, inventoryCount, reservedQuantity, durableQuantityAvailable, createdByUserId, organizationId, posVisible, pesewasMigratedAt and areProcessingFeesAbsorbed. Cost prices and on-hand stock are competitive information; the ids are internal structure. The best-seller route leaked the product fields a second time, because productSku.retrieve nests a whole product document inside each row.

Separately, the admission rail still recorded public: "admit" on nine catalogue reads, with a comment explaining that anonymous storefront routes reached them. That had stopped being true: the routes had already been moved to internal siblings. The admission was a stale grant, and a grant nobody uses is a grant only an attacker uses.

A window, not a filter

Think of the boundary as a window cut to a fixed shape rather than a filter that removes known-bad items. A filter has to be told about each new contaminant; a window only shows what it was cut to show, and anything new outside its frame is invisible by default.

This delivery cuts the window at the route handler and writes the frame down as two explicit lists per schema — kept and dropped. The frame is not inferred from names and it does not recurse blindly: organizationId is dropped on a product but legitimately kept on a store, so a "strip this key anywhere" walker would have been an unbounded behaviour change disguised as a safety fix.

The admission flip is the second half of the same idea. Projecting the window is pointless if the wall next to it is missing, so the query-level door closes at the same time.

What changed and what deliberately did not

The projection is drop-only. Field names are unchanged and every piece of enrichment the queries add on top of the documents — categoryName, colorName, skus and the rest — survives untouched, so the storefront's read set is the same set it had before. Two fields the availability adjustment attaches at read time rather than storing, durableQuantityAvailable and reservedQuantity, are dropped explicitly because they are not schema keys and the enumeration test would not have caught them.

inventoryCount was the one genuinely uncertain drop, and it was settled by characterization rather than by reading the type: a read-set sweep of the storefront showed it gets stock counts from POST /storefront/inventory/batch, and that the one file naming inventoryCount from the catalogue shape is imported by nothing. The batch endpoint is not part of this projection and continues to answer counts.

The admission flip does not change normalUser or operator access on any of the nine reads, and it does not touch the route handlers. It is safe precisely because the routes already call internal siblings; the stale promoCode.ts comment promising the public export would survive "until wave B2" is resolved to describe what is now true.

Deliberately not in this delivery: store.organizationId on the homepage snapshot, the on-hand counts from POST /storefront/inventory/batch, and GET /stores/:storeId returning the whole store document. All three are recorded deferrals on the same surface rather than oversights. A recursive name-based stripper was considered and rejected for the reason above.

Next time

  1. Never answer an anonymous HTTP route with a document spread. Project at the boundary, drop-only, in a module the route imports.
  2. Enumerate the schema in a test. Comparing the schema's key set against keep ∪ drop converts "someone forgot a column" into a red test instead of a disclosure.
  3. Project after the cache, never inside it — otherwise already-cached entries stay unprojected until eviction — and then test a hit and a miss through the same handler.
  4. Characterize the consumer before dropping a field. A field that looks load-bearing may be served by a different endpoint.
  5. Follow the nesting. A query that re-attaches a document inside its rows needs the projection to recurse into the shape it actually produces.
  6. When you move a route to an internal sibling, close the public admission in the same change. A grant left behind outlives the comment explaining it.
  7. When two tickets regenerate the same generated artifact, batch them into one integration branch and regenerate once.

Check your understanding

  1. Why was the leak invisible to the type system and the tests?

    1. The responses were serialized through an untyped helper.
    2. A spread has no fixed shape, so the missing projection step is an absence rather than a wrong value anything could assert against.
    3. The tests ran against a fixture store with no cost data.
    4. The fields were added after the tests were written.

    Nothing was incorrect in the output — the contract was simply "whatever the table holds", so each new column joined the response silently.

  2. Why is the projection applied in the route handler rather than inside the cached action?

    1. The cached action runs in a different Convex runtime that cannot import the module.
    2. Projecting earlier would break the operator app, which shares the action.
    3. Entries already in the Valkey cache would stay unprojected until eviction, and a cache hit would never pass through the projection at all.
    4. Route handlers are the only place with access to the schema definitions.

    Placing it after the read makes a hit and a miss produce the same shape, which is exactly what the route tests assert.

  3. What does the schema-enumeration test actually protect?

    1. That no dropped field is ever referenced by the storefront.
    2. That the projection functions are faster than a spread.
    3. That a newly added schema column cannot ship publicly without someone explicitly putting it in the keep or drop list.
    4. That the Convex schema and the contracts package stay byte-identical.

    It turns the default from "new columns are public" into "new columns block the build until decided".

  4. Why was a recursive "strip these key names anywhere" walker rejected?

    1. It would have been too slow on large best-seller payloads.
    2. Keys like organizationId are legitimate on other documents the storefront reads, so name-based recursion turns a bounded projection into an unbounded behaviour change.
    3. Convex documents cannot be traversed recursively.
    4. It would have conflicted with the admission rail's own field policy.

    The same key name means different things on different documents; the shape-aware projection only touches the shapes it knows.

  5. Why was flipping the nine catalogue reads to deny safe without touching any route?

    1. The routes were already behind a Cloudflare rule that blocked anonymous traffic.
    2. The reads were only used by the operator app.
    3. Every anonymous route already called an internal sibling query, so nothing in the serving path went through the public exports.
    4. Denying a read falls back to the normalUser grant, which the storefront holds.

    The admission was a stale grant left over from before the routes moved to internal siblings; the flip removed reachability nobody was using.

  6. Two SKU fields are dropped explicitly even though they are not schema keys. Why do they need their own list?

    1. They are nullable, and the enumeration test skips nullable keys.
    2. The availability adjustment attaches them at read time rather than storing them, so they reach the wire without ever appearing in the schema the enumeration test walks.
    3. They belong to the product document, not the SKU document.
    4. They are only present on a cache hit.

    durableQuantityAvailable and reservedQuantity are derived, so the schema-key guard would have had nothing to compare them against.

  7. Why do these two tickets share one branch and one PR?

    1. Linear cannot link two tickets to separate PRs in the same project.
    2. The admission flip would fail its tests until the projection landed.
    3. Both regenerate the same admission-checker documents, so separate PRs would replay the same generated-artifact conflict; the batch regenerates once while ticket scope stays separate in Linear.
    4. The repository forbids more than one open PR against the Convex backend.

    The batching is a merge-conflict decision about shared generated artifacts, not a coupling between the two behaviours.

  8. How was the decision to drop inventoryCount from the catalogue responses settled?

    1. By checking that the field was nullable in the schema.
    2. By deferring it until the storefront could be refactored.
    3. By characterizing the storefront's actual read set, which showed counts come from the separate inventory batch endpoint and the one file naming the field is imported by nothing.
    4. By keeping it, since the storefront's low-stock badge reads it.

    The execution posture was characterization-first precisely because the field looked load-bearing until the read set was swept.
