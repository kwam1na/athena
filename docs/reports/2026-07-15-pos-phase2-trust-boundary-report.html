POS Phase 2 — Trust-Boundary Hardening

Re-pricing · Idempotency · Clock · Money · Landed-change report
Issues: V26-1062 (U7), V26-958 (U8), V26-1063 (U9), V26-1064 (U10) · follow-up V26-1066 (U10 constraint-flip cutover). Plan: docs/plans/2026-07-15-001-fix-pos-local-first-hardening-plan.md.

The in-store POS runs local-first and drains events to Convex. Phase 2 closes the client→server trust boundary for the online completion paths, which previously trusted terminal-supplied prices, retries, clocks, and money units. Four coordinated units land together:

  • U7 — the server re-prices every sale line against catalog authority; an unauthorized deviation cannot complete, an authorized one needs a manager proof and writes an append-only audit.
  • U8 — a client-stable idempotency token dedups the transaction mint and guards the drawer cash, so a retry can't mint a second sale or double-charge.
  • U9 — the server derives the business timestamp and operating date from its own timezone authority; terminal clock skew is clamped/flagged without breaking sync retry-matching.
  • U10 — a deterministic, idempotent pesewas migration + completion marker for the never-migrated POS money tables. The schema constraint-flip is deliberately deferred to a gated production cutover (V26-1066).

A local-first cash register is only as trustworthy as the values the terminal sends when it finally syncs. The audit found the online completion paths would:

  • Trust the price. Totals were recomputed from item.price and only checked for internal arithmetic — the catalog price was never compared. A stale-catalog or tampered terminal could sell at any price, with no record.
  • Trust the retry. No idempotency token; every submit minted a fresh transaction number. A network retry after a committed sale created a second sale, a second stock decrement, and — because the drawer-cash call omitted the key the void path uses — double cash.
  • Trust the clock. occurredAt and the operating-day window came straight from the terminal. A skewed clock booked sales into the wrong operating day and skewed closeout variance.
  • Trust the units. POS money is unconstrained v.number() and, unlike the online-store tables, was never migrated to pesewas — it still stores cedis.

The offline projection path already re-priced and deduped. Phase 2 treats it as the template and makes the online paths inherit the same discipline.

Comprehension quiz

Pass required: 8 of 10.

  1. Why must the idempotency dedup happen BEFORE minting the transaction number?

    1. A sale has no stable server id before mint, so keying off the freshly-minted id would produce a new key per retry and dedup nothing
    2. Minting is faster
    3. The client requires it
    4. Convex forbids post-mint reads

    Unlike void (which keys off an existing transaction._id), a new sale has no stable server id until it is minted — so the dedup must key off the client-stable token before mint.

  2. What is the U7 catalog price basis, matching the offline path exactly?

    1. Always sku.price
    2. provisional.importedPrice ?? (netPrice if a number else price)
    3. The client-submitted price
    4. The average of recent sales

    Comparing bare sku.price would spuriously reject legitimate net-priced/provisional-import lines that project fine offline.

  3. When a client price deviates from the basis and NO manager proof is present, the online path…

    1. Silently records the client price
    2. Completes and flags a review
    3. Returns approval_required and mints nothing
    4. Uses the basis and completes

    Online hard-rejects an unauthorized deviation (no sale minted); an authorized override needs a manager proof and writes an audit. Offline keeps its flag-and-project because money already moved.

  4. Why are the U9 server-derived clock values stored in ADDITIVE fields instead of overwriting occurredAt?

    1. To save space
    2. Because isSameLocalEvent compares occurredAt + payload, so mutating them would break the sync retry-match
    3. Because occurredAt is read-only in Convex
    4. To keep the payload smaller

    The retry-match compares occurredAt and the canonical payload; changing them would make a retried event fail to match the stored one. Additive fields are ignored by the match.

  5. How is the U9 clock derivation made deterministic across retries?

    1. It re-derives on every ingest
    2. It is computed once at first ingest and stored; retries reuse the persisted values
    3. It uses a random seed
    4. It is disabled on retries

    serverTimeAt is the first-ingest acceptance time; on retry the existing record is reused and nothing is recomputed, so the outcome is stable.

  6. What does U9 do when the store lacks timezone authority?

    1. Rejects the event and wedges the register
    2. Falls back to the terminal operating date with a missing_timezone_authority flag
    3. Uses UTC midnight
    4. Crashes ingest

    Defined missing-authority behavior: keep the terminal value (preserve liveness) but flag it so it is never silently trusted.

  7. Why does U10 NOT flip the schema money validators in this PR?

    1. It was forgotten
    2. POS money is still cedis and never migrated; flipping before migration completes would reject legacy rows on read — it's a gated production cutover
    3. Convex can't validate integers
    4. The validators are already integer-only

    The constraint-flip is a two-phase, prod-orchestrated cutover tracked as V26-1066; the migration + completion marker must verify completeness first.

  8. What replaces the old `< 10_000` heuristic in the U10 migration?

    1. A machine-learning classifier
    2. A per-row pesewasMigratedAt marker plus a deployment cutoff timestamp
    3. Nothing — it still uses the heuristic
    4. Manual review of each row

    Deterministic + idempotent: convert a row only if it predates the cutoff and is unmarked; re-runs convert nothing already marked.

  9. Where must the U8 idempotency token also be threaded so the drawer cash is guarded?

    1. Only completeTransaction
    2. Every recordRegisterSessionSale call site, including inventory/posSessions.ts completeSession
    3. Only the offline path
    4. Nowhere; the mint dedup is enough

    completeSession records drawer cash itself after calling the handler, so the token must guard recordedTransactionKeys there too — the mint dedup alone doesn't cover it.

  10. Why are pending-checkout lines exempt from U7 catalog re-pricing?

    1. They are always free
    2. They carry an operator-entered price with their own validated review workflow and never appear in the offline path
    3. Re-pricing is too slow
    4. They have no productSkuId

    Pending-checkout items are not governed by trusted catalog authority; their provenance is validated separately, so their price is recorded as-is.
