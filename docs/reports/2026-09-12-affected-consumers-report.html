What this candidate delivers

Athena can qualify which validation checks consume changed files, including relationships that directory matching misses. The planner examines both the previous and candidate source snapshots, keeps conservative coverage for uncertain dependencies, and separates unit groups according to whether reports are inputs.

The output remains a read-only canonical plan. V26-2024 owns activating execution and evidence reuse. Merge, tracker closure, root alignment, and report deployment remain pending for this candidate.

Why directories were insufficient

A shared helper can affect a test in another directory or package. Removing an import can also hide a former consumer if analysis sees only the candidate. Runtime registration, runner setup, and filesystem reads introduce dependencies beyond ordinary imports.

A broad input union creates another problem: adding a delivery report can invalidate the identity of an unrelated static test grouped with a report reader. Selecting the right tests and describing their inputs are separate decisions.

Ask two questions

First ask which checks can observe the change. Follow consumer relationships backward from changed and renamed paths, using both snapshots. Then ask which files each selected check can observe while it runs. Those forward inputs include raw data and configuration as well as executable dependencies.

An unknown read may justify broad inputs for one test. It does not mean the reader executes every import contained in the text it inspects. A runner setup dependency is different: it can affect every member of the runner implicitly.

From paths to consumers

Previously, the canonical planner selected surface obligations without source-consumer qualification. With complete snapshots, it now resolves static imports, aliases, re-exports, literal dynamic imports, assets, and declared runtime relationships across both revisions.

It then discovers candidate tests, preserves removed inputs as absence assertions, adds containing-suite fallback where needed, and binds selected members individually. Each original unit check produces at most two groups: independent of publishing data, and dependent on publishing data. Prerequisite and supersession references follow the partition.

The important behavior boundaries

  • Report-only changes pass through normal consumer analysis. Genuine readers and relevant conservative fallback remain selected.
  • Exact source and configuration guards qualify finite raw-reader contracts. A changed guard restores uncertainty.
  • Bun filesystem and process access remains conservative, including directory scans. Unknown runner configuration or setup reads retain implicit runner membership.
  • Convex lazy-registry qualification rejects shadowed imported factory or API bindings. Unsupported forms retain named fallback.
  • Full-health planning remains complete and conservative. This candidate creates no passing execution evidence and grants no admission or reuse authority.

What the evidence establishes

Current source checks pass 162 focused tests across the impact, registry, planner, and repository-validation suites. A real-source textual audit selects 25 independent operator unit members with 4,138 inputs and 32 publishing-dependent members with 5,824 inputs. Adding a report preserves every independent identity; publishing-dependent membership grows to 34 with 5,825 inputs. This demonstrates planner identity stability for the characterized case, not measured test-execution savings or activated reuse.

How to extend this safely

  • Start with complete base and candidate inventories and honest semantic statuses. The snapshot owner must establish physical containment or bind validated symlink targets.
  • Add a direct consumer and an implicit or unsupported consumer to the same regression fixture. A known direct edge must not hide an omitted peer.
  • For a finite reader contract, pin its actual source and prove every cross-root input. Remove one guard or declared edge to ensure the sensor fails.
  • Inspect fallback reasons, input scope, and retained absence assertions alongside membership counts. Preserve genuine publishing-build dependencies.
  • Use the canonical preparation, independent review, and pr:athena gate before merge. Only the execution owner can bind installed dependencies, environment, toolchain, actual bytes, and passing results.
