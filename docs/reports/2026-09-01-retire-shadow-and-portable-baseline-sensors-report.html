Executive summary

This candidate deletes two families of sensors, plus two adjacent release-pinned checks, and nothing else. It adds no code, changes no application behavior, repoints no test, and lowers no coverage floor. Eighteen files and about 10,900 lines leave the repository, taking 130 tests with them.

The reason is sequencing. Each deleted sensor pins something exactly — a byte digest over Athena's vendored agent-skill layout, a hardcoded list of required normative sources including .agents/skills/track and .agents/skills/execute, a core-v1 release id. A planned projection swap is about to replace precisely those pinned subjects. Left in place, every one of these sensors would turn bun run harness:test red at that swap, and each failure would be the sensor working correctly rather than reporting a defect.

The alternative — re-pinning the digests inside the swap candidate — would bury a deliberate architectural change inside a digest bump. So the retirement gets its own candidate, reviewable on the narrow question of whether anything still references the deleted code, and it lands first.

This removes real detection capability. The portable-baseline sensor was the repository's only mechanical detection of unreviewed change under .agents/skills and .agents/agents. Athena's main has no required pull-request review rule, so after this lands those paths are protected by operator practice. That residual was accepted by the operator and recorded on the ticket before the work began. It is not an executor's call, and this report does not present it as a free removal.

The problem in plain language

A characterization sensor is a tripwire stretched across something you have decided should not move. It works by recording exactly what that thing looks like today — a hash of every byte, a count of every file, a list of every path that must be present — and shouting whenever the observed shape stops matching the recorded shape.

That exactness is the entire value. It is also the entire problem the moment a plan decides the thing should move.

Athena spent late August building a shadow programme: a managed delivery product running side by side with the repository's existing vendored agent tooling, so the two could be compared before any cutover. Three sensor stacks grew up around it. The shadow-discovery guard froze the vendored skill layout byte for byte, so that abandoning the migration would cost nothing but deleting an installation. The portable-baseline sensor pinned the content of the skill closure against a captured characterization. Two adoption sensors pinned migration records against the core-v1 release.

Then the plan re-anchored. The shadow programme is withdrawn, and the projection swap will replace the vendored track and execute skills with a product projection — moving the exact bytes the guard froze, at the exact paths the baseline sensor hardcoded, past the exact release the adoption sensors pinned.

Every tripwire is now stretched across a doorway someone is about to walk through on purpose. The question is not whether they will fire. It is who cuts them, when, and in whose candidate.

The intuition

Think of a museum alarm wired to a specific painting hanging in a specific spot. It is excellent security right up until the curator schedules the painting for relocation.

At that point there are three moves, and only one of them is honest.

  1. Move the painting and re-arm the alarm to its new spot, in one motion. The alarm log shows a brief alert and then green. Anyone reading the log later sees a configuration change, not a relocation. This is the re-pinning move, and it is the one that destroys the evidence.
  2. Move the painting and leave the alarm screaming. Someone eventually silences it under time pressure, without deciding anything.
  3. Decide the alarm's future first, in its own work order, before anyone touches the painting. The decommission is reviewable on its own terms: is anything still wired to this alarm, and what stops being watched when it goes? Then the relocation is reviewable on its own terms too.

This candidate is the third move. It is deliberately boring — the entire review question is "does anything still reference this, and did the floors hold" — and that boringness is the point. The interesting decision, that losing this detection is acceptable, was made by the operator and recorded on the ticket. The interesting change, the swap itself, arrives in a separate candidate that will be readable as an architectural change rather than as digest churn.

Before and after

Before

Three independent sensor stacks, each invoked manually through a package.json script — none of them wired into a GitHub workflow directly, though their test suites ran inside bun run harness:test, which is where the swap would have hit.

  • The shadow-discovery guard held five positions: posture (the activation record must still declare shadow mode and claim no delivery authority), byte-neutrality (the vendored layout hashes to a pinned digest, checked over the git index and against the working tree), scope (a projection may exist only inside a managed delivery worktree), pin evidence, and consumption.
  • The portable-baseline sensor swept the skill closure: per-file SHA-256 over each normative source, per-bundle file counts and tree digests over each bounded member, realpath containment on every path, and outright rejection of symlinked members and inventory symlinks.
  • The canary and batch adoption sensors checked two migration records against RELEASE_ID = "core-v1", a source commit SHA, and a map of per-workflow content hashes.

After

Nothing replaces the byte-freeze, the scope check, or the closure sweep. The only survivor in this area is scripts/portable-shadow-observation.ts, untouched, which validates that a recorded shadow comparison record is well-shaped and fingerprint-matched. scripts/delivery-run-telemetry.ts consumes it as an optional attachment: it attaches a shadow comparison to a telemetry record only when the comparison's candidate fingerprint equals the current one, and re-validates on read-back. It gates nothing, and it never reads a byte under .agents/skills.

So the surviving coverage is one narrow slice — "a recorded comparison is well-shaped and bound to this candidate" — and none of the filesystem positions. That is the accepted residual, stated plainly.

What changed, and what deliberately did not

Changed

  • Eighteen files deleted: the shadow guard and its suite; the portable-baseline driver, contracts, filesystem helper, schema, seven fixtures, and its suite; the canary and batch adoption sensors and their suites.
  • Three package scripts removed.
  • Two members removed from the shadow activation record — the layout digest ownership pointer and the managed-worktree scope rule.
  • Graph artifacts regenerated.

Deliberately unchanged

  • The four historical records. .agents/characterization-baseline.json, .agents/portable-overlay-map.json, .agents/migrations/portable-kernel-canary.json, and .agents/migrations/portable-workflow-batches.json are byte-identical to main. They are evidence of what was captured and decided, not configuration. They will now go unverified by any sensor, and they will keep naming deleted files. That is what a historical record does.
  • The activation record's history. Only the two guard-owned members went. The posture, product pin, host qualification, exclusivity position, consumption record, and characterization observation all remain exactly as recorded.
  • AGENTS.md and the package agent guides.
  • Every coverage floor. Measured, reported, not touched.
  • Every test. No test was repointed or weakened; four test files were deleted whole along with their subjects.
  • The projection swap itself, which is a separate ticket and a separate candidate.

What would have gone red at the swap

This is the evidence that justifies the removal, gathered from the deleted files before they were deleted.

  1. The pinned layout digest. VENDORED_DISCOVERY_LAYOUT_DIGEST in the guard hashes the tracked manifest of the vendored generation tree plus the exposure symlinks. Replacing the vendored skills changes that manifest, raising vendored_layout_drift. The working-tree half fires independently, since the pathspec includes the exposure symlinks and catches an unstaged retarget the index cannot see.
  2. Bounded member drift. The contracts pin the track and execute skill bundles by file count and tree digest, both classified as retained overlays. A projection changes both, raising bounded-member-count-drift and bounded-member-digest-drift.
  3. Normative source drift. The same two skills are pinned per-file by SHA-256 as required normative sources, raising source-digest-drift.
  4. Symlink rejection. A projection that exposes those skills as links trips bounded-member-symlink-unsupported and source-reference-target-symlink-unsupported. These cannot be satisfied by re-pinning a digest at all — the checker rejects the shape, not the content.
  5. Discovery root state. The required roots demand .agents/skills present and .claude/skills absent; a materialized projection root raises discovery-root-required-state-mismatch or discovery-root-unexpected.
  6. Assertion semantic digests over the routing assertions whose citation selectors quote the track and execute skill text.
  7. The release pins. Both adoption sensors hardcode RELEASE_ID = "core-v1", its archive and metadata paths, a source commit SHA, and a per-workflow content-hash map — all pinned to the pre-swap release.
  8. The scope rule. The guard required any projection root to sit inside a managed delivery worktree, treating a sibling-shaped path as a finding.

Items 4 and 5 are the ones that matter most for the argument. A digest drift can be answered by re-pinning, however unwise that would be. A symlink rejection and a required-absent discovery root cannot: the swap produces exactly the shape those assertions exist to refuse, so the sensor's contract would have to be rewritten, not re-pinned. A contract that must be rewritten to describe the opposite of what it was written to enforce is a contract that has ended.

Next time

  • When a plan proposes moving something a sensor pins, schedule that sensor's retirement or rewrite as its own ticket, sequenced before the move. Do not let it surface as a surprise red suite inside the moving candidate.
  • Treat "re-pin the digest so the suite goes green" as a review finding, not a fix — unless the re-pin is itself the deliberate, reviewed change.
  • Before deleting a script family, close its import graph and grep the package scripts, CI workflow steps, and harness registries. The compiler catches only the first of those.
  • Characterize on the untouched tree first. "The suite was green before and after, and here are both numbers" is a much stronger claim than "the suite is green."
  • Measure coverage against the pinned floors after a deletion and report real numbers. Never lower a floor to absorb a removal; a broken floor is a finding for an operator, not a value to edit.
  • Expect a large pure deletion to trip the documentation gates. compound:check and landed-report:check count additions plus deletions, so a deletion-only candidate owes the same solution note and landed-change report a feature would.
  • When a removal costs detection capability, name the capability and the paths it covered, and get the residual accepted by an operator before the deletion lands. An executor performs the deletion; it does not decide the residual is acceptable.

Comprehension quiz

Ten questions on why this deletion is sequenced the way it is. Eight correct to pass.

  1. Why were these sensors deleted rather than updated to match the coming projection swap?

    1. They had been failing intermittently and nobody could fix them.
    2. They were slow enough to matter in the harness suite.
    3. Their contracts pin the exact subject the swap replaces, so updating them inside the swap candidate would bury an architectural change inside a digest bump.
    4. They duplicated coverage that another sensor already provided.

    The sensors worked correctly. The problem is that their pinned subject is scheduled to move, and re-pinning during the move destroys the reviewability of both changes at once.

  2. Which two assertion kinds could not have been satisfied by re-pinning a digest at all?

    1. The per-file source digests and the bounded member tree digests.
    2. The symlink rejections and the required-absent discovery root, because they refuse a shape rather than a content hash — and the swap produces exactly that shape.
    3. The release id pin and the source commit SHA.
    4. The posture checks on installation mode and delivery authority.

    A digest can always be re-pinned to a new value. A rule that says "this member must not be a symlink" or "this root must be absent" has to be rewritten into its own opposite, which is the sign the contract has ended rather than drifted.

  3. What detection capability does the repository lose when this lands?

    1. Nothing — an equivalent check replaces it in the same candidate.
    2. Runtime validation of the operator app's Convex boundaries.
    3. The only mechanical detection of unreviewed change under .agents/skills and .agents/agents, leaving those paths protected by operator practice.
    4. Coverage floor enforcement for the repo scripts.

    Because Athena's main branch requires status checks but no approving review, that detection had no fallback gate behind it.

  4. Who decided that losing that detection was acceptable?

    1. The executing agent, after confirming the suite stayed green.
    2. The review lenses, by approving the candidate.
    3. Nobody — it is an open question tracked for later.
    4. The operator, recorded on the ticket before the work began; the executor performs the deletion and neither makes nor records that decision.

    Accepting a residual risk is an operator decision. An agent that accepts it on its own has quietly changed the repository's safety posture without authority.

  5. What happened to the four historical records the deleted sensors read?

    1. They were deleted alongside the sensors that validated them.
    2. They were rewritten to remove references to the deleted files.
    3. They were left byte-identical to main, even though they still name deleted files and are now unverified by any sensor.
    4. They were moved under docs/reports as historical artifacts.

    They are evidence of what was captured and decided, not live configuration. Editing them to tidy up after a deletion would rewrite the audit trail they exist to hold.

  6. Which two members were removed from the shadow activation record, and why only those?

    1. The product pin and the host qualification, because the product moved.
    2. The layout digest ownership pointer, whose owner field named the deleted guard, and the managed-worktree scope rule the guard enforced — the only members the deleted code owned or read.
    3. The characterization observation and its historical scope block.
    4. The consumption record, because nothing consumes it now.

    The edit was scoped to what the deleted guard owned or read. Everything descriptive of the recorded posture stayed, because the record is history as much as configuration.

  7. What did the pre-deletion characterization step establish?

    1. That the deleted sensors were redundant with the harness suite.
    2. A green baseline on the untouched tree — 1,799 tests passing across 77 files, each retiring sensor green individually, and a closed import graph — so the after-state could be compared against a recorded before-state.
    3. That coverage floors would need re-derivation after removal.
    4. That the projection swap could proceed without this ticket.

    Under a sensor-only posture there is no new behavior to test, so the evidence is the before-and-after comparison, which requires actually capturing the before.

  8. Why did the coverage percentages go up after deleting well-tested code?

    1. The floors were re-derived against the smaller code base.
    2. Deleted files are excluded from the coverage denominator by rule.
    3. The removed code happened to be less covered than the repository average, so the surviving ratio improved — an outcome that had to be measured rather than assumed.
    4. The coverage tool ignores scripts without a matching test file.

    A deletion moves coverage in whichever direction the deleted code's own coverage ran. It could as easily have breached a floor, which would have been a finding for an operator rather than a value to edit.

  9. Which sensor deliberately survives this candidate, and what is its role afterwards?

    1. The shadow discovery guard, reduced to its posture checks.
    2. The portable-baseline schema validator, kept for the swap candidate.
    3. The portable shadow observation reader, which stays wired into delivery telemetry as an optional, fingerprint-matched attachment that gates nothing.
    4. The canary adoption sensor, re-pinned to the next release.

    It validates the shape and candidate-binding of a recorded comparison. It never reads a byte under the skill paths, so the swap does not affect it.

  10. Why did a pure deletion still require a solution note and this report?

    1. Every candidate in the repository requires both, without exception.
    2. The documentation gates count additions plus deletions with no deletion-only exemption, so a large removal clears their thresholds exactly as a feature would.
    3. Because the change touched the agents policy directory.
    4. Because two independent review lenses requested them as a courtesy.

    Both lenses independently ran the gates and found them failing on changed-line count, which is what turned the documentation obligation into a blocking finding on this candidate.
