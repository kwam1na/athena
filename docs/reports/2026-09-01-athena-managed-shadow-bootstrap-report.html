Executive summary

Athena can now exercise the installed managed-delivery product as a shadow decision and evidence layer without handing it orchestration or delivery authority. The existing repository policy compiles through the pinned production installation, exposes exactly the qualified review.green lane, and binds one trusted sensor to Athena's established preparation command.

This bootstrap is deliberately non-counting. It proves installation, policy compilation, facade construction, and the trusted preparation boundary; it does not claim a registered host session, observed projection consumption, a completed real delivery, or M1 progress. The recorded score remains 0 of 3.

The problem this closes

Athena already had a strong delivery system and a read-only product policy projection, but no honest seam connected a real product installation to candidate-bound review and preparation evidence. Without that seam, attempted shadow slots correctly fell back to the normal host workflow and produced no qualifying managed evidence.

The goal was not to build a new runner. The coding host still owns agents, subagents, tools, worktrees, sequencing, pushing, merging, deployment, and lifecycle. The product owns policy compilation, evidence normalization, admission decisions, and the declared finish line.

Mental model: a referee beside the delivery

Think of Claude Code as the team playing the match and Athena's existing commands as the field rules. The product is the referee and scorekeeper: it reads the adopted policy, accepts qualified evidence, decides whether the evidence satisfies the checkpoint, and records that decision. It never hires the players, schedules the match, or moves the ball.

That boundary is why this change adds one policy admission projection and one trusted sensor, but no launcher, registry, scheduler, callback framework, daemon, session manager, control plane, or Codex fallback.

Before and after

  • Before: Athena's policy projection compiled read-only, but no production-installed facade was bound to its live policy and preparation evidence.
  • Before: no Athena-bound managed lane could honestly produce a counting consumption record, so four attempted shadow slots remained manual and non-counting.
  • After: the pinned production installation compiles Athena's exact policy, resolves the two shipped reviewer personas, and constructs the managed facade with one trusted preparation sensor.
  • After: only the qualified Claude Code producer can satisfy product-native review.green; unsupported hosts remain excluded rather than falling back to a divergent contract.
  • Unchanged: bun run pr:athena remains Athena's wider delivery authority, and merge/deploy remain outside the product's grants.

What changed—and what intentionally did not

  • The existing repository-policy document gained one exact review.green admission projection and retained explicit merge/deploy denial.
  • The compiled snapshot and comparison report now bind the production compiler, composition, admission projection, and trusted sensor digest.
  • The preparation sensor delegates to bun run pr:athena:prepare, refuses package.json and scripts/** changes, and reports a successful repair as remediation-needed if the candidate is no longer clean.
  • Athena telemetry ignores managed delivery-record/1 files while still requiring a genuine Athena telemetry record; the contracts coexist without substituting for one another.
  • The activation record names exact generation, install, receipt, distribution, and trust facts while explicitly denying registration, consumption, host-session, or runtime claims.
  • No runtime UI, business behavior, deployment configuration, orchestration system, or Codex delivery lane was added.

Failure boundaries discovered in review

The first review pass found that fencing only the direct preparation files left transitive script imports candidate-controlled. The smallest safe correction was to exclude all script-changing candidates from the MVP lane instead of maintaining a dependency registry.

Review also found that preparation can repair or stage bytes. A plain zero exit would advance a dirty candidate into reviewing, where the facade would reject the moved candidate and could not checkpoint again. The sensor now checks cleanliness after success and returns remediation-needed when preparation changed the candidate. A stale product-pin adjudication was also removed so the comparison report no longer contradicts the current installation.

  • Use an operator-owned Claude Code lane for the first real code, docs, and operations deliveries; the host continues to orchestrate the work.
