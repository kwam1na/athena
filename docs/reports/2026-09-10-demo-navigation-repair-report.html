Demo navigation resolves safely

Product detail and report-to-stock navigation now load the intended catalog information. Unsupported demo administration screens show a clear boundary, and inventory review stops waiting for a query the demo never sends.

Two different failures looked like one

The initial product crash came from a storefront analytics read denied to shared demo sessions. The stock crash came from sending a synthetic report identity such as shared-demo-sku-demo-bolga-basket to a database-ID query. Renaming the displayed SKU would not fix both failures.

A report identity is not a database key

A report fixture identifies a story item. The stock workspace identifies an actual inventory row. The SKU code connects the two: demo report links use a text search for that code, while normal operator links continue using the database ID.

Visibility and authorization are separate checks. A demo-visible page must only mount reads that the demo is allowed to execute.

Behavior and boundaries

The restricted families are legacy dashboard, storefront assets, bags, customer profiles, logs and product editing. Product editing was already disabled in demo product detail; direct edit URLs now respect that boundary. These pages are safe unavailable destinations, not newly implemented demo features.

No backend admission grant, database schema or stock-write behavior changed. Ordinary operator analytics and database-ID stock navigation remain supported. Unknown synthetic references become text searches; they do not gain database authority.

This includes all eight catalog product IDs, all eight fixture report details and their product/stock destinations, the reported Bolga bookmark, order detail, register detail/activity, terminal detail and a workflow trace. How to prevent the next navigation crash

Test a link at its destination, including refresh and old bookmarks. Assert both demo query suppression and preserved normal-operator arguments. Keep synthetic identifiers out of ID-validated queries. When a query is skipped, give its page an explicit empty or unavailable state instead of a loading state.

The earlier demo-read migration showed that grant tests alone do not prove the UI mounts safely. Keep the surface catalog, backend read admission and browser route sweep in the same validation loop.

Check your understanding

  1. Why did the stock link crash?

    1. A synthetic report ID reached a database-ID query.
    2. The visible SKU contained hyphens.

    The identity namespaces differ; display formatting was not the cause.

  2. Why does analytics wait for context to equal null?

    1. Null explicitly identifies a normal operator session.
    2. Any falsy context proves a normal session.

    Undefined means context is still loading and must not trigger a denied demo read.

  3. How do new demo report links find stock?

    1. They pass the SKU code as a text query.
    2. They cast the story ID to a database type.

    Text search connects the story item to the live inventory workspace without pretending its fixture ID is a database key.

  4. What happens to an unknown synthetic stock reference?

    1. It becomes a text search.
    2. It is sent unchanged to the ID query.

    Unknown fixture values cannot safely identify database rows.

  5. What happens to ordinary operator stock links?

    1. They keep their real database IDs.
    2. They all become fixture searches.

    Compatibility translation targets reserved synthetic prefixes and the demo report link.

  6. What does a protected legacy page now show?

    1. The existing demo-unavailable screen.
    2. A fabricated empty analytics report.

    The implementation preserves backend admission boundaries rather than inventing data.

  7. Why was inventory review stuck loading?

    1. It treated a skipped query as pending.
    2. The fixture SKU could not be renamed.

    Demo saved-review reads are skipped; their undefined result is not a pending request.

  8. Does navigation coverage prove stock submissions succeed?

    1. No; navigation and mutations are distinct checks.
    2. Yes; a rendered button proves its mutation.

    The sweep inspected rendering and destinations without submitting stock or payments.

  9. Why keep tests for old stock bookmarks?

    1. Users may reopen URLs produced before the fix.
    2. Old bookmarks are always rewritten by deployment.

    Route validation must normalize already-issued synthetic links.

  10. When should the delivery be called deployed?

    1. After production deployment and live verification succeed.
    2. As soon as a local browser page renders.

    The report is a delivery candidate; local evidence does not establish production state.
