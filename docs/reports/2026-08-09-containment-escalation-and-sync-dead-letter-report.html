Executive Summary

Reporting ingestion contains every internal failure so a reporting bug can never roll back a sale. Two gaps remained: the containment marker itself had no fallback, and a sync batch the server threw away on every attempt retried forever with no manager-visible signal.

This change adds a durable scheduled fallback beneath the containment marker, reports the sync failure streak through the terminal heartbeat as a new sync_failing health alert, and dead-letters a poison batch into the register-session review queue after a bounded number of consecutive upload failures.

Problem and Constraints

When recordFacts failed, it degraded to a write_failure dirty mark and returned normally. If that mark could not be written, the throw propagated and aborted the domain transaction. An atomic abort beats a silent data hole, but it let one unhappy table reject an entire sync batch.

Because the throw escapes the whole sync mutation, nothing commits: no sync event row, no conflict, no review item. The terminal cursor never advances and the batch is resubmitted under exponential backoff. That is correct self-healing for a transient fault and an indefinite silent loop for a persistent one. The existing sync_stuck alert did not cover it, because that condition describes a held batch behind an unadvanced cursor rather than a batch the server rejects.

Constraints: the sale must never be lost, the abort backstop must remain reachable, and escalation must not fire on transient blips or on local read failures that merely resemble server rejection.

Mental Model

Containment is layered, and each layer writes somewhere the layer above could not. The inline dirty mark is the first fallback. A durable scheduled mutation is the second, chosen because the scheduler enqueue targets a different table than the one that just refused and Convex guarantees execution once the transaction commits. The propagating throw is the third and last, reached only when two independent write paths refuse.

On the client, a failure streak is not merely backoff state; it is reported evidence. Once it crosses a threshold it means two different things at once: the terminal is unhealthy, which the heartbeat escalates as an alert, and this specific batch is poison, which the runtime dead-letters for human review.

Before and After

  • Before: a failing dirty-mark write aborted the domain transaction. After: it enqueues a durable scheduled mutation and the sale commits, with the mark landing moments later.
  • Before: the abort backstop triggered on one table failing. After: it requires the dirty-mark write and the scheduler enqueue to both fail.
  • Before: a persistently failing sync was visible only as lastFailureMessage on the terminal detail page. After: it raises a sync_failing health alert through the existing operational event, notification rail, and manager email.
  • Before: a poison batch retried forever with no review item. After: its events are parked needs_review locally and a review conflict is recorded on the register session.
  • Before: the scheduler failure count reset with every drain trigger. After: the streak persists across scheduler instances so a threshold can actually be reached.

Implementation Changes

  • Extracted markDirty into convex/reports/marks.ts and added the markWriteFailureDays internal mutation as the containment fallback target.
  • Wrapped the containment marker loop in recordFacts so a marker failure enqueues the scheduled fallback rather than throwing immediately.
  • Added SYNC_FAILING_ALERT_THRESHOLD and the sync_failing condition to the terminal health classifier, plus its summary in the alert email.
  • Carried consecutiveFailureCount from the sync scheduler through the runtime status builder, the public terminal mutation, and the runtime status schema.
  • Added onPersistentFailure and initialFailureCount to the sync scheduler, counting only uploadBatch rejections via a batch-in-flight guard.
  • Added recordLocalSyncDeadLetter and the reportLocalSyncDeadLetter public mutation, registered in the operation-admission inventory.
  • Classified the dead-letter conflict as reject_only ahead of the general server_rejected branch.

Failure Boundaries

  • If the scheduler enqueue also fails, the throw propagates and the domain transaction aborts atomically. This is deliberate and still covered by a test.
  • Only uploadBatch rejections advance the dead-letter streak. Local read and settlement failures are excluded, so a failing IndexedDB read cannot be mistaken for a poison batch.
  • Local parking happens before the cloud report, so leaving the retry loop never depends on a network call that is failing by definition. The cloud report is best-effort.
  • The dead-letter conflict is idempotent while it remains open. A resolved marker does not suppress a new one, because a wedge that returns after resolution is new information.
  • consecutiveFailureCount is sanitized so an absent or invalid report stays absent rather than asserting zero failures.
  • Review-only escalation drains do not dead-letter, since they already operate on parked events.

Operator and Maintainer Guidance

A terminal whose uploads keep failing now produces a sync_failing alert and a register-session review item naming the wedged batch head. Treat the review item as a pointer to a server-side defect rather than an operator mistake; the local sale record is intact, and once the defect is fixed the review flow re-drains the batch. Replay is safe because report fact identity is structural and an equal-fingerprint replay is a no-op.

When extending containment, keep each fallback on a different write path from the layer above it, or the fallback shares the fault it exists to survive. When adding escalation to a client loop, check whether the state that drives it survives the object lifetime; the failure streak here had to move into a ref before any threshold could be reached.
