Executive summary

The generated-artifact hook now turns an otherwise generic Convex fetch failure into a bounded diagnosis. It probes the configured deployment hostname through the system resolver, retries once only when DNS is actually unavailable, and gives a targeted next action when the bounded retry still cannot reach the deployment.

The repair boundary is deliberately narrow: no global DNS changes, no generation bypass, and no weakening of freshness checks. Credential, source, and type failures retain their original Convex output.

Why the old failure was expensive

Convex already retried the deployment request six times, but an unresolved deployment hostname still ended as only `TypeError: fetch failed`. That message did not name the host, separate DNS from credentials or source errors, or say whether the harness could repair the condition safely.

A local comparison showed the repository's Convex 1.43.0 and the then-current 1.44.0 behaved identically. A dependency upgrade would not have fixed this failure class.

Mental model: diagnose before repairing

Treat the generic fetch error like a smoke alarm, not a diagnosis. The harness asks one narrower question: can the operating system resolve this specific deployment hostname? Only a failed answer authorizes one retry.

A second boundary protects generated files: a timed-out Convex writer must be confirmed stopped before another writer can start. If SIGTERM and SIGKILL cannot confirm exit within their grace windows, the harness stops without retrying or verifying artifacts.

Before and after

Before: source change → Convex performs internal retries → generic fetch error → manual DNS investigation.

After: source change → bounded Convex attempt → preserve semantic errors; otherwise resolve deployment host → one DNS-only retry → either success and normal verification, or a hostname-specific diagnostic.

A healthy DNS result never gets relabeled as DNS failure. A hanging CLI with healthy DNS gets its own timeout message.

What changed and what did not

The harness can derive the hostname from `CONVEX_URL`, `VITE_CONVEX_URL`, or `CONVEX_DEPLOYMENT`; bound the resolver probe at five seconds; bound each Convex attempt at 120 seconds; and use five-second SIGTERM and SIGKILL confirmation windows.

The Convex version, lockfile, `bunx convex dev --once` command, supported-Node selection, source-change detection, generated API coverage check, Graphify rebuild, and tracked-only staging order remain unchanged. No credentials are logged and no resolver configuration is changed.

Failure boundaries

  • Persistent resolver failure reports the deployment hostname and resolver code after one retry.
  • Temporary DNS recovery succeeds on the one permitted retry.
  • A generic fetch failure with healthy DNS remains the original Convex error.
  • Credential and TypeScript failures remain verbatim on both attempt one and attempt two.
  • An unconfirmed child termination blocks diagnosis, retry, verification, and staging to prevent concurrent generators.
  • Missing or invalid deployment-host configuration falls back to the original CLI failure instead of guessing.

Guidance for the next failure or extension

  • Probe the failing dependency boundary before classifying a generic network error.
  • Never mutate machine-wide DNS from a commit or delivery hook.
  • Do not start a recovery writer until the prior writer's exit is confirmed.
  • Keep retry counts and every wait independently bounded.
  • Inject resolver and process timing behavior in tests instead of depending on live DNS.
  • When Convex changes its error wording, update the classifier only with a captured failure and matching separation tests.
