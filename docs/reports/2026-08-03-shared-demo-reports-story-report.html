Serving the Reports workspace from a client-side shared-demo story

The demo paid real Convex reads to render an almost-empty Reports workspace. It now derives every figure in the browser from the transaction fixture the other surfaces already use — and refuses to assert the one thing a client cannot earn.

Executive Summary

Athena's shared demo let a visitor open the Reports workspace, and the workspace ran the real Convex reads against a demo store with almost no reporting data. The visitor saw a near-empty workspace, and Athena paid for it — on every tab visit, every period change, and every debounced search keystroke. ReportsCatalogLookup is mounted by ReportsLayout on all three tabs and subscribes to inventory.skuSearch.searchProductSkus, so search fired everywhere.

Reports subscriptions in demo mode now go to zero. Overview 4 → 0, Weekly 1–2 → 0 (including the history drawer and a pasted reportId), Items and SKU detail 1–2 → 0 — and zero while the demo context is still loading, which is the part that is easy to get wrong.

The delivery is two client-side fixtures plus a thirty-five-line gating hook: sharedDemoReportsFixture.ts (1,332 lines) derives overview, day rows, SKU mix, period SKUs, SKU detail, SKU-day evidence and the weekly briefing; sharedDemoCatalogSearchFixture.ts answers catalog search locally; useReportsSharedDemoMode.ts decides which branch runs. Nineteen files, 3,035 insertions against 67 deletions, one commit off main. The gate counts 1,852 considerable source lines — tests excluded — against a 300-line report threshold.

Two rules carry the design: derive, never invent, and assert only what a client can honestly earn.

Problem and Context

Two costs, one surface. The first was product: a prospect who clicked Reports saw the strongest data surface in Athena rendering nothing. The second was operational: those reads were real. Overview held four subscriptions, the days panel and SKU-mix panel re-issued theirs on every range change, Items re-issued on every period and sort change, and the catalog lookup opened a search subscription per debounced keystroke on all three tabs.

The obvious fix — render from browser fixtures — is where the actual design problem starts. A reporting surface is not a screenshot. It makes claims about money, and it sits beside Transactions and Operations surfaces making claims about the same money on the same dates. A fixture that invents plausible numbers produces a demo that contradicts itself the moment a prospect compares two tabs.

Worse, Weekly is a lifecycle surface. Athena's weekly briefing exists to say that an accepted baseline was earned from an accepted register close and an observed-at cutoff. A browser fixture can mint that state in one line, and doing so would not be a rendering shortcut — it would show an operator an accepted baseline that no close ever produced.

Mental Model

Think of the demo Reports workspace as a projection of one ledger, not as a set of screens with data attached. There is exactly one source of sales truth in the demo, and every surface is a fold over it:

sharedDemoOperationsFixture   (getSharedDemoHistoricalDayFixture)
  -> sharedDemoTransactionsFixture (createSharedDemoTransactionFixtures)
       -> sharedDemoReportsFixture
            overview / day rows / SKU mix / period SKUs
            SKU detail / SKU-day evidence / weekly briefing

There is deliberately no second sales table. If Reports and Operations could disagree for the same date, the demo would contradict itself in front of a prospect. Because the transactions fixture already reconciles line-for-line to each day's salesTotal, transactionCount, totalItemsSold and paymentTotals, folding its completed transactions back up reproduces the Operations day exactly — by construction, not by matching constants.

The second half of the model is a boundary, not a pipeline. Everything a client can compute from the shared history is populated. Everything a server earns is absent:

Derivable in the browser        Earned server-side (never emitted)
  both lane metrics               acceptedBaseline
  summaries + totals              acceptedAt
  scheduleLineage                 cutoffObservedAt
  completeness                    closeId / reportId
  inventoryAttention              closePosture
  priorPeriod / variance          amendment
  ownerRoutes

Before and After

  • Before: Overview opened 4 Convex subscriptions in the demo. After: 0.
  • Before: Weekly opened 1–2, including a history page and a pasted reportId detail read. After: 0 — history is a frozen exhausted page, a pasted reportId settles as absent.
  • Before: Items and SKU detail opened 1–2 each, re-issued per period, sort, and cursor. After: 0.
  • Before: the catalog lookup opened a search subscription per debounced keystroke on all three tabs. After: a local filter over eight products.
  • Before: nothing distinguished "not a demo" from "we do not know yet", so a pending context opened a read that was immediately discarded. After: pending is treated as not-live.
  • Unchanged: the live path. Every call site keeps its exact previous query and arguments; the only change to non-demo behavior is the extra useLiveQuery conjunct, which is true once a real store's context settles.

Layer-by-Layer Mechanics

1. The three-state gate

useReportsSharedDemoMode.ts is the load-bearing piece, and it is thirty-five lines:

const sharedDemoContext = useSharedDemoContext();
const isSharedDemo = sharedDemoContext?.kind === "shared_demo";
const isContextPending = sharedDemoContext === undefined;

return {
  isSharedDemo,
  isContextPending,
  useLiveQuery: !isSharedDemo && !isContextPending,
};

useSharedDemoContext has three states and all three matter: undefined (not settled), null (a real store), and { kind: "shared_demo" }. If useLiveQuery were simply !isSharedDemo, the pending tick would open a live subscription that the next tick discards — the exact read this change exists to remove, now paid once per mount. So useLiveQuery is false for both the demo and the pending state, while isSharedDemo (not !useLiveQuery) selects the fixture branch.

Every call site follows the same shape: the live useQuery gains a && useLiveQuery conjunct on its skip condition, a useMemo computes the fixture value when isSharedDemo, and the consumer picks with isSharedDemo ? demo : live.

2. The day fold: voids are evidence, not revenue

buildDay walks the day's transactions. A non-completed transaction counts toward factCount and contributes nothing else:

if (transaction.status !== "completed") {
  factCount += 1;
  continue;
}

That is the rule the real day fold applies, and it is precisely what keeps demo net sales equal to the Operations salesTotal for the same date. The void is still disclosed — it appears in the fact count and in SKU-day transaction evidence — it just recognises no money.

3. Margin: null, never 0

Cost basis is unitCost from shared/sharedDemoStory.ts, in minor units like every other amount in the module. An unresolvable cost discloses the uncovered revenue and poisons the profit:

if (lineCostMinor === null) {
  metrics.uncostedRevenueMinor += item.totalPrice;
  costMinor = null;                    // day-level poison
} else if (costMinor !== null) {
  costMinor += lineCostMinor;
}
// ... and at the end of the day:
metrics.grossProfitMinor =
  costMinor === null ? null : metrics.netSalesMinor - costMinor;

The same shape runs per SKU. 0 would be a claim of break-even; null is the truth, and it propagates up rather than being swallowed by an aggregate. Every demo SKU currently carries a unit cost, so the null branch is a guard, not a live path — which is exactly why it has its own test rather than a comment.

4. Weekly: the honesty boundary

createSharedDemoWeeklyBriefing returns { status: "available", current, acceptedBaseline: null } with lifecyclePosture: "live" and amendmentPosture: "none". It populates both lanes and their summaries, scheduleLineage, completeness, inventoryAttention, priorPeriod, variancePosture and ownerRoutes.

It never emits acceptedBaseline, acceptedAt, cutoffObservedAt, closeId, reportId, closePosture or amendment. This was an explicit product decision, taken over the alternative of staging a full accepted-week narrative, and it is enforced rather than documented: a seven-weekday sweep asserts field in briefing.current is false for each of the six accepted-only fields, so any of them reappearing fails the build. Note that it tests key presence, not value — re-adding a field as undefined still fails, which is the difference between a boundary and a convention.

Sunday is included: false — outside-schedule, not a scheduled zero day. The demo store trades Monday to Saturday and is genuinely shut on Sunday; reporting it as a scheduled day that happened to sell nothing would be a different and false claim about the business. The Sunday case is asserted directly: six included lineage entries, the seventh not included, and ownerRoutes.dailyClose pointing at Saturday 2026-08-08 rather than at the closed day.

5. Untrusted input at every client entry point

Route search and route params reach these fixtures unvalidated, and the story lookups sharedDemoProductBySku/BySlug throw on a miss. Four gates:

  • isSharedDemoReportsSkuId tests the shared-demo-sku- prefix, and demoProductForSkuId is the non-throwing resolver behind it. A foreign productSkuId in the URL resolves to null — the same "no activity" state the live query produces.
  • An unparseable periodKey yields an empty period rather than a throw.
  • Cursors are base64 JSON validated against v, periodKey, sortBy and typeof afterSkuId === "string", all inside a try. Garbage, a foreign period, a mismatched sort, or a SKU that no longer exists all return null, which falls back to page one.
  • On Weekly, a pasted reportId settles to null (absent), not undefined (pending), so the route renders its unavailable state instead of spinning on a read that was never opened. History is a frozen { page: [], isDone: true, continueCursor: "" } for the same reason.

6. Catalog search

sharedDemoCatalogSearchFixture.ts filters the eight demo products case-insensitively over the same fields the server blends into its searchText (name, sku, slug, category, subcategory), ranking an exact SKU hit ahead of substring hits. It mirrors the server's DEFAULT_LIMIT of 25 and MAX_LIMIT of 50, ships no image bytes because the lookup renders no imagery, and always reports candidateOverflow: false — the demo catalog is enumerated in full, so unlike the server there is never an unread candidate page behind a search index.

Failure Boundaries

  • The context is pending on first paint. Handled: useLiveQuery is false, the fixture branch is not selected either, and the surfaces render their initial-load state. No read is opened and none is discarded. Seven tests — one per Reports surface, including the route shell and Weekly — assert exactly this.
  • Today is always empty. The shared history window ends before the current operating day, so "today" legitimately has zero sales and one unsettled day. This is a real empty state, not a bug, and the sweep asserts overview.today.dayCount === 1 with netSalesMinor === 0.
  • Monday is a one-day week. The precedent is a real crash: sharedDemoOperationsFixture read history.at(-2)! on a week-to-date window that holds exactly one day on a Monday. Reports has period selectors and a weekly tab — the same shape — so no code path here indexes .at(-2)!, and the tests sweep Mon–Sun (2026-08-03 to 2026-08-09) across all seven surfaces. On the Monday case the sweep additionally asserts one day row and a zero weekly total.
  • Sundays divide by zero. Zero-sales days make every share and every change a divide-by-zero risk. changeBasisPoints returns null when the prior period is zero; shareBasisPoints returns 0 when the total is zero. The sweep walks every number in every returned object asserting Number.isFinite, so a NaN anywhere fails.
  • A pasted or stale cursor. Falls back to page one, byte-identical to a fresh first page. Asserted for five cursor shapes: "not-base64", empty string, a foreign periodKey, a mismatched sortBy, and a SKU that no longer exists.
  • A foreign SKU id in the route. Resolves to null detail and empty evidence rather than throwing out of sharedDemoProductBySku.
  • An inverted date range. Returns an empty detail rather than throwing.
  • The trade this makes. requireReportsStoreAccess already calls requireSharedDemoStoreCapabilityIfApplicable(ctx, "reports.read", storeId) in convex/reports/access.ts, so the backend gates demo reports reads today. Going client-only bypasses a check the platform performs. Acceptable for a read-only observational surface whose data is static and compiled into the bundle — there is no authority to escalate — but it is a real trade, and a future demo surface that writes cannot reuse this shape.

What Intentionally Did Not Change

  • The live path. Every call site keeps its exact previous query and arguments; the only difference for a real store is one extra conjunct that is true once the context settles. The live-path tests were kept and still pass.
  • The server read models. The fixtures reproduce the existing shapes field for field — including RANGE_SKU_MIX_VISIBLE_LIMIT, SKU_DAY_EVIDENCE_FACT_LIMIT, REPORT_SKU_PAGE_SIZE and REPORTS_FOLD_VERSION — rather than inventing a demo-shaped payload.
  • The browser-boundary allowlist. The fixture initially imported ~/convex/reports/rollups and failed src/routeTree.browser-boundary.test.ts. That module imports MutationCtx from _generated/server, so it is a genuine server module and not an allowlist candidate — the helpers were reimplemented locally instead. The allowlist is for provably pure modules, not for silencing the check.
  • The weekly accepted lifecycle. No client-side accepted week was staged. The demo shows a live week to date and nothing more.
  • The backend capability gate. requireSharedDemoStoreCapabilityIfApplicable is untouched; it simply is not exercised on this path any more in demo mode.

Next-Time Guidance

  • Treat a three-state context as three states. Gating a live query on !isDemo still opens and discards a subscription while the context settles. Gate on !isDemo && !isPending, and select the fixture branch on isDemo.
  • Derive demo figures from the one fixture that already feeds the adjacent surfaces. A second seeded table is a guaranteed future contradiction between two tabs showing the same date.
  • Apply the real recognition rules, not just the real shapes. A fixture that recognises a void breaks reconciliation silently, and only a cross-surface test will notice.
  • Write at least one test that anchors the fixture to a different surface. Self-consistency tests stay green through a wrong rule; that asymmetry was demonstrated, not assumed.
  • Make an unresolvable cost basis null, never 0, and let the null poison the aggregates above it.
  • Never let a client mint lifecycle state a server earns, and enforce the omission with a test. The next person to "fill in the gaps" will not read the comment.
  • Model a closed trading day as outside-schedule, not as a scheduled zero.
  • Sweep every weekday for any date-relative fixture. Pinning to one weekday tests one seventh of the behaviour — the Monday-only .at(-2)! crash is the standing precedent.
  • Validate URL-borne cursors against the query that minted them — version, period key, sort — and fall back to page one on anything stale or foreign. Never throw on a value a user can paste.
  • When a browser-boundary test fails on a new import, fix the import. The allowlist is for provably pure modules; anything reaching _generated/server is a genuine server module.
