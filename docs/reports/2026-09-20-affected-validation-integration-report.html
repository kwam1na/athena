What this delivers

Athena can describe which checks a change requires, execute them through the installed delivery product, and retain valid results when unrelated files change. This integration adds the repository policy, local health admission and hosted verification needed to qualify that path. The default remains broad validation until the activation requirements are proved.

The reusable execution foundation lives in the delivery product. Athena supplies its own consumer analysis, commands, environment declarations and health policy.

Why validation repeated

A delivery report can change after application tests pass. Whole-candidate freshness makes those tests stale even when their inputs are identical. Replacing broad validation with a list of touched test files would miss deleted consumers, shared dependencies and unknown references. Selection and safe reuse need explicit input coverage and independent evidence verification. Athena’s operator build consumes reports: a report edit can preserve unrelated unit results while invalidating that publishing build. Review reuse does not imply validation reuse.

A plan, an executor and an admission decision

The plan names the required work and why it applies. The product executes that work against pinned inputs and owns its evidence. Admission checks whether the evidence still covers the candidate and current health. A plan is not a passing result, and a passing candidate does not close a global health finding.

What the integration changes

Exact test membership prevents similarly named files from running accidentally. Base and candidate consumer analysis covers renames and deletions; unknown dependencies broaden validation. Separate output profiles prevent a check's write permissions from overlapping tracked assets. Git-free profiles require actual qualification before adoption.

Local admission reads the authenticated default branch's generated inventory and health. After trusted repository, workflow and inventory metadata are established, relevant failures or unavailable health history require full validation. Missing or malformed authority blocks planning; it cannot be bypassed by choosing full validation. A live provider checks the original revision and context again; the product independently requires the selected checks to pass.

Hosted verification reconstructs the plan from trusted source and validates native portable evidence in a fresh job. It rejects raw failures, attributed failures, mismatched invocation bindings and missing checks. Current delivery telemetry is enforced on the original candidate, while isolated checks only validate source artifact bytes.

Application business behavior, global finding closure and the default validation policy are not changed by this integration.

How to extend it safely

  1. Add or characterize a check in the canonical registry, including inputs, membership and execution profile.
  2. Use conservative fallback where dependency coverage is uncertain.
  3. Run negative controls that would expose omitted work; a green narrow run alone is insufficient.
  4. Keep evidence bound to its actual release, candidate and environment.
  5. Use the product's freshness decision, and verify current health at admission.
  6. Preserve failed attempts and global findings through repair and rollback.

Check your understanding

  1. Who owns durable execution attempts?

    1. Athena's uploaded plan
    2. The installed delivery product
    3. A second authoritative attempt ledger maintained by Athena

    The product owns execution and evidence verification; Athena declares repository policy.

  2. What does a plan prove?

    1. All checks passed
    2. Global health is clear
    3. Which checks are required and why

    Selection is separate from execution evidence and admission.

  3. What happens when a consumer dependency is unknown?

    1. Validation broadens to the declared fallback
    2. The consumer is omitted
    3. Any old result is accepted

    Uncertainty cannot justify skipping potentially affected work.

  4. A report changes after application checks pass. Which result may remain reusable?

    1. Every application result, because reports are review-neutral
    2. An unrelated unit result with unchanged qualified inputs; the report-consuming operator build must be reconsidered
    3. Every result whose test filename is unchanged

    Consumer inputs, environment and profile matter as well as test membership.

  5. Does candidate repair close the global finding?

    1. Yes, after a successful full candidate run
    2. Yes, once the affected check passes locally
    3. No, protected approval and revalidation govern global closure

    Candidate admission and global health closure are different decisions.

  6. Can a partial unit slice prove a complete health check passed?

    1. No, repair requires complete applicable coverage
    2. Yes, if its check ID matches
    3. Yes, if it ran recently

    A stable check ID does not imply complete membership.

  7. Why verify hosted evidence in a fresh job?

    1. To trust the uploaded summary
    2. To reconstruct authority and verify portable evidence independently
    3. To avoid checking the candidate

    Execution-job success alone does not establish current, correctly bound evidence.

  8. What does the isolated telemetry command establish?

    1. The current delivery is complete
    2. The current run is fresh and bound to this candidate
    3. Changed telemetry JSON has valid product structure

    Current-run admission is enforced separately on the original candidate.

  9. What happens to evidence after installing a successor release?

    1. Old results are relabeled automatically
    2. Old provenance remains intact and release-sensitive qualification is repeated
    3. Failed history is deleted

    Evidence must describe the release that actually produced it.

  10. Is integration merge the complete activation finish line?

    1. Yes, merge proves all runtime behavior
    2. No, hosted qualification, measured performance and default activation remain required
    3. Yes, if comparison mode exists

    The accepted outcome includes an authoritative qualified default and demonstrated rollback.
