Executive summary

Athena had a security rail that worked and that nobody finished adopting. Two earlier deliveries built an admission boundary for backend writes and reads, but both stopped at the surfaces the shared demo could reach. Everything else kept its old, ad-hoc authorization — and the list of "everything else" was written down, in the codebase, as a 189-entry exemption list that had stopped shrinking.

This delivery finishes the job and then removes the machinery that made being unfinished expressible. Every public Convex mutation, query, and action, and every Hono HTTP route, now declares an operation definition and runs through one canonical wrapper per ingress kind. The checker discovers 609 ingress points and admits 605; the remaining four, plus the HTTP route family Convex Auth installs, are the framework entry points described below. It exits 0 with zero findings, and there is no exemption construct left anywhere in the tree — not renamed, not emptied-but-present.

The largest real-world exposure closed here was not the unmigrated Convex functions. It was the 93 HTTP routes, which the storefront webapp uses exclusively, and which read a shopper's user_id / guest_id cookie and treated it as identity — passing it straight into backend calls, behind a CORS middleware that reflected any origin.

What was actually wrong

The rail's promise was one sentence: capability declared ⇒ admission installed. If a function said "this requires cash.control.write", the rail guaranteed that the caller actually held it, in the right store, before the handler ran.

That promise held for roughly a quarter of the backend.

  • 411 unadmitted Convex exports. 189 raw public mutations against 57 admitted, plus 184 raw queries and 38 raw actions.
  • An exemption list that had become a second policy. 189 entries, structurally indistinguishable from the backlog it represented. Its own documentation described it as "a deliberate map of what has not yet moved through the front desk" — which is exactly what a migration tool looks like right up until it stops shrinking.
  • 93 HTTP routes with no admission at all. Each route independently decided how much to trust the cookie. There was no shared answer, so there was nothing to review.
  • Four hand-maintained registries restating, by hand, facts the definitions already carried — and all four had drifted.
  • About fifty handler-local demo guards, each stating "not the demo" at one statement inside one function, and each only as good as its position in that function.

The mental model

Think of the backend as a building with many doors. Before this delivery, some doors had a front desk that checked your badge against what you were trying to do. The rest had a handwritten note taped inside saying "if it's the demo visitor, turn them away" — and a clipboard by the entrance listing which doors still only had notes.

The three problems with notes taped to doors:

  1. Position matters. A note halfway down a corridor stops nobody who entered from the other end. A guard placed after the first database read has already leaked whatever that read returned.
  2. Nobody can audit them in aggregate. To answer "can the demo reach payment collection?" you had to read every handler, and the answer changed whenever anyone edited one.
  3. The clipboard becomes the map. Once "not yet covered" is a first-class, permanent state, it stops being a countdown and starts being a category.

The rail replaces notes with a declaration at the door: every entrance states who may pass, what capability it requires, which store it is scoped to, and which external systems it can reach. The front desk enforces that before you are inside — so the guarantee no longer depends on where in the corridor someone remembered to stand.

The vocabulary maps onto that picture directly. A capability is what the badge must say for a write ("cash controls"); a read intent is its equivalent for reads, kept separate because being allowed to see something is not being allowed to change it. Scope is which store or organization the door leads into. Readiness is whether the room is in a state to be entered at all. A gateway is a door leading out of the building entirely — to a payment provider, an email sender. A target guard is a rope around one exhibit that stops everyone, including staff. The composition root is the one office that hires the desk clerks and writes their rules; the rail core is the desk procedure, which knows nothing about who works there. And ctx.operationAdmission is the visitor badge the handler is handed — the only place it may learn who it is serving.

The second, subtler idea: if a fact is already on the declaration, never write it down a second time. Four of the things deleted here were lists that restated declarations. Each one could disagree with reality, and each one did.

Before and after

A Convex mutation

// before — policy interleaved with domain logic, position-sensitive
export const recordThing = mutation({
  args: recordThingArgs,
  handler: async (ctx, args) => {
    await requireSharedDemoCapabilityIfApplicable(ctx, "daily_operations.write");
    await requireNonDemoFoundationMutation(ctx, { storeId: args.storeId });
    return recordThingWithCtx(ctx, args);
  },
});

// after — policy declared, enforced before the handler is entered
export const recordThing = mutation({
  args: recordThingArgs,
  handler: admitPublicMutation(recordThingOperationDefinition, recordThingWithCtx),
});

An HTTP customer write

This is the one that mattered. Before, the route read the cookie and used it as identity: 

// before — a cookie read inline by the route IS the identity
//   getStorefrontUserFromRequest = getCookie(c, "user_id") || getCookie(c, "guest_id")
//   getStoreDataFromRequest      = getCookie(c, "store_id")
const userId = getStorefrontUserFromRequest(c);
const { storeId } = getStoreDataFromRequest(c);
await ctx.runMutation(api.storeFront.reviews.create, {
  createdByStoreFrontUserId: userId,   // an unverified cookie value
  storeId,                             // an unverified cookie value
  ...body,
});

// after — the rail admits, and the ADMITTED actor supplies identity
admitHttpRoute(createReviewRouteOperationDefinition, async (c, admitted) => {
  const body = parseIngressJson<CreateReviewRequest>(admitted);
  // Author and store both come from the admitted claim; storeId and
  // createdByStoreFrontUserId are no longer arguments at all.
  const owner = requireAdmittedCustomerOwner(admitted);
  await ctx.runMutation(internal.storeFront.reviews.createInternal, {
    ...body,
    owner,
  });
});

Three things changed at once. The caller's identity now comes from the admitted actor rather than from a cookie the route read for itself — the rail resolves the claim to a row and derives the store from that row, cross-checking the store_id cookie rather than trusting it. The call target moved from api.* to internal.*, because an api.* hop re-enters the rail carrying the server's identity and launders the caller's actor. And the route must declare an origin allowlist, because a SameSite=None bearer cookie is reachable cross-origin and needs a second, independent fence.

The layer map

ingress ──► canonical wrapper ──► composition root ──► rail core ──► handler
             admitPublicMutation      registers policy      pure logic:
             admitPublicQuery         (demo adapters,       definitions,
             admitPublicAction         customer adapter,    adapter chain,
             admitHttpRoute            foundation guards)   target guards,
             admitHttpRead                                  verification

The rail core imports only itself, generated code, and three catalogs. A path-prefix allowlist lint enforces that, with fixtures proving that importing the composition root or a policy module fails. This is what makes "the generic rail must not know about the demo" structural rather than aspirational.

What changed, and what deliberately did not

Changed

  • 605 ingress points admitted — 244 queries, 232 mutations, 35 actions, 45 HTTP writes, 49 HTTP reads. The only non-admitted ingress is Convex Auth: four registrar exports (auth, signIn, signOut, store) and the HTTP route family auth.addHttpRoutes installs — a browser-reachable sign-in surface that is deliberately outside the rail. Auth is the trust root that MINTS the principals the adapters resolve, so admitting it with them would be circular.
  • One wrapper name per ingress kind. admitPublicMutation and admitPublicQuery are renames of the existing withOperationMutationAdmission / withOperationReadAdmission, not new machinery; the transitional re-export modules are gone, so there is exactly one import path per wrapper.
  • A new actor kind, storefront_customer, valid only on HTTP ingress. It records assurance: "bearer_id" in provenance, because a cookie id is proof of possession, not authentication. Declaring it on a Convex-function kind is a validation error — a plain argument is not a claim boundary.
  • 40 orphaned public exports deleted. Once routes switched to internal siblings, these had zero callers anywhere. storeFront/auth now has no public exports at all.
  • The framework entry-point list is not an exemption list wearing a hat — the obvious objection, and worth answering directly. It is five hand-written entries the checker will not fail on. What keeps it honest is that it is verified in BOTH directions: an entry naming a registrar discovery no longer finds is a finding, and a discovered registrar not named in the list is a finding. The old exemption list was one-directional, which is why it could grow silently. Adding an entry here is a deliberate act with a stated reason that a reviewer sees.
  • Four hand-maintained registries deleted and derived — see the drift table in the solution note. reports.read, a write capability that existed only so the demo could read Reports, is replaced by the reports.view read intent.
  • The fail-open catch is gone. resolveOperationAdmission used to catch any throw and retry against the public adapter — including scope-resolver failures. Denials are now typed data, and no adapter classifies by error-message text.

Deliberately unchanged

  • Demo reach was not widened. Not one capability or read intent was added to either grant set. Four narrowings were preserved rather than quietly resolved: pos.session.manage, expenses.view, storefront.reviews.view, storefront.analytics.view. Whether the demo should demonstrate them is a product question.
  • Route paths and payloads. No URL or request shape changed. The route count reads 93 before and 94 after only because the MTN MoMo webhook is registered with .on(["POST","PUT"]) and is now counted as the two ingress points it always was.
  • Normal-user behavior. Characterization-first per unit, with exported-handler parity tests.
  • Roles, membership, staff credentials, approvals, demo fixtures and restore. Explicitly out of scope.

Live behavior changes worth naming

A migration that claims to change nothing is usually lying about something. These are the real caller-visible differences.

Deploy prerequisites — all fail-closed by construction

Five environment variables must be set or the corresponding ingress denies everything: ATHENA_STOREFRONT_ALLOWED_ORIGINS, WHATSAPP_WEBHOOK_APP_SECRET, MTN_MOMO_COLLECTIONS_CALLBACK_SECRET (which must also be appended to the registered MTN callback URL as callbackSecret=…), WALKTHROUGH_ALLOWED_ORIGINS, and ATHENA_WAIVER_BROKER_SECRET.

One data prerequisite: the guest storeId backfill must run before deploy. POST /guests now requires a store, so guest rows without one cannot be re-owned afterwards. The backfill is deliberately conservative — derive only from an authoritative related row, leave unresolvable rows unset so they deny, never default to a store.

Two mechanics worth understanding

Derive, then assert in both directions

Deriving an invariant from the declarations is half the work. The direction you assert it in decides which failure you catch. 

// forward — a grant that nothing implements (a stale grant)
for (const capability of SHARED_DEMO_ALLOWED_CAPABILITIES) {
  expect([...represented]).toContain(capability);
}

// reverse — an operation admitting the demo for something ungranted
for (const capability of represented) {
  expect(granted.has(capability)).toBe(true);
}

The deleted inventory could only ever express the forward direction: it was a list of representatives, so a newly added sharedDemo: "admit" on an ungranted capability was invisible to it. The reverse direction is the one that actually fences the boundary — and it costs nothing once the set is derived.

A test can pass for the wrong reason

The gateway-binding check asserted that each module's source contained the name of its demo guard, via toContain. Those guards were retired during this migration — but each retirement deliberately left a comment naming the guard it replaced, so the substring was still there. From convex/inventory/organizations.ts: 

// `requireNonDemoFoundationMutation({ athenaUserId: createdByUserId })`
// retired here and re-expressed as `target.protectDemoFoundation` bound to
// `createdByUserId`, so the guard still runs for every actor kind.
handler: admitPublicMutation(createOrganizationOperationDefinition, ...)

The comment is good practice — it is the audit trail from retired call site to successor. It also meant the check stayed green for the entire migration while the thing it checked was being deleted underneath it. The same shape appeared in the foundation-binding check, which "verified" that modules still called requireNonDemoFoundationMutation when every remaining occurrence in those files was inside such a comment.

That is worse than having no test. A missing test leaves a gap you can find; a test passing for the wrong reason fills the gap with false confidence and stops anyone looking. The same reasoning is why no source-regex "is this ingress admitted?" assertion was added here: an admitted export still reads export const x = mutation({ handler: admitPublicMutation(...) }), so source shape distinguishes nothing. That question needs the AST, and the checker already answers it as a gate.

One honest caveat. No adapter classifies by error-message text any more — that was the fail-open shape this delivery removed. But a handful of handlers still do, inside their own catch blocks (message !== "Sign in again to continue." and similar), when translating a denial into a CommandResult. The practice is gone from the policy layer, not from the codebase.

What review caught that the migration did not

Four controls that looked present at the call site. Each was introduced by a unit that could not see the whole, and each surfaced only when closure went looking — which is the argument for having a closure unit at all.

  • A wrapper "somewhere in the handler" is not admission. The checker accepted an inline handler if a wrapper call appeared anywhere in its body and no ctx.db write came first. That let nine handlers read the database, call ctx.runQuery/runMutation, or run a second admission probe before the caller was admitted. The rule is now positional, violations raise wrapper-not-first, all nine were converted to a single admission, and resolveWriteAdmission is no longer exported so the double-admission shape cannot come back.
  • A refusal was reported as a server fault. HTTP admission denials escaped the Hono handler and rendered as 500 — so clients retried, monitoring paged, and the body carried the internal error text. Now 401 for unauthenticated, 403 for refused, fixed body.
  • An optional argument disguised a skipped check. assertCustomerOwnsRowIfPropagated returned silently when owner was absent. It was a deliberate transitional measure — and the transition finished without anyone removing it. Eighteen callees (not the nine a first pass found: several inlined the same shape rather than calling the helper) now take a required owner, and genuine absence is explicit via SERVER_INITIATED_OWNER.
  • Body bounds covered the routes someone thought about. Two public marketing routes carried size-limit middleware; the other forty-plus admitted writes read an unbounded body before admission. The bound now lives in the rail and applies to every http write.

And what an independent review round caught after that

Thirteen reviewer personas ran against the closure candidate. The notable result is not the count but the source: three of the blocking findings were defects introduced by the closure work itself — by the round meant to be the safety net.

  • P0 — the webhook break. Bounding the ingress body inside the rail meant the rail read c.req.raw.body directly, while the WhatsApp and MTN MoMo middlewares had already consumed it with c.req.text(). A Fetch body stream reads once, so the rail re-verified an EMPTY body against the same declared verifier and would have denied every genuine callback. The middlewares now reconstruct the request, and the bounded reader throws on an already-consumed body so the next instance is loud rather than silent.
  • P0 — the bag re-owner. The merge admitted a caller matching either side, so a signed-in shopper could name any guest id and absorb — and destroy — that shopper's cart. There was no store bound either. The in-file comment claimed the opposite guarantee.
  • The guest identity chain had five links. Body field → cookie compared against itself → cookie the mint trusted → signed cookie → the recovery marker, which was caller-chosen, five base-36 characters, and whose marker-less lookup resolved the oldest marker-less row. The marker is now treated as what it always was — a session-recovery secret: minted with crypto.randomUUID(), required to be high-entropy, scoped to the store being bootstrapped, and hashed at rest (SHA-256) so a database read cannot hand over live session credentials. GET /homepage-snapshot no longer mints guests at all, leaving two mint points instead of three. When one link in an identity chain is attacker-controlled, fixing it does not end the review — ask what the next input is, and who chooses it.
  • The checker was defeated five rounds running, so it stopped being a blacklist. Each round found an expression form the previous rule did not enumerate: a const-bound wrapper, work hidden in the invocation's arguments, an IIFE argument, and a composition-root match on an unresolved path suffix that any shim — or a package named @evil/operationAdmission — satisfied. Enumerating bad shapes is unbounded. The checker now accepts a closed grammar: the wrapper must resolve, by fully resolved module path, to the composition root, and the handler must be exactly handler: wrapper(definition, handler). Everything else raises wrapper-shape. A novel shape fails closed instead of slipping through, and the repo's own call sites were adjusted to fit — the grammar is the contract, not a description of what happened to be there. Round 5 went further and fixed the grammar's inputs: discovery now enumerates what the bundler registers rather than globbing *.ts, resolves import specifiers by path rather than by suffix, compares definition identity against the registry rather than by name, and reports anything it cannot follow as ingress-not-statically-resolvable instead of skipping it. A name is a coincidence; a resolution is a fact.
  • And the objects the checker trusts are frozen. Comparing definition identity against a registry is only as strong as that registry's immutability — a module pushing an entry in at import time would get a definition treated as declared that no reviewer saw. Definitions are deep-frozen at construction, so an admitted handler cannot mutate the policy it was admitted under, and both registry arrays are frozen too. It closes the gap between "the checker verified this object" and "this object is what runs".
  • P1 — a hole in the new checker rule. It accepted const run = admitPublicMutation(def, fn) as proof the wrapper ran first. A declaration is not an invocation: a handler could write rows before any caller was admitted and still be reported as admitted. And isPreAdmissionCtxEffect, written expressly to catch pre-admission work, was never called from anywhere.
  • P2, found independently by two reviewers — an inverted fault contract. Tagging admission failures at the catch site marked every error as a denial, so a database error reached clients as 403 — an expected status here, so nothing retried and no 5xx reached monitoring. Denials are now tagged at the throw site; anything unmarked surfaces as a 500.

The remainder were genuine migration gaps: guest merges bounded by store and nothing else (so a signed-in shopper could absorb a stranger's order history and reward points), route handlers mapping every fault to an expected client status, and lost behavioral coverage on the checkout and sign-in paths.

The fix that wasn't — and the sharpest lesson here

The guest-merge fix shipped in round 2 bounded by "possession": comparing the body's guest id against the request's guest_id cookie. Two reviewers independently pointed out in round 3 that a cookie is caller-supplied — both operands arrived on the same request, so any caller satisfied the check by typing the same id twice. The exploit precondition was unchanged. And the round had shipped comments asserting the opposite ("they hold no such cookie"): the exact defect this delivery exists to remove, committed while removing it.

That fix was still not enough. A fourth round found that POST /auth/verify minted the grant from the caller's raw guest_id cookie — so an attacker presenting a victim's id while signing in to their own account received a grant on it. Three rounds, three versions of one bug: a body field, a cookie compared against itself, a cookie the mint trusted. The server had no way to tell a guest session it issued to this browser from an id somebody typed.

The complete fix is two layers. The guest cookie is signed — minted as <id>.<hmac> at the two bootstrap routes and verified in constant time by every consumer, gated on ATHENA_STOREFRONT_COOKIE_SECRET. An unsigned or tampered cookie is treated as absent, not as an error: a stale cookie is a shopper to re-bootstrap, not a fault to page on. And the merge authorizes on the server-issued grant, now minted only from a verified guest id. Precisely:

Two mint points and no more: GET /homepage-snapshot had been a third that set a bare, unsigned guest_id — a session no consumer accepted, on a route the storefront never bootstrapped through — and that branch is deleted. And because both bootstrap routes will still resolve an existing guest from the storefront's session-recovery marker and sign a cookie for it, the marker is a secret or nothing: it was caller-chosen, five base-36 characters of Math.random(), unscoped by store and optional — no marker at all matched the oldest marker-less row. guest:getByMarker now requires a high-entropy marker (≥22 chars) and a store, the storefront mints it with crypto.randomUUID(), and anything else mints a fresh guest. The route tests drive the round-4 attack — bootstrap with the victim's marker, sign in, merge — end to end. And a secret is not left in the clear on a row that operator reads and the public GET /guests hand back whole: the guest row now stores only the marker's SHA-256 digest (hashGuestMarker), guest.create gates and hashes before writing and returns the existing row for a repeated (store, marker), getByMarker hashes before the lookup, and guest:getAll — previously every tenant's guests to any signed-in account — is store-scoped. A digest lifted from a document does not resolve; the tests present one and get a fresh guest.

  • A merge is possible only inside a 15-minute window opened by an authenticated sign-in, once per merge kind (bag, savedBag, onlineOrder, analytics, rewards), and bounded to the admitted store.
  • A live, unconsumed grant is never re-pointed to a different account, so a second sign-in cannot strand a half-finished merge sequence.
  • The remaining residual is the legacy-cookie upgrade window. Pre-signing cookies still in browsers are re-minted signed at bootstrap — otherwise the deploy would empty every existing cart — and while that path exists, someone who knows another shopper's guest id can present it unsigned at bootstrap and be handed a signed cookie for it. The upgrade is confined to the two bootstrap routes, and a cookie whose signature fails to verify is treated as tampering rather than as legacy. Delete this path once legacy cookies have aged out — 90 days, the cookie's own max-age. Tracked as V26-1240, which also owns signing user_id: that is not a small delta, since it changes the authenticated-shopper claim path rather than the guest one.

"Caller-supplied" includes cookies — and it kept being forgotten. Three rounds, three versions of the same bug, each shipped believing it was fixed. A guard comparing two caller-supplied values is not a guard, and a server-issued token minted from a caller-supplied value inherits that value's trust class. The fix has to be something the server issued and can verify it issued to this caller. The residual above is written beside the mechanism in customerOwnership.ts, because a comment naming only the guarantee is how each earlier version survived review by its own author.

One lesson from this round is worth more than the fixes. The first regression test written for the webhook P0 asserted not.toBe(403) — and passed with the fix removed, because the test harness returned 500 for an unrelated reason. That is exactly the "passing for the wrong reason" defect this delivery exists to remove, reproduced while removing it. Reverting the fix and watching the test go red is cheap, and it is the only thing that establishes a test actually pins its bug.

The last qualification on the central claim, closed in round 9. Through round 8, router-level middleware was invisible to the route walk except for the single allowlisted cors(...) registration, so a path-scoped .use whose handler never calls next() responded terminally for every method under that path with zero findings — and, contrary to the earlier note, the tree carries five non-CORS .use sites (the WhatsApp, MTN MoMo and harness-waiver verifiers, and boundRequestBody(...) on the two marketing routes). Round 9 walks .use like every registration and judges the handler against a closed pass-through-or-deny grammar: an inline (c, next) => {…} that ends in await next(), returns only next() or a c.json(…, <literal 4xx/5xx>) denial, and touches c only as c.req; or a factory imported by name from http/** whose export is exactly one such returned function; or the hono/cors factory. Anything else is router-middleware-not-statically-resolvable. All five real sites pass unchanged; mutating any one to answer 2xx produces a finding; the pinned residual test now asserts the finding. The qualification on the claim that an ingress is either admitted or flagged is gone.

Residual risks, ranked

Recorded so they are decisions rather than oversights.

  1. Argument-derived scope is a clamp, not an authorization. resolveOperationScope records args[storeIdArg] without verifying membership; handlers still carry that. Only the three inert /organizations operator stubs resolve scope this way on HTTP today, and their handlers read nothing — so no live exposure, but it is easy to misread as stronger than it is.
  2. The legacy-cookie upgrade window. The bootstrap routes no longer trust an arbitrary guest_id — unsigned or tampered cookies are treated as absent, and a bad signature is refused rather than read as legacy. What remains is the migration path: a pre-signing cookie naming a real guest row in that store is re-minted signed so existing carts survive the deploy, and while it exists someone who knows another shopper's guest id can present it unsigned at bootstrap. Confined to the two bootstrap routes. Delete once legacy cookies age out — 90 days. Tracked as V26-1240.
  3. Convex Auth's HTTP route family is unadmitted by design; registration order and single registration are pinned by source inspection, not behaviourally.
  4. Payment audit attribution is still read from client arguments rather than the admitted actor, so the audit record states what the caller claimed. Deferred to V26-1241.
  5. checkoutSession.updateCheckoutSession / getByIdInternal keep an optional-owner no-op, and userOffers.getEligibility asserts nothing on caller-supplied ids. Neither is currently exploitable — every live caller derives the ids from the admitted claim — but the safety rests on callers rather than on the callee refusing. Deferred to V26-1242.
  6. Read amplification, and the one thing this delivery made measurably worse. The shared-demo adapter runs first in the chain for all 605 admitted ingress points, so every authenticated staff request now pays an indexed sharedDemoPrincipal lookup that resolves to null for almost all traffic; before, only the ~17 demo-aware handlers paid it. That is in tension with the project's standing Convex read-minimization rule. Accepted for now because the fix depends on a design call about what the auth identity payload can carry. Deferred to V26-1243.

Guidance

Adding a public function

The full checklist is in convex/operationAdmission/README.md. The short version: declare it in the domain module for its area, state every actor (actors.public is required and never implied), scope it to a store or organization, wrap the export with the canonical wrapper from the composition root, and run the checker. The checker also runs in the merge gate and is asserted by coverage.test.ts — which is why "no exemption construct" stays true rather than decaying.

The four things people get wrong

  • Calling api.* from an admitted body. It re-enters the rail with the server's identity and launders the caller's actor. Use the internal.* sibling.
  • Taking identity from arguments. Every owner / storeId / userId an internal callee needs comes from ctx.operationAdmission. A caller-supplied id is an argument to validate, not an identity to trust.
  • Assuming a dynamic capability is any-of. It is all-of: a batch mixing a granted and an ungranted capability is denied whole, before the handler runs.
  • Testing the *WithCtx helper. That skips the boundary under test. Test the exported handler.

Transferable lessons

  • A migration-tolerance construct needs a deletion date built into its definition of done. Otherwise "not yet covered" becomes a permanent category rather than a countdown.
  • If a fact is already declared, do not restate it in a list. The list is a second source of truth with no mechanism keeping it honest.
  • Retire a runtime guard by promoting it to a declaration, not by deleting the line. A declaration enforced before handler entry is order-independent.
  • Sequence a large parallel migration by pre-creating the shared surfaces. Closing both catalogs and pre-creating per-unit domain modules in Phase A is what let eleven units run without editing a shared file.

Comprehension quiz

Ten questions. Eight correct to pass.

  1. Why was the exemption list deleted rather than emptied?

    1. Emptying it would have broken the checker's type signature.
    2. Its entries were needed as the caller table's input.
    3. An empty list can be refilled in one commit.
    4. It duplicated the framework entry-point list.

    The structure was the problem, not its contents. While "not yet covered" remains expressible, a migration can quietly settle into being a permanent two-policy system.

  2. The gateway-binding check stayed green while the guards it checked were deleted. What made that possible?

    1. A stale CI filter skipped the whole shared-demo suite.
    2. It asserted against the demo fixture store only.
    3. It cached results between runs.
    4. It matched the guard name inside retirement comments.

    Each retirement left a comment naming the guard it replaced — good audit practice — and a substring check cannot tell a comment from a call site.

  3. Which failure does the reverse-direction demo assertion catch that the forward one cannot?

    1. A granted capability that no admitted operation implements.
    2. An operation admitting the demo for an ungranted capability.
    3. A capability declared twice in the catalog.
    4. A read intent used on a write definition.

    Forward finds stale grants; reverse finds widening. The legacy inventory listed representatives, so it could only ever express the forward direction.

  4. Why may an admitted handler never call api.*?

    1. The hop skips the definition's target resource guards.
    2. Convex rejects self-referential API calls at runtime.
    3. The hop re-admits using the server's identity.
    4. It double-counts the operation in the capture port.

    Re-entering the rail means being admitted again, and the second admission sees the server rather than the shopper. Target guards do run on every admitted kind, so that distractor is wrong.

  5. Where must the canonical wrapper appear inside an inline handler?

    1. Anywhere, provided no ctx.db write happens to precede it.
    2. Anywhere, provided it runs on every code path.
    3. After argument validation but before any database access.
    4. As the handler itself or its first unconditional statement.

    The first option was the old, too-weak rule: it permitted reads, ctx.runQuery, and scheduling ahead of admission. A try block starting with the wrapper is the one accepted variation.

  6. Why is a failed HTTP admission a 401 or 403 rather than a 500?

    1. Convex cannot serialize a thrown error across an HTTP route.
    2. A refusal reported as a fault gets retried and pages on-call.
    3. Hono requires an explicit status on every response.
    4. The capture port records only 4xx outcomes.

    It also leaked the internal error text. The 401/403 split is read from typed data on the error, never from its message, because the original error class is gone across the boundary.

  7. Which ingress is deliberately NOT admitted, and what keeps that list from becoming a new exemption list?

    1. Internal functions; they are unreachable from outside.
    2. Webhooks; their signature verifiers replace admission.
    3. Convex Auth; the list is verified in both directions.
    4. Read queries; they perform no writes.

    Auth mints the principals the adapters resolve, so admitting it with them would be circular. A stale entry and an unlisted registrar are both findings, which the old one-directional exemption list could not manage.

  8. Why did HTTP route migration have to follow the Convex function migration?

    1. Route definitions reuse the function definitions' operation ids.
    2. The checker could not discover routes until functions were admitted.
    3. CORS had to be allowlisted before any route could be declared.
    4. Routes call internal.* siblings the function units create.

    Internalization was two-step on purpose — add the sibling keeping the public export, then flip the routes and delete the orphan — so every intermediate state compiles.

  9. A definition scopes itself with storeIdArg: "storeId" and admits normal users. What does the rail guarantee?

    1. The caller is a member of that store.
    2. Only that the handler is confined to the store named.
    3. The store exists and is not archived.
    4. Nothing; argument-derived scope is rejected at validation.

    resolveOperationScope records the argument as the constraint without verifying membership. It is a clamp, not an authorization — proving the caller may act there is still the handler's job.

  10. Why was no source-regex "is this ingress admitted?" check added to the shared-demo suites?

    1. Those suites run before the definition registries are composed.
    2. Regex assertions are disallowed by the repo lint rules.
    3. The type checker already rejects unadmitted exports.
    4. An admitted export and a raw one have the same source shape.

    Both read mutation({ handler: ... }). Writing a weaker version of a check the AST tool already performs is exactly how this codebase acquired a test that passed without verifying anything.
