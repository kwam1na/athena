Executive summary

The first weekly manager report Athena ever produced for a real store asserted two things it had no evidence for: that none of the week's scheduled days were closed, when in fact every one of them was, and that closing cash matched, when several days carried real counted-cash differences. Both statements were confidently rendered, and the report had already been accepted and emailed.

This delivery fixes the cause rather than the symptom. Weekly reports now take each fact from the evidence lane that can actually observe it, carry an explicit vocabulary for "we do not know" so absence can never print as zero, and expose counted-cash variance as its own named signal beside the pre-existing sales reconciliation rather than in place of it. It also adds payment-mix and expense-product evidence to the weekly projection, and a sealed, fail-closed repair that can correct the one already-accepted week without rewriting its immutable baseline.

What went wrong

A weekly report is assembled from a seven-date schedule frame. When a week is accepted, the system freezes a baseline — a permanent record of what was true at acceptance time. That baseline included a field saying, for each scheduled date, whether the day had been closed.

The problem was where that field came from. The accepted baseline was built by folding report facts — the stream that carries sales totals. Report facts know nothing about Daily Close records, so the fold had no way to observe close state. It did not report "unknown"; it reported false for every day. A fully closed week therefore froze as a week in which nothing had been closed.

The second defect was a naming collision with real consequences. The weekly report already had a metric called variance, but it measured something specific: the reconciliation between folded sales and the net sales figure on the close. A manager reading "variance" in a report about closing a store reasonably understands it as counted cash — the money in the drawer against the money expected. Those are different numbers from different lanes, and the report only had the first one while implying it was the second.

Both failures share a shape worth remembering: the arithmetic was correct throughout. Every number was computed accurately from the inputs it was handed. What was wrong was authority — a projection built from one evidence lane was allowed to speak for a fact that lives in a different lane.

How to think about it

Four words used throughout

Frame
The seven dates a weekly report covers, resolved from the store's schedule. Some are scheduled operating days ("included"); the rest are not.
Fold
The act of collapsing many source rows into one weekly shape. Which rows you fold determines what the result can honestly claim.
Lane
One independent stream of evidence — counted cash, payment mix, expense products, transaction counts. Each is sourced, validated, and covered separately, so one lane going dark leaves the others intact.
Coverage
How many of the frame's scheduled days a lane actually has evidence for, expressed as complete, partial, or unavailable plus the counts behind it.

Picture the week's report as a page assembled by several reporters, each allowed to file only on their own beat.

  • The sales reporter reads the fact stream. It can tell you what was sold and for how much. It cannot tell you whether anyone closed the till, because it never visits the till.
  • The close reporter reads Daily Close snapshots. It can tell you which days were certified, what the counted cash came to, how customers paid, and what was consumed as expenses.

The old system let the sales reporter file the close reporter's story. Worse, the newsroom had no way to print "not reported yet" — a blank filed as a zero, and a zero reads to a manager as "nothing happened", which is a claim, not an absence.

The fix gives each beat its own byline and gives the newsroom a way to say it does not know. Every close-backed section now carries its own coverage, along with how many of the scheduled days it actually covers. A certified zero — a day that genuinely counted zero variance — is covered. A legacy day that never recorded the field at all is not. Those two situations produce the same number and must never produce the same statement.

One detail worth holding precisely, because the metaphor smooths it over: the lineage fix does not make acceptance go and read Daily Close records. Each report day row already carries a close-variance field that is set only when a close exists, and dayClosed is derived from whether that field is present. The old fold synthesised its day rows from sales facts, so the field was never set and the derivation always produced false. Acceptance now folds the real stored day rows instead, where the field is genuinely present or genuinely absent. The evidence lanes are the part that reads Daily Close snapshots directly.

Before and after

Before

  • Accepted baseline froze scheduleLineage from a fact-only fold, so dayClosed was false for every day regardless of reality.
  • One variance metric — the sales-to-close reconciliation — carried a name managers read as counted cash. Counted-cash evidence was not surfaced at all.
  • Payment composition and expense-product detail existed on Daily Close records but never reached the weekly projection.
  • Accepted top-sellers stored only SKU identifiers, with product names hydrated from the live catalog at render time — so a later rename silently rewrote history.
  • Nothing could correct an accepted week. The row was immutable and the only alternatives were to rewrite history or leave it wrong.

After

  • Acceptance freezes lineage from the resolved report-day fold, which carries real close lineage. The fact fold still owns financial totals — what it can legitimately know.
  • A shared aggregator reads frozen Daily Close snapshots and produces counted-cash, payment-mix, and expense-product evidence. The sales-fold variance keeps its name, its semantics, and its independent place in the report.
  • Every lane carries independent coverage counts, and renderers gate on coverage so partial weeks disclose their denominator instead of reading as full-week totals.
  • Display identity for products is frozen into the snapshot at acceptance; accepted rendering performs no catalog reads.
  • A set-once correction projection can carry corrected lineage, evidence, and frozen top-seller identity beside an untouched baseline. Reads resolve correction-over-baseline; the automatic email path is structurally baseline-only.

What changed, and what deliberately did not

Changed

  • Accepted lineage is taken from close-bearing day documents, so a fully closed week now states that it was fully closed.
  • Counted-cash variance is surfaced as its own named signal with covered day counts, on both the report and the email.
  • Payment mix reaches the weekly projection as value share in integer basis points with tender-use counts, and expense products reach it as two independently ordered rankings with reconciling remainders.
  • Coverage is modelled per lane, and partial sections disclose their denominator wherever a subtotal is shown.
  • Product display identity is frozen at acceptance and reconstructed by the sealed repair for the legacy week.

Deliberately unchanged

  • The accepted baseline is never rewritten. Refresh paths touch only lifecycle and amendment projections. A correction is a sibling field, not an overwrite, and the original fingerprint, timestamps, and metrics survive intact.
  • Sales-to-close reconciliation keeps its meaning. It was not renamed into cash variance; it now sits beside it.
  • No corrected email is sent. The automatic path cannot read a correction even on a delayed retry. Correcting what a manager already received is a separate, explicit decision.
  • Daily email behaviour, schedule membership, payment allocation semantics, and public read boundaries are untouched.

How evidence travels

The chain has three hops, and each one is allowed to refuse independently.

  1. Certification. When a day's Daily Close completes, it freezes an expense-product snapshot into the close record: per-SKU quantity and spend, with product name and SKU label frozen alongside. The reads are bounded and the totals must reconcile exactly to the close's own expense total, or the snapshot records the lane as unavailable instead.
  2. Aggregation. The weekly aggregator loads at most one close per scheduled date and re-validates what it finds rather than trusting it. A day whose evidence fails validation is dropped from that lane entirely — it is not partially consumed — which is why coverage counts can differ between lanes in the same week.
  3. Presentation. Reports and the email format the aggregated result and nothing else. Where they must say the same thing, they share the exact string: the "not available" sentence is a single constant deliberately kept byte-identical across both surfaces, because two hand-written variants is precisely how the surfaces drift.

This chain also explains why the one already-accepted week needs a reconstruction rather than a re-read. Its closes were certified before step one existed, so they carry no frozen product evidence at all. Cash variance, payment totals, and expense totals were always frozen and are simply read back — but the product composition has to be rebuilt from the retained expense rows inside each close's own window, then reconciled against that day's frozen expense total. The repair says so explicitly in its own output rather than presenting reconstructed history as if it had been recorded at the time.

Failure boundaries

Every new lane fails closed and fails narrowly. The design rule is that a lane may go dark without taking anything else with it.

  • Expense-item reads exceeding their budget mark the product lane unavailable and never freeze truncated product rows — the record keeps how many items were seen, but no partial per-product totals — and the Daily Close itself still certifies.
  • Invalid evidence — negative, fractional, non-finite, or unsafe values, or a spend total that does not reconcile exactly to the frozen expense total — refuses the lane rather than normalizing the numbers.
  • The sealed repair refuses on a wrong target, a non-unique lookup, a census mismatch, a per-day expense total that disagrees with its close, a probe overflow, an unresolvable product identity, or any fingerprint drift between preview and apply.
  • A reopened day drops out of current coverage until a successor close supplies fresh evidence; the accepted baseline stays byte-stable throughout.

Validation and review evidence

The change was reviewed before it was extended. Four parallel review passes covered the weekly backend, the email and notification boundary, Daily Close plus the Reports UI, and an independent test and typecheck run. That review produced a defect list which was then closed by five parallel fix agents with disjoint file ownership, followed by a sixth pass for the top-seller identity gap found while tracing the production backfill.

Findings that mattered, and their resolution:

  • A circular action type and an incorrect context type cascaded into a few hundred typecheck errors across otherwise untouched files. Both root causes were fixed; the package now typechecks clean.
  • The Reports payment mix was computing share from tender-use counts in the browser while the email used persisted value share, so the two surfaces disagreed. The view now renders the persisted value share, and the component tests that had pinned the wrong values were rewritten.
  • The sealed repair reconciled only weekly totals, so a change that moved spend between days while preserving the week could have passed. A per-day seam against each frozen close total was added.
  • The correction did not carry top-seller identity, which would have silently dropped a section the original email displayed. It now reconstructs that identity and fails closed if any product cannot be resolved.
  • A review pass over the draft of this report caught the sharpest one last: the sales-fold card's zero-case copy still read "Closing cash matched across the week." That is the original conflation this work exists to remove, and with the new lane in place it could have printed directly beside a counted-cash card reporting a real difference — worse than the state we started from. The copy now describes recorded sales reconciling to the closes, with a regression test asserting the sales lane never mentions cash.

Operational guidance

Running the correction

Deploy first, then run the dry run, inspect it, then apply with the two fingerprints it returns. The dry run writes nothing and is the real verification step: it proves the day census, the per-day reconciliations, and the notification state before anything is patched. Expect it to refuse rather than proceed if source rows have drifted — that is the feature, not a fault. The most likely first refusal is an unresolvable product identity if a SKU has since been deleted or blanked.

Rules worth carrying forward

  • If a field's name mentions a domain, confirm the fold populating it actually reads that domain. If it cannot, it must not write the field.
  • Never let a formatter turn missing cross-lane evidence into zero. Model coverage explicitly, and keep "certified zero" and "no evidence" distinguishable all the way to the rendered sentence.
  • New projection fields need an explicit writer, a persisted-row test, and a rollout path for rows written before the field existed.
  • Correcting immutable history means a sibling field plus a fail-closed, dry-run-first, fingerprint-verified command — never an in-place recompute.
  • When two surfaces must agree, give them one server-owned source and let both merely format it. The drift here appeared the moment a component was allowed to compute its own percentage.

Delivery-gate notes

  • The gate refuses to start while intended new files are untracked; stage them first.
  • The gate regenerates harness index docs, and those participate in the delivery fingerprint. Let it run, then compute the fingerprint, then embed it in the report and solution note.

Comprehension quiz

Eight of ten to pass.

  1. Why did the accepted weekly report claim that none of the week's scheduled days were closed?

    1. The Daily Close records for that week had been deleted.
    2. The baseline froze schedule lineage from a fold over report facts, which cannot observe close state, and it recorded that absence as false rather than as unknown.
    3. The store's schedule listed the wrong operating days.
    4. A timezone error shifted every close into the following week.

    The fold was reading the sales-fact lane, which has no visibility into Daily Close records. Lacking any way to express "unknown", it emitted a definite negative.

  2. A week's counted-cash variance totals zero, but only four of six scheduled days have cash evidence. What should the email say?

    1. That counted cash matched across covered days, with the four-of-six coverage disclosed alongside it.
    2. That counted cash matched across the week, since the total is genuinely zero.
    3. Nothing — a partially covered lane is withheld until every day reports.
    4. That cash variance is unavailable, because coverage is incomplete.

    The evidence supports a claim about the days it covers and no more. Saying "across the week" would extend a real measurement over two days it never saw, while withholding it entirely would discard evidence that four days genuinely produced.

  3. Under the coverage model, how is a day that certified exactly zero cash variance treated compared with a legacy day that never recorded the field?

    1. Both count as covered, since either way the day contributes zero to the weekly total.
    2. Neither counts as covered, because neither day shows an actual difference to report.
    3. The certified zero is covered; the legacy absence is not.
    4. The legacy day counts as covered as long as the rest of the week is complete.

    A measured zero is evidence. A missing field is not, and collapsing the two is exactly how absence gets rendered as a confident claim.

  4. How does the design let an already-accepted week be corrected while keeping accepted history immutable?

    1. The accepted row is rewritten and the previous version is copied into an archive table.
    2. A set-once correction projection is stored beside the untouched baseline, and reads resolve correction-over-baseline for accepted history only.
    3. The week is un-accepted, recomputed from current data, and re-accepted.
    4. A migration framework replays acceptance against a historical snapshot.

    The original values, timestamps, and fingerprint survive untouched. The correction is an orthogonal sibling field following the existing amendment pattern.

  5. Why can a pending or retried automatic weekly email never send corrected content?

    1. Corrections are applied only after all pending intents drain.
    2. The email payload is fully rendered and stored when the intent is created.
    3. Its preparation runs through a builder that reads only baseline fields and never consults the correction, so the correction is unreachable from that path.
    4. A feature flag disables corrected content in production.

    The separation is structural rather than procedural: the automatic builder has no path to the correction field at all.

  6. What happens to a Daily Close when its expense-product evidence overflows its read budget?

    1. Only the product lane is marked unavailable, no truncated product rows are frozen, and the close still certifies.
    2. The close is blocked until the expense reports are reduced.
    3. The evidence is truncated to the budget and marked complete.
    4. The close certifies and the missing items are backfilled later.

    Lane-level failure is deliberately narrow. An evidence problem must not block store operations, and a partial read must never be frozen as if it were whole.

  7. Why does the sealed repair reconcile each day against its own close's frozen expense total rather than only checking the weekly total?

    1. Weekly totals are stored as floating point and drift.
    2. A change that moved spend between days while preserving the weekly sum would otherwise pass, producing per-day evidence that contradicts each day's certified close.
    3. The weekly total is not available until after the repair runs.
    4. Per-day checks are needed to keep the reads bounded.

    Only the per-day seam catches a void-and-recreate that shifts spend across dates. It was added after review found the weekly-only check insufficient.

  8. Why did accepted top-seller identity have to be frozen into the snapshot?

    1. Because names hydrated from the live catalog at render time mean a later product rename silently rewrites what a historical report says.
    2. Because SKU identifiers are not stable across deployments.
    3. Because product names are too long to resolve at send time.
    4. To reduce the number of database reads in the weekly query.

    Accepted reports are evidence. Anything they render from mutable tables can change after the fact, which defeats the point of an immutable baseline.

  9. What caused the Reports page and the email to disagree about payment shares before review caught it?

    1. The email rounded to whole percentages while the page used decimals.
    2. The page computed share from tender-use counts; the email used the persisted value share.
    3. They read from different weekly rows.
    4. The page cached a stale projection.

    Once a renderer is allowed to do its own business arithmetic, the single-source guarantee is gone. The fix has the component format the persisted basis points instead.

  10. Why is the repair's dry run the real verification step rather than a formality before applying?

    1. It applies the correction to a shadow copy of the accepted row so the result can be inspected before the real write.
    2. It runs the merge gate's test suites against production data to confirm the deployed code matches the branch.
    3. It sends the corrected email to an internal address so the wording can be reviewed before the manager sees it.
    4. It writes nothing while proving the target and reconciliations, and returns the fingerprints apply must match.

    Apply re-derives the same candidate and refuses if either fingerprint has moved, so anything the dry run did not prove cannot be silently written afterwards.
