The server cannot record its own refusal

The shared demo is a real store that strangers walk into, and until now nothing recorded what they did there. This delivery puts demo visitor behavior on the existing context event rail — and discovers, on the way, that half the story cannot be captured where you would naturally reach for it, because a Convex mutation that refuses an action destroys the evidence of the refusal in the same breath.

Executive Summary

Athena's shared demo had admission, restore, capability policy and effect simulation — a complete machine for letting strangers safely operate a real store — and no record whatsoever of what any of them did. There was no evidence for which parts of the demo land, which parts people never find, and which parts turn them away.

This delivery adds a first-class shared_demo surface to the context event rail with six registered events, a fold that answers operator questions (how many visitors, how deep did they go, what did they finish, where did they hit a wall), and an internal rollup query.

The design is shaped by one constraint that is easy to miss and fails silently if you miss it: a denied shared-demo admission throws, and a Convex mutation throw rolls back every write in its transaction. An event recording the denial — or a ctx.scheduler call arranging to record it — dies with the transaction that refused. So denials are observed from the browser, and admitted actions are recorded server-side inside the operation's own transaction, which turns the rollback rule from an obstacle into a guarantee: a surviving row is an operation that committed.

Closing the coverage gap then forced a second discovery. Two of the five demo-reachable writes still off the rail were Convex actions, and admitPublicMutation requires a MutationCtx an action does not have. Rather than leave them uncovered, actions now enter the rail through ctx.runMutation, which carries caller identity.

Problem and Context

The shared demo is deliberately not a sandbox of fake data. A visitor rings real sales against a real store, and a nightly restore resets it. That realism is the product bet — and it made the absence of telemetry expensive, because nobody could answer basic questions about it.

Two properties of the demo make naive telemetry actively wrong rather than merely incomplete.

Every demo visitor is a store admin of the same store. Each admission mints its own Convex Auth user and sharedDemoPrincipal, but every principal points at one synthetic athenaUser, one organization, one store. Telemetry written at store_admin visibility would be readable by the next visitor who walks in. And grouping by athenaUser would collapse every visitor in history into a single actor.

The demo's own policy documents forbid careless capture. The principal-policy note is explicit: never include visitor payloads in telemetry, keep free text bounded and rate-limited. A demo pathname such as /demo/store/central/products/lace-front-24/edit carries slugs; a naive route capture leaks them.

Mental Model

Think of the transaction boundary as a door that locks behind a refusal.

When a demo visitor attempts something the demo does not allow, the shared-demo adapter throws. In Convex, that throw rolls back the entire mutation — every db.insert, every scheduler.runAfter. There is no "log it on the way out", because the way out is the rollback. Anything you wrote to explain the refusal is erased by the refusal.

This cuts the observation problem cleanly in two, and the seam is not a matter of taste:

Things that succeeded
Record them inside the transaction. The rollback rule now works for you: if the handler throws later, the observation vanishes too, so a row that survives is an operation that actually committed. No reconciliation, no phantom successes.
Things that were refused
Cannot be recorded by the refusing server at all. The only witness still standing is the browser that received the error.

The second model worth holding: identity is whatever the server can prove, not what the browser says. The browser supplies an opaque session id for grouping tabs; the visitor is always the auth user the server resolved from the demo principal. That is why the client may report navigation but is structurally forbidden from claiming action_admitted.

Layer-by-layer Mechanics

1. Registration is the authority

Six events are registered in eventDefinitions.ts with required and allowed payload keys. The append path stamps visibilityMode and retentionClass from the registration, never from the caller — so a caller cannot request wider visibility than its event class allows. All six are support.

2. Two capture paths, one identity

Server-side, captureSharedDemoAdmittedActionWithCtx is invoked from publicMutation.ts after admission resolves and before the handler runs. It no-ops for non-demo actors and swallows its own failures — visibility must never decide whether a demo operation succeeds.

Client-side, runCommand already normalizes every command failure in one place, but it must stay browser-safe and free of Convex imports. So it calls notifySharedDemoDenial(), a one-slot observer that the demo runtime hook registers and detaches.

3. Closed identifiers versus free text

The rail scans payload values for sensitive text — patterns covering email, phone, tokens and payment words. capability and operationId skip that scan and validate against a strict identifier shape instead, because they are generated server-side from a compile-time catalog and never pass through a browser. The scan is tuned for visitor-authored text, and a future catalog id such as payment.collect would trip it on a word boundary.

The dividing line is who supplies the value, not how it looks. An early draft of this change also gave surfaceKey the bypass — which was wrong, and the report review caught it. surfaceKey is an allowed payload key on the client-reportable events, so a crafted browser could have put anything identifier-shaped into it and skipped the scan entirely. It now stays on the normal validation path, with a regression test asserting both halves: a token-shaped value is rejected, and every key in the shipped surface catalog still passes.

4. Route templates, never pathnames

resolveAthenaViewRoute was extracted from the existing surface catalog so a pathname resolves to the matched template. The payload records /:orgUrlSlug/store/:storeUrlSlug/products/:productSlug/edit, never the slugs.

Be precise about where that guarantee lives: it is enforced by the client builder. The server's safe-route pattern rejects unsafe characters, but it cannot tell a template from a pathname — a slug-bearing path passes it cleanly. So this is one fence, not two, and the same is true of surfaceKey: the server validates its shape and scans it, but does not check it against the catalog.

5. Actions reach the rail through a mutation

admitOperationForAction is an internal mutation an action calls via ctx.runMutation, which carries caller identity. It looks the definition up by operationId, resolves admission, and captures the event. Both email actions declare a protected gateway so the demo adapter simulates the send rather than denying it.

What Changed, and What Deliberately Did Not

Changed

  • A shared_demo surface across the shared primitives, the Convex schema validator, and the tracking types — additive literals only.
  • Six registered events, a client-reportable mutation, a server-side capture helper, and a fold plus internal rollup query.
  • A one-slot denial observer seam in the browser error foundation.
  • Five operation definitions; three mutations and two actions routed onto the rail.
  • resolveAthenaViewRoute extracted additively from the surface catalog; classifyAthenaViewSurface keeps its signature and delegates.
  • Harness registry scenario extended to cover the new paths, then regenerated.

Deliberately not changed

  • The two reports.read queries. They are reads, not actions; they emit no admitted-action event, and public read migration stays out of scope per the read-admission plan. Migrating them would not have moved visibility.
  • SHARED_DEMO_PUBLIC_FUNCTION_INVENTORY. Migrated functions stay listed. It is the demo capability representation registry, not a list of unmigrated writes — removing the orders.return entries would have broken the coverage check that requires every allowed capability to have a representative.
  • Internal mutation twins. They remain unadmitted because they are server-invoked only, matching the existing pattern.
  • The telemetry mutation itself is not on the rail. Routing it through admission would make a demo observation depend on the demo write-capability allowlist it exists to observe. It carries a reasoned migration-inventory exemption instead.
  • runCommand's denial presentation. Only a notify call was inserted; the visitor-facing copy and the Convex-free boundary are untouched.

Three repo sensors caught real gaps

Worth recording because they are the system working: the shared-demo coverage test and the migration-inventory test both failed on the new public mutation until it was classified in the capability catalog and inventoried; the Convex lint refused it until a return-validator contract test asserted every outcome shape.

Two defects this delivery found in itself

A NUL byte in source. The blocked-surface fold key joined its two parts with a literal NUL byte and split on the same byte. Both sides agreed, so every test passed — but git classified the whole module as binary, making it unreviewable in a diff, and any tool that normalized or stripped the byte would have silently desynchronized the join from the split. Caught by reading the diffstat, not by a test. Fixed to use |, which neither part can contain.

A scan bypass on a client-supplied key. The report review found that surfaceKey had been given the closed-identifier bypass alongside capability and operationId. Those two are server-generated; surfaceKey is not — it arrives on the client-reportable events, so a crafted browser could have skipped the sensitive-text scan with any identifier-shaped string. Fixed, with a regression test covering both directions. This one surfaced from adversarial review of the report's own privacy claims, which is an argument for writing such claims down.

Four more defects found by pre-merge code review

An adversarial review of the delivered diff returned no blocking findings, but four real bugs in the new code — all fixed before merge rather than deferred:

  • The rollup dropped rows inside its own window. The query took the newest 2,000 rows at or after the window start and filtered the end bound afterwards, so any window with more than 2,000 events after it returned zero — reading as "nothing happened" for a window that was full. The end bound now lives in the index range.
  • Two actions in the same millisecond deduplicated to one. The admitted-action idempotency key was visitor + operation + timestamp, directly contradicting the comment above it promising that three sales show up as three. The key now carries a per-execution discriminator.
  • Unattributed events inflated the visitor count. A synthetic bucket was folded into the headline number, reporting one more person than ever visited.
  • Session ids were not namespaced by visitor. Idempotency uniqueness is scoped to store and key, so a browser that guessed another visitor's session id could pre-claim their keys and have their real events dropped as duplicates. Keys are now prefixed with the server-resolved visitor, and the comment that overstated this guarantee has been corrected.

Guidance for Next Time

  • Before recording anything about a rejected call inside a Convex mutation, find the transaction boundary. If the call throws, your record is gone — including scheduled work. This failure is silent and reads as "it never happened".
  • Choose event visibility from who can read the store, not from who the event is about. A shared store inverts the usual intuition.
  • Never key per-user analytics on an identity the product shares. Check whether the id you are grouping by is actually per-person.
  • Capture route templates, not paths. If a catalog of route templates exists, resolve through it; a pathname is a slug leak waiting to happen.
  • Telemetry must never decide whether real work succeeds. Swallow capture failures deliberately and say so in a comment.
  • Read the diffstat, not just the test output. A source file reported as Bin is a defect even when everything passes.
  • Adding a public Convex mutation is a three-registry change — capability catalog, migration inventory, and a return-validator contract test. The focused suite catches all three.
  • Actions are not mutations. If work must be admitted and it lives in an action, route it through ctx.runMutation and state the non-transactional consequence rather than pretending the semantics match.

Comprehension quiz

Eight of ten to pass.

  1. Why can the server not record a shared-demo action it just denied?

    1. The denial happens before authentication resolves, so there is no actor to attribute.
    2. The denial throws, and a Convex mutation throw rolls back every write in the transaction, including the event insert and any scheduled work.
    3. Denied actions have no operation id, so the payload would fail validation.
    4. The context event rail rejects events whose status is not recorded.

    The rollback is total. Anything written to explain the refusal is erased by the refusal itself, and ctx.scheduler offers no escape because scheduling is also transactional.

  2. Admitted actions are captured inside the operation's own transaction. Why is sharing that transaction a feature rather than a risk?

    1. It makes the write cheaper by batching it with the handler's writes.
    2. It guarantees the event is written before the handler can overwrite it.
    3. If the handler throws, the observation rolls back with it, so a row that survives corresponds to an operation that actually committed.
    4. It allows the event to reuse the handler's idempotency key.

    The same rollback rule that blocks denial capture becomes a correctness guarantee for success capture — no phantom successes, no reconciliation.

  3. Why are all six shared_demo events registered as support visibility rather than store_admin?

    1. Support visibility has a longer retention window.
    2. Store-admin events are compiled into insight bundles and would be too expensive.
    3. Every demo visitor is a store admin of the one shared demo store, so store-visible telemetry would let one visitor read another visitor's activity.
    4. The demo store has no admin, so store-admin events would be unreadable.

    The shared store inverts the usual assumption that store-scoped means private to one merchant.

  4. What identifies an individual demo visitor across their events?

    1. The shared athenaUser that every demo principal points at.
    2. The browser session id the client mints and sends.
    3. The auth user behind that visitor's demo principal, resolved server-side.
    4. The store id, since each visitor gets their own demo store.

    Each admission mints its own auth user, but all principals share one athenaUser — grouping by that would collapse every visitor into one. The client session groups tabs, and cannot be trusted for identity.

  5. The client-reportable event validator deliberately omits shared_demo.action_admitted. Why?

    1. Admitted actions are too frequent and would exhaust the write quota.
    2. A browser must not be able to claim it performed an operation it never performed; that event is server-captured only.
    3. The client has no way to learn the operation id.
    4. It is captured by the storefront surface instead.

    The split is a trust boundary, not a convenience: the client may report where it navigated, but not what work it did.

  6. capability and operationId skip the rail's sensitive-text scan, but surfaceKey does not. What decides which side a payload key falls on?

    1. Whether the value is required or optional on the event.
    2. Whether the value is a dotted identifier or free prose.
    3. Whether a browser can supply the value: the first two are generated server-side and never client-supplied, while surfaceKey arrives on client-reportable events.
    4. Whether the event is compiled into insight bundles.

    The bypass is safe only for values a client cannot influence. An early draft extended it to surfaceKey, which would have let a crafted browser skip the scan with anything identifier-shaped; it now stays on the normal path.

  7. Navigation events record the matched route template instead of the visited pathname. What does that prevent?

    1. Duplicate events when a visitor refreshes the page.
    2. Leaking org slugs, store slugs, product slugs, and record ids into telemetry.
    3. Events being attributed to the wrong store.
    4. The payload exceeding the maximum allowed length.

    A concrete demo path carries slugs; resolving through the catalog yields the parameterized template. Note the guarantee is enforced by the client builder — the server's safe-route pattern cannot tell a template from a pathname.

  8. Why could the two customer-email functions not be migrated with admitPublicMutation?

    1. They send external email, and the rail refuses operations with external effects.
    2. They are internal functions and therefore already exempt.
    3. They are Convex actions, and admitPublicMutation requires a MutationCtx, which an action does not have.
    4. Their store scope cannot be resolved from their arguments.

    Actions have no db. They now reach the rail through ctx.runMutation, which carries caller identity so the same definition applies.

  9. How does an action_admitted row written from an action differ in meaning from one written from a mutation?

    1. It carries no capability, because actions have no definition.
    2. An action is not transactional, so its row means "admitted and started"; a mutation's row means "committed".
    3. It is written at a different visibility level.
    4. There is no difference; both mean the operation completed.

    The admission mutation commits independently of whatever the action does afterward. The difference is inherent to actions and is documented rather than hidden.

  10. The blocked-surface fold key used a literal NUL byte and every test still passed. What actually went wrong?

    1. The fold silently dropped every blocked-surface event.
    2. The NUL byte was rejected by the payload validator at append time.
    3. Both sides agreed so the logic worked, but git classified the module as binary — making it unreviewable — and any tool normalizing the byte would desynchronize the join from the split.
    4. It caused the rollup query to exceed its row limit.

    A passing test suite is not proof a file is well-formed. This was caught by reading the diffstat, and fixed with a delimiter neither part can contain.
