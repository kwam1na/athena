A token-resolved catalogue read for a caller that is not a person

A store can hand an external assistant a revocable credential, and that credential — not a cookie, not an argument — decides which catalogue is read and how little of it comes back.

What landed

Hey Lobby, an external front-desk assistant, can now answer "do you have a burgundy bob wig?" from a store's real catalogue. It does so by presenting a per-store bearer token on GET /assistant-catalog/search and receiving a closed assistant_catalog.v1 projection of the live, visible catalogue — and nothing else.

Four pieces land together because they are only safe together: a hashed, revocable token table with its store-configuration section; a fifth admission actor kind, catalog_reader, with the ingress claim and adapter that resolve it; a second search projection and index that never contained a barcode or an invisible row; and the endpoint that ties them into one answer.

They ship as one PR because all four regenerate the same admission-checker documents, harness indexes and graph artifacts. Ticket-level scope stays in Linear.

Why none of the existing pieces would do

Every credential Athena could issue belonged to a person. Every catalogue read was shaped for a browser session. And the one search index over the catalogue — searchText on productSkuSearch — contains barcodes and covers draft and hidden rows.

That last point is the sharp one. An endpoint that searched the existing index and then filtered its results would still have computed the ranking over private data. A caller could send a guessed barcode and learn from the shape of the answer — the order, the hasMore, the exhaustive — whether the guess was real. Filtering the output does not close an oracle that lives in the input.

Two logging hazards sat alongside it. The admission rail spreads a request's whole query string into operationArgs, which is recorded, so a shopper's sentence sent as ?q= becomes a stored record. And a Convex ArgumentValidationError prints the value it rejected, so a validator strict enough to reject a malformed question is itself a way to write that question into a log line.

Ingress identity, not delegated authority

Athena's rail already knows two ways a caller can appear. A delegated caller acts for a signed-in operator and is modelled with a derived grant. An ingress caller presents its own credential and acts for itself — the storefront cookie claim is the existing example.

The assistant is the second kind. It holds a credential the shop issued to it, not a borrowed operator session. So it gets an actor kind, catalog_reader, sitting between storefront_customer and public in the adapter order. The doctrine note that says "add a caller kind by giving it a derived grant, not by adding an actor kind" is amended in this same change to scope that bullet to delegated callers, which is what it was written about.

The second model to hold: the private data is not filtered out, it was never in. The assistant's candidate set comes from an index built without barcodes and pre-filtered to visible rows. A real barcode and an invented one are indistinguishable to it because neither is in the haystack.

The path a question takes

Before. There was no path. The nearest thing was searchProductSkus, a staff-facing lookup that resolves a SKU by document id, by barcode or by anything else on the row, behind an operator session.

After. The question arrives in the X-Assistant-Query header, with only limit in the URL. The rail extracts the ingress claim, hashing X-Assistant-Token only when it matches the token shape. The catalogue-reader adapter looks that hash up, requires an active row, and takes the store from the row itself. The route then applies every bound on the question — 2,400 raw bytes, a guarded decode, control characters collapsed, 200 codepoints, lone surrogates dropped — before calling an internal query whose arguments are a plain string and a number. That query reads assistant_search filtered to the admitted store and assistantVisible: true, hydrates only the SKUs that can appear, and returns the closed validator. The response goes out with Cache-Control: no-store, private.

A question that cannot be read is answered rather than reported: 200, no matches, exhaustive: false. The assistant then says the shop's listing does not cover it, which is true, instead of announcing an outage to a shopper.

What changed, and what deliberately did not

A presented credential is recognised identity. The storefront adapter treats an unrecognised cookie as "not my caller" and lets the request continue anonymously. The catalogue-reader adapter does not. A token was chosen and sent, so a route that denies the kind refuses terminally before any lookup, and a withdrawn credential cannot fall through to whatever anonymous callers may read. The refusal body {"code":"reference_token_rejected"} is pinned byte for byte and selected from typed data — which adapter refused — never from message text.

A store scope does not bind a row. resolveOperationScope only echoes args.storeId, so revoke loads the target row and compares its own storeId to the admitted constraint before touching it. Authorization is two-layered: the rail clamps the claimed store, then the handler requires full_admin membership in that store's organization.

The search is a sibling of searchProductSkus, not a caller of it. It keeps the SKU-code exact lookups and drops the imported codes that are really barcodes, so nothing the shop keeps to itself can move a ranking. exhaustive is !candidateOverflow; tokens of two characters or fewer and a short stop list are dropped first, because Convex text search is an OR over tokens and "do you have any of the" would otherwise match the whole shop and then claim to have covered it.

A read writes exactly one thing, about itself. lastUsedAt is stamped after the response is built, in a try/catch, at most once a quarter hour, through a mutation whose only argument is the token id. A failed stamp never costs the shopper an answer. The precedent is GET /storefront, which mints a guest inside an admitHttpRead; both the definition and the rail's header comment record the side channel so "a read writes nothing" is not quietly false.

Both projection fields are optional so the schema pushes before the backfill runs, and registerCatalogProjectionsEqual ignores them so the POS register revision does not bump for a field the register does not read.

Not in scope, on purpose. Per-token rate limiting and the shared-demo baseline rows that lack the new projection fields until the next baseline bump are both recorded plan deferrals, not oversights.

The window between deploy and backfill

Order matters: deploy, then backfill, then mint. Between the deploy and the backfill the two projection fields are absent from existing rows, so the index is incomplete — and an incomplete index still returns exhaustive: true, because exhaustive describes the search, not the corpus. A token minted in that window would let the assistant claim it had covered a catalogue it had not.

Athena has one store, so the window is closed by hand rather than by machinery: run the dry run, apply the backfill, run the count query until rows carrying assistantSearchText equal the store's SKU rows, and only then mint. The exact commands live in the projection-backfill solution note, not in deploy-vps.sh, because they are run once by a person who reads the count.

Revoking is the inverse and needs no deploy. The next call answers 403 with the rejection body.

Next time

When a new caller kind arrives, ask first whether it acts for a person or for itself. Delegated callers get a derived grant; a caller holding its own credential gets an actor kind, and the rail requires every http_read definition to state its answer for that kind rather than defaulting one.

Because requireValidReadDefinition runs per request, a validator that newly requires a field and the helpers that supply it must land in the same commit. There is no half-migrated state that answers requests.

When caller-supplied free text must reach a backend, put it in a header and bound it in the route. The rail records the query string, and a validator error prints what it rejected; both hazards are closed only by bounding before the call, never by a stricter validator.

When a projection table gains a field, make it optional, push the schema, backfill by hand with a dry run and a count query, and only then turn on the thing that depends on it.

Comprehension quiz

  1. Why was filtering barcodes out of the existing search results judged insufficient?

    1. Filtering would have been too slow for the response budget.
    2. The ranking, hasMore and exhaustive would still have been computed over private data, so a guessed barcode could be confirmed by the shape of the answer.
    3. The existing index does not store barcodes at all.
    4. Convex does not allow filtering a search result set.

    An oracle in the candidate set survives any filtering of the output. The fix had to change what enters the search, which is why a second index exists.

  2. Why does the shopper's question travel in a header rather than the query string?

    1. Headers can carry more bytes than a URL.
    2. The query string is reserved for admission arguments by convention.
    3. The rail spreads the query string into operationArgs, which is recorded, so a question sent as ?q= would be stored and logged.
    4. Header values are encrypted in transit while query strings are not.

    Only limit is in the URL. The question is read in the route after admission, so it never enters the recorded arguments.

  3. Why are the question's length and character bounds applied in the route instead of in the internal query's validator?

    1. Convex validators cannot express a length bound.
    2. A Convex ArgumentValidationError prints the value it rejected, so a strict validator on the question would itself write the question into a log.
    3. Route-level checks run faster than validator checks.
    4. The internal query is shared with the staff-facing search.

    Bounding first keeps the internal query's arguments a plain string and number, so no validator can ever echo the text.

  4. A valid catalogue token is presented to a route whose definition sets catalogReader: "deny". What happens?

    1. The adapter returns not_applicable and the request continues as an anonymous caller.
    2. The token is looked up, found active, and then refused.
    3. The adapter refuses terminally before any lookup, because a presented credential is recognised identity and must not fall through to the anonymous adapter.
    4. The rail admits it and the handler decides.

    Falling through is how a withdrawn credential keeps reading whatever anonymous callers may read. The refusal is terminal and its body is chosen from typed data.

  5. Revoke is called with another organisation's token id while admitted on this store. What stops it?

    1. The store scope constraint, which binds the addressed row.
    2. An explicit handler check, because resolveOperationScope only echoes args.storeId and never binds a row addressed by id.
    3. The by_tokenHash index, which is organisation-scoped.
    4. Nothing — cross-organisation revoke is permitted for full_admin.

    The handler compares the loaded row's own storeId against the admitted constraint and raises scope_denied; the row stays active.

  6. Why must the store's token be minted only after the backfill's count query reports equality?

    1. The mint mutation reads assistantSearchText and would fail before the backfill.
    2. The schema cannot push until every row carries both new fields.
    3. Until the backfill drains, the index is incomplete while exhaustive still describes the search, so the assistant would claim to have covered a catalogue it had not.
    4. The token's hash depends on the projection revision.

    Both fields are optional precisely so the schema can push first; the ordering deploy, backfill, mint is what closes the window, and with one store it is closed by hand.

  7. Why does a question made only of stop words return exhaustive: false rather than the whole shop?

    1. The response validator caps the match count at eight.
    2. Convex text search is an OR over tokens, so short tokens and stop words are dropped first, and a question with nothing left is not a search that covered anything.
    3. The index rejects queries below a minimum length.
    4. The route treats it as an unreadable header.

    exhaustive means a search happened and did not overflow. With no usable tokens, no search happened, so claiming coverage would be a lie told to a shopper.
