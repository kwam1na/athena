Executive summary

This batch adds a second backend authority boundary to Athena: an agent harness under convex/agentHarness that lets an operator ask a question in plain language and get back an answer grounded in data the operator is actually allowed to see. The model never touches the public API. It is handed a derived, shrink-only grant, five fixed tools, and a sandboxed facade of get/list reads that domain packages publish into a kernel that is forbidden from importing them.

Daily Operations is the first surface. Its eleven capabilities (store day, attention, approvals, activity, day sales, week performance, store pulse, register sessions, automation evidence, inventory positions, replenishment) are declared next to the domain code, compiled into a generated registry by a conformance-gated generator, and reached only through internal read ports. A second, synthetic, organization-scoped profile proves the kernel needs no change per surface.

Release is one switch and one fence: profiles are default-off, daily_operations.v1 is published but disabled until an operator flips the durable switch, and a behavior-changing deploy advances a compatibility epoch in one atomic transaction that disables profiles and terminalizes idle runs. No cohorts, canaries, staged versions, or drain windows exist, on purpose.

The candidate is proven four ways: 56 test files in the package (including four release-gate suites that run against the published composition rather than fixtures) plus the root harness suites; the full webapp suite, which ran clean at integration (818 files / 9,748 tests) and which the merge gate re-runs on this head before merge, recording the result in artifacts/harness-delivery-runs; a deployed direct-harness smoke while the switch was off, repeated at every fence; and real end-to-end operator turns on the dev deployment with gpt-5-nano — the first produced two reconstructible citations with claim-support slices in 62.6 seconds, and the turn on this head answered a question about open registers and morning automation with two citations and a plain statement of what could not be read. Six independent review passes, thirteen lenses each, ran between the first candidate and this head; pass 3 caught two P1 defects the suites and the first two passes had not, and the merge gate's contract preflight caught an unmapped package-root file (convex.json) that six approving passes had not.

Why this mattered

Athena already had an intelligence layer for one-shot structured generation, but nothing that could answer an open question across several domains while honoring the operator's exact authority. Letting a model call the public API under the operator's session would have made every read a potential tenancy leak, and letting it write SQL-like queries would have made every answer unverifiable.

The plan therefore required an agent that is a reader, not an actor: it may only read what the delegating operator may read at the moment of each read, it must cite the data it used so an answer can be reconstructed later, and it must be impossible to widen its authority through configuration drift, prompt injection, or a stale deployment.

The two failures found by the release gate show why the posture is structural rather than advisory: store removal initially left the capability-call ledger behind (rows carrying request arguments and store-authored labels), and a capability refusal never reached the model, so the model read every denial as an access restriction and burned its attempt cap repeating the same malformed call.

The mental model: a courier with a sealed letter of authority

Think of a turn as sending a courier into the warehouse with a sealed letter. The letter (the run grant) names the operator who sent the courier, the exact shelves they may look at, and the date it was written (the compatibility epoch). The courier cannot rewrite the letter, and every door (a capability call) re-reads it against the live staff register before opening. If the operator was removed from the register mid-trip, the next door stays shut.

The courier does not carry tools for every shelf. It carries five: discover what shelves exist, describe one shelf, run a bounded read program, keep scratch notes, and hand in the finished answer. The read program runs inside a sealed room (QuickJS) with no clock, no randomness, no network, and no way to reach anything but the facade the letter permits.

Everything the courier brings back is stamped with where it came from and how sensitive it is. The answer inherits the highest sensitivity of anything it read, and a later reader who cannot see that class cannot see the answer either. Citations are receipts that tie each claim to a result hash, so an investigator can later ask whether the evidence still exists, has expired, or was deleted by the store's own lifecycle.

  • Kernel: convex/agentHarness — lifecycle, grants, delegated admission, executor, evidence, citations, turns, retention, deployment state. It imports no product domain.
  • Domain packages: capability declarations and read ports living next to the domain code (operations, reports, cashControls, automation, stockOps).
  • Profiles: which packages a surface gets, its budgets, egress ceiling, prompt policy, and presentation adapter (daily_operations.v1; a synthetic second surface).
  • Runtime adapter: AgentRuntimeAdapter in shared/agentHarness, implemented by Convex Agent under agentRuntime/ — the only place the AI SDK exists.
  • Host: src/components/agent — one reusable panel, one presentation contract, a closed-vocabulary inert renderer.

Before and after

Before: one authority boundary (the operation-admission ingress rail). Domain reads were UI-shaped queries. Intelligence runs did one-shot generation through TanStack AI. The docs said Convex Agent was not installed.

  • Ingress: before, public functions and Hono routes only. After, the same rail plus exactly five operator-turn operations (start, resume, cancel, acknowledge, inspect citation evidence) plus three admitted read queries (turn view, answer, thread history) — the only agent surface on it.
  • Authority: before, per-request session checks. After, a derived grant pinned at turn start, re-derived on every capability call, before every result release, before citation minting, and before completion; shrink-only intersections everywhere.
  • Reads: before, UI queries. After, domain-owned internal read ports behind a declared manifest (verbs get/list only, declared filters, projections, freshness, completeness, citation, evidence, cost), reached through a generated registry the model never sees.
  • Execution: before, none. After, model-authored bounded TypeScript validated by a Babel AST pass and run in QuickJS under frozen ceilings (60 s elapsed, 3 attempts, 24 calls, 5,000 rows, 2 MiB bridge bytes, 240 KiB per call output, 64 MiB heap).
  • Evidence: before, artifacts and source references on an intelligence run. After, per-attempt and per-call evidence, replay payloads, claim-support slices, citation bindings keyed to result hashes, and an access audit that records reads without storing what was read.
  • Release: before, not applicable. After, a durable per-profile switch (default off), a capability kill switch, and an atomic compatibility fence with a repair sweep for idle runs.
  • Browser: before, nothing. After, a reusable panel mounted on Daily Operations for authorized operators only, rendering through a closed-vocabulary inert text renderer that cannot emit links, images, or raw HTML.

Layer-by-layer mechanics of one turn

1. The operator submits a prompt through the Ask Athena entry. turns.startTurn admits the request on the ingress rail, checks the per-operator active-run and spend ceilings, records the intent, and schedules runtimeHost.driveTurn.

2. The host mints the grant (operator identity, projected capabilities and projections, authority digest, epoch, admission-policy version) and walks the turn binding through intent_recorded, runtime_thread_bound, runtime_input_saved, scheduled, and running. Each step is durable, so a crash between two systems is repairable rather than lost.

3. The Convex Agent adapter runs the model turn with the five fixed tools. Every tool call carries a fingerprint over adapter version, turn, tool id, canonicalized args hash, and call id; an exact replay returns the recorded outcome and any mismatch fails without invoking a handler.

4. athena.executeProgram validates the model's program (no imports, eval, timers, clock, or randomness; facade shape checked against the grant; exactly one explicit output) and runs it in QuickJS. Each facade call goes through delegated admission, a budget reservation, the domain's internal read port, and a release check. Denied calls consume a call attempt but no rows, bytes, or provider budget.

5. athena.completeRun prepares privately, then one Athena transaction reauthorizes the cited calls, commits evidence, the artifact, the run, and operator_release_committed. An idempotent outbox later projects the committed narrative back into runtime history with backoff (1 m, 10 m, 1 h, 6 h).

6. The panel reads the turn view reactively, shows server-authored milestones in a polite live region, moves focus to the answer heading on completion, and records the operator's view receipt through an admitted acknowledgement mutation — never through the read itself.

Failure boundaries

  • Authority revoked mid-run: the next capability call denies; a result whose authority disappeared before release is settled as evidence only with no payload; after provider egress has happened the exposure is recorded truthfully and the release and citations are suppressed.
  • Kill switch: a switch row can only narrow the published baseline, never widen it; it is read live on every dispatch, release, citation, and completion. Unpublished reads profile_unpublished, switched off reads profile_disabled, capability off reads capability_disabled.
  • Epoch fence: one atomic transaction disables profiles and advances the epoch; dispatch, release, and completion compare pinned versus current epoch and deny compatibility_epoch_fenced; repairFencedRuns terminalizes idle old-epoch runs.
  • Provider failure: no automatic failover to a less-trusted provider; a profile with no authorized provider for the turn's maximum egress class is rejected before any runtime or provider work.
  • Cancellation: the abort signal reaches the QuickJS interrupt handler; late host results are dropped; usage is settled conservatively (charged, not forgiven).
  • Sandbox: eval, Reflect, Math.random, Date, and Proxy are absent; prototype constructors throw; the facade is deep-frozen; only JSON crosses; an output past the ceiling is rejected, not truncated; guest error text never becomes evidence.
  • Read-port contract violation: undeclared fields, raw document ids, exceeded page bounds, or undeclared completeness sources fail the call closed with port_contract_violation.
  • Absence, not zero: an unheld projection is absent at both type and runtime; a figure that does not exist is unknown(not_recorded); a get the caller may not see returns an empty object with sources unavailable.
  • Retention: prompts, scratch, provisional programs, and candidate outputs live 30 days; only cited attempts' exact source, result, and claim slices are promoted to 365 days; store and organization removal delete agent content (including the capability-call ledger) and mark grants and citations deleted_by_lifecycle.

What changed and what intentionally did not

Changed: 204 source, test, script, and documentation files (about 58k insertions), plus the regenerated Convex API, the generated capability registry and schemas, the harness doc indexes, Graphify output, and the lockfile. Fifteen new Convex tables and one new index on intelligenceRun. Eight exact-pinned runtime, sandbox, and parser dependencies (zod stays at its existing caret range). Three new bounded crons (retention every 6 hours; fence repair and outbox repair every 5 minutes in production, hourly elsewhere).

Two deviations from the plan, both evidence-backed and recorded: the root convex.config.ts imports the Convex Agent component definition directly because mounting it through a local module made the deployment reject the push with an opaque start_push 500 (bisected across fourteen pushes); and program validation uses @babel/parser instead of the typescript checker because the latter would have pushed the isolate bundle past Convex's 32 MiB cap, trading away semantic type-checking of model programs in favor of runtime argument validation at the bridge.

Also delivered at integration, per the user's instruction: every plan-unit label (U1 through U10, wave N) was swept out of harness comments, docstrings, scripts, and docs and replaced by the module, contract, or invariant it referred to — 185 hits to zero, with the focused suite byte-identical before and after.

Changed by the review loop, on top of the first candidate: spend settled exactly once at every terminal end a turn can reach (finalize, outbox projection landed or exhausted, suppressed release, resume-on-read of an abandoned binding) with a guard for bindings the pre-marker path already paid out; the answer's egress class floored at the class of the history replayed to the provider; agent answers excluded from the legacy intelligence queries and dismiss mutation so only the harness's reauthorized views ever release one; thread admission scoped to the operator's own active runs and thread history read newest-first per viewer, so colleagues share a store context without blocking or starving each other; bounded, newest-first purchase-order scans for replenishment; typed host seam references; and seven uncalled internal functions removed.

  • Did not change: the ingress rail's shape, the intelligence run as the durable business parent, TanStack AI, or Daily Operations business logic (only export widening).
  • Did not add: mutations of any kind (command verbs are rejected at generation as reserved_command_verb, distinct from the versioned-extension code), RAG, durable agents, workflow or workpool components, LangChain or LangGraph, a second orchestration runtime, or any rollout machinery.
  • Did not stream: v1 buffers the model narrative server-side and shows only server-authored milestones while a turn runs. Provisional streaming is a separately planned follow-up with its own reviewed plan.

Next time: extending or debugging the harness

  • To add a capability: declare it next to the domain code, write its read port as an internal query, register it in manifestRegistrations.ts, run bun run agent-sdk:generate, and let the conformance gate tell you what the port leaks. Read docs/agent/capability-authoring.md first; the kernel must not learn about your domain.
  • To add a surface: define a profile (packages, budgets, egress ceiling, prompt policy, presentation adapter), re-declare the presentation adapter in src/ behind the drift test, and mount AthenaAgentSurface. The synthetic second surface is the template.
  • To change a port's behavior: bump implementationVersion on both the binding and the port, then fence on deploy. The generator refuses a moved source under an unchanged version.
  • To investigate a turn: bunx convex run agentHarness/evals/directHarness:describeRunDiagnostics with the run id shows status, budget charged, each attempt's validator diagnostic, each capability call's refusal, and the authored program; describeDeploymentState shows the epoch and switch state.
  • To roll back: bun scripts/agent-harness-switch.ts --profile daily_operations --disable --reason <incident>. Invoke the fence and switch scripts directly; bun run <script> -- --reason "a b" re-splits the quoted value.
  • Before trusting a green suite: run bunx convex dev --once before tsc, run tsc for any type-level claim, run lint:frontend:changed for shared/, and run the browser for anything about network, touch targets, or scroll ownership. The sensor ladder note in docs/solutions/harness records what each sensor cannot see.

Comprehension quiz

Pass required: 9 of 12.

  1. How does the model reach Athena data during a turn?

    1. It calls the public Convex API under the operator's session.
    2. It writes a bounded read program against a grant-projected facade that runs in a QuickJS sandbox and reaches domain-owned internal read ports through delegated admission.
    3. It queries the database directly with table names from the schema.
    4. It asks the TanStack AI adapter to fetch records on its behalf.

    The agent is never an actor on the ingress rail. Its only path to data is the facade compiled from its grant, executed in the sandbox, with every call re-admitted against the operator's live authority.

  2. Why can a kill switch never widen what the model may read?

    1. Switch rows are validated by a separate admin approval flow.
    2. Enablement rows can only narrow the published baseline; the intersection with the pinned grant is shrink-only and re-read live on every dispatch, release, citation, and completion.
    3. The switch is only consulted once, at turn start.
    4. Switch rows are signed by the deployment key, so a widened row is rejected on read.

    The overlay is shrink-only by construction and is consulted at every authority-bearing step, so a flip denies immediately even for a run pinned to an older digest.

  3. What happens to a figure the operator is not allowed to see in a result?

    1. It is returned as zero.
    2. It is returned as null with a warning.
    3. The key is absent at both the type level and at runtime; a figure that does not exist is unknown(not_recorded), never 0.
    4. The whole result is rejected.

    Absence, not zero, is the doctrine: an unheld projection cannot be confused with a real measurement, and a get the caller may not see returns an empty object with sources unavailable.

  4. What does the one-command fence do on deploy?

    1. It drains active runs over a grace window and then disables profiles.
    2. It disables the named profiles and advances the durable compatibility epoch in one atomic transaction; a repair sweep then terminalizes idle runs pinned to the old epoch.
    3. It rolls traffic to a canary cohort first.
    4. It regenerates the registry and restarts the Convex deployment.

    There is no drain, cohort, or canary machinery. The fence is atomic, dispatch and completion compare pinned versus current epoch, and repairFencedRuns cleans up idle work.

  5. Why does the root convex.config.ts import the Convex Agent component definition directly?

    1. Because the component has no other export.
    2. Because mounting it through a local module made the deployment reject the push with an opaque start_push 500, found by bisecting fourteen pushes.
    3. Because the import-boundary test requires every component to be imported from node_modules.
    4. Because the plan specified it from the start.

    The plan originally allowed a local shim. Deployment reality amended it, and the finding is recorded in agent-harness-runtime.md and a solution note.

  6. What did the first real provider turn on the dev deployment expose?

    1. That the sandbox leaked the clock.
    2. That capability refusals never reached the model, so it read every denial as an access restriction and repeated the same malformed call until its attempt cap.
    3. That citations were minted from data the program never read.
    4. That the fence did not advance the epoch.

    Surfacing the refusal reason and clarifying the executeProgram contract turned three wasted attempts into a self-correcting sequence on the very next run.

  7. Which sensor is the only one that can prove a type-level claim such as expectTypeOf or internal.* reachability?

    1. The Vitest suite.
    2. bun test over scripts/.
    3. tsc (the project typecheck).
    4. lint:convex:changed.

    Bun and Vitest strip types. The sensor ladder note records that tsc caught six real errors the green suite tolerated, and that bunx convex dev --once must run before tsc for module-graph claims.

  8. What evidence states can a citation resolve to later?

    1. found or missing
    2. reconstructible, provenance_only, evidence_expired, or evidence_deleted_by_lifecycle
    3. valid, stale, or revoked
    4. cached or uncached

    Missing is not a state. Each answer says something specific: the evidence can be rebuilt, only its provenance survives, it aged out of retention, or the store's own lifecycle deleted it.

  9. A reviewer wants to add a feature flag that lets a profile skip the conformance gate for a capability during development. What should happen?

    1. Add it; development velocity matters.
    2. Do not add it: the generator refusing to write on a conformance finding is the release gate, and the plan deliberately excludes rollout and bypass machinery.
    3. Add it behind a second switch row.
    4. Add it only for the synthetic profile.

    Generation is a gate, not a formatting step. A bypass would let an unconformant port reach the published registry, which is exactly what the design exists to prevent.

  10. What is the production and Linear status of this candidate as of this report?

    1. Deployed to production and all tickets Done.
    2. Not deployed to production; dev carries the candidate with daily_operations enabled; all eleven tickets stay In Progress until the integration PR merges.
    3. Deployed to production behind a canary cohort.
    4. Merged to main but not yet deployed.

    The report is a delivery-candidate artifact. Merge, production deploy, and Linear closure are pending events that this report does not predict.

  11. Adding agent_answer to the shared artifact-kind validator exposed agent answers to which surface, and how was it closed?

    1. The public discovery tool — fixed by removing the kind from the validator.
    2. The legacy intelligence queries and dismiss mutation, which any full admin of the store could call — fixed by excluding agent answers and agent runs in those handlers while keeping the validator the schema shares.
    3. The Convex Agent component's message store — fixed by deleting runtime threads on commit.
    4. The operator's own turn view — fixed by a new authority epoch.

    Widening a validator that several readers share gives every one of them the new member. The harness reauthorizes every read of an answer; the legacy full-admin queries never did, so the candidate filters agent answers in their handlers and pins it with tests for two admins of the same store.

  12. Why does the thread-history projection read the index newest-first and filter by the viewer's actorRef before counting toward the bound?

    1. Because Convex indexes can only be read in descending order.
    2. So a thread that outgrows the limit keeps the most recent turns, and a colleague's turns on the shared store thread key cannot push the viewer's own history out of the window.
