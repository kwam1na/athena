Executive Summary

The /docs section shipped behind a blanket sign-in gate, which meant solution notes and landed-change reports could not be linked to anyone outside the app. This branch removes the blanket gate and replaces it with a single per-category access policy: everything is public except the security-issues solution category, which is filtered out of public listings, redirects signed-out readers to login on direct navigation, and never has its document body read at loader time.

Opening the section to anonymous readers also made docs traffic invisible, so the branch adds one context event per browser-tab session and authentication state. Because docs have no store, this required the context-event append boundary to accept an unscoped write for the first time — and it does so through an exact allow-list rather than by relaxing the rule.

Two smaller fixes ride along: the screen-redact browser extension now masks per-glyph animated currency values, and the report date-range calendar stretches to the full width of its popover.

Problem

The docs viewer landed with DocsAuthGate in -docs-layout.tsx wrapping the entire route tree, on the reasoning that the corpus contains security writeups. That is true of exactly one category. Applying its confidentiality requirement to the whole corpus made every architecture note and delivery report unreachable without an Athena account.

Making the section public then created a second problem. The existing context-event append path required a storeId on every write, and a docs reader has no store — signed-out readers have no identity at all. There was no registered writer for the athena_webapp.workspace_viewed event even though the event definition already existed.

Separately, the screen-redact extension silently failed on the numbers that most need redacting. FlipNumber renders one text node per glyph, so no single text node ever contains both a currency marker and its digits, and the extension's SYMBOL_AMOUNT regex never matched.

Mental Model

Access is one predicate applied at four places, not four independent checks. canAccessSolutionCategory(category, isAuthenticated) in src/lib/docs/access.ts is the whole policy; the nav, the docs overview, the solutions list, and the document loader each call it or its list-shaped sibling filterAccessibleSolutionDocs.

The load-bearing call is the one in the route loader, and it passes false for isAuthenticated unconditionally. The loader never assumes a reader is signed in, so a restricted document's body is never read into the route payload. Authentication is resolved afterwards, client-side, and only then does the body load.

For tracking, think of the append boundary as a gate with one named exception rather than an optional field. storeId became optional in the validator, but the first check in appendContextEventWithCtx rejects any unscoped event that is not the exact (surface, eventId, route, workspace) tuple for a docs visit.

  • Policy: one predicate, four call sites, hardcoded false at the loader
  • Boundary: unscoped writes are allow-listed by exact tuple, not by relaxed validation
  • Identity: the client supplies a session id; the server derives the actor

Before vs After

Before: DocsAuthGate read useAuth(), showed a spinner while loading, and redirected to LOGIN_PATH when user === null — for every docs route. All listing routes called listSolutionDocs() and listSolutionCategories() unfiltered, and the $category/$slug loader unconditionally resolved findSolutionDoc, loadSolutionDocBody, and the frontmatter strip.

After: the gate is deleted. loadSolutionDocPageData in the new src/lib/docs/solutionPage.ts returns { doc, body: null, requiresAuthentication: true } for a restricted category without touching the body. SolutionDocPage dispatches to AuthenticatedSolutionDocPage, which resolves useAuth, redirects on null, and only then loads the body in an effect guarded by an isCurrent cancellation flag.

Before: appendContextEvent was an internalMutation whose logic lived entirely in its handler, and storeId was a required v.id("store") in both the append validator and the stored contextEvent row.

After: the handler body is extracted verbatim into an exported appendContextEventWithCtx(ctx: Pick<MutationCtx, "db">, args: ContextEventAppendArgs). That narrow ctx type is what lets the new public recordDocsWorkspaceVisit mutation reuse the boundary in-process instead of scheduling an internal mutation. Most of the 255 changed lines in contextEvents.ts are the resulting re-indent.

What Changed

Access gating: new src/lib/docs/access.ts and src/lib/docs/solutionPage.ts; -docs-layout.tsx loses DocsAuthGate and its "Back to Athena" header link, and DocsNav gains an isAuthenticated prop so its solution count matches what the reader can open. docs.index.tsx and docs.solutions.index.tsx filter both documents and categories; the latter also redirects to LOGIN_PATH via effect when an inaccessible category search param is present and auth has finished loading.

Tracking: three layers. docsWorkspaceTracking.ts holds pure helpers — a sessionStorage-backed visitor id under athena-docs-visitor-session-v1, viewport bucketing, and the visit builder that produces the idempotency key docs-workspace:${sessionId}:${visitorKind}. useDocsWorkspaceTracking.ts fires the mutation from DocsLayout, skipping while auth is loading and swallowing rejections. athenaWebappEvents.ts exposes a public recordDocsWorkspaceVisit mutation with literal-constrained args, validates the visit, resolves the actor server-side, and appends.

Append boundary: storeId becomes v.optional(v.id("store")) in both contextEventAppendArgsValidator and contextEventSchema; a new exported ContextEventAppendArgs type makes the extracted function callable with a plain object; and isAllowedGlobalContextEvent gates the unscoped case. A new by_surface_eventId_status_occurredAt index is added to contextEvent — nothing in this branch reads it; it is forward-provisioning for querying events that have no store-prefixed index to use.

Registration: adding a public mutation obliges two registries. workspace.telemetry.write joins ATHENA_CAPABILITY_CATALOG and contextTracking/athenaWebappEvents maps to it in PUBLIC_WRITE_MODULE_CAPABILITIES, which is what lets shared-demo coverage classify the mutation instead of defaulting it to denied. The mutation is then named in OPERATION_ADMISSION_MIGRATION_INVENTORY: it has no store scope and no authenticated actor, so it does not fit the current operation-admission actor model, and it stays inventoried rather than defined until a public-actor definition exists. The capability is deliberately not added to SHARED_DEMO_ALLOWED_CAPABILITIES — nothing enforces it on this path, and default-deny is the repo's stated posture.

Not changed: the event registry entry for athena_webapp.workspace_viewed already existed in eventDefinitions.ts with its payload keys, visibility mode, and retention class; this branch only added a writer for it. Dedupe, hashing, and quota logic are untouched — unscoped events simply occupy their own undefined-storeId partition of the existing indexes.

Riding along: tools/screen-redact-extension/content.js classifies flip-animated values on the stable data-value attribute of the flip root and applies maskDigits per glyph, and ReportDateRangeField.tsx adds w-full plus a classNames={{ root: "w-full" }} override so react-day-picker's own root stretches. Two backward-compatibility test guards were added, pinning that legacy "daily" shared-demo restore sources and legacy weekly scheduleLineage[].dayClosed stay readable through schema widening.

Failure Boundaries

This is an application access boundary, not confidentiality. The docs corpus is still compiled into browser assets, so gating security-issues in the app does not protect it against direct asset discovery. Real confidentiality needs a server-authorized content endpoint, which this branch does not add. The loader also still returns a restricted document's metadata (title, date, category) — only the body is withheld.

Signed-out access to a restricted doc fails in three independent places: listings filter it out, a ?category=security-issues deep link redirects after auth resolves, and a direct document URL returns body: null from the loader so the markdown never reaches the client payload at all. The third is the one that actually holds; the first two are consistency, not enforcement.

An invalid docs visit is rejected with the single opaque string "Invalid docs workspace visit." — no detail is leaked about which rule failed. The rules are a sessionId matching /^[A-Za-z0-9][A-Za-z0-9-]{0,63}$/, an idempotency key that is exactly docs-workspace:${sessionId}:anonymous or :authenticated, and a symmetric ±5 minute clock-skew bound. Nothing throws; every outcome is a returned kind.

Repeat writes are absorbed by idempotency rather than rejected: a remount or re-render for the same tab-session and auth state yields duplicate, and signing in produces a distinct key ending :authenticated rather than an idempotency_conflict.

The abuse quota partitions on docs-workspace:${sessionId}, and the session id is client-chosen. A caller can rotate sessions to evade it, so treat that quota as noise control, not abuse control. The real protection against docs visits polluting intelligence is nonCompilable: true, which makes compileContextEvent return null so the event never enters a context bundle.

Tracking failure is invisible by design — useDocsWorkspaceTracking catches and discards, so a rejected or failed write never degrades the docs UI. A body-load failure on the authenticated path is not swallowed: it is stored and rethrown on the next render so the nearest error boundary handles it.

Next-Time Guidance

When a route's data depends on authentication, decide it in the loader with authentication assumed absent, not in the component. Passing a hardcoded false into the access predicate is what guarantees a restricted body never enters the route payload; a component-level check would have shipped the content and then hidden it.

When an append boundary needs to accept a new shape, allow-list the exact tuple rather than relaxing the validator. Making storeId optional without isAllowedGlobalContextEvent would have silently permitted every unscoped event on every surface.

Adding a public Convex mutation is never a one-file change. Two static sensors — the shared-demo coverage classifier and the operation-admission migration inventory — fail on any unregistered public mutation, and both key on a catalog capability. This branch's own gate run caught exactly that; budget for the capability entry, the module mapping, and the inventory entry as part of the change rather than as follow-up.

Do not describe an in-app category gate as confidentiality. Anything compiled into the client bundle is discoverable regardless of routing, and saying so in the solution note is what keeps the next reader from treating /docs as a place to store secrets.

When redacting DOM that an animation owns, classify on a stable attribute and transform the leaf nodes in place. Rewriting the flip root's text would have masked the value correctly and broken the animation; reading data-value to decide and then masking per glyph preserves both.

Extension tests can execute the real content script — readFileSync plus new Function with a stubbed chrome.storage — instead of reimplementing its logic in the test. That is what makes the post-mutation re-mask case meaningful, since it exercises the actual MutationObserver rather than a copy of it.

Comprehension quiz

Pass required: 8 of 10.

  1. Why does loadSolutionDocPageData pass a hardcoded false for isAuthenticated instead of the reader's real auth state?

    1. The loader runs before Convex is initialised, so auth state is always false there
    2. So the loader never assumes authentication and a restricted document's body is never read into the route payload; auth is resolved afterwards, client-side, before the body loads
    3. It is a placeholder that a follow-up branch will replace with the real value
    4. TanStack Router loaders cannot receive props, so no other value is available

    Deciding access in the loader with authentication assumed absent is what guarantees the content never ships to an unauthorized client. A component-level check would have delivered the body and then hidden it.

  2. What protection does gating the security-issues category actually provide?

    1. Full confidentiality — the documents are encrypted at rest and served only to authorized users
    2. An application access boundary only; the docs corpus is still compiled into browser assets, so it is not protected against direct asset discovery
    3. Nothing — the gate is cosmetic and the body is always sent to the client
    4. Network-level protection, since the category is served from a separate origin

    The loader does withhold the body from the route payload, but the corpus is still bundled. Real confidentiality would need a server-authorized content endpoint, which this branch deliberately does not add.

  3. Why was storeId made optional without simply letting any unscoped context event through?

    1. Convex validators cannot express a conditionally required field
    2. Unscoped events are rejected later by the event registry anyway, so the allow-list is redundant
    3. isAllowedGlobalContextEvent permits exactly one (surface, eventId, route, workspace) tuple; relaxing the validator alone would have silently allowed every unscoped event on every surface
    4. The allow-list exists only to produce a clearer error message

    The store-scope check is the first thing appendContextEventWithCtx does, before any database read. Optionality in the validator is the type-level enabler; the allow-list is the actual policy.

  4. Why is the append handler extracted into appendContextEventWithCtx with a Pick<MutationCtx, "db"> parameter?

    1. To let the function run inside a Convex query as well as a mutation
    2. So the new public docs-visit mutation can reuse the same append boundary in-process rather than scheduling an internal mutation, while the narrow ctx type documents that the path only touches the database
    3. Because internalMutation handlers cannot be exported from a Convex module
    4. To avoid a circular import between the schema and the mutation

    Most of the 255 changed lines in contextEvents.ts are the re-indent from that extraction. The narrow ctx type is a deliberate signal: no auth, no scheduler, just db.

  5. A reader opens /docs signed out, reads for a while, then signs in without closing the tab. What happens to the context events?

    1. The second write returns idempotency_conflict because the session id is unchanged
    2. The second write returns duplicate and is discarded
    3. Two events are recorded — the idempotency key ends in :anonymous then :authenticated, so the auth state is part of the key
    4. The first event is retroactively updated to attach the signed-in actor

    The key is docs-workspace:${sessionId}:${visitorKind}. Auth state is part of it precisely so a sign-in produces a distinct event rather than a conflict, while re-renders within one state collapse to duplicate.

  6. Can the abuse quota on docs visits be relied on to stop a determined caller?

    1. Yes — the partition key is derived server-side from the authenticated user
    2. No — the partition key is docs-workspace:${sessionId} and the session id is client-chosen, so a caller can rotate sessions to evade it; it is noise control, not abuse control
    3. Yes — the mutation is rate-limited by IP address before the handler runs
    4. No, because the quota is disabled for unscoped events entirely

    Worth naming honestly. The protection that does hold is nonCompilable: true, which keeps docs visits out of context bundles regardless of volume.

  7. What does nonCompilable: true do to a recorded context event?

    1. It prevents the event from being written to the contextEvent table at all
    2. It makes compileContextEvent return null, so the event is persisted but never enters an LLM context bundle
    3. It marks the event for deletion at the end of its retention window
    4. It skips payload validation against the event registry

    The event is still a real, queryable row. The flag governs only whether it can become store or customer intelligence evidence.

  8. Why did the screen-redact extension fail to mask currency values rendered by FlipNumber?

    1. The extension skipped elements carrying a data-motion attribute
    2. FlipNumber renders one text node per glyph, so no single text node contains both the currency marker and its digits, and the SYMBOL_AMOUNT regex never matched
    3. The MutationObserver was not attached to animated subtrees
    4. chrome.storage.sync returned enabled: false during animation

    The fix classifies on the flip root's data-value attribute, which holds the complete value, and then applies maskDigits to each glyph node so the per-glyph DOM the animation depends on survives.

  9. Does anything in this branch read the new by_surface_eventId_status_occurredAt index?

    1. Yes — the docs-visit mutation uses it for its idempotency lookup
    2. Yes — the abuse quota check reads it
    3. No — it has no reader here; it is forward-provisioning for querying unscoped events, which have no store-prefixed index to use
    4. No — it is dead and should be removed before merge

    Dedupe and quota still traverse the existing storeId-prefixed indexes, where unscoped events simply occupy the undefined partition. The new index anticipates reporting that cannot start from a store.
