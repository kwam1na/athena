Executive summary

An agent asked to validate an Athena frontend test file reaches for `bun test <file>`. That is the wrong runner. The file needs Vitest's jsdom environment and its `vi` mocking API, so under Bun it dies on `Can't find variable: document`, a missing `vi.mock`, or an unresolved Vite-only module. None of those errors mention the runner. They read as defects in the code being validated, which is why the mistake survived documentation that already named the right command.

This delivery adds a guard that intercepts the mistake at the moment it is made. A Bun test preload registers one `Bun.plugin` per Vitest-owned workspace package; each plugin's `onLoad` hook fires when Bun loads a test file inside that package, prints a diagnostic naming the owning package and the exact replacement command, and exits non-zero before any test body runs.

A second, unrelated change rides along because the delivery could not proceed without it. The operator required this delivery to be reviewed by exactly two independent reviewers. Athena's configuration hard-coded six additional reviewers on top, so the prepared review context bound charters no reviewer would answer for. Rather than leave bound charters unreviewed, the roster wiring was changed: `harness.config.ts` now reads the additional roster only from `.agents/review-selection.json`, and this candidate sets that file to `[]`.

Why this mattered

Athena is a Bun workspace monorepo. Root-level tooling under `scripts/` is tested with `bun test`. The two frontend packages, `@athena/webapp` and `@athena/storefront-webapp`, are tested with Vitest. Both kinds of file end in `.test.ts`, sit in the same repository, and are opened by the same agents.

The ticket was filed from a real incident. During an unrelated POS delivery a subagent reported: "The direct bun test command is not the repo's React/Vitest path: it failed on missing document and vi.mock APIs rather than on the code under review." That subagent recovered, but only after spending its budget diagnosing a failure that had nothing to do with the code it was reviewing.

Documentation was not the gap. `AGENTS.md` and `packages/athena-webapp/docs/agent/testing.md` already named the Vitest command, and still do — this delivery did not rewrite them. The gap is one of timing: the misleading failure arrives *after* the command has been chosen, and it looks like evidence about the code rather than about the invocation. A reader who trusts the error text draws exactly the wrong conclusion.

The mental model

Think of it as a wrong-platform announcement rather than a signpost. A signpost at the station entrance (documentation) only helps someone who reads it before choosing a platform. An announcement on the train you just boarded reaches you at the moment the mistake is still cheap to reverse, and it tells you which platform you actually wanted.

The guard is that announcement. It runs inside the process that is about to make the mistake, and it names the destination:

  • Ownership is derived, not listed. A package is Vitest-owned if its own `package.json` `test` script runs Vitest. No hardcoded package names.
  • The remedy is a command the reader can paste, scoped to the one file they were trying to run.
  • The run exits non-zero and executes nothing, so a guarded invocation can never be mistaken for a passing run.
[athena] `bun test` is not the test runner for @athena/webapp.
  file:   packages/athena-webapp/src/App.test.tsx
  reason: this package runs Vitest, so its tests rely on the jsdom environment and the
          `vi` mocking API. Under `bun test` they fail on unrelated errors such as
          "Can't find variable: document", a missing `vi.mock`, or an unresolved
          Vite-only module.
  run:    bun run --filter '@athena/webapp' test -- src/App.test.tsx

Before and after

The mechanism changed once during the delivery, and the difference between the two versions is the most instructive part of this report.

The first implementation asked Bun which file it was about to run, via `Bun.main`, and classified that one path. It worked for the case anyone would test by hand — a single named frontend file — and independent review proved it insufficient. A preload is evaluated once per process, and `Bun.main` names only one file of the whole discovered set. Pass two targets, or run bare `bun test`, and the other files walk straight into the failure the ticket exists to remove.

The second implementation classifies files instead of runs. It registers a `Bun.plugin` per Vitest package whose `onLoad` filter is anchored to that package's directory. `onLoad` fires for every file Bun loads, so target count and argument order stop mattering.

  • Before: one classification per process, keyed on `Bun.main`. Multi-target and bare runs escaped.
  • After: one classification per loaded file, keyed on an `onLoad` filter per package. No escape by ordering or target count.
  • `build.onResolve` was tried and ruled out empirically: it does not fire for entry-point test files.
  • An `onLoad` handler that returns `undefined` makes Bun throw `TypeError: onLoad() expects an object returned`, so the filter is scoped narrowly enough that the handler always exits and never needs a pass-through return.

How it is wired, layer by layer

There are only two moving parts: where the preload is found, and what it registers.

  • **Discovery.** Bun reads `bunfig.toml` from the working directory only — it does not walk up to a repository root. That single fact is why three near-identical `bunfig.toml` files exist: one at the repo root for root-relative runs, and one in each Vitest package for runs started inside that package. Without the package-level files, `cd packages/athena-webapp && bun test src/App.test.tsx` bypasses the guard entirely.
  • **Package detection.** `vitestPackages(repoRoot)` reads the root `package.json` `workspaces` globs, keeps those ending in `/*`, and for each directory beneath them keeps packages whose own `test` script matches `/(?:^|[^\w-])vitest(?:[^\w-]|$)/`. Today that is exactly `@athena/webapp` and `@athena/storefront-webapp`. The root package is excluded because its `test` script delegates via `bun run --filter`, and `valkey-proxy-server` is excluded because it runs `node --test`.
  • **Registration.** For each such package the module calls `Bun.plugin` with an `onLoad` filter of `^<package dir>/.*[._](?:test|spec)\.[cm]?[jt]sx?$`. The filter is anchored on the absolute package directory, so a sibling package with a longer name — `packages/webapp-extra` against `packages/webapp` — cannot match.
  • **The repo root is derived from the module's own location** (`path.resolve(import.meta.dir, "..")`), not from `process.cwd()`, so detection is identical whether the run started at the root or inside a package.

What the guard covers, and what it does not

The guard's coverage is exactly "the working directory has a `bunfig.toml` that preloads it". Everything below was executed against this candidate rather than reasoned about.

  • `bun test packages/athena-webapp/src/App.test.tsx` from the repo root — **fires**, exit 1, nothing executed.
  • `bun test scripts/bun-version-check.test.ts packages/athena-webapp/src/App.test.tsx` — **fires** on the frontend file after the root script rows pass. Reversing the argument order gives byte-identical output; Bun reorders targets, and the guard is order-independent either way.
  • Bare `bun test` at the repo root — **fires**. All root script files run, then the run aborts at the first frontend file with exit 1. A bare run is therefore no longer a "run everything" command; that is intentional, and `bun run harness:test` is unaffected because it passes explicit `scripts/*.test.ts` targets.
  • `cd packages/storefront-webapp && bun test src/hooks/useQueryEnabled.test.ts` — **fires**, naming `@athena/storefront-webapp`.
  • `cd packages/athena-webapp/src && bun test App.test.tsx` — **does not fire**. A nested working directory has no `bunfig.toml` and Bun does not walk up, so the original misleading failure returns. This is a known, documented boundary, not an oversight: closing it would mean a `bunfig.toml` per directory.
  • `bun test scripts/bun-version-check.test.ts` — **does not fire**, and still passes. The root package's `test` script is not Vitest, so no plugin is registered for it.
  • `bunx vitest run <path>` and `bun run --filter '@athena/webapp' test -- <path>` — **do not fire**. `[test] preload` applies to `bun test` only; these are the commands the diagnostic recommends.

What changed, and what deliberately did not

The delivery has two halves. The first is the runner guard and the harness wiring it needs. The second is the reviewer-roster policy change, which exists only because the operator required a two-reviewer review of this candidate and the configuration would otherwise have bound thirteen additional charters that no reviewer would answer for.

On the roster half: `harness.config.ts` previously listed six always-on reviewer ids inline and appended the contents of `.agents/review-selection.json`. It now takes the roster only from that file. The six are not abolished as policy — responsibility for naming them moved into the file, which is why `AGENTS.md` and `.agents/skills/ce-code-review/SKILL.md` had to change in the same commit. Leaving `AGENTS.md` as it was would have left two tracked policies disagreeing, and an executor following the older one would hit a hard `no activated review lens defines` refusal at the evidence boundary.

  • **Not changed: any product or runtime behavior.** Nothing under `packages/*/src` or `convex/` was touched. The guard is development tooling.
  • **Not changed: package test scripts, `vitest.config.ts`, or `harness:test`.** `bun run --filter … test` and `bun run harness:test` behave exactly as before.
  • **Not changed: the existing runner documentation.** `packages/athena-webapp/docs/agent/testing.md` still instructs `CI=1 bunx vitest run <paths>`. The ticket asked for no redundant documentation; the guard exists because that documentation did not stop the misuse, not to replace it.
  • **Not changed: the reviewer charters themselves.** `.agents/agents/*.agent.md` are untouched. Only which of them get activated changed.
  • **Not added: any new override machinery.** The roster change reuses the selection file that already existed and already sat in `preparationWiringPaths`.

Next time

Three things in this delivery generalize.

  • **Adding a Vitest package.** Root-relative coverage is automatic once the package's `test` script runs Vitest. The package-relative case is not: add a two-line `bunfig.toml` beside its `package.json` pointing at `../../scripts/bun-test-runner-guard.ts`, and register that path in `scripts/harness-app-registry.ts` so `pr:athena:preflight` stays green. The `vitestPackages` equality assertion in the guard's own suite fails loudly if you forget the first part.
  • **Testing a process-level guard.** A row that asserts the absence of an error string is usually vacuous — the target may fail earlier for an unrelated reason and satisfy the assertion without the guard existing. Assert the positive instead: that the run aborted before any test executed (`not.toContain("(pass)")`, `not.toContain("Ran ")`). That assertion fails under a hook that prints but does not abort; the one it replaced did not.
  • **Choosing a Bun hook.** A `[test] preload` runs once per process and can see only one file of the run. If behavior must apply per test file, use `Bun.plugin` with `onLoad`. `onResolve` does not fire for entry-point test files, and an `onLoad` handler must return an object or Bun throws — so scope the filter narrowly enough that the handler always terminates.
  • **A caveat on the roster file.** `.agents/review-selection.json` lands on main as `[]`. It is the sole machine-readable source of the additional review roster, so a later delivery that forgets to repopulate it will get a two-lens review that still passes the gate. The enforcement is prose in `AGENTS.md` and `.agents/skills/ce-code-review/SKILL.md`; there is no sensor for an under-populated roster, and adding one was explicitly out of scope here.

    3. Bun merges all `bunfig.toml` files it finds in the workspace.

    2. It checks whether the package directory contains a `vitest.config.ts`.

    4. It asks Bun which runner is configured for the file.

    Deriving ownership from the package's own `test` script means a new Vitest package is covered root-relative as soon as it exists, and the root package — whose `test` script delegates via `bun run --filter` — stays inert.
