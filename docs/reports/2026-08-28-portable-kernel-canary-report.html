Executive summary

This candidate switches only compound-delivery-kernel from Athena's repository copy to the exact qualified portable core-v1 generation. Codex and Claude Code resolve the same managed workflow body. Every other Athena workflow remains repository-local.

The accepted zero-mismatch, zero-mutation shadow comparison is a prerequisite, not authority by itself. The reversible canary decision is also bound to the exact qualified release and retained rollback path. A current sensor verifies that identity and a disposable rehearsal proves rollback works from the installed generation even after the original release inputs are removed.

The complete qualified generation is tracked because lifecycle status and rollback execute from that installed generation. Discovery remains narrow: only compound-delivery-kernel is exposed through the two host symlinks.

Why the canary exists

Shadow observation proved that the portable evaluator could match Athena without gaining authority. The next safe step is not a batch migration. It is one reversible authority switch whose inputs, exposure, baseline, and rollback path are all inspectable.

The difficult boundary is preserving two different truths: the active workflow is now portable, while the accepted characterization baseline must still describe the Athena behavior that was qualified before the switch.

Mental model: one rail changes points

Think of Athena's workflow discovery as a rail junction. The canary moves one set of points, compound-delivery-kernel, onto a qualified managed generation. It does not move the rest of the network.

The migration record is the route card: it pins the release, accepted shadow evidence, host exposures, predecessor, and rollback command. The canary sensor checks the current route card. The baseline sensor looks through a verified predecessor projection so the historical comparison target does not move with the active rail.

Before and after

Before: Athena's local .agents skill body was authoritative for the kernel; the portable core could only observe the same frozen inputs in shadow mode; Claude Code had no portable kernel exposure.

After: both .agents and .claude expose the same managed core-v1 kernel through relative symlinks. The original Athena body is retained by digest as the rollback predecessor and the characterization reference. The remaining workflow corpus and the host-native Linear adapter are unchanged.

How admission and rollback work

  • The migration record binds the canary to the qualified archive, metadata, source commit, workflow body, and accepted shadow-comparison digest.
  • The active lifecycle receipt lists one selected skill and the two host exposures. Status must report current with no blockers.
  • The canary check recomputes archive, metadata, workflow, predecessor, and shadow identities rather than trusting labels.
  • The rollback rehearsal creates a disposable Git repository, adopts the same release, deletes its copied archive, metadata, and extraction driver, then rolls back through the installed generation.
  • The rehearsal verifies restoration, source independence, absence of the added Claude exposure, and preservation of unrelated bytes.

What changed and what did not

Changed: a managed release generation and lifecycle receipt are tracked; compound-delivery-kernel is exposed through managed symlinks; a narrow migration record and canary sensor enforce the switch; the baseline sensor can project the verified predecessor; delivery fingerprints now hash a symlink's exact target instead of trying to read a directory target as a file.

Intentionally unchanged: no other workflow changes authority; the accepted characterization documents and shadow telemetry stay immutable; no new orchestration or telemetry plane is introduced; Linear create, read, update, search, relation, and reconciliation capability remains governed by normal policy and user authority; the application is not deployed.

Failure boundaries

  • A changed archive, metadata file, workflow body, shadow comparison, receipt, predecessor, or host link fails the canary sensor.
  • Unexpected Claude discovery content fails the baseline projection instead of broadening the canary silently.
  • The characterization check refuses to project a predecessor unless the canary record and both current exposures are valid.
  • Rollback does not depend on the original extracted driver or copied release inputs; it runs from the installed generation.
  • Batch migration remains blocked until this canary is reviewed, merged, and accepted without unresolved mismatches.

Validation and finish line

Current local evidence: portable-canary:check passes, including the source-independent rollback rehearsal; portable-baseline:check validates 31 assertions, 24 closure members, 7 scenarios, and 145 out-of-scope discovery files; harness:test passes 1,690 tests with zero failures; focused regressions cover migration-record and active-receipt binding, release metadata, shadow digest, host-link target, and delivery symlink identity; Graphify has been rebuilt.

The evidence-bearing reviewer checkpoint, full pr:athena authority gate, hosted CI, merge, and root alignment are still pending. Production deployment is deliberately deferred because this is repository infrastructure and does not affect the application runtime.

Guidance for the next migration

  • Advance only from accepted shadow evidence to one reversible canary, then from an accepted canary to batch migration.
  • Keep current-authority checks separate from the immutable characterization baseline.
  • Use the managed lifecycle receipt and installed generation as the rollback authority; do not create a second adoption path.
  • Preserve full policy-authorized tracker capability. Qualification-fixture hygiene is not a production capability limit.
  • If any canary identity or mismatch is unresolved, stop and rerun the existing qualification path.
