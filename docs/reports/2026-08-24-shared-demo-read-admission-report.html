Summary

An in-app sweep of the shared demo — every surface its sidebar and hub link to, plus the actions a visitor can take — found eight surfaces broken after the backend operation-admission migration. Each threw shared_demo_action_denied on load and rendered the router's error boundary instead of the store, including /pos, the destination of every “Make a sale” entry point in the demo.

All eight are read failures. The write rails came through the migration intact: the sweep completed a POS sale end to end (synced), voided it with a manager approval proof, submitted a cycle count, corrected an opening float, fulfilled an online order, and sent a review request — every one succeeded.

The fix grants four read intents and admits ten read definitions, and adds a sensor for the class of failure that let this ship: neither existing demo-policy test could see a demo surface losing its read.

A second defect surfaced separately, reproducible only on an expired demo session: the "Open demo again" button the app offers did nothing. Minting a demo session had come to require holding one, so every route back in was closed. That is fixed, and the recovery now happens automatically, with no button to press.

Problem

Shared-demo read admission takes two keys, both checked in sharedDemo/readOperationAdapter.ts: the read definition must say actors.sharedDemo: "admit", and its intent must be listed in SHARED_DEMO_ALLOWED_READ_INTENTS. Two keys is a deliberate containment property — granting an intent does not silently admit every read carrying it.

Migration units U3, U5 and U7 moved these reads onto the rails taking the sharedDemo: "deny" default. That is the correct default. It is the wrong answer for a read the demo's own navigation walks into, and every one of these was a plain, unwrapped query before the migration — so the demo had always answered it.

Two sensors already guard demo read policy and both stayed green the whole time. readIntentGrants.test.ts asserts seed ⊇ derived; coverage.test.ts asserts the grants agree in both directions. Both describe the grants that exist, and a demo surface going dark leaves both statements true.

Mental model

Think of demo read access as a door with two locks. The intent grant is the building key: it says which wings of the building a demo visitor may enter at all. The definition's actors.sharedDemo flag is the room key: it says whether this specific door opens.

The migration re-keyed every room in the building and, sensibly, defaulted the new locks to closed. The existing sensors audit the keyring — that every key matches a real door and every door a real key. What nobody checked is whether the rooms the tour walks through are still unlocked. A locked room the tour never enters is fine; a locked room the tour walks into is the tour ending in a corridor.

That distinction — keyring coherence versus route reachability — is exactly the gap the new sensor fills.

Before and after

Before, on main, for a demo visitor:

  • Clicking “Make a sale” on the demo hub → /pos → error boundary. The register itself (/pos/register) worked, so the demo was reachable only by knowing the deeper URL.
  • All four /services/* sidebar entries → error boundary.
  • /reviews/new (the sidebar's Reviews target) → error boundary, while /reviews/published rendered.
  • /pos/expense-reports and /pos/settings → error boundary.
  • The sidebar's pending-review badge threw on every demo page.

After: each of those surfaces resolves its reads and renders.

What did not change: the surfaces that intentionally show a “demo boundary” screen rather than an error — /products/archived and the inventory cost-overlay step — still show it. Those are designed copy, not breakage, and the sweep distinguished the two by whether the page rendered a boundary card or the router's error component.

The expired-session deadlock

A demo admission lasts three hours. Past that, the app correctly detected the expiry and showed "Your demo session ended" with an Open demo again button — and the button returned to the same screen, every time.

sharedDemo/admission:issueSharedDemoTicket is the operation that MINTS a demo session, and its own definition says public: "admit" — an anonymous visitor may call it, which is how anyone enters the demo at all. But the shared-demo adapter resolves the caller's principal first, and for an expired principal it raised a terminal denial, so the chain never reached the public adapter. You needed a live admission to obtain an admission. The visitor's only escape was clearing site data.

Three changes clear it:

  • The recovery write gets through. An expired session is not a demo actor, so for operations public already allows the adapter now falls through instead of denying. It cannot escalate: a demo auth identity is stored with a name and no email, and the normal-user adapter resolves its Athena user by email, so it finds nothing and falls through too. Only public picks these up, which grants strictly less than the demo already did.
  • Reads keep denying. Deliberately, and found the hard way: letting the identity probe fall through to public answers it successfully, so the app sees a half-identified visitor instead of an expired demo and redirects to a sign-in form they have no credentials for. The read denial is the signal the client renews on.
  • The signal became structured. Expiry now travels as a ConvexError carrying shared_demo_session_expired. It previously travelled as a plain Error message, and Convex scrubs those outside dev — so the client's message test matched on a developer's machine and would have matched nothing in production.

Renewal is then automatic: take a ticket, sign in over the dead session, reload. It does not sign out first, which the demo entry route does — signing out leaves the app with no identity, the router redirects to sign-in, and the renewal is unmounted mid-flight. A capped counter stops a renewal that keeps landing back on the same failure, and past the cap the manual button returns as the fallback.

What changed

Ten read definitions flip to sharedDemo: "admit", and the four intents behind them join the grant set. Both edits are required — either alone still denies.

The admitted set deliberately includes reads reached one click past the surface that failed on load: getExpenseTransactionById, getServiceCaseDetails, and searchCustomers. The sweep could only see the first read each page issued; fixing only those would have produced pages that render and then break on their next interaction.

Two mechanisms are in play, and the report is explicit about when each applies, because using the wrong one is how this recurs:

  • Admit the read when the demo genuinely renders the surface.
  • Skip the query client-side and leave the read denied when the demo does not need what it returns. This is the sidebar badge: a shared demo has no reason to display a moderation backlog, so the query is skipped and the definition stays denied.

Doing both to the same read is the case to avoid — an admitted grant no caller reaches is reach nobody reviewed.

What intentionally did not change: demo write capabilities, the effect-gateway simulation policy, and every read whose intent is outside the grant set. Demo read reach moves from 157 to 167 admitted definitions and no further; the delta was diffed definition by definition rather than assumed.

Validation

Green in the worktree:

  • convex/sharedDemo and convex/operationAdmission suites — 323 tests, including readIntentGrants, coverage (both-direction grant agreement) and readBoundary.
  • bun scripts/convex-operation-admission-check.ts — every ingress admitted, zero findings.
  • typecheck, audit:convex, lint:convex:changed.
  • src/components/app-sidebar.test.tsx, covering the shared-demo skip.

The new sensor was mutation-tested rather than merely run: reverting one definition to deny made it fail with serviceOps/appointments:listAppointments: expected 'deny' to be 'admit', and it passed again once restored. A sensor that has never been seen to fail is not yet evidence.

In-app, post-fix. The full 42-route sweep was re-run against the live demo with the fix deployed to the dev backend: 42/42 clean — no denials, no error boundaries, no page errors. All eight previously broken surfaces render real content, and nothing that worked before regressed. The POS hub shows its store-time header again, which is the exact read that was denied.

The deadlock, reproduced and re-verified. A demo admission lasts three hours, so a temporary internal mutation was deployed to expire principals on demand, the broken CTA was observed first-hand, and the tool was removed from the deployment afterwards. With the fix in place, expiring a live session and navigating to a demo page renews silently and lands on the requested page — confirmed on Cash controls, Daily Operations and Reports. A principal count taken across one renewal (321 → 322) proves a fresh admission was actually minted rather than the expiry failing to apply.

One write was re-driven after the deploy (a cycle count, applied) to confirm the write rails were undisturbed by the policy change.

Guidance

When you move a Convex read onto the admission rails, the question is not only “what is the safe default?” but “does any shipped surface walk into this?” For the shared demo the answer is enumerable: the demo sidebar and hub name every surface a visitor can reach.

If you add a surface to the demo sidebar, add its reads to demoSurfaceReads.test.ts. That list is intentionally hand-maintained — deriving it by walking the React tree for useQuery calls would go stale in exactly the silence the sensor exists to break.

More generally: a default-deny policy with a closed grant set needs a sensor pointed at reachability, not only at internal coherence. Coherence sensors stay green while the product goes dark.

Worth repeating as method: this was found by driving the app, not by reading the diff. The migration's own test suite was green throughout. A sweep that clicks every surface the product advertises catches a class of regression that no amount of internal-consistency checking will.

Comprehension quiz

  1. Why did the existing demo-policy tests stay green while eight demo surfaces were broken?

    1. They were skipped in CI.
    2. They audit whether the grants that exist agree with each other, and a surface losing its read leaves that agreement intact.
    3. They only run against the storefront package, not the operator app.
    4. They assert reachability but were pointed at the wrong store id.

    Both sensors describe the grant set's internal coherence. Removing a demo-admitted read keeps the remaining grants perfectly coherent, so nothing fails — the missing question was whether the demo's own navigation still resolves.

  2. What are the two keys shared-demo read admission requires?

    1. A valid demo principal and an unexpired admission window.
    2. The store scope matching and the organization scope matching.
    3. The definition's actors.sharedDemo being admit, and its intent being in SHARED_DEMO_ALLOWED_READ_INTENTS.
    4. A granted write capability and a matching read intent.

    Both are checked in the read adapter. Requiring both is what stops an intent grant from silently admitting every read that happens to carry that intent — and it is why fixing only one of them still leaves the read denied.

  3. Why were getServiceCaseDetails and searchCustomers admitted, when neither was the read that failed on page load?

    1. They share a definition object with the reads that did fail.
    2. They are reached one click deeper, so admitting only the load-time reads would give pages that render and then break on their next interaction.
    3. Admitting an intent automatically admits every read that carries it.
    4. They are required for the coverage test to pass.

    A browser sweep only observes the first read a page issues. The admitted set was chosen by tracing which reads each demo view's component tree actually calls, not by fixing the observed error alone.

  4. The sidebar's pending-review count is skipped client-side and its read definition stays denied. Why not admit it too, for safety?

    1. Admitting it would break the both-direction coverage check.
    2. The count query is too expensive to run in a shared demo.
    3. A grant no caller reaches is read reach nobody reviewed, and it would make the reachability sensor assert something the product does not do.
    4. Denied reads render faster because the adapter short-circuits.

    The two mechanisms answer different questions. Once the demo deliberately stops issuing a read, the honest state is denied and unlisted — otherwise the grant set and the sensor both overstate what the demo does.

  5. What did the sweep establish about the migration's effect on writes?

    1. Writes were broken in the same way and fixed by the same grants.
    2. They were unaffected — a POS sale, an approval-gated void, a cycle count, a float correction, an order fulfilment and a customer message all completed.
    3. Writes could not be tested because the POS hub was broken.
    4. Only writes that avoid manager approval still worked.

    The damage was confined to reads. Notably the approval path was exercised in full: the void consumed a manager approval proof and recorded both a payment reversal and an inventory movement.

  6. Why did the "Open demo again" button fail to do anything?

    1. The link pointed at a route that no longer existed.
    2. The operation that mints a demo session was itself denied to an expired session, so obtaining an admission required already holding one.
    3. The button was disabled whenever the demo store was restoring.
    4. Clicking it signed the visitor out without signing them back in.

    The ticket mint declares public: "admit", but the shared-demo adapter resolved the caller's expired principal first and denied terminally, so the chain never reached the public adapter. Every route back in was closed, including the manual one.

  7. An expired session now falls through to public on writes but is still denied on reads. Why the asymmetry?

    1. Reads are cheaper to deny, so the rail short-circuits them.
    2. Public read definitions do not carry an actor list.
    3. The read denial is how the client learns the session ended; answering the identity probe successfully instead makes the app treat the visitor as half-identified and redirect them to a sign-in form.
    4. Writes are re-validated inside the handler, so falling through is safe only there.

    Recovery is a write, so that is where reachability matters. Reads carry the signal, and it was letting reads fall through that produced the silent redirect to /login during development of this fix.

  8. Why is the demo-surface read list hand-maintained rather than derived from the code?

    1. Convex definitions cannot be introspected at test time.
    2. Deriving it would be too slow to run in CI.
    3. A derivation walking the React tree for useQuery calls would go stale in exactly the silence the sensor exists to break.
    4. The list is generated, and editing it by hand is a temporary workaround.

    A sensor that derives both sides of its own comparison can agree with itself while the product is broken — the same failure mode as the coherence tests it supplements. Writing the expected reach by hand is what makes it an independent claim.

Subagent evidence

No subagents were used on this delivery; it was carried out in a single session at the user's direction.

The evidence this change rests on instead:

  • A scripted Playwright sweep driving the live demo over 42 routes plus discovered detail routes, capturing console errors, page errors, failed requests and rendered text per surface. This produced the eight failures and separated them from intentional demo-boundary screens.
  • Manual in-browser driving of six write flows end to end, with screenshots at each confirmation step.
  • A definition-level diff of demo read reach before and after (157 → 167), enumerated per definition rather than counted.
  • Git archaeology against 50bf2711^ confirming every failing read was an unwrapped query before the migration — establishing regression rather than intended tightening.
  • A mutation test of the new sensor, confirming it fails when a definition is re-denied.
  • A temporary internal mutation, deployed to the dev backend to expire demo principals on demand and removed afterwards, so the three-hour expiry path could be reproduced and then re-verified rather than reasoned about.
