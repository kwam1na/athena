Executive Summary

docs/solutions/**/*.md and docs/reports/**/*.html were repo files with no in-app way to browse them, and landed-change reports were standalone HTML pages with embedded CSS, JS, and forms authored ad hoc by whichever agent generated them. This branch adds a themed /docs section to the Athena webapp that indexes and renders both content types, and migrates every landed-change report to a semantic 'contract-v2' format that carries no styling or scripting of its own — the webapp owns presentation and hydrates the quiz.

The two changes ship together because the viewer is what makes report presentation worth standardizing: previously reports could only be shown in a sandboxed iframe.

Problem

There was no route in the app to read a solution note or a landed-change report; readers had to find the raw file in the repo. Reports that did exist were structurally consistent (they followed the render_report.py payload contract) but visually inconsistent, because rendering style was left to whichever agent authored the CSS for a given report.

This was a direct product ask, not a bug: expose solution docs and delivery reports as an in-app docs section styled like the rest of Athena, then encode and enforce report style at the skill level instead of leaving it to each agent.

Mental Model

Think of it as a two-layer split: an index layer and a content layer.

The index layer is a Vite plugin (vite-docs-content-plugin.ts) that walks docs/solutions and docs/reports at build/dev time and emits a virtual module (virtual:athena-docs-index) containing only metadata — titles, dates, categories, slugs. It never embeds file bodies.

The content layer loads lazily per page via import.meta.glob, so opening the docs index page never pays the cost of parsing every report or solution doc — only the one a reader opens.

  • Index: cheap, built once, holds metadata for every doc
  • Content: lazy, one file loaded per page view
  • Reports: semantic content only; the app supplies all styling and the quiz UI

Before vs After

Before: docs/solutions/*.md had no reader surface at all. docs/reports/*.html were self-contained pages — each with its own <style>, <script>, and a scripted quiz form (id="changeQuiz") — opened as raw static files or shown inside a sandboxed iframe by the one place the app referenced them.

After: /docs, /docs/solutions/:category/:slug, and /docs/reports/:slug are TanStack Router routes behind the same auth gate as the rest of the app. Reports are a single <article data-athena-landed-change-report="v2"> with no CSS/JS/forms; the webapp parses that DOM (reportContract.ts), themes it, and renders the quiz as a React component (DocsReportQuiz.tsx) that grades client-side against the encoded answer key.

What Changed

Changed: report rendering pipeline (render_report.py rewritten to emit v2 markup from the same JSON payload contract), a new corpus-wide presentation sensor (report-presentation-check.ts) and an updated per-branch gate sensor (landed-change-report-check.ts) that now also checks diff-fingerprint staleness against v2 markup, a deterministic migration script that converted all ~65 existing reports in place, and the new docs viewer routes/components/vite plugin in packages/athena-webapp.

Not changed: the report-authoring workflow. Agents still produce the same JSON payload (title, sections, keyFiles, quiz, subagents) described in report-payload.md; only what render_report.py emits from that payload changed. Report prose was not rewritten during migration — the converter moves existing DOM text nodes rather than retyping them, so wording is preserved exactly, only the structural wrapper changed.

Enforcement is intentionally split: reports:presentation:check runs over the whole corpus always (root marker, no styling/scripting, header/pills, section order, well-formed quiz). landed-report:check additionally requires the full section vocabulary, key-files table, subagent evidence, and a five-question quiz — but only for reports authored or changed on the current branch, so historical reports are never held to requirements they never had.

Failure Boundaries

A report missing the v2 root marker is not a hard failure at read time: parseReportDocument returns null and DocsReportView falls back to a sandboxed <iframe sandbox="allow-scripts">, isolated from the app shell but still executing that file's own embedded script if one exists. reports:presentation:check exists specifically to make this fallback path unreachable in normal operation.

Empty docs/solutions or docs/reports directories do not crash the index: safeReadDir catches a missing directory and returns an empty list, so the index and list pages simply render empty.

The /docs section is not public — DocsAuthGate redirects unauthenticated visitors to the login route, the same gate the rest of the app uses. There is no additional role check beyond being signed in.

A malformed or unresolvable cross-reference link in a solution doc renders as muted, non-clickable text rather than a dead route — links only become real TanStack Links when verified against the doc index.

Next-Time Guidance

When adding a new docs/reports/*.html by hand instead of via render_report.py, follow report-html-contract.md exactly: no <style>/<script>/<img>/<form>, exactly one <h2> per section, quiz and subagent-evidence sections last, in that order.

When a new build-pipeline file is added under packages/athena-webapp (like a new vite plugin), add it to the matching harness validation scenario's touchedPaths in scripts/harness-app-registry.ts and its harness-audit fixture, or the contract preflight will flag it as an uncovered surface.

Regenerate a report's diff fingerprint after the final code/workflow edit on a branch, not before — an earlier fingerprint goes stale the moment later edits land, and the delivery gate will reject it as stale.

If bulk-migrating many generated files, prefer a deterministic script over per-file subagents once the file count is large — subagent-per-file migration hit a spend limit partway through this branch's own report migration.

Run bun install with the exact bun version pinned in package.json's packageManager field. This branch's own delivery hit a CI-only failure ('error parsing lockfile: Outdated lockfile version') because a newer local bun rewrote bun.lockb into a format the CI-pinned bun couldn't read; scripts/bun-version-check.ts now runs first in pr:athena:prepare so that drift fails locally instead of only in CI.

Comprehension quiz

Pass required: 8 of 10.

  1. Why does vite-docs-content-plugin.ts build a metadata-only virtual module instead of embedding full document bodies?

    1. Embedding bodies would break TypeScript's module resolution
    2. So the index stays cheap to build and load; bodies lazy-load per page via import.meta.glob only when a reader opens that page
    3. Convex does not allow static file imports larger than 64KB
    4. The webapp's router requires all route data to be metadata-only

    The index layer is deliberately separated from the content layer so opening the docs list never pays the cost of parsing every report or solution doc — only the one a reader actually opens.

  2. What happens when DocsReportView encounters a docs/reports/*.html file that is missing the v2 root marker?

    1. The build fails immediately
    2. The file is silently skipped from the index
    3. parseReportDocument returns null and the view falls back to rendering the raw file in a sandboxed iframe
    4. The webapp auto-converts it to v2 at render time

    The fallback exists as a safety net, not an intended path — reports:presentation:check is what should make this branch unreachable in normal operation, since the iframe still executes the file's own embedded script if one exists.

  3. Why is reports:presentation:check applied corpus-wide while the full narrative section requirement (landed-report:check) only applies to reports touched on the current branch?

    1. Corpus-wide checks are faster to run in CI
    2. Historical reports predate parts of the v2 narrative contract; requiring the full section vocabulary retroactively would mean fabricating content they never had
    3. The distinction is arbitrary and could be merged
    4. Presentation rules only apply to reports created after 2026-07-01

    Presentation rules (no styling/scripting, structural shape) are cheap and universal, but narrative completeness (validation section, key-files table, subagent evidence) is a delivery-time requirement that only makes sense for new or edited work.

  4. Why did the bulk migration of all ~65 existing reports end up using a deterministic script instead of one subagent per file?

    1. Subagents cannot write HTML files
    2. The per-file subagent approach hit a spend limit partway through and could not guarantee verbatim text preservation, so a DOM-based converter that moves existing prose nodes was used instead
    3. The script was required by the report-html-contract.md spec
    4. Subagents do not have access to docs/reports/

    Subagent-per-file migration died mid-run after converting only 9 of 65 files; the deterministic script also guarantees byte-for-byte prose preservation, which a rewriting agent cannot.

  5. Does report authoring change for agents generating a new landed-change report after this branch merges?

    1. Yes — agents must now hand-write HTML directly instead of using a script
    2. Yes — the JSON payload contract gained required new top-level fields
    3. No — agents still produce the same JSON payload described in report-payload.md; only what render_report.py emits from that payload changed
    4. Yes — quizzes are now optional

    The authoring workflow is intentionally unchanged. Only the renderer's output shape moved from styled/scripted v1 HTML to semantic contract-v2 markup that the webapp themes and hydrates.

  6. Who can view the new /docs section in the running app?

    1. Anyone, unauthenticated, since it's just documentation
    2. Only admins with a specific role flag
    3. Any signed-in user — DocsAuthGate uses the same auth check as the rest of the app shell with no additional role check
    4. Only the user who authored the report being viewed

    DocsAuthGate redirects unauthenticated visitors to the login route, matching the rest of Athena, but does not add a separate authorization layer on top of being signed in.

  7. What is the correct order to compute a report's data-athena-report-diff-fingerprint before delivery?

    1. Compute it before the final code edits so it's stable throughout review
    2. Compute it once at branch creation and never touch it again
    3. Compute it after the final code/workflow edit on the branch, since an earlier fingerprint goes stale the moment later edits land
    4. The fingerprint is generated automatically by git on commit

    The delivery gate compares the stamped fingerprint against the current deliverable diff; computing it before final edits means the very next source change invalidates it and the gate rejects the stale value.

  8. If a new build-pipeline file (like a Vite plugin) is added to packages/athena-webapp, what additional step is required for the harness gate?

    1. Nothing — the harness auto-discovers all .ts files in the package root
    2. It must be added to the matching validation scenario's touchedPaths in scripts/harness-app-registry.ts (and its harness-audit fixture), or the contract preflight flags it as an uncovered surface
    3. It must be renamed to match an existing vite.config.ts pattern
    4. It must be moved into src/ to be discoverable

    This branch itself hit this: vite-docs-content-plugin.ts had to be registered under the 'Route runtime or build-pipeline edits' scenario, with a matching fixture file added to harness-audit.test.ts, before the harness contract preflight passed.

  9. Does report prose (the written explanation text) change as part of the v1-to-v2 migration of the ~65 existing reports?

    1. Yes, every report was rewritten and shortened for the new format
    2. No — the migration script moves existing DOM prose nodes rather than retyping them, so wording is preserved exactly; only the structural wrapper changes
    3. Only reports older than 30 days had their prose rewritten
    4. Prose is regenerated on every page load by the webapp

    migrate-reports-to-v2.mjs is explicitly a structural converter, not a rewriter — it repositions existing text nodes into the new contract shape rather than generating new prose.
