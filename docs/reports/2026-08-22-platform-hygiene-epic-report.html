Executive summary

Six tickets land together: one production bug fix, four structural boundary refactors, and the documentation that makes the bug fix's rule durable. They ship as one PR because they share generated artifacts — the Convex generated API, the graphify knowledge graph, and the harness doc indexes — which would otherwise conflict across five separate pull requests. Ticket-level scope stayed separate: each was implemented in its own isolated worktree, and the shared artifacts were regenerated exactly once at integration.

The headline change is V26-1171: archiving a product can no longer strand open sale-inventory review work. Alongside it, three refactors move code across boundaries without changing behavior, and V26-967 deletes a frontend fallback that had been quietly reporting offline terminals as healthy.

Independent review found three real defects in this branch's own work — one of them a false "migration complete" signal that gates a money-validator constraint flip, and one of them a regression introduced by the fix for the first. All three are fixed here, each with a regression test proven to fail against the unfixed code before being committed. The review is part of the story of this delivery, not a footnote to it.

What was wrong, in plain language

Products could be archived out from under their own unfinished work. When a POS sale needed an inventory review, that review lived in the Stock adjustments workspace. But Stock adjustments hides archived SKUs. So archiving a product made its open review work unreachable while the weekly inventory-attention count still counted it. Operators saw a count of 59 items needing attention and a workspace that could only render 58. The missing one was invisible and unresolvable.

Browser code was importing Convex server internals. Eight allow-listed exceptions had accumulated in a boundary test, each individually justified in a comment. An allowlist that long stops being an exception list and becomes the architecture.

The storefront compiled through the admin app's root. Shared DTOs were imported from @athena/webapp, so the storefront's type graph ran through another application's internals and its generated Convex model paths.

Terminal Health had two brains. The server computed an authoritative operational state, and the frontend kept a parallel derivation as a fallback. The two had drifted.

Amount migrations could not be run safely. They read entire tables into memory, had no idempotency marker, and resolved genuinely ambiguous values by heuristic guess.

The idea that ties it together

Five of these six tickets are the same shape: something was being decided in two places at once, and the two places disagreed.

  • Product archive: the source workflow decided a product was done; the destination workspace decided its work was unreachable. Nobody reconciled them.
  • Terminal Health: the server decided operational state; the frontend re-decided it from raw ledgers.
  • Convex boundary: "what is browser-safe" was decided by an allowlist in a test, not by where code lived.
  • Storefront contracts: the shape of a shared DTO was decided inside the admin application root.
  • Amount migrations: "has this row been converted?" was decided by guessing at the value's magnitude, not recorded.

In every case the fix is the same move: give the decision one owner, and make the other side read it rather than recompute it. A precondition on the source transition. A server aggregate the UI renders. A module location instead of an allowlist. A contract package. A marker column written in the same transaction as the data it describes.

The durable rule V26-1172 records is the general form: a source transition must not make unresolved operational work unreachable. Either the work becomes terminal, or the transition is blocked. Silently orphaning it is the one option that is never acceptable.

Before and after, per boundary

Product archive (V26-1171)

Before: two public paths reached availability: "archived" — the dedicated archive mutation and the generic update — and neither consulted the product's SKU-scoped inventory review work.

After: both call one guard, guardProductArchiveTransition, before any write. The scan is bounded and store-scoped, and it fails closed: if it cannot prove it saw all the work, it blocks rather than allowing an orphan.

Amount migrations (V26-963)

Before: full-table .collect() behind a lint suppression; no marker, so a second run multiplied by 100 again; a price < 10_000 heuristic that silently guessed in both directions and buried the guess in the same counter as genuine skips.

After: cursor-paged batches that schedule their own successors, dry-run by default, and a pesewasMigratedAt marker written in the same ctx.db.patch as the money fields. Ambiguous values are now a first-class outcome — reported with a reason, never written, never marked, so they resurface until a human decides.

Convex/browser boundary (V26-965)

Before: an allowlist of eight patterns. After: exactly one entry, for generated Convex modules. Six of the other seven were resolved by moving the implementation into shared/ and leaving a re-export at the old Convex path, so no server import site changed. (convex/utils.ts is a partial extraction rather than a pure shim — it still owns toSlug, getAddressString, and getProductName.) The seventh, convex/emails/, was resolved differently and left no shim: the two receipt templates had no server caller at all, so they moved to src/lib/pos/receipts/ and their two browser import sites were rewritten. That move is one of three independent reasons this branch regenerated convex/_generated/api.d.ts — the other two are the new archive-precondition helper and the migration module swap.

Storefront contracts (V26-964)

Before: the storefront imported @athena/webapp. After: a new @athena/contracts package, with exactly one type-only seam to the generated Convex model. The admin app's types.ts shrank from 350 lines to a 16-line facade, so roughly 200 existing call sites were untouched.

Terminal Health (V26-967)

Before: buildLegacyOperationalExplanation, about 145 lines re-deriving lanes from runtime status and recovery ledgers when the server aggregate was absent. After: deleted. The presentation layer now only normalizes and labels what the server returned, tagging each result with its source.

What changed — and what deliberately did not

Visible changes

  • Archiving a product with open sale-inventory review work is rejected with "Archiving on hold" and a count of reviews to resolve. No backend identifiers are exposed.
  • Terminal Health badges, headline, sale impact and next step now come from the server lane on both list and detail. A response with no aggregate says so plainly instead of guessing a green state.
  • Operators gain dry-run-by-default backfill mutations and a read-only verifier; the old migration module is deleted.

Deliberately unchanged

  • V26-964 and V26-965 change no runtime behavior. The evidence is in the tree: re-export shims at every old import path, the types.ts facade, file renames whose contents are unchanged, and characterization tests written before each move.
  • onlineOrder.amount and paymentDue are still not converted. The legacy module had those conversions commented out, so they were never converted in any environment. Converting them here would be a new, unreviewed data change wearing a refactor's clothes.
  • catalogImport.ts can still insert a product directly as archived. That is creation, not a transition of a product that could already own work, so the guard does not apply. It is documented so a future reader does not read it as a gap.
  • classifyTerminalHealth is retained. It answers a different question and still drives the roster count tiles. Only the badge path moved to the server — and confusing those two is exactly what review defect #2 was.
  • Existing production work items were not repaired. Cleanup of the observed mismatch is explicitly out of scope; this ticket prevents the next one.

The three defects review caught

All three were introduced by this branch's own work and found by independent reviewers reading the code, not by a failing test. The second was introduced by the fix for the first.

A migration that could claim it was finished when it was not

The POS migration recorded complete: true on a run record, and that flag gates flipping the money validators to integer-only. The guard read: 

const complete = !dryRun && page.isDone && totals.pending === 0;

But pending is only incremented inside the if (dryRun) branch. In an applying chain it is structurally zero, so the third condition is dead and the guard reduces to page.isDone. An operator resuming from a supplied cursor would skip every page before it, reach the end, and mark the table drained while unconverted rows remained behind the start point — green-lighting a constraint flip that would then reject those rows on read.

Completion now also requires that the chain started at the table beginning, threaded through the scheduled successors. Separately, a dry run no longer writes the run record at all: it previously called the upsert unconditionally, so a sanity dry run before cutover could clear an existing complete: true.

A fix that broke the field next to it

Re-review of the fix above found that it had gone too far. Only a dry run can measure how much work is left — an applying batch converts what it sees, so its own pending count is structurally zero. By stopping dry runs writing the record at all, the fix removed the only path that ever wrote a truthful remaining, leaving it permanently zero. The gate stayed correct, but the field an operator polls to see outstanding work reported "none left" from the first batch onward.

Dry runs now write the record again but never touch the gate: complete and the cumulative migrated carry forward untouched, so a sanity dry run still cannot clear a finished table. Applying batches own the gate and carry the last measurement forward instead of overwriting it. This is the third round of changes on the same handful of lines, which is itself the lesson: a guard, the counter feeding it, and the field reporting it are one mechanism, and changing any of them in isolation moves the bug rather than fixing it.

A terminal that appeared in no metric tile

When badges moved to the server lane, the roster's "Needs review" count also lost its classification disjunct. But local-runtime review work classifies as "Needs review" while the server routes it to the needs_terminal_action lane. Such a terminal fell out of the review tile, and because the other tiles are label-driven and none match, it appeared in no tile at all — visible only in the total. The disjunct is restored; tiles stay classification-driven, badges are server-driven, and the asymmetry is now documented in place.

Guidance for next time

  • In Convex, "reject the transition" and "audit the rejection" are mutually exclusive if you throw. A throwing mutation rolls back its own audit row. When the rejection must leave a record, return a result instead of raising.
  • A migration marker must be written in the same patch as the data it describes, and classification must check the marker before inspecting any value. Once converted, a row's own magnitude is actively misleading evidence.
  • Never let a dry run touch a completion gate. Not the flag, not the record it lives in.
  • A completion flag must prove coverage, not just termination. "I reached the last page" and "I saw every page" are different claims.
  • A guard, the counter that feeds it, and the field that reports it are one mechanism. Fixing the guard alone moved the bug into the neighbouring field. Re-review caught it; the first fix would otherwise have shipped a quieter version of the same problem.
  • A parallel fallback that mirrors a server policy will rot. This one missed the Offline case and reported offline terminals as healthy. When the server contract makes a field required, delete the fallback in the same slice — the safety net was the hazard.
  • "Pure module" is not the same as "browser-safe." The audit unit is the transitive closure, not the file.
  • Write characterization tests before the move, not after. On this delivery they caught the author twice — expectations were wrong and the code was right. Written afterwards, those would have been "fixed" to match and the signal lost.
  • Adding a rule to a shared ESLint config is not safe until you falsify it. Flat config merges no-restricted-imports last-wins, not by union, so a broad new rule silently disabled a narrower existing one — and the boundary check stayed green because no file violated the rule that had just been switched off.
  • Do not run review agents inside the active delivery worktree. One reviewer's cleanup of its own scratch work reverted staged edits and produced an empty commit. Reviewers should read from an isolated copy.

Comprehension quiz

Ten questions on the mechanics and the judgement calls.

  1. Why can a rejected product archive not simply throw an error?

    1. Throwing is slower than returning in the Convex runtime.
    2. A throwing mutation rolls back its own writes, so the audit row recording the rejection would vanish with it.
    3. The frontend cannot catch errors raised by Convex mutations.
    4. Thrown errors bypass the store-scoping check.

    The rejection has to be auditable. Since a throw rolls back everything the mutation wrote, including the operational event, the decision is returned as a result instead.

  2. What made the old migration's completion flag unsafe?

    1. It was written before the rows were converted.
    2. It was stored in memory and lost on restart.
    3. Its "nothing pending" condition was dead code in apply mode, so it reduced to "I reached the last page" — which a cursor-resumed chain can do without seeing earlier pages.
    4. It was only set for the first table in the registry.

    The pending counter is only incremented in dry-run mode. In an applying chain it is structurally zero, leaving termination masquerading as coverage.

  3. Why must migration classification check the marker before inspecting the value?

    1. Reading the marker is cheaper than reading the value.
    2. After conversion, the row's own magnitude no longer indicates whether it was converted — it is misleading evidence.
    3. The value may be null on legacy rows.
    4. The marker is only present on rows created after the cutoff.

    A converted row looks like a large unconverted one. Only the marker distinguishes them, so it must be consulted first.

  4. What does the migration now do with a genuinely ambiguous value?

    1. Converts it and records a warning.
    2. Skips it silently, as before.
    3. Reports it with a reason, writes nothing, and does not mark it — so it resurfaces on every verification until a human decides.
    4. Deletes the row and logs the deletion.

    The old code buried a guess in the same counter as genuine skips. Ambiguity is now a distinct, persistent outcome.

  5. How did the boundary refactor avoid changing any server import site?

    1. It updated every server import in the same commit.
    2. Implementations moved into shared/ while the old Convex paths were kept as re-exports — except the email templates, which had no server caller and so needed no shim.
    3. It added a bundler alias mapping old paths to new ones.
    4. Server code never imported those modules to begin with.

    Move the implementation, leave a re-export. Server import statements are untouched, so the change carries no server-side churn.

  6. What real bug did deleting the Terminal Health frontend fallback remove?

    1. Drawer-open terminals rendered twice on the roster.
    2. The fallback never handled the Offline classification, so an offline terminal fell through and rendered as "Healthy / No action needed".
    3. Recovery actions were shown to users without permission.
    4. Stale terminals showed a negative age.

    It branched on "No check-in" and "Stale" but not "Offline", so an offline terminal reached the healthy branch.

  7. Why did a terminal end up counted in no metric tile at all?

    1. Its store id was missing from the roster query.
    2. The tile only counts terminals seen in the last hour.
    3. The review tile dropped its classification disjunct, and local-runtime review work classifies as "Needs review" while the server routes it to a non-review lane — and the remaining tiles are label-driven, matching none of them.
    4. Its lane was unknown, which no tile renders.

    Badges moved to the server lane, but the counts were meant to stay classification-driven. Applying the badge's source to the count opened a gap between the two.

  8. Why was the 100× discount display bug characterized rather than fixed here?

    1. It could not be reproduced reliably.
    2. It is pre-existing, and fixing it inside a refactor whose contract was "change no behavior" would have hidden a behavior change in a move.
    3. The owning team had not approved the fix.
    4. The correct value was unknown.

    A behavior-preserving refactor must preserve even the wrong behavior. The bug was pinned as-is and filed as V26-1315.

  9. Why did adding a new ESLint boundary rule silently weaken an existing one?

    1. The new rule ran in a separate config file.
    2. The old rule had been deprecated upstream.
    3. Flat config merges no-restricted-imports last-wins rather than by union, so the broader block replaced the narrower one for overlapping files.
    4. The rule severity was set to warn instead of error.

    The boundary check stayed green because no file violated the rule that had just been disabled. Only the config's own unit test caught it.

  10. What is the reusable lifecycle rule this epic records?

    1. Archived records should be hidden from every workspace.
    2. Operational work should be auto-completed when its subject is archived.
    3. A source transition must not make unresolved operational work unreachable — the work becomes terminal, or the transition is blocked.
    4. Attention counts should exclude any archived subject.

    Silently orphaning the work is the one unacceptable option, which is precisely what produced the 59-vs-58 mismatch.

Subagent evidence

This delivery was carried out by a set of subagents, each scoped to one ticket and one isolated worktree, followed by an independent review pass. What each contributed:

Implementation subagents (six, one per ticket)
Each held to the execution posture its ticket specified — test-first for the archive bug, characterization-first for the four refactors, sensor-only for the documentation. Each reported its red-first or characterization evidence, real sensor output, and merge-conflict risks for its siblings.
Review subagents (four, one per subsystem)
Independent of the implementers, each given the delivery contract so scope was judged against the actual tickets. They cleared the archive slice and both boundary refactors, and produced the three defects fixed here. One verified the moved modules byte-for-byte against their originals; another traced every write path to availability rather than trusting the two named in the ticket.
Delivered-diff subagent
Produced the changed-file map, the before/after per boundary, the risk list, and the test inventory used throughout this report, and independently confirmed the defect descriptions against the code.

One process failure is worth recording: the review subagents were run inside the active delivery worktree, and one of them reverted files it had touched during its own test runs, wiping staged edits and producing an empty commit. No work was lost, but read-only reviewers belong in an isolated checkout.
