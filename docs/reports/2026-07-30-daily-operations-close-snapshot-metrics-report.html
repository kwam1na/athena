Executive Summary

PR #712 changes where Daily Operations gets financial metrics for finalized operating days. A trustworthy completed Daily Close v2 report snapshot becomes the close-time authority; today and any date without trustworthy close evidence continue using live transactions, adjustments, and expenses.

The normal weekly read shape changes from four per-date metric-source reads across seven displayed days plus the prior Saturday (32 total) to one bounded close-range read plus three live financial reads for each fallback date: 1 + 3k. A fully finalized window therefore uses one metric-source query.

This report describes an open delivery candidate. It is not merged or deployed. Linear issues V26-1129 and V26-1130 are In Review; production deploy and root alignment are pending.

Why This Mattered

Daily Close already freezes the financial summary an operator closed against. Reconstructing finalized days from mutable source tables wastes Convex database I/O and can make historical Daily Operations metrics drift away from close-time truth.

The safe optimization is not to trust every snapshot. It is to establish a narrow authority boundary: only one unambiguous, date-local, completed close with internally consistent v2 evidence may replace live reconstruction.

Mental Model: One Gate, Two Paths

Think of the close snapshot as a sealed daily ledger. The resolver first asks whether the seal and its evidence are trustworthy. If yes, it reads the frozen summary. If not, it does not partially trust the close; it follows the established live path for that date.

8 operating dates -> 1 bounded close-range probe
  eligible date  -> frozen close summary -> existing metric response
  fallback date  -> POS + adjustments + expenses -> existing metric response
normal financial-source cost = 1 + 3k

Before and After

  • Before: each of eight dates read Daily Close, POS transactions, adjustments, and expenses, for 32 metric-source queries.
  • After: one indexed Daily Close candidate range covers all eight dates, and only fallback dates read the three mutable financial sources.
  • Before: finalized historical metrics were reconstructed from tables that may change later.
  • After: a valid close-time report summary remains frozen until lifecycle evidence says the day is open or reopened.
  • Unchanged: public query arguments, response keys, financial redaction, ordering, prior-week comparison, selected-day decoration, and client stale-response protection.

Authority and Failure Boundaries

  • The snapshot must be contract v2, match store and operating date, and carry complete aggregate and source evidence.
  • Financial source ranges must match frozen close metadata; 23–25 hour operating-day ranges and up to one hour of request-boundary drift are accepted for DST transitions.
  • Required source lanes are POS completed, adjustment applied, and expense completed. POS void evidence may coexist without disqualifying the snapshot.
  • Money must be finite; counts must be nonnegative integers; payment methods must be unique; source counts must reconcile with the summary.
  • The date-local reciprocal replacement chain must resolve to one completed terminal close. Open, reopened, broken, ambiguous, or competing terminals use live calculation.
  • A 201st close candidate proves the 200-row authority budget was truncated. The whole eight-date window then uses bounded live recovery so truncated history can never select financial truth.

Refresh and Client Contracts

The narrow current-day refresh uses the same frozen-or-live resolver for the selected date and prior date. It does not widen or rename the payload.

The browser still replaces only the selected row, preserves its six sibling week rows and prior boundary, and rejects an older response when refreshRequestedAt no longer matches. Shared-demo analytics remain client-provided. No production UI component changed.

What Did Not Change

  • No Convex schema, backfill, close mutation, Reports projection, cache invalidation, or production UI change.
  • Daily Close History keeps its existing no-reconstruction behavior; only Daily Operations uses live fallback for unusable snapshots.
  • POS-only callers remain redacted and short-circuit before snapshot-summary or financial-source work.
  • Existing client cache lifetime remains unchanged, so a mounted historical row updates at its existing remount, refetch, or current-day refresh boundary.

Next-Time Operational Guidance

  • When adding a new frozen metric, update snapshot validation, projection, live calculation, response-parity tests, and source-count reconciliation together.
  • Treat malformed or lifecycle-ambiguous evidence as a fallback signal, never as permission to use a partial snapshot.
  • Keep the candidate range bounded with one-row lookahead, and preserve whole-window recovery when truncation is detected.
  • Use aggregate Convex Usage/function telemetry to measure overall read reduction. Add dedicated instrumentation before attempting to measure the rare 201-row overflow cohort separately.
  • For regressions, begin with the query observer tests: they expose tables, indexes, bounds, terminal operations, limits, and exact read counts.
