Executive summary

Athena now runs the linear-v2 agent-skills release, pins the published delivery-harness CLI at exactly 0.2.0, and declares the run-event command that release asks an adopting repository to name. A second command, this one Athena's own, installs the next release and proves it converged. Root AGENTS.md loses its restatements of the review round bound, the grace round, and the deferral rules, and points at the installed workflow for them instead.

Nothing in pr:athena changed, and no product runtime surface changed. The nine authored files are repository tooling and documentation.

The problem

The most valuable thing about a delivery is invisible after it ends. Which review lenses the executor chose and why, how many rounds it took, which candidate each round bound to, what each round cost, where the executor decided something by judgement rather than by a rule — all of it lives in a coding host's transcript and nowhere else. The operator learned those facts about the last two deliveries by reading three transcripts by hand.

The delivery product's answer is a run journal that the executor writes as it goes. The workflow release cut for it names the moments to emit and leaves the command itself to the adopting repository: every emission rule in the installed skills reads through the run-event command the repository's root instruction file declares, when it declares one. Athena declared none, so every one of those rules was inert here.

A second, quieter problem: installing an agent-skills release in Athena was a multi-step operator procedure whose success check lived in a human's eyes. Each release meant re-deriving the same sequence.

The mental model

Think of the delivery workflow as a product Athena installs, the way an application installs a library. Three surfaces, with a clear owner each:

The installed workflow (.agent-skills/current/skills/)
Owns portable delivery semantics: what an actionable finding is, how many review rounds a delivery gets, when a grace round is available, how a deferral is discharged, which moments produce a run event. Generated payload — Athena reads it, never edits it.
The overlay (root AGENTS.md)
Owns what Athena adds: the pr:athena gate, the review run root, the reviewer set, worktree bootstrap, branch and PR conventions, and now the two commands below. Every rule the workflow already carries is referenced, not repeated.
The commands (package.json scripts)
The sockets the workflow plugs into. delivery:emit is the run-event command the skills look for; agent-skills:install is how the next release arrives.

The rule that keeps this honest: a run event is observability, never evidence. No gate, approval, or finish-line decision reads the journal, and a refused emission never changes a command's outcome.

Failure boundaries a reader should know

  • The install is not hermetic. It shells out to python3 and build-release.py inside a checkout outside this repository, named by AGENT_SKILLS_CHECKOUT. It cannot run in CI, and its invocation is itself the repository authority for a lifecycle mutation.
  • The CLI entry is a deep path. src/main.ts sits outside the package's exports map, because 0.2.0 publishes no bin. The exact pin bounds that coupling; a repackaging upstream would break it.
  • Emission has no sensor of its own. Because a failed emission may never change an outcome, an emission path that quietly stops working produces no signal.
  • Review semantics now arrive through payload. A future release that changes the bound changes Athena's delivery policy with no diff to AGENTS.md. The contract test pins the delegation sentences, not the rules.

Next time

  • Never route a structured argument through bun run <script> -- <args>. Bun concatenates trailing arguments into a string it hands to bash -c, so a JSON object is brace-expanded before the program parses it. Carry it in an environment variable and forward it with Bun.spawn([...]).
  • Prove a wrapper by running it. Both failures behind this design — the brace expansion and the CLI's stdin path failing under bun with EBADF — are invisible to a unit test of the argument builder.
  • When trimming an overlay against an installed product, check that the product actually carries each rule you delete. Three of the four rules trimmed here were genuinely duplicated; the fourth was Athena's alone and had to come back.
  • Install a release with the command, not by hand. If it reports anything other than a converged status, the install did not happen.

Comprehension quiz

Ten questions. Eight correct to pass.

  1. Why did the run-event payload have to travel in an environment variable rather than on the command line?

    1. Reading a payload on stdin fails under bun with EBADF in the run store.
    2. bun run … -- <args> hands the trailing arguments to bash -c, which brace-expands the JSON.
    3. An argument longer than the operating system's limit is silently truncated.
    4. The harness CLI refuses a payload supplied as an argument.

    Original quoting is gone by the time bash sees the string, so {"a":1,"b":2} becomes two words and the CLI reports that emit takes one kind. The stdin failure is real too, but it is why the wrapper never reads stdin — not why the payload travels in an environment variable.

  2. What does the install command treat as proof that the install actually happened?

    1. The lifecycle update exiting zero.
    2. The built archive's digest matching the release qualification file.
    3. A status read showing lifecycle: current, no blockers, and the just-built release active.
    4. The host projection symlinks resolving to the new generation.

    assertInstalled reads the lifecycle's own status sensor, so the check does not live in a human's eyes. The other options are necessary conditions the sensor already accounts for, not the proof itself.

  3. What happens to a delivery when a run-event emission is refused or fails?

    1. The delivery is recorded as partial with a typed blocker.
    2. The current review round is invalidated and must be re-obtained.
    3. Nothing. Emission is observability, and no gate, approval, or finish-line decision reads it.
    4. The gate fails closed until the journal is repaired.

    A failed emission never changes a command's outcome or the delivery's result.

  4. Why was the reviewer churn-control rule restored to AGENTS.md after being trimmed?

    1. A repository sensor asserted its exact text.
    2. No installed workflow carries it, so removing it would have retired an Athena-owned rule under cover of a product-ownership trim.
    3. It was restored only to keep the diff smaller.
    4. The grace round depends on it mechanically.

    The trim's whole principle is to remove only what the installed product now owns.

  5. Which three rules did AGENTS.md stop restating and start referencing?

    1. The pr:athena gate, the review run root, and the reviewer set.
    2. The review round bound, the grace round, and the deferral rules.
    3. Branch naming, PR body sections, and commit message format.
    4. Worktree bootstrap, generated-artifact repair, and deploy classification.

    The first option lists things Athena still owns and still states itself.

  6. Why does the emit wrapper reject a caller-supplied --json instead of passing it through?

    1. The CLI rejects a duplicated flag with an unhelpful error.
    2. The wrapper appends its own --json last and the CLI's parser is last-wins, so the caller's payload would be silently discarded while the command still exited zero.
    3. A payload on the command line would be brace-expanded before the wrapper sees it.
    4. The flag is reserved for the CLI's own internal invocations.

    The caller's object loses to whatever DELIVERY_EVENT held. With a valid payload there the command exits 0 having recorded the wrong object, which the caller can never see; with nothing there the CLI refuses the empty object and blames the wrong input.

  7. What is the declared review scope for a release install?

    1. The whole .agent-skills/ directory.
    2. .agent-skills/active.json; the rest is generated payload.
    3. Only the .agent-skills/current symlink.
    4. Nothing — a release install is exempt from review.

    Reviewers check the payload's internal consistency and whether it supports the overlay's claims, not its style or structure.

  8. Where does the current-run pointer live?

    1. In a harness.config.ts at the repository root.
    2. In an environment variable the executor keeps for the session.
    3. In the run store under the git common directory, keyed by worktree.
    4. In .agent-skills/active.json.

    run.started allocates a run and points the invoking worktree at it; --run names another.

  9. Which surface did the two new commands deliberately not join?

    1. The repository's package.json scripts.
    2. The frozen lockfile.
    3. The pr:athena merge gate, whose sub-scripts are byte-identical to origin/main.
    4. The root AGENTS.md overlay.

    They are standalone operator commands; the other three surfaces all changed to admit them.

  10. Who decides which review lenses a round runs?

    1. The repository, which fixes the full reviewer set in AGENTS.md.
    2. The executor alone, with no lens mandated by anyone.
    3. The product mandates a correctness and a testing lens; Athena declares the two ids for them; every other lens in a round is the executor's own selection.
    4. The installed release, which enumerates every lens a round must run.

    Round 1 here ran ten lenses: the two mandated ones plus eight the executor chose for this change.
