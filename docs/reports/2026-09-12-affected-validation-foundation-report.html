What this foundation delivers

This candidate adds a read-only validation planner, a callable trusted-health module, and a live same-gate optimization that avoids repeating equivalent webapp tests after aggregate coverage. The existing gate remains authoritative. Full affected-validation activation is a later, dependent delivery.

Why validation repeated

The gate starts with aggregate coverage and adds mapped commands. A command string cannot show that coverage already executed the ordinary webapp inventory. Removing commands indiscriminately would let different inputs or execution profiles inherit a success they did not earn.

Three separate questions

  1. Selection: which correctness obligations and test members are required?
  2. Execution evidence: what actually passed under the required inputs and profile?
  3. Repository health: which known failures still require a repair proof?

The planner answers the first question. The delivery product owns durable evidence authority. Health distinguishes candidate repair from trusted-main closure.

Behavior boundaries

Comparison computes a proposed plan without executing a second gate. Full-health names complete registered inventory even on unchanged main. Unknown input, including a deletion or either side of a rename, blocks when no obligation covers it. A plan identity fingerprints declarations and membership; it is not a receipt or a hash of captured source bytes.

The live optimization applies only to equivalent full webapp tests in the current provider invocation. Configuration, source/base, dependencies, toolchain or environment drift prevents reuse. Restoring source or dependency bytes and modification times during execution still invalidates reuse through mutation metadata. Timer stress, browser and custom targeted profiles remain separate. There is no persisted Athena result cache.

The health module is callable qualification capability. This candidate does not activate a schedule, install the upcoming scoped-evidence product, or enable authoritative affected validation. Candidate repair evidence cannot globally close a failure or impersonate hosted proof. Missing required health requests full-health recovery while retained known failures still require repair proofs. A main-branch classification file alone does not prove maintainer approval: an explicit trusted verifier must accept it before scope narrowing or global closure. Approved historical revalidation is resolved independently of newer healthy runs, while newer real failures remain open. A bounded reader deadline reaches conservative recovery when an adapter or subprocess stalls; owned processes are terminated and temporary downloads cleaned.

Evidence and pending delivery

Characterization used injected no-op executors to capture the existing report-only and empty-diff broad selection. Corrections include historical revalidation lookup, source/dependency mutation guards, qualified configuration controls, typed explanations and prerequisite-preservation tests. Guard-removal mutations fail the new negative controls. The final combined gate remains pending for the corrected candidate.

Check your understanding

  1. Does a successful planning command prove the checks passed?

    1. No. It explains selection and reports evidence as not evaluated.
    2. Yes, its digest is a passing receipt.

    Planning does not execute or verify checks.

  2. What allows same-gate ordinary webapp test reuse?

    1. Any previous green CI run.
    2. Successful qualified aggregate coverage with unchanged input and execution bindings.

    The optimization is transient and tied to this provider invocation.

  3. Can equal filenames merge timer-stress and ordinary profiles?

    1. No, their execution conditions remain distinct.
    2. Yes, filenames define equivalence.

    Profile semantics are part of the check contract.

  4. What does full-health do on an empty diff?

    1. Returns an empty green plan.
    2. Selects the complete registered inventory.

    Scheduled health must work without a PR diff.

  5. What does an uncovered deleted input do?

    1. Blocks planning with a typed diagnostic.
    2. Disappears from selection because the file is gone.

    Deletion can remove an important contract or consumer.

  6. What does a local repair proof close?

    1. The global repository finding.
    2. Only its matching candidate/profile obligation.

    Global closure needs approved main resolution and newer trusted revalidation.

  7. What happens when required health is unavailable?

    1. Full-health recovery is requested while known failures remain retained.
    2. The last green state is assumed forever.

    Unavailable evidence is not health success.

  8. What is a plan check identity?

    1. Verified source bytes and hosted execution provenance.
    2. A fingerprint of declarations and membership.

    The product must separately capture and verify execution inputs.

  9. Does this foundation activate affected validation?

    1. No, upstream evidence, adoption and hosted qualification remain prerequisites.
    2. Yes, the planner replaces the legacy gate immediately.

    Only the final activation ticket changes authority.

  10. Focused tests pass while review and the final gate are pending. What can you conclude?

    1. The candidate is merge-ready because focused tests are green.
    2. Those focused checks passed; delivery is still incomplete.

    Final review, gate, merge and root alignment require their own evidence.
