Reporting was rebuilt around a fact ledger and a day fold.

Delivery candidate · Athena operations

This delivery replaces it wholesale with an append-only fact ledger, a pure day-fold correctness authority, and metric-as-field, singleton-doc read surfaces — verified against independently recomputed domain totals on the wigclub dev store.

The driving constraint was database read cost.

What changed, and why

On the wigclub dev deployment (jovial-wildebeest-179), 1,284 canonical facts over 64 operating days had fanned out into roughly 35,800 derived and audit rows — about 28 rows per fact. reportingProjectionEvidence alone held 21,546 rows, 16.8× the fact count, because every rebuild re-copied evidence. The store-day projection was metric-per-row, so a trailing-30 overview read touched roughly 340–440 documents, and because those rows changed on every applied fact, the subscribed overview re-executed 15–45 times a day per subscriber: an estimated 6,000–19,000 reads per day for a single dashboard.

Structural identity

Facts are unique on indexed fields (storeId, sourceDomain, sourceId, lineId, factKind), not a concatenated string key — the escaping/forgery bug class is designed out rather than mitigated.

One fold, one authority

foldDay is a pure function from a day's facts to a day result. It is the rebuild, the reconciliation, and the backfill apply step — there is no separate machinery for any of them.

Metric-as-field

Day, sku-day, and overview documents hold metrics as fields, not rows. The dashboard subscribes to one singleton overview document per store.

Intentionally unchanged: domain source tables (POS transactions, orders, closes, payments, stock ops) are never written by this layer. Reporting is fully derived; rollback is a redeploy of prior code.

An append-only ledger and a fold-over-incremental correctness model.

Architecture

  1. Ingest
    Emitters write reportFact rows inside the same domain transaction that commits the sale, order, close, or stock move.
  2. Patch open day
    An arriving fact for the still-open day incrementally patches reportDay/reportSkuDay — provisional, best-effort.
  3. Dirty closed day
    A late fact against a closed day never patches it directly; it upserts a reportDirtyDay mark.
  4. Fold
    foldDay(facts, close?) is the one authority: sorts facts deterministically and derives day + sku-day results from scratch.
  5. Sweep
    A single 5-minute cron drains dirty marks, refolds, rebuilds the store's overview doc, and re-marks the still-open day.
  6. Read
    UI surfaces read the overview singleton, bounded day/sku-day index pages, and calendar rollups — never raw facts.

Fold-over-incremental removes whole bug classes rather than patching around them. Incremental patching means every code path that can touch a fact (live ingest, replay, correction, backfill) must independently get the arithmetic right, and any drift between those paths is invisible until an audit finds it. The fold has exactly one implementation of "what a day means": replaying that day's facts through it always produces the same result, regardless of arrival order, replay, or how the day was originally built. Backfill, live ingest, and disaster recovery are the same code path for exactly this reason — there is nothing to drift.

The incremental patch on the open day exists only to keep an in-progress day's numbers roughly current between sweeps; it is explicitly best-effort and never the record of truth. A replayed fact can transiently double-count today's numbers, and that is an accepted trade — the next fold, at close or at the next sweep, replaces every incrementally patched number with the deterministic fold result. No part of the system treats the incremental path as authoritative, so there is no reconciliation step between "what the incremental patch said" and "what the fold said" — the fold simply overwrites.

Business time (occurredAt) drives which operating day a fact belongs to; arrival time (recordedAt) is metadata only. This is why reseed — which ingests historical rows long after they occurred — still lands facts on the correct historical operating day instead of the day the reseed job happened to run.

verifyDayAgainstSources deliberately does not share code with the fact emitters: it recomputes each day's totals straight from domain rows (POS transactions, orders, closes, payments, stock ops) using an independent implementation, then diffs against the folded reportDay. Legacy projections — with their known double-count and truncation bugs — are not used as a reference for anything.

The two defects the verifier found

  • Currency-normalization mismatch. The store config carried currency as "ghs" while emitters normalized fact currency to "GHS". The sweeper/ingest/overview paths were passing the raw, unnormalized store value into the fold, so every fact was excluded as "foreign currency" and all days folded to zero. The fix routes every fold input through one shared contract helper, normalizeCurrencyCode, so there is exactly one place currency casing can be gotten wrong.
  • Till-billed service revenue was silently dropped. posTransactionServiceLine rows carry revenue on the transaction header with no corresponding item rows, and the emitters were skipping them — undercounting three real days. The POS sale/void emitters (and the reseed mappers, so backfilled history gets the same fix) now emit a revenue-only fact per service line with zero merchandise units.

UI outcomes

One period at a time

The overview shows one period window (today, week-to-date, trailing-30, prior week) at a time through a tabs switcher, instead of a wall of simultaneous panels.

Settlement, not a status badge

The days table communicates settlement in words — "Under close", "Matches close", "Not closed yet" — because "reconciled" describes timing against the close, not whether the numbers agree with it.

Stale-while-refreshing reads

Changing the selected date range no longer tears the page down; the previous result stays visible while the next one loads.

One paint, not three

The overview route used to mount three sections independently, arriving 69ms apart with a measured cumulative layout shift of 0.165. Gating the page on the overview query it now shares collapses that to a single paint — measured shift 0.

How to extend or debug this area

Next-time guidance

  1. Never add a code path that writes day/sku-day metrics directly. All correctness changes go through foldDay; the incremental open-day patch is a best-effort preview only, never a source of truth.
  2. New fact-producing domains call recordFacts from inside the same transaction that commits the domain write, with business-time occurredAt — never sync/arrival time.
  3. If a metric looks wrong, check the fold's unit tests first, then verifyDayAgainstSources against real domain data for the affected store and day — do not trust the incremental patch or the old projections as a reference.
  4. Currency, and any other value that gets compared for equality across the ingest/fold/overview boundary, must go through the single shared normalization helper in shared/reportsContract.ts — the wigclub "ghs" vs "GHS" bug is exactly what happens when a raw value skips it.
  5. Before assuming a source is fully captured, check for header-level revenue with no item rows (the till-billed service-line bug). A domain that bills at the header level needs an explicit revenue-only fact, not an inference from item rows.
  6. Schema and metric-name changes go through shared/reportsContract.ts first; it is frozen after Wave 0 for a reason — slices and the UI depend only on it, never on each other's internals.

Comprehension quiz

Pass required: 8 of 10.

  1. Why does the days table say "Under close" / "Matches close" / "Not closed yet" instead of a "reconciled" badge?

    1. Because reconciliation is deprecated
    2. Because "reconciled" describes timing relative to the close, not whether the folded numbers agree with it
    3. Because the close doc no longer stores a variance

    Settlement state and numeric agreement are different facts; collapsing them into one badge hid which one had actually failed.

  2. Why is foldDay the sole correctness authority instead of the incrementally patched open-day doc?

    1. The incremental patch is deleted after every sweep
    2. The incremental patch runs faster, so it wins ties
    3. The incremental patch is explicitly best-effort and can transiently double-count; only a full fold over that day's facts is deterministic and replayable

    The open-day patch exists only to keep numbers roughly current between sweeps. The fold always overwrites it — there is no reconciliation step between the two because only one is ever authoritative.

  3. Why is fact identity structural fields (storeId, sourceDomain, sourceId, lineId, factKind) rather than a concatenated string key?

    1. A composite index on real fields removes the string-escaping/forgery bug class instead of merely mitigating it
    2. Convex indexes cannot be built on string fields
    3. String keys are slower to hash

    A concatenated key can be crafted or mis-escaped to collide or diverge; separate indexed fields have no such ambiguity.

  4. What did the wigclub "ghs" vs "GHS" defect actually teach?

    1. Currency codes should be optional
    2. Any value compared across the ingest/fold/overview boundary must go through one shared normalization helper, or a casing mismatch silently zeroes everything
    3. The fold should ignore currency entirely

    Because the raw store currency skipped normalization in one path, every fact was excluded as "foreign," folding all 67 days to zero — invisible until the independent verifier compared against domain totals.

  5. Why does reseed stamp facts with business time (occurredAt) as the driver of operating date, rather than the time the reseed job ran (recordedAt)?

    1. Because reseed cannot access historical timestamps
    2. Because Convex requires monotonic timestamps
    3. Because reseed re-derives historical facts long after they occurred; using arrival time would collapse months of history onto the reseed run's date

    Business time is what makes reseed = backfill = disaster recovery a single code path — the same emitter logic lands facts on the correct historical day regardless of when it runs.

  6. Why is the store overview a single denormalized document rather than a query that aggregates day docs live?

    1. So a dashboard subscription costs one document read, invalidated only by the sweep, instead of scanning tens to hundreds of day/sku-day docs on every execution
    2. Because Convex cannot aggregate across documents
    3. Because the overview only needs today's numbers

    The sweeper computes the aggregation once per cadence and writes the result; the dashboard's job becomes reading one doc, not repeating the aggregation on every reactive re-run.

  7. What did the till-billed service-line defect reveal about capturing revenue from a new domain?

    1. Service revenue should never be reported
    2. A source that bills at the header level with no item rows needs an explicit revenue-only fact — inferring facts purely from item rows silently drops that revenue
    3. Service lines must always have a unit cost

    posTransactionServiceLine carried header revenue with no items; the emitters were only walking items, so three real days were undercounted until a revenue-only, zero-unit fact was added per service line.

  8. Why were the inventory valuation ledger and operating-day/timezone authority moved to their own namespaces instead of deleted with the rest of legacy reporting?

    1. They were left in place for backward compatibility
    2. They failed their tests, so deletion was deferred
    3. They were never reporting code — other non-reporting domains (six for the cost ledger; closes/POS/scheduling for operating-day math) depend on them

    Deleting them with the rest of convex/reporting/ would have broken unrelated domains; they were extracted to convex/inventoryLedger/ and convex/storeTime/ instead.

  9. What does the source-truth verifier deliberately avoid using as its reference?

    1. The legacy reporting projections, which had known double-count and truncation bugs
    2. The store's daily close documents
    3. The reportFact ledger itself

    verifyDayAgainstSources recomputes totals independently from domain tables, deliberately not sharing code with the emitters, and never compares against the known-buggy legacy projections.

    1. Merged and deployed to production, one week of read metrics collected
    2. Delivery candidate: local validation and dev deploy complete, wigclub dev verification at 67/67; PR, merge, production deploy, and the week of read-metric measurement are pending

Subagent Evidence

Delivery provenance

The rebuild was fanned out across parallel subagents against a frozen contract (shared/reportsContract.ts) and typed stubs, so each slice compiled against the others from the start. Every slice shipped its own tests; the integration issues they surfaced are listed with their resolutions.

  • Contract and schemas (in-session): froze the metric vocabulary, fact/derived table schemas, and fold/ingest/query signatures, plus a parity test making backend/frontend metric divergence a compile error.
  • Fold engine: pure foldDay with 26 tests — determinism over shuffled input, close variance, amendment, quarantine and mixed-currency exclusion. Documented eight deliberate divergences from legacy sign conventions.
  • Ingestion core: structural identity with quarantine-on-conflict, contained failures, bounded timezone resolution; 30 tests.
  • Sweeper, overview, rollups: 5-minute cron over declarative dirty marks, at-least-once semantics, store allowlist; 49 tests, no skipped integrations.
  • Read queries and access: five queries with access checks, cursor context binding, and a per-query read budget; 23 tests.
  • Domain emitters (five parallel slices): POS, storefront, service, ops, and stock rewritten onto recordFacts with business-time occurredAt; POS domain alone re-verified at 1,235 tests.
  • Verifier and reseed: independent recomputation from domain tables — deliberately not sharing the emitters' code — plus a resumable reseed. 29 tests. This slice escalated three integration defects (void sign convention, reseed recordedAt vs close, stale generated API), all fixed before cutover.
  • Legacy deletion: import-closure analysis found 105 of 131 legacy files reachable only from other legacy files; the remaining 26 were inventory costing and time authority, which were extracted rather than deleted.
  • UI alignment: restyled against the app's existing Store Pulse and Daily Operations patterns rather than new primitives.
Adversarial value: the source-truth verifier existed precisely to distrust the pipeline that fed it, and it earned its keep — the currency-normalization and till-billed-service defects were both caught by it on real data, not by unit tests.
