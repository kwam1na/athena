Executive Summary

This batch completes the typed blocker contract for the Athena delivery harness. The contract's promise is that every blocking exit a harness CLI can produce renders a structured blocker with a stable code, a registry-owned source, and at least one remediation. Before this batch, that promise had known holes: three reachable CLIs were explicitly excluded from coverage, one blocker source id had no producer, an inventory sensor ignored a suppression flag that had already let prose-only failures ship twice, new provider finding codes could silently void human waivers, interrupted and usage-error exits rendered as crashes or bare prose, and documentation findings carried generic repair-everything guidance instead of pointing at the artifact that actually needs to change.

Seven tickets close those holes. Each is small, each pins its boundary with tests, and together they turn 'the harness tells you what blocked you and how to fix it' from an aspiration into an enforced invariant.

Problem and context

The delivery gate (pr:athena) runs a spine of sensors and private providers. When something fails, the operator sees terminal output. The typed blocker system (scripts/harness-blockers.ts) exists so that output always answers three questions: what failed (code), which component owns the failure (source), and what to do next (remediations). A single constructor, createHarnessBlocker, sanitizes every blocker: secret redaction, control-character stripping, kebab-case id enforcement, registry-owned source validation.

The gaps this batch closed were all cases where an exit path bypassed that constructor or the contract was pinned by convention rather than by test:

Three live CLIs (delivery:documentation-check, delivery:telemetry-check/record, pr:athena:record-proof) still printed prose and called process.exit directly. The inventory sensor documented them as knowingly outside the contract.

HARNESS_PREPARATION_SOURCE_IDS contained mechanical_failed, but no code path ever produced a preparation blocker with that source. Dead vocabulary in a guarded tuple invites drift between the runtime guard and reality.

A CLI passing renderNonZero: false to runHarnessCliBoundary suppresses the shared harness_command_failed fallback. That is legitimate only when the file renders its own conformant blocker, but nothing checked it - and prose-only suppressions shipped twice before a human caught them.

waivableBlockedObligationIds is all-or-nothing: one finding code missing from WAIVABLE_FINDING_CODES makes the waiver unofferable for the entire run. Nothing pinned which codes an obligation can emit, so a new provider code would default to silence.

Interrupted delivery runs and malformed invocations reached the operator as either a bare prose summary or an internal-error stack with a reproduce command for a crash that was not a crash.

After obligations moved to typed blockers, LiveProviderFinding narrowed to code | message, so documentation findings lost their provider-specific remediation and fell back to generic repair guidance.

Mental model

Think of the blocker contract as a border checkpoint. Every non-zero exit from a harness CLI must cross the checkpoint, and the checkpoint stamps three things onto whatever passes: a stable lowercase code, a source owned by a registry (gate, obligation, provider, preparation, candidate, or command), and at least one remediation with a stable kebab-case id.

This batch closes the smuggling routes around the checkpoint rather than adding new checkpoints:

  • Registration: every CLI that can block must be listed in HARNESS_BLOCKER_CLI_INVENTORY, the manifest the static sensor walks (V26-1274).
  • Vocabulary hygiene: a source id nobody produces gets removed, and a test asserts every remaining member has a producer (V26-1278).
  • Sensor policing of suppressions: opting out of the shared fallback requires proof that you render your own conformant blocker (V26-1279).
  • Exhaustiveness pins: every emitable finding code must be classified as waivable or intentionally not waivable, enforced by compile-time witnesses and guard tests (V26-1276).
  • Total rendering: even interrupted and usage-error exits get stamped blockers, so no exit path prints unstructured text (V26-1284).
  • Specific guidance: remediations keyed on finding codes tell the operator which artifact to fix, not just that documentation is stale (V26-1285).

Before vs after

  • Before: three CLIs printed prose and exited via process.exit, explicitly listed in a sensor comment as knowingly outside the contract. After: they run inside runHarnessCliBoundary, are registered in HARNESS_BLOCKER_CLI_INVENTORY, and bad flags throw HarnessUsageError instead of Error.
  • Before: mechanical_failed sat in HARNESS_PREPARATION_SOURCE_IDS with no producer. After: removed; a test names a producing site for every member of the union.
  • Before: renderNonZero: false was unchecked. After: inspectRenderNonZeroSuppression fails any inventory file carrying the literal suppression without also constructing a blocker via createHarnessBlocker, HarnessBlockedError, or formatHarnessBlockers.
  • Before: WAIVABLE_FINDING_CODES was a hand-maintained list with nothing proving completeness against what obligations emit. After: EMITTABLE_BLOCKED_FINDING_CODES and INTENTIONALLY_NOT_WAIVABLE_FINDING_CODES partition the space exactly; exhaustive Record witnesses make a new provider union member fail to compile until it is classified.
  • Before: an interrupted delivery run exited 1 printing only a prose summary; a bad CLI flag surfaced as harness_internal_error with a stack. After: interrupted runs render a delivery_run_interrupted blocker naming the signal; usage errors render harness_usage_error listing supported flags.
  • Before: both documentation policies shared one repair-delivery-documentation remediation.   • Before: pr-athena-delivery-run defined its own commandToString quoting helper. After: it uses formatHarnessCommand, the canonical quoting used by remediation rendering; span labels are byte-identical for every registered command.

Layer-by-layer mechanics

Data flows through four layers. The constructor layer (harness-blockers.ts) owns sanitization and shape: createHarnessBlocker validates sources against the registry at runtime because scripts/ is not typechecked, redacts secrets, bounds details at 8000 characters, and rejects unstable ids. It also now owns two expected-outcome constructors: createHarnessUsageErrorBlocker and the HarnessUsageError class (extending HarnessBlockedError so catch-all wrappers cannot reclassify it), plus the delivery_run_interrupted rendering in the delivery-run spine.

The inventory sensor layer (harness-blocker-inventory.ts) polices shape statically. It walks HARNESS_BLOCKER_CLI_INVENTORY, checks that each file runs through runHarnessCliBoundary, does not call console/process.exit at the boundary level, uses no free-form sources, and - new in this batch - proves that renderNonZero: false files construct their own blockers. Its stated residual limit is honest: literal-only detection; runtime indirection stays owned by createHarnessBlocker, and unregistered CLIs are invisible.

The admission layer (harness-gate-admission.ts, harness-gate-obligations.ts) evaluates gate obligations per candidate binding. Waivers intersect blockers against WAIVABLE_FINDING_CODES; the new exports pin that intersection's inputs. The obligation evaluator maps finding codes to typed remediations, restoring code-specific repair for documentation policies.

The provider CLI layer (delivery-documentation-check.ts, delivery-run-telemetry.ts, pre-push-validation-proof.ts) wraps its entrypoint in runHarnessCliBoundary with a source matching its registered command id, so every failure it produces crosses the checkpoint with full structure.

Failure boundaries

  • Malformed invocation (unknown flag, missing value): throws HarnessUsageError, which survives catch-all wrapping in CLIs like harness:review and renders as harness_usage_error with a rerun-with-supported-flags remediation - never as an internal-error stack.
  • Interrupted delivery run: non-SIGINT signals exit 1 through the spine and now render delivery_run_interrupted naming the interrupting reason; SIGINT also renders, since a stable code costs nothing and keeps every non-zero exit total.
  • Suppression without emission: a file adding renderNonZero: false without constructing a blocker fails the inventory sensor statically with blocker-emission-missing.
  • New provider finding code: fails to compile until named in the exhaustive Record witness, then fails the classification guard test until placed in the waivable or intentionally-not-waivable set - silence is no longer a default.
  • Unknown blocker source at runtime: createHarnessBlocker throws loudly ('not registry-owned') rather than letting free-form drift serialize.
  • Old data: serialized blocker envelopes keep schemaVersion 1 semantics; the decision event schema remains v2 with the exclusive blockerEnvelope field.

Next-time guidance

  • Adding a new harness CLI: route its entrypoint through runHarnessCliBoundary with a source whose kind/id match a registered command, add the file and command ids to HARNESS_BLOCKER_CLI_INVENTORY, and let the inventory sensor police the shapes. Do not print prose and process.exit.
  • Suppressing the shared fallback: pass renderNonZero: false only if the file constructs and formats its own blockers; the sensor will fail otherwise. Prefer keeping the fallback.
  • Adding a provider finding code: add it to the provider's code union, name it in the exhaustive Record witness, classify it in exactly one of WAIVABLE_FINDING_CODES or INTENTIONALLY_NOT_WAIVABLE_FINDING_CODES, and let the guard tests tell you what is left. Remember the waiver offer is all-or-nothing per run - an unclassified code voids waivers entirely.
  • Adding a preparation blocker source: extend HARNESS_PREPARATION_SOURCE_IDS and name a producing site in the producer test in harness-blockers.test.ts, or do not add the id.
  • Writing remediations: key remediation ids on the specific repair (see telemetry_record_malformed and the documentation-code precedents); distinct ids survive deduplication, identical ids with divergent bodies confuse operators.
  • Quoting commands anywhere user-facing: use formatHarnessCommand from harness-blockers.ts; never re-implement shell quoting locally.
  • If a landed-change report check blocks delivery: regenerate the report after the final code edit so data-athena-report-diff-fingerprint matches bun scripts/landed-change-report-check.ts --base origin/main --print-fingerprint.

Comprehension quiz

Pass required: 8 of 10.

  1. Why does createHarnessBlocker re-validate blocker sources against registries at runtime when the TypeScript types already restrict them?

    1. Because runtime validation is faster than typechecking
    2. Because nothing typechecks scripts/, so the discriminated union is only a convention until checked at construction
    3. Because providers may send sources over the network
    4. To support JavaScript callers that bypass the types

    scripts/ is not part of a typechecked build surface, so a free-form source id would otherwise serialize silently; the constructor fails loudly on anything not registry-owned.

  2. What did V26-1274 change about delivery:documentation-check, delivery:telemetry-check/record, and pr:athena:record-proof?

    1. They were deleted and folded into pr:athena
    2. They were brought into the blocker contract and registered in HARNESS_BLOCKER_CLI_INVENTORY
    3. They were renamed to harness-prefixed commands
    4. Their exit codes were inverted to avoid process.exit

    The sensor comment explicitly excluding these three CLIs was removed; they now run inside runHarnessCliBoundary and appear in the inventory the static sensor walks.

  3. A file passes renderNonZero: false to runHarnessCliBoundary. What keeps it legitimate?

    1. Nothing; the flag always disables blocker rendering safely
    2. The file must contain a unit test covering the suppressed path
    3. It must also construct a conformant blocker via createHarnessBlocker, HarnessBlockedError, or formatHarnessBlockers, or the inventory sensor reports blocker-emission-missing
    4. It must register the suppression in HARNESS_BLOCKER_CLI_INVENTORY

    inspectRenderNonZeroSuppression fails any inventory file carrying the literal suppression without emitting its own blocker, because suppressing the shared fallback twice shipped prose-only failures.

  4. What is the stated limit of inspectRenderNonZeroSuppression?

    1. It only runs on CI, not locally
    2. It detects literal declarations only; runtime-computed suppressions and dataflow to the suppressed exit are invisible, and runtime shape stays owned by createHarnessBlocker
    3. It scans git history for prior violations
    4. It requires every file in the repo, not just inventory files

    The rule reads whole files for literals, like the other shape rules; following indirection or control flow would report drift it could not prove.

  5. Why does one unclassified finding code void waivers for an entire run?

    1. Because waivers expire when codes change
    2. Because waivableBlockedObligationIds uses an all-or-nothing every() check: every blocker on every blocked resolution must match WAIVABLE_FINDING_CODES, so one miss makes the offer impossible
    3. Because unclassified codes crash evaluateGateObligations
    4. Because waivers require manager approval proofs

    The waiver offer returns [] unless every blocked resolution's blockers are covered by the allowed-code lists; a single unknown code silently fails that predicate for the whole run.

  6. You add a new member to a provider's finding-code union. What happens under V26-1276's pins?

    1. Nothing until a waiver is attempted, then it is silently waived
    2. The exhaustive Record witness fails to compile until the code is named, then guard tests fail until it is classified as waivable or intentionally not waivable
    3. The code defaults to waivable for interactive humans
    4. The inventory sensor removes the provider from the registry

    Compile-time witnesses (Records keyed by the full union) force the new member to be enumerated, and the classification guard tests force it into exactly one set instead of defaulting to silence.

  7. An operator Ctrl-C interrupts a pr:athena delivery run mid-spine. What does the terminal show after V26-1284?

    1. A Node.js stack trace for SIGINT
    2. Only the prose phase summary, as before
    3. A delivery_run_interrupted blocker naming the interruption reason with a rerun-pr:athena remediation
    4. An harness_internal_error blocker with a reproduce command

    Interrupted runs now render a typed delivery_run_interrupted blocker so a signaled run never looks like a crash; harness_internal_error is reserved for genuinely unexpected exceptions.

  8. What distinguishes harness_usage_error from harness_internal_error?

    1. Usage errors exit 0; internal errors exit 1
    2. Usage errors cover malformed invocations and render supported flags as remediation; internal errors are unexpected exceptions rendering a stack detail and reproduce command
    3. Usage errors apply only to Convex functions
    4. There is no difference; both share one code

    A bad flag or malformed invocation is an expected outcome, not a crash; HarnessUsageError extends HarnessBlockedError so catch-all wrappers cannot reclassify it as an internal error.

  9. After the typed-blocker migration briefly lost provider-specific documentation remediation, how does the landed-change-report policy guide repair now (V26-1285)?

    1. With the generic repair-everything-delivery-documentation instruction only
    2. By telling the operator to delete docs/reports and rerun
    3. With a regenerate-landed-change-report remediation pointing at refreshing the report under docs/reports/ with a current diff fingerprint
    4. By opening a Linear issue automatically

    Each documentation finding code carries a typed remediation: compound-solution points at authoring docs/solutions/ notes; landed-change-report points at regenerating the report with a current fingerprint. The obligation-level remediation remains the fallback for structural codes.

  10. The delivery-documentation-check provider blocked this branch demanding a report fingerprint of cf37f29e.... When must a report's data-athena-report-diff-fingerprint be regenerated?

    1. Once, when the branch is created
    2. Only after merging to main
    3. After the final code and workflow edits land on the branch - rerun the fingerprint command and re-render the report so the attribute matches, since any deliverable-file change moves the hash
    4. Never; the fingerprint is fixed at authorship

    The fingerprint hashes the current deliverable diff (excluding docs/reports/, docs/solutions/, and other non-deliverable paths), so it only matches when regenerated after the last code edit - which is why review-loop changes require re-rendering the report.
