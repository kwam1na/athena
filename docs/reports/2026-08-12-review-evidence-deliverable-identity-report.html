Executive summary

Athena refuses to spend merge-grade validation on code no reviewer has approved. That rule is enforced by an obligation called review.green, whose evidence binds to the exact tree a reviewer looked at. The rule is right. Two side effects of how it was implemented were not, and both cost the previous delivery (PR #758) three extra full review rounds.

First, the cheap deterministic checks — a lint rule, a formatting rule — lived inside the expensive gate. So a two-line lint failure could only be discovered after three reviewers had already approved the tree, and fixing it invalidated all three approvals. Second, evidence bound to the raw Git tree, so committing the mandatory landed-change report (a document written after the code it describes) invalidated the approval of code it never touched.

This change puts the mechanical checks in front of review and makes that ordering structural rather than remembered, and it rebinds review evidence to a deliverable identity that ignores delivery narration and nothing else.

The problem, in plain language

Imagine a building inspector who signs off on a floor plan. The signature is only valid for the plan they actually read, which is correct: if you move a wall afterwards, the signature should not carry over. Athena implements that by hashing the whole set of files and binding the approval to the hash.

Two things went wrong with that arrangement.

The cheap inspection ran last. Checking that the drawing uses the right line weights needs no judgement at all, and costs almost nothing. But that check was bundled into the expensive post-approval stage. So the trivial defect surfaced only after three expert reviews were paid for, and correcting it voided them. In Athena's terms: lint:convex:changed ran only inside the heavy pr:athena provider, which harness-gate-admission will not start without current review evidence.

The hash counted the cover letter. Delivery requires a landed-change report and a solution note — documents describing the work, necessarily written after it. Because the hash covered every file, filing those documents changed the hash and voided the approval. The repo already knew better: isDeliverableFingerprintPath in scripts/delivery-diff-fingerprint.ts had excluded docs/reports/ and docs/solutions/ from what counts as a deliverable change for years. The evidence binding had simply never been told.

The mental model

The useful question is not "did the bytes change?" but "is this the thing the reviewer approved?" Those are different questions, and answering the second one with the first is what produced the friction.

Think of three concentric rings around a delivery:

  • Reviewed content — source, tests, configuration, harness scripts, generated artifacts. A reviewer's approval is about this ring. Any change to it invalidates the approval, including a comment-only edit.
  • Delivery narration — docs/reports/ and docs/solutions/. Written after the reviewed content, to explain it. Changing it does not change what was approved.
  • Everything about the base — base ref, base tip, merge base, worktree. Still bound exactly, because an approval of a diff against one base says nothing about another base.

The new identity, deliverable-tree/v1, is just a hash of the first ring plus an exact match on the third. The second ring is excluded — and only the second ring.

The second idea is even simpler: a check that needs no judgement must not be discoverable only after judgement has been paid for. Rather than documenting that ordering and hoping agents remember it, preparation now refuses to issue the receipt that review requires.

Before and after

Ordering of the deterministic checks

Before:

  1. pr:athena:prepare publishes a receipt
  2. harness:review-context names the candidate
  3. Reviewers review; harness:review-evidence records the approval
  4. pr:athena admits the heavy provider — and only here does lint:convex:changed run
  5. Lint fails on two lines; the fix changes the tree; every approval in step 3 is now stale

After:

  1. pr:athena:prepare runs the mechanical stage (pr:athena:mechanical) and publishes no receipt if it fails
  2. harness:review-context and gate admission both require a current receipt, so a mechanically-failing tree can never reach a reviewer
  3. Reviewers review a tree that has already passed every deterministic rule

What changed, and what deliberately did not

Changed

  • A mechanical stage runs inside pr:athena:prepare and is also available on its own as bun run pr:athena:mechanical.
  • Review evidence freshness compares a deliverable identity rather than the raw tree SHA, at both recording time and gate time.
  • The gate decision event carries the identity that authorized it.
  • Obligation records from an earlier identity are reported as superseded and skipped.

Deliberately unchanged

  • The preparation receipt still binds to the raw tree. A documentation commit still requires re-running prepare — which is cheap and deterministic. Only the expensive half was loosened.
  • Admission still requires an unchanged candidate across the whole run: before, immediately before spawning, and after the provider. That check compares the full raw candidate, not the deliverable identity.
  • The neutral set is narrower than the delivery fingerprint's. isDeliverableFingerprintPath also excludes _generated/, routeTree.gen.ts, graphify-out/, and artifacts/. Those stay inside the reviewed deliverable here: they are executable or gate-consumed content, and nothing in the identity re-derives them to prove they still match their reviewed sources.
  • Which obligations exist, the reviewer set, and the admission policy for unreviewed code — all explicitly out of scope for this ticket.
  • Tests, build, and typecheck stay in the heavy provider. The mechanical stage is lint-only on purpose, because it runs on every prepare.

Stated residual risk

docs/reports/ and docs/solutions/ compile into the Athena webapp's in-app docs bundle, so this does admit post-review edits to shipped content. Those paths keep live gate obligations (delivery:documentation-check, landed-report:check, compound:check), and any divergence between the reviewed raw tree and the current one stays visible in the decision event. That trade is recorded in the solution note rather than left implicit.

Guidance for next time

  • Prepare, then review, then validate. pr:athena:prepare now fails on a deterministic lint error and publishes no receipt. If preparation blocks, fix and prepare again — never dispatch reviewers against a tree that has not been prepared.
  • A documentation commit no longer costs a review round. Commit the landed-change report and the solution note, re-run bun run pr:athena:prepare, and continue. Any other edit — including a comment — still requires a complete re-review.
  • Still write the report before the final review loop. The identity removes the re-review cost of that ordering; it does not license documenting after merge.
  • Copy the candidate from harness:review-context verbatim into the review manifest, including deliverableTreeSha and identityVersion. The recorder rejects a manifest that names no current identity.
  • If you ever version the identity again, give old records a distinct non-blocking diagnostic in the same change and test the transition. A blocking diagnostic would strand every worktree holding an older record.
  • Run bun run pr:athena:mechanical directly for a fast answer to "would the deterministic rules stop me?" without preparing.

Comprehension quiz

Ten questions; eight correct to pass.

  1. Why could a two-line lint failure invalidate three reviewer approvals before this change?

    1. Reviewers were required to run lint themselves and had skipped it.
    2. The lint ran only inside the heavy provider, which will not start without recorded review evidence — so the failure surfaced after the review, and the fix changed the approved tree.
    3. The lint rule was newly added in the same branch.
    4. Evidence expired on a timer that the lint run exceeded.

    The gate deliberately refuses heavy validation for unreviewed code, and the deterministic checks were on the wrong side of that gate.

  2. What makes the new ordering structural rather than merely documented?

    1. A pre-push hook rejects the push when lint fails.
    2. The delivery skills instruct agents to run lint first.
    3. Preparation publishes no receipt when the mechanical stage fails, and both review-context and gate admission require a current receipt.
    4. CI runs the lint before the review job is scheduled.

    The receipt is the shared precondition, so removing it removes both the path to review and the path to admission.

  3. Which paths does deliverable-tree/v1 exclude from the reviewed deliverable?

    1. docs/reports/ and docs/solutions/, and nothing else.
    2. Everything isDeliverableFingerprintPath excludes.
    3. All Markdown and HTML files anywhere in the repo.
    4. All generated artifacts, since they are derived from reviewed sources.

    The neutral set is deliberately narrower than the delivery fingerprint's, which answers a different question.

  4. Why do generated artifacts such as _generated/ stay inside the reviewed deliverable, even though the delivery fingerprint excludes them?

    1. They change too rarely for the exclusion to be worth it.
    2. Git cannot compute a stable hash for generated files.
    3. They are executable or gate-consumed content, and nothing in the identity re-derives them to prove they still match their reviewed sources.
    4. Reviewers are required to read them line by line.

    Excluding them would assume a derivation the identity never checks.

  5. A reviewer approves the tree. You then fix a typo in a code comment. What happens?

    1. Nothing; comments are not reviewable content.
    2. The deliverable identity changes, the evidence goes stale, and a complete re-review is required.
    3. The evidence survives but the decision event records a warning.
    4. The gate prompts for a human waiver automatically.

    The identity hashes blob SHAs, so any content change to a non-neutral path moves it. The anti-tamper property is unchanged.

  6. After the final review pass you commit the landed-change report. What must you do before running bun run pr:athena?

    1. Re-run the complete reviewer set against the new tree.
    2. Re-run bun run pr:athena:prepare; the receipt still binds to the raw tree, but the recorded review does not.
    3. Nothing — both the receipt and the evidence ignore that path.
    4. Record a fresh evidence manifest with the new tree SHA.

    Only the expensive half was loosened. Preparation is cheap and deterministic, so it kept the strictest binding.

  7. How does a past authorization stay interpretable after the identity rule changed?

    1. A new identity_change event type is emitted.
    2. The old records are rewritten into the new format on read.
    3. The existing gate decision event carries both the raw tree and the deliverable identity with its version.
    4. The identity version is inferred from the record's timestamp.

    The ticket explicitly required reusing the existing event and adding no new event type.

  8. What happens to an obligation record written before the deliverable identity existed?

    1. It is upgraded in place and continues to satisfy the obligation.
    2. It is reported as a malformed record, which blocks the gate.
    3. It is reported as a superseded record: it satisfies nothing and blocks nothing.
    4. It is deleted automatically the first time it is discovered.

    Treating a version transition as tampering would have blocked the gate in every worktree holding an older record.

  9. Why is the mechanical stage limited to per-package lint rather than also running tests and typecheck?

    1. Tests and typecheck are not deterministic.
    2. They are already covered by the pre-push hook.
    3. The stage runs on every prepare, so it must stay cheap; the expensive checks remain in the heavy provider.
    4. They cannot be selected from the validation map.

    Preparation is re-run often, including after every review fix, so minutes spent there would be paid repeatedly.

  10. Why does the freshness comparison require a known identity version and a non-empty digest on both sides?

    1. To let records from any future version continue to match.
    2. So a record with absent identity fields can never match by comparing two undefined values; it must fail closed as stale.
    3. Because the digest is optional for waiver records.
    4. To keep the comparison constant-time.

    An equality check over missing fields is the classic way a fail-closed rule quietly becomes fail-open.
