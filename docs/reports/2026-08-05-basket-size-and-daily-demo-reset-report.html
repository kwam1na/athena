A number you can check, and a reset that waits for midnight

Reports gains Transactions and Units per sale — a basket size that refuses to state itself until the evidence covers the whole period. Getting there required a fold-version bump to 5, because version 4 stamped history without persisting the field it added. Alongside it, the shared demo stops wiping visitors every hour and resets once, at midnight.

Executive Summary

Three strands ship together because they share a seam: what a reporting surface is allowed to claim when its evidence is incomplete.

  • Basket size. reportDay now records how many completed POS transactions a day settled. Periods sum it, and unitsPerTransaction divides units by transactions — but only when every day in the period contributes a count. Otherwise it returns null and the tile says “3 of 7 days closed” rather than a number.
  • A version nobody had seen. The field first shipped as fold version 4 and was silently dropped on write. Because staleness is foldVersion !== REPORTS_FOLD_VERSION, correcting the write could not reach the days version 4 had already stamped. Version 5 is the same field, actually persisted.
  • Demo reset cadence. The hourly restore became shared-demo-daily-restore at midnight. A separate shared-demo-hourly-provision-heal keeps the old rhythm for the one thing that genuinely needed it.

A fourth strand is pure extraction: the scroll-and-focus restoration built for the units-moved sheet is now three shared modules, adopted by Daily Operations and Daily Close.

Problem and Context

Average basket size is a ratio, and a ratio is only as honest as the alignment of its two inputs. In Athena those inputs come from different places at different times:

InputSourceWhen it becomes true
Units soldFolded from reportFact rowsThe instant a sale lands
Transaction countSettled by the register closeEnd of day, at close

Divide a whole-period numerator by a closed-days-only denominator and the result is not slightly high — on a day still trading it is arbitrarily high, and it renders identically to a real measurement. That is the failure this change is built to make impossible.

The second problem was operational. The shared demo reset every hour, on the hour. A visitor mid-way through exploring could lose their work to a cron that fired while they were reading. But the hourly rhythm was load-bearing for something else: SHARED_DEMO_BASELINE_VERSION lives in code and is compared against a version persisted in sharedDemoRestoreState, and while the persisted value trails, admission rejects every visitor. The deploy script migrates it, but if that step fails, a scheduled run is the only recovery.

Mental Model

Absent means unknown, never zero. Every new field here is v.optional, and every read treats absence as “I cannot answer” rather than “nothing happened”. A closed day with no sales stores 0; a day that predates the field stores nothing. Those are different facts and the code never conflates them.

Coverage travels with the number. transactionCount is meaningless without transactionCoveredDayCount, so the pair is written together and read together. Both the Transactions tile and the Units-per-sale tile go through the same helper, settledTransactionCount — because a stated count sitting beside a withheld ratio derived from it would read as a bug.

Provisioning and restoring are different risks. Provisioning is idempotent and touches no visitor data. Restoring wipes it. Once you see them as two jobs rather than one, the cadence question answers itself: the safe half stays hourly, the destructive half moves to midnight.

Before and After

Counting transactions

A transaction cannot be summed the way money is — the same transaction emits facts more than once over its life. Two paths compute it, and they must agree:

PathRule
foldDay (whole-day rebuild)Walk the facts already in hand; distinct pos sourceIds that sold and were not voided. On a closed day the close’s settled figure wins, falling back to the derived count when the summary carries none.
ingest (open day, incremental)A delta against what was already on record: first sale +1, void of a counted transaction −1, sale-and-void in one batch nets zero, further facts on a counted transaction change nothing.

Payment facts are unusable for this: they are one per allocation, so split tender would count a single sale twice. sourceId on a pos-domain fact is the transaction id, which makes the count exact and free.

What Changed, and What Did Not

Changed

  • Schema: three optional fields — reportDay.transactionCount, and transactionCount / transactionCoveredDayCount on the period snapshot. Plus dayClosed on weekly lineage.
  • Overview tiles: Refunds removed; Transactions and Units per sale added. The “Open transactions” link moved off Net sales onto Transactions, beside what it describes.
  • Weekly “View EOD Review” link: lastClosedScheduledDate replaces finalScheduledDate. The old rule took the last included scheduled date — routinely today, open, never closed — producing a link into a review that never happened.
  • Shared demo: live SKU identity is carried inline on getLiveOperatingDay and listLiveSkuStock, which is what lets a POS quick-add SKU be named at all. The client-side catalogue-search fixture is deleted; the demo now searches the store’s real catalogue and re-keys results into the story id space.
  • Sheet return: one sheetReturn search param app-wide, replacing the sheet-specific unitsFocus/unitsScroll pair.

Deliberately unchanged

  • Refunds data is untouched. refundsMinor remains in the contract, the fold and the snapshot. Only the two tiles were removed — refunds are no longer reachable from the overview and SKU-detail surfaces, which is a presentation decision, not a data one.
  • "hourly" is still a valid restoreSource. Nothing writes it any more; it is retained so historical audit rows continue to validate. A grep hourly will still hit.
  • livePosTransactionCount is not dead code. It remains reachable for day rows folded before version 5 and must not be deleted until the repair has completed everywhere.

Operational Guidance

  • The repair is a required rollout step, not a cleanup. Clean days never refold on their own. Without it, the metric only ever covers days closed after the deploy, and every historical period shows partial coverage instead of a basket size.
  • Run reports/foldVersionRepair:markStaleFoldVersionDays per store, for the stores named by the sweep allowlist env var. Confirm with countStaleFoldVersionDays before considering the rollout complete.
  • Adding any field to DayFoldResult is a two-file edit. The fold result type and the explicit day-document literal in foldAndReplaceDay. Assert on the persisted row, not the fold return value — a fold-level unit test passes happily while the write drops the field.
  • If a version bump has already shipped with a broken write, the fix needs a higher number. Re-running the repair at the same version is a no-op by construction.
  • If the deploy’s shared-demo provisioning step fails, shared-demo-hourly-provision-heal repairs the baseline row within the hour; the manual command is npx convex run sharedDemo/scheduledRestore:verifyDailyRestoreNow '{}'.
  • The midnight cron is coupled to the demo store’s timezone. 0 0 * * * is correct only while that store is Africa/Accra. Nothing in code enforces this; moving the demo store means moving the cron hour.

Comprehension quiz

Pass required: 8 of 10.

  1. Why did REPORTS_FOLD_VERSION go from 3 to 5 with no working version 4?

    1. Version 4 was reserved for a concurrent branch.
    2. Version 4 stamped days without persisting the new field, and since staleness is foldVersion !== REPORTS_FOLD_VERSION, those days could only be reclaimed by a version they had not yet seen.
    3. Convex requires odd version numbers for schema migrations.
    4. Version 4 was rolled back before reaching production.

    Once history carries 4, it matches the constant and is invisible to the repair forever. Correcting the write is necessary but not sufficient — the number itself has to move.

  2. What mechanism caused version 4 to drop the field silently?

    1. foldAndReplaceDay builds an explicit day document field by field rather than spreading the fold result, and the schema field is optional, so an omitted key produces no type error.
    2. The Convex validator stripped unknown fields at write time.
    3. The sweeper batched writes and lost the last one.
    4. The field was declared after the document was constructed.

    This is why a fold-level unit test passes while the write drops the field: the fold returns the count correctly. Only an assertion on the persisted row catches it.

  3. Why does unitsPerTransaction return null instead of dividing when coverage is partial?

    1. Division by zero risk.
    2. Convex queries cannot return floats.
    3. Units are folded from facts the instant a sale lands while transactions settle only at close, so a whole-period numerator over a closed-days-only denominator overstates the basket — arbitrarily so on a day still trading.
    4. The UI has no format for fractional baskets.

    A withheld number is recoverable; a confidently wrong one is not. The tile shows the coverage gap instead.

  4. Why do the Transactions tile and the Units-per-sale tile read through the same helper?

    1. To share a memoization cache.
    2. So they can never disagree about whether the evidence is whole — a stated count beside a withheld ratio derived from it would read as a bug.
    3. Because the contract exports only one function.
    4. To keep the tiles the same width.

    Two independent coverage checks would eventually drift. One rule, two readers.

  5. Why can’t payment facts be used to count transactions?

    1. They are written asynchronously after the sale.
    2. They lack a sourceId.
    3. They are emitted one per allocation, so a split-tender sale would be counted twice.
    4. They are quarantined by default.

    sourceId on a pos-domain fact is the transaction id, which makes that lane exact and free.

  6. In the incremental ingest path, why is findRecordedPosTransactions queried before any insert?

    1. To take a write lock on the day row.
    2. Afterwards the batch’s own newly inserted rows would look like history, so every new transaction would read as already counted.
    3. Because Convex forbids reads after writes in a mutation.
    4. To warm the index cache.

    The query has to describe the day as it was, not as the batch is leaving it.

  7. An open day already carries no transactionCount. A new batch arrives with one sale. What does ingest write?

    1. 1 — start counting from here.
    2. 0 — the day is not closed.
    3. Nothing; the field stays absent, because the base is unknown and any number written would be a guess presented as a measurement.
    4. It throws, forcing a full refold.

    Same rule as skuDayRowCount. A day opened after the field landed starts from zero and accumulates honestly; a pre-existing day waits for the repair.

  8. Why did the destructive demo reset move to midnight while a separate job stayed hourly?

    1. Convex rate-limits daily crons.
    2. The restore lease cannot be held for an hour.
    3. Provisioning is idempotent and begins no restore lease, so it can heal a stale baseline hourly without wiping visitor activity — which is exactly what the cadence change existed to stop.
    4. Midnight is the only hour with spare capacity.

    While the persisted baseline trails the constant in code, admission rejects every visitor. Splitting the jobs keeps recovery at an hour while the reset becomes daily.

  9. Why is the idempotency bucket exactly one reset cycle wide?

    1. To match the Convex scheduler’s retry window.
    2. Narrower and a retried firing restores a second time; wider and a genuine next-day reset is swallowed as already-done.
    3. So audit rows sort chronologically.
    4. To keep the key under the index size limit.

    Hence daily:<UTC day number> over an 86,400,000 ms cycle.

  10. Why was dayClosed added rather than deriving “closed” from dayStatus !== "open"?

    1. dayStatus is not indexed.
    2. The sweeper folds a day to provisional on its own, so a day can leave open having never been closed — dayClosed tracks an actual EOD close on record.
    3. dayStatus is optional on legacy rows.
    4. The weekly view does not load dayStatus.

    It uses the same evidence computeWeeklyVariancePosture counts: the presence of closeVarianceMinor. Rows folded before the field carry none, and absent means unknown, so the fallback is the old approximation rather than a false “not closed”.
