Executive summary

This delivery candidate adds a temporary, one-terminal diagnostic around Athena's existing POS receipt print flow. It does not attempt another print fix. It records enough branch, document, return, and popup-lifecycle evidence to compare attempts with versus without the matching rejection using the telemetry rail already deployed in production.

Detailed capture is restricted to the affected terminal's known browser fingerprint. The exact known rejection can receive a recent attempt snapshot when correlation is unambiguous. No Convex schema, backend query, receipt caller, product UI, or print condition changes are included.

Why evidence had to come before another fix

Production repeatedly reported: Failed to execute 'print' on 'Window': The provided callback is no longer runnable. Two earlier lifecycle fixes continued to fail in the field: print-once/closed-window guards in PR #701 and afterprint-based teardown in PR #718.

Backend inspection found a persistent incident cluster on one affected terminal after POS completion across multiple deployed builds. The existing rows had a stack and fingerprint, but not the invocation branch, ready state, event order, return classification, or stable attempt ID required to choose a fix. Customer-linked counts, timings, and deployment history remain in the access-controlled incident record rather than this public report.

Mental model: a flight recorder, not an autopilot

The helper is a small flight recorder attached to an existing print attempt. usePrint writes lifecycle checkpoints into one in-memory slot. Finalization emits one compact baseline through the existing offline buffer when capacity permits. The global rejection listener asks for the same snapshot only when the browser error exactly matches and one recent candidate is safe to name.

The recorder observes; it does not steer. The suspicious one-second fallback still invokes print only while readyState is not complete. Existing 250 ms afterprint close timing, 60-second fallback cleanup, print-once guards, and all receipt callers remain authoritative and unchanged.

Before and after data flow

Before: usePrint opened, wrote, printed, and closed a popup. An asynchronous browser failure reached the global unhandled-rejection listener as a generic error, entered the local buffer, drained to Convex, and appeared in the backend export without an attempt context.

After, on the affected terminal only: an attempt begins before window.open; usePrint records load versus one-second fallback, readyState, print invocation and return, safe return type, ordered beforeprint/afterprint/beforeunload/unload/cleanup checkpoints, closed state, timing, and causal completion reason. When the baseline is emitted, a stable printAttemptId joins it to the matching rejection; correlation metadata remains available in memory when buffer pressure skips the baseline.

  • A second attempt inside the 60-second retention window makes correlation ambiguous instead of assigning the error to the wrong print.
  • An exact target rejection without a recent attempt receives a no-candidate marker.
  • Unrelated errors and all non-target terminals remain on the generic path.

How the browser lifecycle is recorded safely

window.close may dispatch unload synchronously, queue it, or omit it. The implementation carries the initiating reason—afterprint, fallback cleanup, or a throw—across close. Unload appends its checkpoints and finalizes with that pending reason. A one-second diagnostic-only grace timer finalizes with the same reason when unload never arrives.

Reference return values are recorded as not_inspected. Reading an arbitrary .then property could execute a getter or proxy trap and perturb the race under observation. Primitive and null returns can be classified without property access.

Failure boundaries and deliberate tradeoffs

  • The fingerprint gate is a rollout selector, not authorization. Backend analysis must still restrict rows to the known affected store and terminal association.
  • Metadata is limited to primitive values, no more than 20 keys, and a lifecycle event string no longer than 300 characters. Receipt, order, customer, payment, and function-source content never enter the helper.
  • At 150 buffered events, this canary stops consuming buffer capacity, leaving headroom that other telemetry may still use. The in-memory candidate can still correlate an exact rejection.
  • Duplicate global listeners may produce duplicate raw error rows. Analysis must report raw rows separately and deduplicate by attempt ID.
  • Object-window unit tests do not reproduce Chromium callback ownership or deferred printing. The production canary is the decisive sensor.
  • The canary cannot observe physical printer output, distinguish user cancellation from a completed print, or classify failure signatures other than the exact targeted rejection.

What changed and what intentionally did not

Changed: one temporary attempt-state helper, print lifecycle checkpoints in usePrint, exact-error metadata enrichment in the existing telemetry drain, focused tests, the approved plan artifacts, generated repository indexes, and a reusable diagnostic-pattern note.

Intentionally unchanged: print branching and timers, receipt generation and callers, telemetry transport and backend persistence, Convex schema and indexes, terminal authorization, UI, expense flows, and rejection handling. The error remains unhandled and visible; correlation only adds evidence.
