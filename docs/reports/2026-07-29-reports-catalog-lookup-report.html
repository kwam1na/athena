Executive Summary

Reports can now start a catalog lookup from Overview or Items, select an exact SKU variant, and enter the existing SKU-detail route with the originating period and tab retained for the return path.

The change also makes the product table more truthful and usable: canonical product names win over incomplete denormalized SKU names, Items uses cursor pagination while detail paginates its already-bounded range client-side, and freshness is disclosed without changing report facts or metric calculations. Overview materialization now carries a compatible yesterday snapshot.

Problem and context

Delivery candidate: make catalog discovery a safe path into existing report detail without changing report facts or metrics.

Before: report detail was primarily reached from an activity row, and a blank productSku.productName could render the SKU code as the product name.

Before: navigation could lose the visible reporting window and detail used two independent date controls.

Mental model: discovery is not reporting

Treat the generic inventory search as the catalog directory and the reports detail route as the activity ledger. Search finds an identity; the existing report query answers what that identity did during a selected period.

That separation means a catalog SKU with no activity remains selectable. Its destination shows the established empty state instead of silently hiding the SKU or inventing report data.

Overview or Items period → generic store-scoped SKU search → exact productSkuId → existing detail route(range + origin)

No new report search backend. No report filtering. No fact or rollup mutation.

Before and after

  • Before: report detail was primarily reached from an activity row, and a blank productSku.productName could render the SKU code as the product name.
  • After: both primary tabs offer grouped name/SKU/barcode lookup; the backend resolves name as product.name → legacy SKU name → SKU code → document ID.
  • Before: navigation could lose the visible reporting window and detail used two independent date controls.
  • After: each route maps its selected period to an inclusive detail range, stores the origin in URL state, and detail uses one atomic range control.

Behavior boundaries

  • Existing generic search keeps exact SKU and barcode ranking; the Reports UI groups variants without client-side re-ranking.
  • Lookup text and results are transient. They are cleared after navigation and are not shareable report state.
  • Reports remain read-only and retain their existing access checks. The generic search authorization contract is not narrowed or replaced here.
  • Older overview documents without yesterday receive an empty snapshot until the regular sweeper refreshes them.

Read-budget and risk notes

Items now pages at 10 rows with its existing backend cursor. Canonical product naming adds a linked product read to each displayed SKU, bounded at two reads per row and guarded against cross-store mismatches: a linked product from a different store is ignored and the legacy fallback resumes. Freshness comes from the already-existing overview singleton rather than a separate client query.

SKU detail and day views first fetch their bounded report range (at most 92 day documents) and then paginate that in memory for presentation; they do not introduce a new backend cursor. A known Items cursor-design caveat remains: a sort-key tie group larger than the fixed tie-boundary overfetch can make a later page appear terminal while tied rows remain. This delivery preserves that query shape; current coverage does not mitigate that case.

Worktree bootstrap guard

Linked worktrees now require an internal Git marker created by scripts/worktree-manager.sh setup-env. Both pre-commit and pre-push check that marker before changing directories or running other hooks, so an unbootstrapped worktree fails with the exact setup command instead of reaching delivery with missing environment setup.

The primary checkout remains exempt. The manager writes the marker only after it copies or preserves local environment files and installs locked dependencies, and its tests cover primary-checkout allowance, linked-worktree rejection, marker acceptance, hook order, and setup idempotence.
