Executive summary

Athena requires a review loop before the merge gate, and that loop earns its place — it catches edge cases nothing else does. But reviewers regularly propose changes that are correct and out of scope: "also handle X", "make this configurable", "generalize this helper". The merge gate demanded zero unresolved actionable findings, and deferral was not a recognized way to resolve one. So the only legal move was to implement the suggestion, and the delivery quietly grew.

This change gives every finding a scope — is fixing it part of delivering this ticket, or is it expansion beyond it? Critical defects are unaffected: P0 and P1 always block, whatever their scope. Lower-severity expansion work can now be resolved the honest way, by filing a follow-up ticket, and the harness refuses to accept a deferral that has no ticket id attached.

Measuring whether that works needs data the repo did not keep. Every record of how a delivery actually ran — its duration, its review iterations, its cost — lived in a gitignored file, a Git-private per-worktree directory, or /tmp. Since each ticket starts in a fresh worktree, none of it survived. The second half of this change adds telemetry/delivery-runs/: a small tracked record per run, so the trend outlives the worktree that produced it.

The problem

A gate that counts findings turns every good idea into scope

Findings carried two axes: severity (P0-P3, "how urgent") and autofix_class ("who acts next"). Neither answers "does fixing this belong in this delivery?". There was exactly one escape hatch — pre_existing — and it only covers untouched code, not a good suggestion about code the diff genuinely changed.

Meanwhile the evidence recorder rejected any actionable finding whose disposition was not resolved or pre_existing, and the execute loop treated unresolved actionable findings as blocking. A valid P2 saying "this should also be configurable" had no disposition that satisfied the gate except being built. And because each fix produced fresh diff for the next round to review, the loop could ratchet: more scope inviting more scope, with no convergence definition beyond "every reviewer approves".

Nothing remembered how a delivery ran

The delivery-run ledger is gitignored and overwritten every run. Its companion baseline.json was read by the scorecard but written by nothing, and the ledger writer's history option had no caller — dead code describing a feature that did not exist. Obligation records live under .git/codex/, which for a linked worktree resolves inside that worktree's private directory and is never pushed. Reviewer findings live in /tmp and are reaped.

The practical consequence: "is the review loop getting more expensive?" was unanswerable, and the iteration counts the workflow posts to Linear existed nowhere in the repo.

The mental model

Think of a finding as answering three questions, not two. How urgent is it? is severity. Who acts next? is routing. The new question is whose job is it? — this delivery's, or a future one's.

Scope has three values. in_contract means the delivery is incomplete without the fix; every defect in behavior the diff ships lands here. adjacent means the fix hardens the changed code beyond what was promised. expansion means the fix grows the delivery — new capability, generality, configurability nobody asked for.

Only a narrow slice may be deferred: P2/P3, classified expansion, with a concrete fix proposed. Two guardrails keep that honest. P0 and P1 block regardless of scope, because shipped breakage is always the delivery's job. And deferral is not deletion: the finding is only resolved once a follow-up ticket exists, and the recorder rejects a deferral whose issue id is missing.

For telemetry, the model is the one the repo already uses for the landed-change report and the solution note: an artifact that describes a delivery must not count as part of the delivery it describes. Otherwise writing it invalidates the review evidence it reports on. That is why telemetry/delivery-runs/ is registered review-neutral and fingerprint-neutral — the same exemption, for the same reason.

What changed

Scope discipline in the review loop

Findings carry scope, proposed by personas and finalized by synthesis, judged against a delivery contract passed into the review. On disagreement synthesis keeps the more in-contract classification. Deferral candidates in externalizing modes pass an independent scope check before deferral is confirmed, because the orchestrator that wrote the code should not adjudicate its own scope unchallenged. Confirmed deferrals are reported in their own section and excluded from the verdict, exactly as pre-existing findings already were.

Telemetry, and a durable home for it

The final manifest carries iteration count, finding counts by severity, deferral facts, and a review cost. Cost is deliberately agent-harness agnostic: it names its own unit and the platform that reported it, is never converted between units, and the run summary withholds a delta when the previous run metered differently. Records land in telemetry/delivery-runs/, one file per run named by timestamp and branch so parallel worktrees never conflict.

Enforcement sized to the delivery

A telemetry.recorded obligation and a CI check require a record whose fingerprint matches the current deliverable diff — but only at or above 150 changed source lines, the same threshold the solution-note sensor uses. An interactive human may waive it; an agent cannot. Making that waiver work exposed a latent bug worth naming: waivers were only consulted on the historical-evidence path, so humanWaiverAllowed was silently inert on live obligations.

Guidance for the next delivery

  • When a reviewer proposes something good but out of contract, classify it rather than arguing about it. If it is P2/P3 expansion, file the follow-up ticket and record the id — the gate will accept that and reject silence.
  • Never reach for scope to soften a real defect. P0 and P1 block regardless, and inflating or deflating severity to route around that is the one failure mode this design cannot catch for you.
  • Record telemetry after the gate passes, never mid-run: the gate proves the tree it validated, and a mid-run tracked write invalidates that proof against its own run.
  • If review-loop edits change the deliverable after you recorded, the record is stale — re-run and re-record, the same way a stale report is regenerated.
  • When adding a registry flag, check that the code honoring it runs on every path the registry can select. Test the cross-product, not the flag.

Comprehension quiz

Ten questions; eight correct to pass.

  1. Before this change, why did a valid "this should also be configurable" finding tend to grow the delivery?

    1. Reviewers were instructed to expand scope when in doubt.
    2. The merge gate required zero unresolved actionable findings and deferral was not a recognized resolution, so implementing it was the only legal disposition.
    3. The gate had no way to detect the finding at all.
    4. Findings were always auto-applied by the fixer.

    A gate that counts unresolved findings without a disposition for out-of-contract work leaves implementing the suggestion as the only legal move, so good ideas silently become scope.

  2. Which findings may be deferred?

    1. Any finding the agent judges unimportant.
    2. Any finding classified expansion.
    3. P2/P3 findings classified expansion with a concrete proposed fix, once a scope check confirms them.
    4. Only findings in untouched code.

    Deferral is narrow on purpose: only lower-severity work whose fix grows the delivery beyond its contract, and only once a scope check confirms it.

  3. A P1 defect is classified expansion. What happens?

    1. It is deferred, since scope outranks severity.
    2. It blocks. P0 and P1 block regardless of scope; the classification is recorded but never defers them.
    3. It becomes advisory.
    4. The gate asks the user to choose.

    Severity and scope are independent axes with one hard interaction. Newly shipped breakage is always the delivery's job, so no scope classification defers it.

  4. What makes a deferral "resolved" as far as the evidence recorder is concerned?

    1. Marking it deferred in the manifest.
    2. A deferred disposition carrying the filed follow-up issue id, on an actionable, non-blocking finding.
    3. A reviewer agreeing in prose.
    4. Nothing — deferrals are never recorded.

    The harness cannot verify the work was really filed, but it can refuse a deferral that names nothing — so deferral degrades into a ticket, never into silence.

  5. Why is telemetry/delivery-runs/ registered review-neutral and fingerprint-neutral?

    1. To keep it out of code review for convenience.
    2. Otherwise recording a run would invalidate the review evidence and stale the report for the very run it describes.
    3. Because it is generated code.
    4. Because CI cannot read it otherwise.

    The record describes a run that already happened. If it counted as reviewed content, writing it would invalidate the very evidence and report it describes.

  6. Why did the cost trend need a tracked corpus rather than the existing ledger?

    1. The ledger format was too large to keep.
    2. The ledger is gitignored and per-worktree, and every ticket starts in a fresh worktree, so its baseline is always empty on a first run.
    3. The ledger is written only in CI.
    4. The scorecard cannot read JSON.

    The ledger is gitignored and lives in one worktree, and every ticket starts in a fresh one, so its baseline is empty on a first run and can never span deliveries.

  7. Two runs report cost in different units. What does the run summary print?

    1. A delta computed after converting units.
    2. No delta, and a note that the last passing run metered in the other unit.
    3. A delta with a warning.
    4. Nothing at all.

    Different platforms meter different work, so a cross-unit subtraction would produce a number with no meaning. Withholding the delta is more honest than computing one.

  8. When is a telemetry record demanded, and of whom?

    1. Every change, from everyone, with no waiver.
    2. At or above 150 changed source lines; an interactive human may waive it, an agent may not.
    3. Only in CI, never locally.
    4. Only when a reviewer asks for one.

    The artifact scales with the delivery, matching the solution-note threshold, and the waiver exists for the population the obligation is not aimed at.

  9. Why must delivery:telemetry-record run after the gate rather than inside it?

    1. It is slower than the gate.
    2. The gate records a proof over the tree it validated, so writing a tracked file mid-run would invalidate that proof against its own run.
    3. The ledger is only readable after CI.
    4. Git refuses writes during the gate.

    The gate proves the tree it validated. Writing a tracked file mid-run changes that tree, invalidating the proof against the very run that produced it.

  10. Why was humanWaiverAllowed silently inert on live obligations?

    1. The registry validator rejected it.
    2. Live obligations cannot be blocked.
    3. The live evaluator was never passed the records or execution context a waiver needs, and no layer reported the mismatch — the block looked identical to a declined waiver.
    4. Waivers expired before evaluation.

    The live evaluator was never passed the records or execution context a waiver needs, and a block from an unconsulted waiver is indistinguishable from a declined one.
