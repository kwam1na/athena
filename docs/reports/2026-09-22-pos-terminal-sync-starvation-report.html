Executive summary

A POS terminal could stop uploading events forever while reporting itself healthy. The background drain read only the oldest 250 local events; if none of those 250 happened to be uploadable, the drain concluded there was nothing to do and never looked further. The queue behind that window grew without bound and no signal ever said so.

This delivery fixes the starvation by paging forward until it finds a candidate or reaches the end of the log, stops mislabelling register-less expense events as activity-reportable, repairs the review-event count that the operator health surface reads, and adds a schema round-trip so a terminal can hand back a read-only sample of its upload pages for diagnosis.

The server-settled review recovery path is deliberately not part of this change. It was written and reviewed, but review established that no client could reach it, so it was removed rather than shipped as dead code. V26-2087's "converge without manual intervention" criterion is therefore carried entirely by V26-2114, and a reviewed implementation is preserved at commit d5681c5e.

This code is unusual in one respect: it was deployed to production from a local unpushed branch on 2026-09-17 and has been running ever since. Production data already carries the field it adds. Main lacked the commit, so deploying main would have failed schema validation and reverted a live fix. This PR reconciles main to production, with every gate re-run from scratch rather than trusting that history.

The problem in plain language

The POS is local-first. Every sale, refund and drawer movement is written to an IndexedDB event log on the terminal, and a background worker drains that log to the server. The terminal is usable whether or not the network is.

The drain worked in pages of 250 events, ordered oldest first. Each cycle it asked the local store for the first 250 events, filtered them down to the ones actually worth uploading, and uploaded those. If the filter produced nothing, the cycle ended.

The unstated assumption is that if there is anything to upload, some of it will be in the oldest 250. That holds right up until 250 consecutive non-uploadable events accumulate at the head of the log. Then the drain reads the same dead 250 events on every cycle, forever, while real sales pile up behind them. Nothing errors. The terminal reports itself idle, because from its own point of view it has nothing to do.

Expense events recorded outside a register session made that head-block easy to reach. They were marked as pending activity reports even though they have no register session to report activity against, so they looked like work the drain should care about, were counted as pending, and never cleared.

A second, quieter failure: the operator-facing terminal health surface reports how many events are sitting in review. That count was read from a debug field the runtime published, and if the runtime had published a stale zero while review samples were in fact present, the operator saw zero. A zero reads as "nothing wrong here", which is the most expensive thing a broken counter can say.

Mental model

Think of the local event log as a conveyor belt with a 250-item inspection window at the front. The drain looks only at what is inside the window. It never moves the window; it assumes that if the belt has anything worth shipping, some of it is on screen.

Put 250 items on the belt that the inspector is required to ignore, and the belt jams. Not because anything broke — because the inspector correctly concluded that everything it can see is fine, and it can only see the jam.

The fix is not a bigger window. A bigger window just moves the number at which the jam happens. The fix is to let the window slide: keep advancing it until either something worth shipping appears or the belt genuinely ends. A short page (fewer than 250 events) is the end-of-belt signal.

Before and after

Upload drain

Before
One read of the oldest 250 events per cycle. No candidates in that page means no work this cycle, and the same page is re-read next cycle. Unbounded starvation, reported as idle.
After
Page forward by afterSequence until a page contains a drain or activity candidate, or the page comes back short. A continuation that fails to advance the sequence throws rather than looping silently.

Expense events without a register session

Before
Given an initial activity state of pending purely on event type, so they permanently occupied the head of the log as work that could never clear.
After
Expense-typed events appended without a localRegisterSessionId are given no activity state and are excluded from the activity-candidate predicate, on the same condition in both places so the two decisions cannot drift apart.

Review-event count on the health surface

Before
Read from the published debug counter alone.
After
The maximum of the debug counter, the events actually in needs_review, and the number of published review diagnostic samples. Any one source seeing review work is enough; a stale zero can no longer mask the other two.

Upload page diagnostics

Before
No way to ask a stuck terminal what its upload pages actually contained, short of physical access.
After
A bounded, read-only sample travels back on the recovery command acknowledgement. The collector reads at most 2 pages of 250 events per terminal id in scope and excludes review events; the service then rejects any acknowledgement carrying more than 4 pages, an event page over 250, a page index other than 0 or 1, or a string over 160 characters. Those bounds reject rather than truncate, and they live in the service, not the shared validator, which pins the payload shape plus the 250 page size and includeReviewEvents: false literals. Collecting the sample changes and retries nothing.

What changed, and what deliberately did not

Changed

  1. The upload drain pages forward instead of re-reading a fixed head window, with a non-advancing continuation treated as a hard error.
  2. Expense events without a register session are neither given a pending activity state nor treated as activity candidates.
  3. reviewEventCount takes the maximum of three independent sources rather than trusting the debug counter.
  4. A bounded, read-only upload-page diagnostics sample travels back on the recovery acknowledgement, shape-validated by a shared Convex validator and bounds-checked by the service.
  5. The drain no longer republishes the runtime sync debug snapshot from its pending read. That deletion is exactly why the review count now derives from three sources rather than trusting that publication.

Deliberately unchanged

  • The 250-event page size. The bug was the fixed window, not its size, and changing the size would only move the failure threshold.
  • The operator UI and the recovery preview. Delivering the server-settled clear action is a cross-layer feature change tracked in V26-2114, so convex/pos/application/queries/terminals.ts is left byte-identical to main.
  • Review-event inclusion in diagnostics. Samples deliberately exclude review events so collecting diagnostics cannot itself perturb the review queue.

What is not here, and why

V26-2087 asked that a terminal stuck on locally-flagged reviews the server has already settled should converge without manual intervention. That criterion is out of scope for this change and is carried entirely by V26-2114.

An implementation of it was written and went through three review rounds. Review then established that it was dead code end to end: the action was produced by previewTerminalRecovery, which no client calls, and the operator UI's action finder matches only commandContext.localReviewClearAll === true, which the new action never set. Nothing could request it, so the claim-time revalidation could never fire.

Rather than ship a dead path, or defer a P0 finding against it, the path was removed from this change. Removing it is behaviour-neutral against what production runs today, since it was unreachable there too. The reviewed implementation is preserved at commit d5681c5e, and the findings already fixed in it — append to terminalActions rather than replacing, cache the page read per register session, scan newest-first, make the claim gate all-or-nothing — are recorded on V26-2114 so they are not reintroduced.

One further follow-up is open against code that is in this change: V26-2117, a bound mismatch found while fact-checking this report. The diagnostics collector emits 2 pages per terminal id in scope while the service rejects above 4 pages total, so a scope resolving to three or more ids can have its whole acknowledgement refused.

Guidance for next time

  • A bounded read that reports "nothing to do" needs a liveness argument. Any fixed-window scan over a growing log should say why the window is guaranteed to contain work when work exists, or it should page.
  • Silence is the expensive failure mode. This bug produced no error and a healthy-looking terminal. When adding a drain, ask what it looks like when it stops making progress.
  • Derive a flag from the data it describes. The expense-event bug existed because the initial activity state was decided from the event type while the candidate predicate looked at the register session. Two places, one fact.
  • Never let a counter that gates operator attention read from one source. A stale zero is indistinguishable from good news.
  • A fix's own tests need mutation pressure too. Round 2 caught that the round-1 fixes were unpinned. Fixes written under review pressure are exactly the code least likely to have adversarial tests.
  • Deploying from an unpushed local branch creates a schema trap. Production carried a field main did not know about, so main became undeployable. If it is worth deploying, it is worth pushing.
  • An unreachable code path is not a partial feature, it is an undelivered one. Round 1 traced the call graph instead of trusting that server-side tests meant the feature worked, and the path was removed rather than shipped dead.
  • Do not relabel a finding to get past a gate. The delivery gate refuses a deferred P0. Reclassifying it would have passed in seconds and left a false severity in the permanent record; reducing the scope removed the finding honestly instead.

Comprehension quiz

Eight of ten to pass.

  1. Why did the upload drain stop making progress while reporting the terminal as idle?

    1. The network connection was silently dropping uploads.
    2. Its fixed 250-event window filled with non-uploadable events.
    3. The IndexedDB transaction deadlocked silently on every drain cycle, leaving the queue untouched.
    4. The server rejected the batch without an error code.

    The drain read only the oldest 250 events each cycle. Once 250 non-uploadable events sat at the head of the log, it correctly found nothing to do in the only page it could see. Nothing failed, so nothing was reported: from the terminal's point of view there was genuinely no work.

  2. Why was raising the page size above 250 rejected as the fix?

    1. It would have exceeded the Convex argument size limit.
    2. It would have broken the diagnostics schema's page bound.
    3. A larger fixed window only moves the number of head-blocking events at which the same starvation occurs.
    4. IndexedDB cannot return more than 250 rows per read.

    The defect is the fixed window, not its width. Only advancing the window removes the failure mode rather than relocating it.

  3. What tells the paging loop it has reached the end of the log?

    1. An explicit end-of-log sentinel event.
    2. A page shorter than 250 events, since a full page means more may follow.
    3. A null afterSequence returned by the store.
    4. The sequence number wrapping back to zero.

    A short page is the conventional end-of-stream signal for sequence-paged reads, and it costs no extra round trip.

  4. Why had main become undeployable before this commit landed?

    1. The production Convex deployment had been pinned to an older schema version by an operator.
    2. Production data already carried a field main's schema did not declare, so deploying main failed schema validation.
    3. Main's lockfile had drifted from the deployed one, so the build could not be reproduced.
    4. The POS E2E job was cancelled by a concurrency group.

    The commit was deployed to production from an unpushed local branch, so production began writing acknowledgement.uploadPageDiagnostics while main still knew nothing about it. Deploying main would have failed validation and reverted a live fix.

  5. Why did register-less expense events make the head-block easy to reach?

    1. They were written to the log twice per expense.
    2. They were marked pending activity reports with no register session to report against.
    3. They carried no sequence number, so the paging cursor skipped over them on every pass.
    4. They were rejected by the server and retried forever.

    They looked like unfinished work that could never clear. The initial activity state was decided from the event type alone, while whether the report could ever succeed depended on the register session.

  6. Why is reviewEventCount now the maximum of three sources rather than the debug counter alone?

    1. To make the number match the server's count exactly.
    2. Because the debug counter was removed from the runtime.
    3. Because a stale zero from any one source would otherwise hide review work from the operator, and a zero reads as "nothing wrong".
    4. To avoid an extra IndexedDB read on the health path.

    Any single source observing review work is sufficient evidence that review work exists; only the maximum preserves that.

  7. Why do the diagnostics bounds reject an oversized acknowledgement instead of truncating it?

    1. Truncation would break the shared Convex validator's shape.
    2. A silently trimmed sample would give a confident but wrong answer about why the drain looked empty.
    3. The acknowledgement is written in a single transaction that cannot be partially applied.
    4. Convex rejects any payload above a fixed byte ceiling.

    The sample exists to diagnose a terminal that is already misbehaving, so a quietly incomplete one is worse than none. The bounds are explicit service-side checks on page count, event count, page index and string length; the shared validator pins only the shape and the 250 and includeReviewEvents: false literals.

  8. Why is the register-session condition applied in two places for expense events?

    1. Convex requires client and server predicates to be declared separately.
    2. One guards the append path and the other guards a legacy migration path.
    3. The initial activity state and the activity-candidate predicate are two decisions about the same fact, so they must not drift apart.
    4. The second check exists only to satisfy the typechecker after the signature changed.

    The original defect was exactly this drift: the initial state was decided from the event type alone, while whether the activity report could ever succeed depended on the register session.

  9. Why was the server-settled review path removed rather than shipped with its finding deferred?

    1. Its tests were too slow for the CI budget.
    2. It conflicted with a schema field already live in production.
    3. A P0 cannot honestly be deferred, and the path was unreachable, so removing it was behaviour-neutral against production.
    4. The reviewers could not agree on whether the claim gate was correct.

    The delivery gate refuses a deferred P0, and relabelling the severity to get past that would have put a false record in the permanent evidence. Because no client could reach the path, deleting it changed no behaviour anywhere.

  10. What does a mutation that leaves the suite green tell you?

    1. The mutated code is unreachable and can be deleted.
    2. No test actually pins that behaviour, whatever the coverage report says.
    3. The test suite needs to be run in a different order.
    4. The behaviour is correct and therefore needs no test.

    Every claim in this delivery was checked by deleting or weakening the behaviour and confirming a test fails. Round 2 found that the fixes written under round-1 review pressure were themselves unpinned — code written in a hurry is the least likely to arrive with adversarial tests.
