Executive Summary

Operators can now change a reporting date range without losing the surrounding day table. The selected range is highlighted inside a stable rendered scope, and choosing one day temporarily focuses that date without erasing the range it came from.

Operational drill-downs now use the materialized report-day lifecycle on the surfaces that own those actions. Overview’s Today status links to Daily Operations or EOD Review, while Overview and standalone Items transaction metrics choose ordering from the same open-day rule. Days-table date links still open Items. The standalone Items route also presents its metrics as Operations-style cards while preserving the original reusable card variant.

Why This Mattered

Previously, the selected date range also defined the rows loaded into the Days table. Changing the range removed nearby context and could leave pagination on a page unrelated to the new start date. A single-day selection had no stable range to return to.

Report destinations also lacked one authoritative definition of an in-progress day. Always forcing oldest-first Transactions made live operations less useful, while browser-clock inference would be wrong for store-local operating days and lifecycle transitions.

Mental Model

Treat the workspace as 3 independent questions. Rendered scope asks which bounded rows remain available. Period focus asks which rows and aggregates matter now. Lifecycle asks whether the materialized store day is still operationally open.

  • Rendered table scope: daysTableStart and daysTableEnd feed the bounded listDays query.
  • Selected range or day: daysStart, daysEnd, and selectedDay control emphasis and SKU mix.
  • Day lifecycle: materialized report status is the authority for open-day navigation and transaction ordering; each surface consumes it through its existing read model.

Before and After Flow

Before: URL range → listDays range → replacement table rows. Date changes coupled query scope, visual focus, and pagination.

After: URL table scope → stable listDays rows; selected range/day → highlighting and SKU mix; shared lifecycle helper → Daily Operations or EOD Review plus transaction ordering.

A range start already present in the table moves directly to its containing page. If the range expands the table query, the panel records the pending start date and calculates the correct page after the expanded rows settle.

Behavior Boundaries

  • A contained range keeps the existing rendered table scope. A wider union expands only while it stays within 92 days; otherwise the selected range becomes the fresh scope. The helper does not shrink a selected range that is itself wider than 92 days. The backend rejects that query instead of truncating it.
  • Selecting a row focuses one day. Selecting it again, or using Show selected range, clears only selectedDay and restores the prior range focus.
  • Only a single-day Items period with a matching open reportDay is Today in progress. Week and month periods remain historic-style navigation even if they include the open day.
  • Missing lifecycle materialization fails conservatively per surface. Items falls back to historic ordering. Overview renders no transaction or status destination when it has no anchor range; a non-open anchor uses historic ordering.
  • The Days table uses 14 rows per page. Expanded-range page targeting waits for the new rows because the old 14-row slices cannot locate a date outside their query scope.
  • The o search parameter records the originating Reports URL. Daily Operations and Transactions preserve it so their standard back action can return the operator to the reporting context.
  • The default embedded Items component keeps its card treatment; only the standalone route opts into the canvas variant.
  • Access control, totals, cursor mechanics, fact limits, freshness authority, and newest-first day-table ordering are unchanged.

Next-Time Guidance

  • Keep query scope, analytical focus, and operational lifecycle as separate state dimensions.
  • When navigation depends on newly fetched rows, defer the derived page decision until those rows settle instead of calculating from stale data.
  • Derive current-day behavior from report lifecycle state, never browser time.
  • Carry the origin parameter across operational drill-downs so each owning workspace can offer a reliable return path.
  • Cover contained and expanded range paths separately; only the expanded path exposes stale-row pagination errors.

  1. A selected start date is outside the currently loaded rows, but the expanded table scope remains under 92 days. What should happen?

    1. Keep the old query forever and highlight nothing
    2. Expand the query, temporarily use page 1, then move to the page containing the start date after rows settle
    3. Replace the table with only the selected day

    The old rows cannot locate the new date. Deferring the final page avoids the former stale-row mistake while preserving bounded surrounding context.

  2. The union of the current table scope and a new 20-day range would exceed 92 days. Which scope is queried next?

    1. The unbounded union
    2. The old table scope, ignoring the selection
    3. The new 20-day selected range as a fresh table scope

    The union is rejected as context expansion, but the selected range itself is safely bounded. An independently over-wide selected range would still be rejected by the backend.

  3. An operator focuses one day inside a custom range, then activates that same row again. What remains?

    1. The custom range, with its rows highlighted again
    2. The global trailing-14-day default
    3. A one-day table query

    Only selectedDay is cleared. The selected range and stable table bounds remain, so the operator returns to the context they chose.

  4. A weekly Items period includes the store’s open report day. How are its Transactions metric links ordered?

    1. Newest-first because any included open day controls the period
    2. No order because week periods cannot link to Transactions
    3. Oldest-first because only a single-day open period qualifies as Today in progress

    The lifecycle exception is deliberately narrow. Multi-day periods retain chronological review ordering even when one constituent day is open.

  5. Items loads a single day but no matching materialized reportDay exists. What is the conservative transaction behavior?

    1. Infer open from the browser date and omit order
    2. Treat it as not in progress and request oldest-first
    3. Disable all metrics

    Items defaults isTodayInProgress to false. It never substitutes wall-clock inference for missing lifecycle materialization.

  6. Overview has no anchor day, so it cannot derive a transaction range. What should it render?

    1. No Transactions or operational status destination
    2. An oldest-first link with today’s browser date
    3. A Daily Operations link without an operating date

    Overview requires an authoritative anchor to construct both range and status destinations. Unlike Items, its fallback may be no link rather than a historic link.

  7. The Overview Today status says In progress. Which action opens Daily Operations?

    1. Clicking any date in the Days table
    2. Clicking the Items units-sold metric
    3. Clicking View Daily Operations beside the Today status

    Surface ownership matters: Days dates still drill into Items, while the Overview Today status owns the operational workspace destination.

  8. Why do report drill-down links carry the o parameter?

    1. It selects oldest-first ordering
    2. It preserves the originating Reports URL for the destination’s back action
    3. It identifies the open reportDay

    Ordering and lifecycle use separate fields. The origin parameter exists only to preserve a reliable return path across route ownership.

  9. A direct URL supplies a selected range wider than 92 days. What prevents silent partial reporting?

    1. Backend range validation rejects the query
    2. The UI quietly truncates it to the newest 92 days
    3. Pagination hides the excess dates but totals remain complete

    The scope helper limits expansion but does not sanitize an over-wide selected range. The backend fails closed rather than returning plausible partial data.
