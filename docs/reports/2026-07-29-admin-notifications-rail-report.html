One place to add a communication, one place for it to fail visibly.

Executive summary

Emit, don't send

Domain mutations call emitNotificationWithCtx inside their own transaction with a kind, subject refs, and a minimal payload. Emits are idempotent by a kind-specific structural dedupe key — which replaced every marker field patched onto a domain row.

Audience is data

notificationSubscription rows (org × optional store × category × channel) resolve at dispatch. ADMIN_EMAILS is the pre-seed bridge only, and only when the org has zero rows for the category.

Delivery is leased

One notificationDelivery row per intent × recipient × channel, born in_flight with a lease token, token-guarded completion, backoff-capped retries, and a provider idempotency key equal to the delivery id.

The shape to remember: emit → intent ledger → reserve/lease → render fresh → send → complete, with one notifications sweep cron (5 min in prod, 60 elsewhere) as the only backstop. Adding a new communication = one registry entry plus one template. Call sites never touch email again.

Three flows each reinvented email, badly.

Problem in plain language

Register closeout, the EOD daily manager report, and POS terminal health each looped over the hardcoded ADMIN_EMAILS constant, duplicated the MailerSend fetch, and invented their own dedupe by patching marker fields onto domain rows (varianceNotificationScheduledAt, closeoutNotificationLocalEventId). That has four concrete costs:

  • Alerts were lost forever. A closeout alert was sent from a fire-and-forget runAfter(0) action. If the send failed, the marker was already set, so nothing ever retried.
  • The pipeline was never exercised outside production. Each call site gated itself on STAGE === "prod", so staging proved nothing.
  • No routing. Every admin got every category for every store, with no way to change it short of a deploy.
  • Dedupe bookkeeping lived in domain data. Delivery state on an approvalRequest or registerSession conflates what happened in the business with whether an email went out.

A ledger of moments, a lease per envelope, one janitor.

Mental model

  1. Emit
    Record the domain moment, dedupe-keyed.
  2. Resolve
    Turn category into recipients.
  3. Lease
    Reserve up to one bounded batch.
  4. Render
    Rebuild content from fresh data.
  5. Send
    Idempotency-keyed, classified result.
  6. Sweep
    Recover leases, retries, lost chains.

The intent ledger is the event: it says a drawer was short at a moment in time. The delivery ledger is the envelope: one row per person who was supposed to hear about it. Keeping them separate is why a failed send is now a retryable row rather than a marker field that silently ends the story.

Bound the batch, do not stretch the lease

A dispatch sends its leased batch serially. The instinct is to make the lease long enough for the whole audience — but a 200-recipient serial run at one send timeout each outlives the platform's action time limit. The action gets killed mid-batch while every leased row has already burned an attempt, so the tail is never contacted and is eventually terminalized as failures that were never actually attempted. So the batch is what is bounded (MAX_DELIVERIES_PER_DISPATCH = 25), the lease is sized to that batch and capped below the action limit (DELIVERY_LEASE_MAX_MS = 9 min), and each dispatch re-schedules itself for the remainder.

And the tail must stay visible. The un-leased tail of a large audience exists only as an in-memory flag and a scheduled continuation — it has no delivery rows yet. So the intent stays pending until the audience is fully materialized, which keeps the sweeper's pending-intent phase as the backstop for a lost continuation. Marking it dispatched at first reserve would make the tail invisible to every sweeper phase. Note the deliberate split: hasMore drives scheduling, materialization drives status. Conflating them let a fully-materialized intent with two batches of due retries flip backwards from dispatched to pending and be labelled dispatch_unrecoverable after it had already delivered to part of its audience.

Two failure shapes, never one

prepareEmail loads fresh payload data at send time, which makes it double as a sendability check. It has two distinct negative outcomes and collapsing them is the tempting bug: 

prepareEmail returns null  → genuinely unsendable (subject gone/resolved)
                           → suppress the delivery, suppress the intent

prepareEmail throws        → transient fault (read limit, OCC, missing row)
                           → retryable_failure with backoff, chain continues

Collapsing throw into suppress would let one flaky query permanently silence an alert. The dispatch action catches separately for exactly this reason.

The fallback is a bridge, not a safety net

resolveRecipients keys the ADMIN_EMAILS fallback off "this org has no subscription rows for this category at all" — never off "no row matched". Keying off the filtered result inverts the feature: disabling every subscription, or scoping them all to another store, would silently re-broadcast to the hardcoded list instead of narrowing the audience. The operational consequence is stated plainly: once seeding has happened, disabling every subscription in a category does silence it, and the intent is suppressed as no_recipients.

What moved, and what was left alone on purpose

Changed and deliberately unchanged

Changed

Three new tables and their indexes; a seven-file convex/notifications module; one new cron; three call sites ported from scheduled send-actions to intent emits; the legacy per-flow admin loops and automationNotificationDelivery writers retired; the environment gate moved from call sites into the transport.

Intentionally unchanged

Every React Email template and every payload query is reused as-is. The EOD outcome policy is unchanged: completed-classified skips emit nothing, and action-required stays once per store-day. ADMIN_EMAILS is not deleted — it is still the resolution fallback and is still used by sendNewOrderAdminEmail.

Deliberately outside the rail

Customer-facing email (orders, verification codes, discounts) and the WhatsApp customer-messaging module. The manual explicit-recipient report actions (sendMostRecentDailyManagerReport, sendDailyManagerReportsForDateRange) stay on-demand and outside the rail.

Schema-supported but stubbed

The in_app channel exists in the channel enum and notificationDelivery carries readAt, but no in-app deliveries are created and there is no inbox UI. A kind with no email channel suppresses as no_deliverable_channel rather than stranding rows.

Cutover guards, three lanes, one release. The legacy markers varianceNotificationScheduledAt and closeoutNotificationLocalEventId are no longer written but are still read, and the EOD action-required path consults the legacy automationNotificationDelivery ledger via wasActionRequiredNotifiedBeforeRail. Without them, a sync batch replayed across the deploy boundary — or the hourly EOD automation's first post-deploy run — would re-alert a moment the pre-rail path already reported, because those moments have no notificationIntent row to dedupe against. EOD applied/prepared sends are deliberately unguarded: the pre-rail path never ledgered those outcomes, so there is nothing to cut over. All three lanes are deletable after one release.

The failure class that kept coming back

One defect dominated the review: a false "register closed" all-clear for a drawer that was actually short. The closeout path looks for a variance review; if it does not find one, it reports the register as closed cleanly. Across the rounds that lookup turned out to be defeatable four different ways:

  1. Pending-only lookup. Once a manager resolved the review, a status: "pending" query found nothing and the code fell through to the all-clear branch. The session-level marker that used to prevent this is no longer written, which made this lookup the last guard.
  2. Legacy-marker skip falling through. A review the pre-rail path had already reported was skipped for emit — and then fell through to the all-clear. Skipping the variance emit must not promote the closeout to "closed cleanly".
  3. Index-page truncation. Round 2's widened lookup paged the session's approvals and filtered in code. Voids, item adjustments, and payment corrections all carry registerSessionId and sort ahead of variance_review, so a busy shift could push the review out of the page.
  4. A missed approval status. Hand-listing the statuses to query means a status added to approvalRequest later silently stops matching reviews in that status.

It is now guarded four ways, each with a test that was verified to fail against the broken form: the lookup queries every status on the full (registerSessionId, status, requestType) index prefix (which cannot truncate); a found review suppresses the all-clear regardless of its status and regardless of whether its emit was skipped; the per-status page reads one row past its bound and, on a genuine breach, refuses the all-clear and records a register_closeout_notification_skipped operational event; and the status list is derived from the schema union rather than hand-listed.

Round 5 is the honest part. Round 4's breach check compared the flattened total across four per-status pages against a per-page bound. Eleven variance reviews merely spread across statuses — a complete, untruncated result — therefore suppressed a legitimate "register closed" report and recorded a reason that was factually wrong. Round 4 also bounded the dispatch batch, and in doing so left the un-leased tail invisible to every sweeper phase. Both of those were new defects created by round 4's fixes to round 3's defects. Two of six rounds found regressions introduced by the round before them. A review loop that only ever looks at the original code misses this entirely.

Round 6, and the invariants that stopped the drift

Round 6 found that making pending a mid-chain state opened a hole: abandonment patches only the intent, and reserve returns early for a suppressed intent without touching rows — so an abandoned mid-chain intent left non-terminal deliveries behind. Because their nextAttemptAt never advances and the retry index is ascending, a couple dozen of them sort to the head of the queue and permanently consume the entire retry budget, killing the backstop for every notification in the system. Both sweeper phases now terminalize a delivery whose intent is suppressed.

The seventh commit exists because two blockers recurred purely as silent drift — neither raising the batch past what the lease covers nor adding an unenumerated approval status produced a type error or a failing test. So both are now pinned: MAX_DELIVERIES_PER_DISPATCH × SEND_TIMEOUT_MS < DELIVERY_LEASE_MAX_MS is asserted directly (a batch of 40 fails it while every other test stays green), the lease is asserted to stay inside the platform action limit, and the derived status list is verified at module load to be a flat union of string literals — because a nested union would silently yield q.eq("status", undefined) and reopen the false all-clear.

Post-deploy steps

  1. Run internal.notifications.seed.seedAdminSubscriptions manually from the Convex dashboard. It has no cron or migration entry. It is idempotent and safe to re-run. Until it runs for an org, that org's audience resolution falls back to ADMIN_EMAILS — by design, not a bug, and the reason the deploy is not order-sensitive.
  2. Optionally set NOTIFICATIONS_DEV_RECIPIENT in non-prod. It is not in any .env template, so a fresh non-prod environment runs in suppressed mode (full pipeline, no provider call, delivery recorded as suppressed) until someone sets it.

Deferred follow-ups — stated as deferred, not done

  • No retention or cleanup job exists for notificationIntent or notificationDelivery. Both tables grow unbounded until a follow-up adds one.
  • No admin UI and no read query over the new tables. Subscriptions are seeded by internal mutation and edited with data tools; triage happens through operational events and function logs.
  • The in_app channel is stubbed. Schema support exists; no inbox UI, no in-app deliveries.
  • The three cutover guards are deletable after one release, once no unnotified pre-deploy moment remains. The EOD lane in particular can only ever match pre-cutover store-days, since operatingDate strings are never reused.

How to extend or debug this area

Next-time guidance

  1. To add a communication: one registry entry plus one template. Do not add a per-call-site email send, and do not add a marker field to a domain row for dedupe — that is what the intent's dedupeKey is for.
  2. Keep the two prepareEmail failure shapes distinct. Return null only when the subject is genuinely unsendable. Let transient faults throw.
  3. When a bounded read feeds a decision, ask what the dropped rows would have said. If the answer is "the opposite decision", read one past the bound and refuse rather than guess. A bounded page over a filtered query can hide exactly the row you are looking for.
  4. Derive enumerations from the schema. Any hand-listed copy of a status union is a silent-drift trap. If the derivation needs a cast, validate the shape at module load.
  5. Pin cross-module numeric invariants with an assertion, not a comment. If raising one constant can break another module's guarantee without failing a test, write the inequality as a test.
  6. Never mark work complete while part of it exists only in memory. An intent stays pending until its audience has rows, because a status is a promise to the recovery path.
  7. Re-review the fix, not just the original. Two of six rounds here found defects created by the previous round. Budget for that instead of treating the last round as a formality.
  8. To debug a missing notification: find the intent by dedupeKey, then check status and suppressedReason; then its deliveries by by_intentId for status, attemptCount, and errorCode; then the subject's operational timeline for notification_delivery_failed or register_closeout_notification_skipped. In non-prod, suppressed_non_prod is the expected code.

Comprehension quiz

Pass required: 8 of 10.

  1. A closeout's variance review exists but has already been resolved by a manager. What must the closeout path do?

    1. Report the register as closed cleanly, since nothing is pending
    2. Emit the variance alert again for the resolved review
    3. Suppress the all-clear and emit nothing — a closeout under review is never also "closed cleanly"

    A pending-only lookup falling through to the all-clear is the false "register closed" report for a drawer that was short. Every status is queried; the alert itself is only for a review still awaiting a decision.

  2. Why is the dispatch batch bounded instead of the delivery lease stretched to cover the whole audience?

    1. To reduce database reads per sweep
    2. A 200-recipient serial send outlives the platform action limit, so the action is killed mid-batch with every leased row already holding an attempt — leaving the tail uncontacted and terminalized as failures never actually attempted
    3. MailerSend rejects more than 25 recipients per hour

    Each dispatch takes at most one bounded batch, sizes its lease to that batch capped below the action limit, and re-schedules itself for the remainder.

  3. prepareEmail throws because it momentarily hit a read limit. What happens?

    1. The batch stays retryable with backoff, and the dispatch chain continues
    2. The intent is suppressed as payload_unavailable
    3. The delivery is marked sent with empty content

    A throw is a transient fault; only a null return means genuinely unsendable and suppresses. Collapsing the two would let one flaky query permanently silence an alert.

  4. An org has subscription rows for cash_controls, but every one of them is disabled. What is the audience?

    1. ADMIN_EMAILS, as the fallback
    2. Every admin user in the organization
    3. Intentionally empty — the intent is suppressed as no_recipients

    The fallback fires only on zero rows for the category, never on an empty filtered match. Keying it off the filtered result would make disabling subscriptions re-broadcast to the hardcoded list.

  5. Why must a delivery under a suppressed intent be terminalized by the sweeper?

    1. To keep the delivery table small
    2. Reserve returns early for a suppressed intent, so the row is never advanced — a couple dozen of them sort to the head of the ascending retry index and permanently consume the sweeper's whole retry budget, killing the backstop for the entire rail
    3. Because suppressed intents can be requeued and would otherwise double-send

    Their nextAttemptAt never advances, so they starve every other notification's retries. Both sweeper phases now terminalize them, and staleLeasesRecovered no longer counts an orphan as recovered.

  6. An audience larger than one batch has been partly leased. Why does the intent stay pending rather than becoming dispatched?

    1. The un-leased tail has no delivery rows yet, so pending is what keeps the sweeper's pending-intent phase as the backstop if the continuation is lost
    2. Because dispatched is only set after every recipient is confirmed sent
    3. To keep the intent eligible for a second dedupe check

    Status reflects materialization of the audience; hasMore drives scheduling only. Conflating them let a fully-materialized intent flip backwards to pending and be labelled dispatch_unrecoverable after partly delivering.

  7. Two blockers recurred in new forms across the review. What was the shared root cause, and the fix?

    1. Missing null checks; stricter TypeScript settings were enabled
    2. Insufficient test coverage; the suite was expanded broadly
    3. Silent drift — neither raising the batch past what the lease covers nor adding an unenumerated approval status produced a type error or a failing test. The batch/lease inequality is now asserted, and the status list is derived from the schema and validated at module load

    An invariant that only lives in a comment is not pinned. Both are now falsifiable: a batch of 40 fails the inequality test while every other test stays green.

  8. What is the most important thing the six review rounds proved about the review process itself?

    1. Six rounds is excessive; the first round found everything material
    2. Two rounds found defects introduced by the previous round's fix, so a fix must be re-reviewed as adversarially as the original code
    3. The lenses disagreed, so review outcomes were arbitrary

    Round 4's per-page bound was compared against a flattened total, suppressing legitimate all-clears; round 4's batch bound left the tail invisible to every sweeper phase. Both were new defects created by fixes.

  9. In a staging environment with no NOTIFICATIONS_DEV_RECIPIENT set, what does the transport do?

    1. Runs the full pipeline but records the delivery as suppressed without calling the provider
    2. Records the delivery as sent so dashboards stay green
    3. Skips emitting the intent entirely, as the old call sites did

    A row claiming sent for mail that was never transmitted is indistinguishable from a real send during an incident. The gate lives in the transport so every environment exercises the pipeline.

  10. What is the delivery's status at report generation, and what must happen after deploy?

    1. Merged and deployed; the seed runs on a cron
    2. Delivery candidate; nothing manual is required because subscriptions self-seed on first emit
    3. Delivery candidate, pre-merge and not deployed; after deploy, seedAdminSubscriptions must be run by hand from the Convex dashboard, and NOTIFICATIONS_DEV_RECIPIENT optionally set in non-prod

    The seed has no cron or migration entry. Until it runs for an org, audience resolution falls back to ADMIN_EMAILS by design, which is why the deploy is not order-sensitive.
