What this bridge delivers

This bridge prepares Athena to adopt affected validation safely. It separates declared policy from the configuration that starts validation, lets the trusted guard authenticate ordinary pull requests, and adds health incident and diagnostic artifacts. Legacy validation remains the default.

The product owns portable execution, attempt history, redaction and evidence admission. Athena owns its policy, selected checks and hosted workflow. The bridge uses those public product capabilities rather than reading private attempt storage.

Why the bridge is needed

A reader that only needs declared policy must not start live health loading or capture another validation plan. Importing a named export from an active module still runs that module, so metadata and documentation identity readers could trigger work they did not need.

The first protected-main health inventory observed 44 checks and reported 9 failures. It retained authoritative outcomes but not useful command failure detail. The failures were real observations; their underlying causes could not be recovered from the published digest. A subsequent diagnostic repair must make the next run useful without rewriting that history.

Three separate responsibilities

Declared policy says which rules and sensors exist. Active configuration chooses a mode and captures the work that must run. The installed product executes that work and decides whether its evidence is acceptable.

Health is the authoritative record of observed outcomes. Incidents name ownership and scope. Diagnostics explain the execution, including what is unavailable. Neither presentation artifact can turn a failed result into a passing one.

How the flow changes

Before this change, passive readers could load the active entrypoint, and the health workflow published only a digest of outcomes. After it, passive readers use an explicit base-policy module and loader. The active entrypoint alone selects legacy, comparison or full-health mode.

Hosted execution still begins with authenticated run, head and base bindings. It then loads protected policy, computes the plan and invokes native validation. The adapter retains diagnostics before a later health read can fail; incident presentation follows the authoritative digest. Each artifact has a separate upload.

Behavior and boundaries

The base loader requires a physical, explicit repository root and a regular contained policy file. It validates the declaration and does not fall back to an active entrypoint. Documentation identity capture uses that same passive policy path while preserving preparation and waiver authority.

The guard gains authenticated pull-request support. This is preparatory: ordinary PR routing and the default mode are not switched here. A guard refusal remains a refusal, not permission to use a legacy fallback.

Diagnostics match new attempts against the actual native candidate capture. Planning and native CI use different identity policies, so equal source trees do not justify comparing their deliverable digests. Returned provider, generation, input, profile and origin bindings must agree before diagnostic detail is attached.

Output tails are bounded and redacted by the product. Unknown exits, unavailable output and unclassified failures remain explicit. Athena retains a bounded diagnostic artifact without copying raw exception messages, environment values or private attempt files.

What a failure means

A complete inventory can contain failed checks. Complete does not mean healthy. The original nine hosted failures remain unclassified until sufficient new evidence supports a diagnosis; a later run does not retrospectively reveal their old cause.

Missing or mismatched diagnostic data remains unavailable. A setup failure without an attempt does not receive a fabricated attempt or raw command exit. Stale diagnostic files are removed before the new invocation, and failure to write diagnostics cannot authorize validation.

The incident report assigns the repository maintainer to triage, retains the protected scope and leaves classification pending. Only the existing authenticated health process can close a finding.

How to extend and troubleshoot this path

Use the base declaration for passive policy or identity inspection. Use the active entrypoint only when selecting or running validation. Test that passive readers still work when an active entrypoint deliberately throws.

For a hosted failure, start with the authenticated run and health digest, then the separate diagnostic artifact. Match the actual canonical check and its attempt binding. If detail is unavailable, preserve that fact rather than assigning a likely cause.

Keep historical receipts bound to their original release and candidate. Reuse requires a positive product freshness decision. Before cutover, retain the actual broad validation and rollback controls, then write the final record under the intended default mode.
