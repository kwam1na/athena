Executive summary

Athena's delivery authority — the pr:athena aggregate and the gates it chains — is now also expressed as a layered policy projection under .agents/policy/: a declarative repository-policy document, twelve typed leaf capability adapters, a compiled snapshot produced by the real harness policy compiler, and a frozen pre-cutover oracle recording the exact phase order, activation rules, and blocker codes of the legacy authority. A new read-only sensor, scripts/policy-projection-check.ts, continuously compares all of it against the live routing. Nothing about active delivery authority changes: bun run pr:athena remains the only authority and the comparison's judge.

Problem and context

The managed delivery product will eventually compile Athena's policy and drive deliveries through checkpoints. Before any of that can be trusted, two things must exist: a faithful declarative mapping of what Athena's delivery authority actually is today, and an independent, tamper-evident record of pre-cutover behavior that later parity claims are judged against. Without the second, the "truth" could quietly be rewritten to match whatever the new system happens to do. The ticket's other half (shadow-mode product install, managed projection materialization, discovery guard) stays blocked on upstream product work and is explicitly not built here.

Mental model

Think of three layers that must always agree, with the oldest one frozen in amber:

  • The live authority — pr:athena, the gate registry, the mechanical selection, the blocker codes. It keeps running exactly as before.
  • The projection — a declarative document ("Athena grants merge-ready and pr-creation, forbids merge and deploy, activates these obligations") plus typed adapters ("here is what Athena can execute"). Declaring a merge adapter grants nothing: discovery never grants authority.
  • The oracle — a frozen snapshot of the live authority's observable behavior, pinned by digest. The projection is compared against both the oracle and the live code, so drift in either direction surfaces as a typed finding.

Before and after

Before: delivery authority existed only as executable script wiring. Any future managed-policy comparison would have had nothing independent to compare against, and no declarative statement of what Athena grants or forbids.

After: the same authority also exists as data — compiled through the harness policy compiler with zero rejections, digest-bound, and watched by a read-only sensor. Merge-ready is the only granted finish line; pr-creation is the only granted authority; merge and deploy are explicitly forbidden while their adapters exist as discovery-only leaves. The oracle freezes phase order (prepare, preflight, validate, record-proof, scorecard), obligation activation (review projection threshold 50 relevant lines, telemetry blocking threshold 150 source lines), per-candidate-class mechanical selection, and thirteen seeded failing candidates with the codes they must produce.

Comprehension quiz

  1. After this delivery, what decides whether an Athena delivery may merge?

    1. The compiled policy snapshot under .agents/policy/
    2. The unchanged legacy authority: bun run pr:athena and its gates
    3. The pre-cutover oracle
    4. The managed delivery product in shadow mode

    The projection is compiled and compared read-only. The legacy aggregate remains the only active delivery authority until the separately gated cutover ticket.

  2. Why are merge and deploy adapters declared even though merge and deploy are forbidden?

    1. So the compiler can grant them automatically later
    2. Because every adapter must have a matching authority grant
    3. Adapters are discovery, not authority: they describe what Athena can execute, while grants come only from the declarative document
    4. To satisfy the tracker-absence fallback

    The policy model separates capability discovery from granted authority; an adapter output cannot claim an ungranted action, and absence of a grant is denial.

  3. What makes the pre-cutover oracle immutable in practice?

    1. The file is committed with read-only permissions
    2. Its sha256 is pinned inside the projection sensor, so any edit fails the sensor and its tests until both places change deliberately
    3. Git hooks reject commits touching it
    4. It is stored outside the repository

    Immutability is enforced by digest pinning: recharacterizing the frozen truth requires a visible two-place edit, never a quiet drift.

  4. Why is aggregate pr:athena deliberately not registered as a leaf adapter?

    1. It is too slow to run as a leaf
    2. It re-enters review, evidence, admission, and validation, so registering it would duplicate the command graph inside the policy model
    3. The compiler rejects adapters with colons in their names
    4. It is owned by the harness repository, not Athena

    Leaves are single-purpose sensors and operations. The aggregate is the comparison authority; the sensor fails if anything registers it as a leaf.

  5. When does a missing telemetry record block a delivery today?

    1. On every delivery, unconditionally
    2. Never; telemetry is advisory
    3. Only for a substantial deliverable — at or above the 150 changed-source-line threshold — with a completed local gate run against the current deliverable, or in CI mode
    4. Only when the branch touches Convex functions

    The oracle freezes exactly this: telemetry.recorded activates always but blocks only when currently required, matching the live threshold logic.

  6. How does the sensor catch a policy document edit that skipped recompilation?

    1. It recompiles the document itself on every run
    2. The compiled snapshot records sha256 digests of its input bytes; a mismatch with the current document or adapter bytes is a snapshot_input_stale finding
    3. It compares file modification times
    4. It cannot; recompilation is on the honor system

    Athena CI has no harness compiler available, so compile freshness is enforced through recorded input digests rather than recompiling in place.

  7. What happens to an observed-only mismatch between the projection and current behavior?

    1. It silently becomes blocking policy on the next compile
    2. It is deleted from the comparison report
    3. It is adjudicated: recorded in the comparison report with a disposition, and the sensor fails if any adjudication lacks one
    4. It reverts the policy document automatically

    Eight adjudications are recorded (lens category projection, host-provided tracker, deferred admission projection, generator invocation surface, and others), each with an explicit non-blocking disposition.

  8. Which finish lines and external authorities does the compiled Athena policy grant?

    1. merge-ready and merge, with operator approval for merge
    2. Only the merge-ready finish line and only pr-creation authority; merge and deploy are explicitly forbidden
    3. merge-ready, merge, and deploy behind approvals
    4. No finish lines; the document is empty until cutover

    Merge-ready stays the default and merge/deploy stay ungranted; the sensor and a planted test both fail if a candidate copy grants merge.

  9. How do generated artifacts like graphify-out and the Convex generated API appear in the projection?

    1. As writable paths in every checkpoint grant
    2. They are excluded from the policy model entirely
    3. As generator-owned groups behind the generated-artifact repair stage, with the non-docs generated trees protected in every checkpoint grant
    4. As sensor adapters with credentials

    Derived-artifact ownership is preserved: generators produce the bytes, sensors verify them, and model-driven stages must not hand-edit the protected trees.

  10. Why did this delivery mark the ticket partial rather than complete?

    1. The review found unresolved merge-blocking findings
    2. The oracle could not be frozen
    3. The ticket's second sub-deliverable — shadow-mode preconditions — waits on the composition-lifecycle and host-integration tickets and was deliberately not built
    4. The compiler rejected the Athena document

    Only the policy-mapping half was unblocked. Building the shadow preconditions early would have duplicated product-owned work behind its dependencies.
