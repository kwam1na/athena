The cheap query sizes the expensive one: measured read routing for SKU mix

The SKU mix chart routed every selection longer than two days through admission control and a snapshot build — to fold, in production, a few hundred rows. The span rule was provable but calibrated to a worst case wigclub sits 23× below. This delivery publishes the fold’s own row count onto the days rail, so the read that is already loaded can measure the read that is about to be issued.

Executive Summary

Multi-day SKU mix was moved onto the bounded resumable range-snapshot lifecycle in the previous delivery. Correct, but the routing predicate was a proxy: a selection qualified as cheap only by being at most two days long. That threshold was provable from the fold’s 2,000-rows-per-operating-day ceiling — two days × 2,000 = 4,000 rows, under the reader’s 5,000-row cap.

Production sits nowhere near that ceiling. Wigclub’s busiest day in seventeen months folds 88 SKU rows; the median day folds 30. The entire 184-day window reads 2,366 rows — inside the synchronous cap. The chart was buying admission control to fold a few hundred rows.

The fold already knows the number. foldDay returns a skuDays map that is the day’s row set, so skuDays.size equals the post-fold reportSkuDay count exactly. The sweeper now writes it onto the day document in the same mutation as those rows, and the days rail publishes it as skuDayRowCount.

Routing became two tiers. The span rule survives as an unconditional floor that never depends on loaded data. Above it, skuMixSyncRowProbe sums the counts across the selection from rows the panel already holds and stays synchronous when the total clears a 4,000-row budget. Day, week, month and quarter selections now avoid admission entirely.

What this does not fix. At wigclub’s current run rate a fully operating 184-day window is roughly 6,214 rows — genuinely over the cap. The six-month window legitimately belongs on the async rail from around 2026-10-07. The win is everything narrower, which was never actually expensive.

Problem and Context

The reported symptom was interaction latency: the mix chart felt unresponsive after it moved onto the heavy rail, while the days table loaded the same range quickly.

The obvious fix does not work. listDays and the mix chart share a metric name, not a grain. reportDay holds one document per operating day with store-wide scalars — its unitsSold means “the store sold 412 units that day”. The pie slices by SKU, which exists only in reportSkuDay, one row per (day, SKU). For a 184-day window that is 184 documents versus up to 368,000 rows. Routing the chart at the days rail yields a single total with nothing to divide it into.

The pre-aggregated rail is also not the answer. reportPeriodSkuRollup already stores per-SKU totals per period key, and trailing-six-month windows are month-aligned at the start. Measured against production it compresses only 1.0×–2.8× per month; across the window, 2,366 rows collapse to 1,082. Wigclub’s catalogue is long-tail — 628 distinct SKUs over 2,366 SKU-days, so a SKU sells on about 3.8 days total — and month rollups only help when SKUs repeat across days. A hybrid whole-months-plus-partial-tail fold to save ~1,300 row reads was rejected as not worth the seam.

The real defect was the question being asked. The predicate asked how wide is this range as a stand-in for how much will this read cost, because cost was not knowable without doing the read.

Mental Model

Four ideas carry the change.

1. A span ceiling is a proxy for cost

Span, page count and item count are all stand-ins. If another query on screen already covers the same range, cost is knowable for free. The days rail is the right source not because it holds the data, but because it already covers the range. The cheap query sizes the expensive one.

2. Unknown is not zero — but a missing row is

A day whose count is absent makes the whole range indeterminate, not “the sum of the rest”. But reportDay is sparse: wigclub has 108 day documents across 511 calendar days, and a day with no document had no activity and so no SKU rows. A missing field means unknown; a missing row legitimately means zero. Both are encoded, and callers must pass explicit coverage bounds so “the reader never looked” cannot masquerade as “there was nothing there”.

3. A derived counter is only as trustworthy as its slowest writer

reportDay has two writers. The sweeper folds it; ingest.ts maintains it incrementally between folds, including inserting new reportSkuDay rows as facts arrive for the open day. A count written only by the fold goes stale-low all day, on exactly the day operators watch most.

4. Trust predicates and performance predicates are different claims

Both send a day through the same refold, which makes merging them tempting. But certifiedFoldRevision is the movement lane’s trust boundary, while skuDayRowCount is the mix lane’s sizing hint. A day missing the count is fully trustworthy.

What Intentionally Did Not Change

No fold-version bump. The fold’s output is unchanged, so refolding is not a correctness repair. A bump would have invalidated certified provenance for stores already cleared for the movement lane.

The async lifecycle. rangeSnapshotLifecycle.ts and the mix snapshot path are untouched. So is the held-snapshot UI: the prior donut already stays on screen, dimmed and desaturated, while a new range builds — that behavior shipped previously and was left alone rather than rebuilt.

The legacy movement reader. listRangeSkuMovement keeps RANGE_SYNC_READER_MAX_SPAN_DAYS at 92. It has no probe, so span remains its only proxy for cost.

The span floor. Selections of at most two days route synchronously without consulting any loaded data, so a day click cannot regress because the days rail has not answered yet.

Shared-demo behavior. Demo fixtures carry no counts, so the probe is indeterminate there and the span rule governs exactly as before.

Operational Guidance

The backfill is required, not optional. Historical settled days never refold under normal traffic, so they never acquire the count on their own, and one uncounted day makes its whole range indeterminate. Without it the feature self-heals forward at one day per day — full six-month coverage in six months.

Run it off-peak. Each refold advances certifiedFoldRevision, so completed Units moved and multi-day mix snapshots covering refolded days go terminal_source_stale and rebuild on next ensure. Self-healing, but visible to anyone with a wide sheet open.

Command and drain rate: markStaleFoldVersionDays per store with autoContinue, then let the sweeper drain at SWEEP_DIRTY_BATCH (10 days) per 5-minute tick. Prod wigclub is 108 days — about 55 minutes, sharing the queue with real dirty days.

Confirm with countStaleFoldVersionDays, whose missingSkuDayRowCountCount should reach zero. Note this is deliberately not on countUncertifiedDays, which remains the movement-readiness gate.

Watch the budget over time. The 4,000-row budget is not permanent headroom. At wigclub’s run rate the quarter view crosses it at roughly 2× volume and the month view at roughly 3×. Re-measure before assuming a range is still cheap.
