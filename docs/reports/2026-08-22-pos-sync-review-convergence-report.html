Executive summary

Four coordinated tickets close the split-brain the M Supplies audit found between POS terminal sync conflicts, register-session projection, and Operations Open Work. They land through one integration PR because they share Convex generated APIs, Graphify output, projection types, and terminal evidence contracts; Linear scope stays per ticket.

V26-1247 makes projection classify every register open as fresh, duplicate, obsolete, or unsafe against the latest authoritative close boundary. V26-1250 lets terminal cloud repair durably resolve obsolete drawer conflicts without replaying the open. V26-1248 settles a synced inventory review's source conflicts in the same mutation that makes the work terminal. V26-1249 creates expense stock-shortfall Open Work on the existing synced inventory-review rail. The integration adds one seam: expense members settle their conflicts through the same settlement helper, keyed by their own expense identity.

This is a delivery candidate. Nothing here is merged, deployed, or marked Done.

Problem and context

A terminal can replay very old local events. Before this change, a historical register_opened event arriving after its drawer had long since closed could create a brand-new cloud register session, because freshness was only checked when some session was still blocking. One terminal accumulated tens of thousands of stale permission conflicts over a couple of dozen events this way.

Separately, an operator could complete a synced sale inventory review in Operations while the posLocalSyncConflict rows that created it stayed needs_review forever, so terminal health and Open Work disagreed about whether anything was still owed.

Expenses that consumed stock the cloud did not have were projected with the decrement silently skipped and no Open Work at all, so nobody was asked to correct the count.

Finally, terminal cloud repair only considered conflicts whose blocking drawer was still unresolved or current; once the drawer settled, the stale rows had no durable path to resolved short of replaying the obsolete open, which is exactly the projection bug above.

Mental model

Think of each scoped drawer (store plus terminal) as having one authoritative close boundary: the latest close occurrence derived from closeout records, then closeoutOwnedAt, then closedAt, never from document insertion order. Any register open at or before that boundary is history, not a new drawer. Projection and repair both ask the same shared policy the same question, so they can never disagree.

Think of a synced inventory review as a work item that owns a durable pointer back to its source: the canonical inventoryReviewWorkItem mapping. That mapping is the only key that may settle conflicts. Sale members prove store, terminal, register session, and local id; expense members prove store, terminal, and their local expense event id. The shared synced_sale_inventory_review discriminator is the rail; sourceKind on the member says which proof applies.

Settlement is not a separate action. Whenever the work becomes terminal, by hand, by a qualifying stock adjustment, or by a retry of already-terminal work, the same mutation resolves the mapped conflicts and records how many it touched.

Before and after

  • Before: projection checked freshness only while a session was blocking. After: findScopedRegisterSessionLifecycle returns the boundary even with no blocker, and classifyRegisterOpenAgainstLifecycleBoundary decides fresh, duplicate, obsolete, or unsafe on both paths; obsolete and unsafe opens create a permission conflict and no session.
  • Before: repair candidates excluded conflicts whose blocker had settled. After: settled-blocker rows are repair candidates; obsolete or duplicate source events settle every row for that event and mark the event rejected or projected without calling projection. Fresh replacements still take the existing safe projection path.
  • Before: completing inventory review work left its source conflicts open. After: settleInventoryReviewSourceConflictsWithCtx runs inside the resolve, group-resolve, and stock-adjustment auto-resolve mutations; retrying terminal work returns already_terminal and settles only lingering rows.
  • Before: an expense with a stock shortfall produced no Open Work. After: projection creates or reuses one synced inventory review keyed by the local expense event, the retry branch backfills it for already-projected expenses, queue and weekly attention include it, and operator copy says expense rather than sale.
  • Before integration: expense members would have reported an unmapped settlement because their mapping carries no register session. After: the settlement identity is source-kind aware and uses the per-terminal mapping index for expense members.

Layer-by-layer mechanics

Register open arrives. localSyncRepository.findScopedRegisterSessionLifecycle reads a bounded terminal window, derives the close boundary with getRegisterSessionAuthoritativeCloseBoundary, and reports any blocking session. projectLocalEvents.projectRegisterOpened reuses a duplicate mapping, supersedes when allowed, then runs the shared classifier. A candidate with no occurredAt or an ambiguous boundary is unsafe; one at or before the boundary is obsolete; both produce a permission conflict with the disposition and reason in details.

Terminal repair. terminalRecoveryRepository lists candidates including settled blockers. cloudRepairPolicy.classifyTerminalCloudRepairConflict checks source-event presence, store and terminal scope, active blocker, business facts, and then the same lifecycle classifier. resolveTerminalCloudRepair verifies the preview precondition hash, settles obsolete and duplicate events row by row within the row budget, projects only fresh ones, and reports obsolete_resolved, duplicate_resolved, or fresh_projected.

Open Work. openWorkInventoryReviews.resolveSyncedSaleInventoryReviewWithCtx validates the member's own source context (sale or expense), then either records already_terminal and settles lingering rows, or transitions the work and settles in the same mutation. The settlement helper resolves the canonical mapping, requires it to point at this exact work item, unions the mapping's and the item's local event ids, and calls resolveLocalSyncReviewWithCtx, which is idempotent and bounded.

Expense shortfalls. projectExpenseRecorded keeps the transaction, skips only the unavailable decrement, and creates a synced inventory review with sourceKind expense and a per-terminal mapping. ingestLocalEvents routes an already-projected expense replay through createMissingExpenseInventoryReviewForProjectedExpense so the work target is rebuilt from the open inventory conflicts without duplicating expense facts.

What changed and what did not

Changed: the shared register lifecycle policy and its repository read; register-open projection; terminal recovery candidate reads, repair policy, repair command, terminal queries and public DTO; the Operations inventory-review resolver and stock-adjustment auto-resolution; expense projection and ingest retry; operational work item and logical group source validation; weekly inventory attention; and four operator-facing copy sites.

  • No sale, payment, closeout, variance, or inventory fact is rewritten by classification, settlement, or repair.
  • No new work type, workspace, route, repair endpoint, or remediation framework. synced_sale_inventory_review remains the storage and DTO discriminator.
  • Read caps are unchanged: 100 candidates per conflict type in terminal recovery, 2,000 rows per event and per repair, 100 event ids per settlement request. The per-event read is status-scoped (new by_store_terminal_localEvent_status index) so only open rows count toward the cap and an event's settled history never blocks convergence. A regression test keeps 5,010 settled rows reporting an incomplete bounded read until repair.
  • closing register sessions are no longer counted as blocking in cloudRepairPolicy because every path into closing leaves close-occurrence evidence (a submitted closeout stamps closeoutOwnedAt; a reopen after rejection appends a closeout record), so the shared boundary already represents them.
  • Skipped settled-blocker rows are omitted from the terminal recovery preview after the bounded read, so a terminal whose stale rows are converging is not newly pushed to manual review; the incomplete flag is computed before that filter.
  • Generated artifacts were regenerated once on the integration tree by the pre-commit hook; the explicit regeneration afterwards was a no-op.

Failure boundaries

  • Missing occurrence time or ambiguous close evidence: the open is unsafe, no session is created, and the conflict keeps the reason.
  • Repair: missing source event, store or terminal mismatch, active blocker, ambiguous lifecycle evidence, or a business-fact conflict is skipped; a changed preview hash rejects apply with no partial repair; repeating repair converges to a no-op.
  • Settlement: a work item whose canonical mapping is missing or points at another row reports unmapped and touches no conflict; an expense member cannot be settled through a sale-shaped mapping and a sale member never consults the expense index.
  • Forged or cross-store context on a first resolution or an already-terminal retry fails validation before any write; a settlement failure rolls back the work transition because both are in one mutation.
  • Expense replay: an identical replay reuses the transaction, mapping, conflict, and work item; a historical replay with an open conflict and no target gains exactly one target.

Next-time guidance

  • When a register lifecycle question appears anywhere new, call classifyRegisterOpenAgainstLifecycleBoundary with a scoped boundary from findScopedRegisterSessionLifecycle; do not add a second freshness rule.
  • When adding a member kind to the synced inventory-review rail, give it its own mapping identity and validation branch, and extend inventoryReviewSourceMappingIdentity rather than special-casing the settlement helper.
  • Treat settledConflictCount and sourceSettlement.disposition in the resolution metadata and operational event as the audit of convergence; unmapped means investigate the mapping, not the conflict.
  • Keep repair previews and applies bound by the precondition hash, and keep caps; make a capped read say incomplete rather than clean.
  • For coordinated batches, merge the branch that carries a dependency first, resolve the shared file semantically, and regenerate generated artifacts once on the integration tree.

Comprehension quiz

Pass required: 8 of 12.

  1. What decides whether a replayed register_opened event may create a cloud register session?

    1. Whether any session is currently blocking
    2. The shared lifecycle classifier comparing occurredAt with the latest authoritative close boundary
    3. Document insertion order of register sessions
    4. Whether the terminal is online

    Both the blocking and no-blocker paths call classifyRegisterOpenAgainstLifecycleBoundary; an open at or before the boundary is obsolete and creates a conflict, not a session.

  2. How is the authoritative close boundary derived?

    1. From the newest registerSession document
    2. From closeout records, then closeoutOwnedAt, then closedAt, taking the latest occurrence
    3. From the terminal's last sync cursor
    4. From the register number across all terminals

    getRegisterSessionCloseOccurrenceAt reads lifecycle occurrence evidence, never insertion order, and the boundary stays scoped to the terminal.

  3. A register open has no occurredAt and the drawer window has ambiguous close evidence. What happens?

    1. It projects as fresh
    2. It is treated as a duplicate
    3. It is classified unsafe, creates no session, and keeps a conflict with the reason
    4. It is silently dropped

    Ambiguous chronology fails closed with review evidence retained.

  4. What does terminal cloud repair do with an obsolete register-open conflict behind a closed boundary?

    1. Replays the open through projection
    2. Settles every duplicate row for that source event and marks the event rejected without projection
    3. Raises the candidate cap so all rows load
    4. Moves the terminal to needs_manual_review

    Obsolete and duplicate events settle without projection; only genuinely fresh replacements take the existing projection path.

  5. Why are closing register sessions no longer counted as blocking in cloudRepairPolicy?

    1. Closing drawers cannot have conflicts
    2. Every path into closing leaves close-occurrence evidence, so the shared boundary already represents them
    3. The status was removed from the schema
    4. Repair never runs while a drawer is closing

    A submitted closeout stamps closeoutOwnedAt and a reopen after rejection appends a closeout record; the boundary, not the flag, decides freshness.

  6. Which key may settle the source conflicts of a synced inventory review?

    1. The receipt number
    2. The product SKU id
    3. The canonical inventoryReviewWorkItem mapping that points at this exact work item
    4. Any conflict on the same terminal

    The mapping proves store, terminal, local identity, and cloud id; anything else reports unmapped and touches no conflict.

  7. How does an expense member's settlement identity differ from a sale member's?

    1. It has no identity and cannot settle
    2. It is keyed by local expense event id through the per-terminal mapping index, with no register session
    3. It uses the sale's register session
    4. It uses the expense transaction number

    Expense mappings carry an empty register session, so the helper uses by_store_terminal_localKindId for expense members and the register-session-keyed index for sale members.

  8. An operator retries completion on a review that is already completed but still has open mapped conflicts. What happens?

    1. A conflict error is returned
    2. The work is re-completed and a duplicate completion event is recorded
    3. The recorded outcome is kept, lingering conflicts settle, and a settlement-only event is recorded
    4. The work is reopened

    already_terminal is an idempotent convergence path: only lingering rows are settled and the outcome is unchanged.

  9. What happens when a zero-stock expense is projected?

    1. The expense is rejected
    2. The expense projects, no stock is decremented, and one synced inventory review is created or reused
    3. Stock goes negative
    4. A new expense_inventory_review work type is created

    The transaction is retained, only the unavailable decrement is skipped, and the existing rail carries the work.
