Executive summary

This candidate adds a read-only comparison boundary between Athena's existing delivery workflow and one exact, qualified portable core release. Both paths receive the same frozen input, but Athena remains the only authority.

The portable path can report routing, posture, gate, evidence, and attempted mutations. It cannot mutate Linear, change status, merge, deploy, authorize a canary switch, or influence Athena's result. The comparison is stored beside the existing ignored delivery ledger and can later be carried by the existing tracked delivery telemetry.

Why this boundary is needed

Replacing Athena's local workflow body immediately would confuse parity evidence with authority. A portable core can look equivalent while still carrying a stale release, evaluating a different candidate, attempting a forbidden mutation, or losing history when release pins advance.

The delivery therefore needs an observable intermediate state: compare the two paths first, disposition any mismatch against the characterized Athena baseline, and only then consider a separately reversible canary switch.

Mental model: a sealed witness beside the judge

Athena is the judge: it runs the authoritative gate and owns the outcome. The portable core is a sealed witness: it sees the same evidence and reports what it would decide, but it has no controls connected to tickets, status, merge, deployment, or authority.

The comparison record is the transcript. Its digest binds when the observation happened, which candidate and frozen input were used, the exact baseline and release identities, both decision sets, mismatches, mutation attempts, and the authority boundary.

  • Judge: Athena's existing baseline and delivery gate.
  • Witness: the exact qualified portable archive in an isolated temporary directory.
  • Transcript: a closed-schema, candidate-bound comparison artifact.
  • Archive: the existing tracked delivery telemetry, which retains valid older transcripts after pins advance.

Before and after

Before: pr:athena produced the authoritative ledger and delivery:telemetry-record preserved run and review-loop data, but Athena had no same-input portable comparison or durable shadow evidence.

After: a passing ledger must still describe the current deliverable. The runner verifies the frozen input, Athena baseline, portable archive, and release metadata; evaluates both paths; recomputes mismatches; writes a sibling artifact without changing the ledger; and lets the existing telemetry recorder attach the validated comparison.

  • No new orchestration service or telemetry plane.
  • No change to host discovery roots or workflow authority.
  • No application-package behavior change.
  • No runtime limit on Linear capability.

How the evidence flows

First, the runner reads a passing Athena delivery ledger and recomputes the current deliverable fingerprint with the same changed-path rules used by telemetry. A moved candidate is rejected before evaluation.

Second, the same frozen request is evaluated by the source-backed Athena characterization and the exact portable release. The release is copied into an isolated temporary directory, verified by digest and metadata, and evaluated with tracking disabled.

Third, the runner compares routing, posture, gate, evidence, and reported mutation attempts. A difference produces an unresolved mismatch. An unavailable release produces an unavailable observation. Neither outcome changes Athena's authoritative result.

Finally, the sibling artifact is validated against exact current pins and a closed redacted schema. The ordinary telemetry recorder requires the nested and outer candidate fingerprints to match, then persists one validated copy. Historical readers check structural integrity without applying today's pins to yesterday's record.

Failure boundaries

  • Missing, blocked, or fingerprint-less ledger: stop before evaluation or artifact creation.
  • Candidate changed after the gate: reject the stale ledger before evaluating.
  • Wrong archive, metadata, baseline, or frozen input: fail exact verification; Athena remains authoritative.
  • Decision drift or a reported mutation attempt: record an unresolved mismatch; switching authority remains prohibited.
  • Tampered digest, forged status, unknown field, or mismatched outer fingerprint: reject the artifact before tracked persistence.
  • Later release pins differ from an older valid record: retain the historical record through structural self-consistency validation.

What changed and what intentionally did not

Changed: Athena now vendors one exact portable core release outside discovery roots, owns a frozen comparison input, can produce a read-only shadow artifact after a current passing gate, and can include that evidence in existing delivery telemetry.

Unchanged: Athena remains authoritative; the delivery ledger is not rewritten; the portable path has no mutation or delivery capabilities; no canary switch or batch migration occurs here; deployment is not applicable; and Linear keeps its full policy-authorized create, read, update, search, relations, and reconciliation surface. The two-disposable-issue ceiling applies only to authenticated qualification-fixture hygiene.

How to extend this safely

  • Run the authoritative gate first, then observe; never use a stale passing ledger.
  • Treat match, mismatch, and unavailable as evidence only. Keep mismatch disposition and authority switching separate.
  • When changing release or baseline pins, refresh exact-current evidence but preserve older structurally valid telemetry.
  • Keep the comparison schema closed and redacted before using the single-copy persistence path.
  • Reuse Athena's ledger, candidate fingerprint, review evidence, and telemetry instead of adding parallel control planes.
  • Do not begin a batch migration until the shadow comparison is accepted and the reversible canary succeeds.
