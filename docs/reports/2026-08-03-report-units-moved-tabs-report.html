Scaling Units moved into top-mover and granular tabs

A trailing-30-day period could not open the Units moved sheet, because the answer was computed in one transaction with a 100-SKU ceiling on top of it. It is now a resumable, fenced snapshot whose identity includes the certified fold revision of every day it read — a field that did not exist on a single historical row until this change forced a refold.

Executive Summary

The Units moved sheet aggregated a whole range inside one Convex query. listRangeSkuMovement read reportSkuDay for the span with a 5,000-row ceiling, then rejected any result with more than 100 distinct SKUs. A normal trailing-30-day period at a busy store failed both checks — while the canonical projections held every unit of the evidence.

Removing the 100-SKU check would not have fixed it. The 5,000-row ceiling sits behind it, the transaction read budget sits behind that, and each ceiling resolves into unbounded identity hydration and a complete result shipped to the browser. The ceiling was a symptom; doing unbounded work in one transaction was the defect.

The delivery extends the existing reportRangeResult lifecycle with a second request kind rather than building a parallel framework. One admitted request is one immutable snapshot, accumulated one operating day at a time into indexed child rows, ranked in bounded batches, and published only after a fresh recheck of its source lineage. The sheet reads a single 20-row page at a time behind Top movers and All items tabs.

The hard part was not the worker. Snapshot trust needs per-day fold provenance, and reportDay/reportSkuDay had none. Stamping certifiedFoldRevision in the fold path certifies only future folds — a clean historical day is never refolded, so it would have stayed inadmissible forever. The plan originally claimed no historical backfill was required; a planning review falsified that before implementation. The delivery therefore bumps REPORTS_FOLD_VERSION 2 → 3 and runs the existing per-store foldVersionRepair, making the migration a hard rollout prerequisite with an observable coverage gate.

Problem and Context

Two ceilings and a missing fact. RANGE_SKU_MOVEMENT_LIMIT is 100 distinct SKUs; RANGE_SKU_MIX_ROW_LIMIT is 5,000 reportSkuDay rows. Both are enforced inside a single query, and the supported Units moved contract is up to 92 inclusive days. The two are simply incompatible at real volume, and the operator-facing failure — "choose a shorter range" — blames the operator for asking a supported question.

Making the work resumable is the only structural answer, and it immediately raises a correctness question the old design never had to face. Work spread across ten transactions reads evidence that can change between them. "What did this range move?" is only meaningful if every batch sees the same generation of source data, and if publication can prove it did. The canonical projections carried foldedAt and a foldVersion — nothing identifying which fold produced a given row.

And a fold-written field does not reach history. Athena's sweeper folds a day only when a reportDirtyDay mark exists for it. Clean days never refold. So stamping revisions in foldAndReplaceDay would have left every existing day permanently uncertified: not loudly broken, just perpetually "waiting" behind a spinner no operator could clear.

Mental Model

Think of a movement result as a photograph with its negatives attached, not as a query result. The request key is the photograph's identity:

movement:hash([
  "sku_movement", storeId, startDate, endDate,
  REPORTS_FOLD_VERSION, REPORT_MOVEMENT_CONTRACT_VERSION,
  [ [day, certifiedFoldRevision | "empty"], ... ]   // one entry per included day
])

Everything else follows from that one decision. Reopening with unchanged sources reuses the completed snapshot. Any included day changing revision yields a successor request instead of mutating a published one. A custom-summary and a movement request over identical dates cannot collide, because the kind is inside the hash. An absent day is an explicit "empty" sentinel — "this day had no fold" is part of the identity, not an omission from it.

The second model is the division of background responsibility, which this change deliberately splits in two and writes down in the sweeper's own header comment:

FOLDS      declarative dirty marks  -> sweeper is the single fold authority
MOVEMENT   own eligible-work queue -> prompt action continuations,
                                      cron is a BACKSTOP that only SCHEDULES

The sweeper's movement section runs unconditionally — never gated on touchedStores — because a dropped continuation has to be recoverable at a store with no dirty days at all.

Before and After

  • Before: a range with more than 100 moving SKUs threw. After: SKU count is never a terminal reason — a live 30-day dev range completed with 138 moving SKUs across 7 pages.
  • Before: more than 5,000 reportSkuDay rows threw. After: source evidence is accumulated one operating day at a time, and a day is already capped at 2,000 rows by the fold.
  • Before: the complete ranked result was hydrated and shipped. After: at most 20 identities are resolved after rank selection, and the browser holds one 20-row page.
  • Before: reportDay/reportSkuDay carried no fold provenance. After: every fold stamps a monotonic certifiedFoldRevision on the day and every SKU row it replaces, together.
  • Before: the sheet was one list. After: Top movers (one ranked page, chart-first) and All items (20-row table with numbered pagination), sharing one absolute-net ordering.
  • Before: Overview used replace: true for the units key and Weekly did not, so browser Back behaved differently per route. After: one convention — replace for open/close and intra-sheet state, a real history entry only for the drill-down itself.
  • Unchanged: the legacy listRangeSkuMovement query and its exact response, kept additively so already-open clients survive the rollout.

The Lifecycle State Machine

Public states are a separate discriminated union from durable phases, and three of them carry no durable row at all — the ensure mutation returns them having written and scheduled nothing.

StateDurable?Meaning and exit
not_availableNo writeStore is outside REPORTS_SWEEP_STORE_ALLOWLIST. Checked first, before validation. Non-retrying — such a store never folds, so it can never certify, so waiting would be forever.
waitingNo writeAn included day is dirty or not yet revision-certified (repair still draining). Client re-polls ensure after a jittered server-supplied interval.
backpressureNo writeA principal / store / global fixed-window admission budget is saturated. Zero writes, zero schedules, retryable.
queuedYesReset lane: deletes children left by a superseded attempt in bounded batches so accumulation cannot double-count. Fresh requests fall straight through.
aggregatingYesOne operating day per batch. Verifies no dirty marker, that the day's revision equals the admitted one, and that each SKU row carries that same revision, then accumulates into indexed child rows.
rankingYesResumes off the maximum assigned rank and continues exactly across the compound sort-key index: the remainder of the resume key's group first, then strictly greater keys.
retry_waitYesCapped exponential backoff (30s base, 10min ceiling, 5 attempts). Re-entry phase is inferred from durable state: no cursor → ranking; cursor at start with children present → queued reset; otherwise aggregating.
completedYesPublished only after a fresh bounded recheck finds the identical clean revision vector. Totals, count, completion time, and ranked pages are immutable.
terminal_errorYesSanitized code (movement_worker_failed or movement_source_stale) plus an opaque correlation id. Retry creates a new fenced attempt, never the failed row's state.
cleaningYesExpired: children drain first through their own by_expiresAt index; the header is deleted only once none remain.

Fencing

Every committed batch increments movementFence, and every batch is dispatched with an expected pair:

if (row.movementPhase !== args.expectedPhase ||
    row.movementFence !== args.expectedFence) {
  return { next: "stale" };
}

A duplicate scheduled worker, a superseded attempt, or a replayed continuation observes the mismatch and no-ops. In a resumable worker these are the normal case, not the edge case.

Atomic work, separate failure record

The module's first internalAction never touches the database. It invokes one batch mutation, and that mutation deliberately does not catch unexpected defects — Convex rolls back aggregates, cursor, and fence together. The action then records retry metadata in a different transaction, so attempt count, backoff, and eligibility survive the rollback that discarded the work:

} catch (error) {
  const outcome = await ctx.runMutation(MOVEMENT_FAILURE_REF, {
    rangeResultId: args.rangeResultId,
    expectedFence: args.expectedFence,
  });
  console.error("[reports.skuMovementRange] worker batch failed ...", error);
}

The failure mutation is itself fenced, so a late report from a superseded attempt records nothing.

Conservative completion

deriveMovementRequestLifecycle reports completed only when phase, totals, and completion time are all present together, and terminal_error only when both the sanitized code and the correlation id are. Partial aggregation or ranking state can therefore only ever surface as pending — a header cannot half-publish.

Fold Provenance and the Migration

foldAndReplaceDay now computes a per-day monotonic counter and stamps it on the day document and on every reportSkuDay row the fold replaces, in the same mutation:

const certifiedFoldRevision = (existingDay?.certifiedFoldRevision ?? 0) + 1;

A counter, not the fold timestamp: two folds in the same millisecond must not collide, and a counter is deterministic inside the transaction. Because a fold already rewrites the day's SKU rows wholesale, the SKU rows ride along at no extra cost — which is what lets movementSourceRowMatchesRevision prove a SKU row belongs to exactly the day generation the snapshot admitted.

That change alone certifies nothing that already exists. Clean days never refold. So REPORTS_FOLD_VERSION goes 2 → 3 in the same change, purely so the repair's staleness predicate can see pre-revision days:

export function needsCertifiedRefold(day) {
  return (
    day.foldVersion !== REPORTS_FOLD_VERSION ||
    day.certifiedFoldRevision === undefined ||
    day.certifiedFoldRevision === null
  );
}

The repair marks stale days reason: "fold_version_bump" and lets the sweeper — the single fold authority — rewrite them. No second writer was introduced: an in-place backfill script would have been exactly that, and the module forbids it. A new read-only countUncertifiedDays reports per page staleFoldVersionCount, missingRevisionCount, uncertifiedCount and certifiedCount, so readiness is observable rather than assumed.

Rollout ordering (hard sequence)

  1. Deploy the schema fields — optional on both generations, so a mixed-generation store validates.
  2. Deploy fold stamping plus the version bump. New folds certify from here.
  3. Run markStaleFoldVersionDays per allowlisted store and let the sweeper drain. The bump refolds every historical day of each repaired store; the drain rate is bounded by SWEEP_DIRTY_BATCH (10 days) per five-minute tick, so the window is computable from history length.
  4. Confirm uncertifiedCount: 0 on every page of countUncertifiedDays.
  5. Only then deploy the movement backend and enable the UI for that store.

Admission's two negative outcomes are deliberately asymmetric. An allowlisted store mid-repair returns waiting, because the repair genuinely will finish. A non-allowlisted store returns not_available before any validation or read, because for that store the wait can never end.

Security and Tenancy Boundaries

  • Generation vs. read. ensureMovementRange and retryMovementRange are registered under reporting.generate in capabilityCatalog.ts, beside reports/customRange. Page and status reads sit behind the ordinary requireReportsStoreAccess boundary.
  • Shared demo cannot generate. requireSharedDemoCapabilityIfApplicable(ctx, "reporting.generate") runs first on both mutations, so a demo actor is denied server-side regardless of any client-side demo gating. The demo sheet renders createSharedDemoReportMovementPage, an always-completed page derived from the transaction fixture already in the browser.
  • Workers are private. The batch mutation, the failure mutation, and the worker action are all internal; the sweeper hooks are plain functions invoked from sweepWithCtx.
  • Every lookup is store-prefixed. Headers resolve through by_storeId_requestKey, children through by_storeId_rangeResultId_*. A cross-tenant request key substitution resolves to nothing rather than to another store's snapshot.
  • Strict validation on the durable path. Movement uses validateReportRangeRequest — strict YYYY-MM-DD shape and calendar validity plus the 92-day ceiling — not the legacy loose span-only check, because a malformed label must never enter a durable request identity. Page input must be a positive safe integer and is then canonicalized against the completed count.
  • Nothing internal crosses the public boundary. Cursors, fences, revision vectors, and exception text stay server-side; a terminal state exposes a generic code and an opaque correlation id, with the real error logged against that id.
  • Admission before writes. Principal, store, and global fixed-window counters are all checked before anything is written; reuse of an existing request never spends budget, while a retry does, because a retry creates work.

The UI State Matrix and the Direction-Word Decision

The sheet shell is persistent in every state: title and date, then tabs (Top movers / All items), then the lifecycle or count message, then the active tab's content.

UI stateContentAccessibility
Waiting / queued pending"Preparing item movement". No partial chart, table, or pagination.Polite role="status"; retries are not announced individually.
Not available (store)Calm "not available for this store"; no retry loop.Announced once, politely.
Page transitionThe settled page label, rows, and links stay together under busy styling.aria-busy on the content region; the new range announced only once settled.
Completed empty"No SKU movement was recorded in this period."Announced once.
Completed successCount and subset disclosure, then chart or 20-row table with pagination.Native tab semantics; textual chart summary.
Terminal errorGeneric message, correlation id ("Reference:"), explicit Retry.role="alert"; focus moves to the error heading.

Poll-then-subscribe. Waiting, backpressure, and not-available write nothing, so there is no document to subscribe to — and inventing one would make backpressure durable. The sheet calls the idempotent ensure mutation on open, re-polls on the server-supplied jittered interval while the outcome is waiting or backpressure, and subscribes to getMovementRange only once a request key exists. The timer belongs to the effect that armed it, so closing the sheet cancels it and a StrictMode double effect tears down its first timer before arming the second. Duplicate ensures land on the same request because dedupe is checked before admission budget is consumed.

Signs are data; direction is presentation. Ranking is by absolute net movement and the stored value keeps its sign, so −24 ranks ahead of +18 and a fully cancelled SKU still appears at net zero with its real sold and returned counts. But in a retail context a leading + reads as stock received, which inverts the meaning for the reader. So no user-facing value carries a sign:

export function formatNetUnitsMoved(netUnits) {
  if (netUnits > 0) return `${formatUnits(netUnits)} out`;
  if (netUnits < 0) return `${formatUnits(-netUnits)} returned`;
  return "0 net";
}

with a matching spoken form ("289 units out"), direction-aware bar corners on a zero-centered axis, and axis labels reading returned / out where the ticks no longer carry direction. The signed number is untouched in the data, the ranking, and the contract.

Navigation continuity. reportRouteSearch.ts gains unitsTab, unitsPage, unitsFocus and unitsScroll, shared by both Reports routes and omitted at their defaults so a plain units=true URL stays canonical. The sheet's existing scroll map survives only within one mount, so returning from SKU detail uses a new mechanism: the underlying report offset is captured into sheet-owned navigation state on drill-down and reapplied on animation frames once the settled content has laid out. If the originating SKU disappeared or its page contracted, focus falls back to the Granular heading with an announcement rather than landing on a different item.

Failure Boundaries

  • A day goes dirty mid-flight. The aggregating batch checks for a dirty marker and revision equality before touching the day; a mismatch goes terminal as movement_source_stale rather than mixing generations.
  • A day changes after its batch but before publication. Rank finalization re-reads the bounded revision vector and compares entry for entry. A mismatch goes terminal and erases the running totals — a terminal row carries no totals, partial or otherwise.
  • A continuation is dropped. The sweeper's unconditional by_movementEligibleAt scan reschedules it, budgeted per tick, pushing each rescheduled row's eligibility one stall window out so a poison row cannot monopolize every tick.
  • A poison job. Capped attempts move it to terminal instead of letting it retry forever; backoff doubles from 30s to a 10-minute ceiling.
  • Duplicate workers. The phase/fence expectation makes the second application a no-op, so no day is aggregated twice and no rank interval is assigned twice.
  • A superseded attempt's children. The queued reset lane deletes them in bounded batches before re-aggregation, so a retry cannot double-count.
  • An expired identity is re-requested. Inserting beside a draining row would break (store, requestKey) uniqueness, so ensure returns waiting until cleanup finishes.
  • A movement row reaches the summary path. computePendingRanges and expireRangeResults both skip sku_movement, and computeRange short-circuits on it as defense in depth — the summary compute path can never overwrite movement lifecycle state, and header deletion can never skip child-first cleanup.
  • An uncertified store. Waiting, not a wrong answer; a non-allowlisted store gets the distinct sanitized outcome instead.

What Intentionally Did Not Change

  • The legacy reader. listRangeSkuMovement keeps its exact response and both of its ceilings, so clients open during the rollout are unaffected. Removing it is later cleanup.
  • Legacy custom-summary rows. A reportRangeResult row without a kind is still a custom summary with its original request-key shape, failed-row reuse until TTL, and 366-day span. Span limits became per-kind rather than global.
  • The single fold authority. The repair still only marks days dirty; the sweeper still performs every fold. No second writer of reportDay was added.
  • The custom-summary compute lane. It keeps its existing touchedStores coupling; generalizing it is deferred.
  • The demo gate as a non-authorization boundary. The demo fixture derives its page client-side, and the server independently denies demo generation.

Next-Time Guidance

  • Assume any new fold-time metadata is invisible on history until proven otherwise. Clean days never refold, so "no backfill required" is a claim to falsify against the refold trigger, not to read off the diff.
  • Migrate with a version bump plus the existing repair, and gate acceptance on a coverage query reading zero — not on a successful deploy.
  • Never add a second writer for a projection with a single fold authority. A one-field in-place backfill is still a second authority.
  • Check the never-reachable case before the wait state. A precondition some tenants can never satisfy needs a distinct non-retrying outcome; a wait that cannot end is a hang.
  • Put provenance inside the request identity. Reuse, invalidation, and successor creation then fall out of one hash comparison instead of bespoke freshness logic.
  • Verify lineage at admission, at every batch, and again at publication. Evidence clean at the start is not evidence clean at the finish.
  • Fence every phase transition and advance the fence on every commit. Duplicate and replayed continuations are the normal case.
  • Let the atomic batch fail and record the retry separately, or the rollback that saves correctness will also discard the backoff that saves liveness.
  • Require every field that makes a state meaningful before reporting it. Completed means phase and totals and completion time.
  • When a new lane contradicts a module's written design stance, rewrite the stance. A comment that disagrees with the code teaches the wrong invariant.
  • Waiting states that write nothing need a poll, not a subscription — server-supplied interval, jitter, one timer per effect, dedupe before charging admission.
  • Keep signs in the data and direction words in the UI wherever a + carries a domain meaning that conflicts with the reader's.

  1. Why was removing the 100-SKU check in listRangeSkuMovement rejected as the fix?

    1. The check is required by the Reports read-model boundary document
    2. Removing it would have broken the shared-demo fixture's parity assertions
    3. The 5,000-row read ceiling sits behind it, the transaction read budget behind that, and each one resolves into unbounded identity hydration and a complete result shipped to the browser

    The ceiling was a symptom. Doing an unbounded amount of work in one transaction — and calling the result trustworthy because it happened to finish — was the defect.

  2. Stamping certifiedFoldRevision in foldAndReplaceDay is not enough on its own. Why?

    1. The fold writes reportDay but not reportSkuDay, so SKU rows need a second pass
    2. The sweeper only folds days marked dirty, so a clean historical day never refolds and would never acquire the field
    3. Convex optional fields default to 0, which movement admission would misread as a valid revision

    The plan originally claimed no historical backfill was required. A planning review falsified that, which is why the version bump, the repair step, and the coverage query exist.

  3. What is the specific role of bumping REPORTS_FOLD_VERSION from 2 to 3?

    1. It makes foldVersionRepair's staleness predicate see every pre-revision day as stale, so the repair can mark them dirty and the sweeper rewrites them with revisions
    2. It invalidates cached movement snapshots computed under the old contract
    3. It switches the fold to a new aggregation algorithm for units sold and returned

    Without the bump, existing rows are simply invisible to the repair. The bump is the mechanism that turns "history is uncertified" into "history is stale", which the module already knows how to fix.

  4. A store is not in REPORTS_SWEEP_STORE_ALLOWLIST. What does ensure return, and why is it different from the uncertified-history case?

    1. The same waiting state, since both resolve once the operator acts
    2. A validation error naming the allowlist, so the operator knows what to change
    3. A distinct sanitized non-retrying not_available, checked before validation and any read — that store never folds, so it can never certify, so waiting would be forever

    An allowlisted store mid-repair legitimately waits, because the repair will finish. A wait that cannot end is a hang wearing a spinner.

  5. What is folded into the movement request key, and what does that buy?

    1. Store, range, and a request timestamp — so each open gets a fresh snapshot
    2. Kind, store, range, fold and contract versions, and the certified revision of every included day — so unchanged sources reuse the snapshot, any revision change yields a successor request, and a summary request over the same dates cannot collide
    3. Store, range, and the requesting principal — so admission budgets can be charged per user

    An absent day is an explicit "empty" sentinel, so "this day had no fold" is part of the identity rather than an omission from it.

  6. The batch mutation deliberately does not catch unexpected exceptions. What handles the failure, and why is that split necessary?

    1. The internal action catches the failed call after Convex has rolled back aggregates, cursor, and fence together, then records attempt, backoff, and eligibility in a separate mutation — so retry state survives the rollback that discarded the work
    2. The batch mutation retries itself in a loop with backoff before returning
    3. The sweeper detects the missing progress on its next tick and resets the row

    A mutation that catches its own defect cannot roll back cleanly; a rollback that also discards attempt counters cannot back off. The failure mutation is itself fenced, so a superseded attempt's late report records nothing.

  7. An included day changes revision after its aggregation batch but before ranking finishes. What happens?

    1. The snapshot completes; the changed day is re-aggregated on the next open
    2. Only the affected day's child rows are recomputed, then publication proceeds
    3. Rank finalization's fresh recheck of the revision vector mismatches, so the request goes terminal as movement_source_stale with its running totals erased — it never publishes as complete

    Evidence that was clean when the work started is not evidence that was clean when it finished. A terminal row carries no totals, partial or otherwise.

  8. Why does the sheet poll the ensure mutation instead of subscribing while it waits?

    1. Convex subscriptions are unavailable inside a Sheet dialog
    2. Waiting, backpressure, and not-available deliberately write nothing durable, so there is no document to subscribe to — and creating one would make backpressure durable
    3. Polling is cheaper than a subscription for a query that changes rarely

    The interval is server-supplied and jittered, the timer belongs to the effect that armed it so closing cancels it, and dedupe runs before admission budget is charged so StrictMode double effects are free.

  9. Signed net units are the ranking basis, yet no user-facing value carries a sign. Why?

    1. In a retail context a leading + reads as stock received, inverting the meaning — so the UI says "289 out", "24 returned", "0 net" while the signed value stays untouched in data, ranking, and contract
    2. The chart library cannot render negative values on a zero-centered axis
    3. Screen readers announce minus signs inconsistently, so signs were dropped for accessibility

    Presentation only. −24 still ranks ahead of +18 by absolute net, and a SKU whose sold and returned units cancel still appears at net zero with its real counts.

    2. The repair was skipped because the dev store had no historical days; the live range returned an empty snapshot
