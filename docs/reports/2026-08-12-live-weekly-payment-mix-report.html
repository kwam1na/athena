Executive summary

Weekly Payment mix now answers the same question as the Payments section directly above it: how did this week's gross payments arrive, by tender method. It reads from the payment-allocation report facts that already feed Payments received, so it covers open days and outside-schedule payments instead of only completed Daily Closes.

The hard part was not the money. It was the count. A single POS transaction routinely carries several allocations of the same method, so counting allocation rows would report one cash sale as two cash uses and disagree with Daily Close. The fix is a participation identity: count distinct pairs of (participation identity, normalized method), where the identity is the POS transaction when there is one and the allocation itself otherwise.

Nothing was backfilled and no accepted report was rewritten. Existing accepted and corrected reports keep their frozen close-backed mix, and a revision that cannot produce a breakdown reconciling exactly to its own total says so rather than publishing a partial one.

The problem in plain language

Two adjacent sections of the weekly report were describing different weeks.

Payments received had already moved onto payment-allocation report facts. It updates as payments arrive and covers the whole labelled date range, including days that are still open and payments taken on days the store was not scheduled to trade.

Payment mix still aggregated completed Daily Closes. A close only exists for a day someone closed, so the mix silently excluded open days and outside-schedule payments. A manager reading the two together saw a method breakdown that did not add up to the total printed immediately above it, with nothing on the page explaining why.

This supersedes exactly one earlier decision — the close-backed payment mix from the 2026-08-09 plan. Daily Close remains authoritative for everything else it owns: close status, cash variance, completed POS transaction count, and expense-product evidence.

The mental model

Think of a week's payment evidence as two different kinds of question asked of the same pile of receipts.

"How much came in as cash?" is additive. Every receipt contributes its amount. Two cash receipts of 20 and 10 make 30. You can add these in any order and merge partial sums freely.

"How many times was cash used?" is not additive, because the thing being counted is not the receipt. It is the occasion. If one customer pays for one transaction with two taps of cash, that is one use of cash, not two. Daily Close already answers it this way — buildPaymentTotals counts the transaction.

So the fold carries two different accumulators. Value sums. The count is a set of (occasion, method) pairs, and the occasion is named explicitly: the POS transaction when the allocation has one, the allocation itself when it does not. Several same-method allocations on one transaction collapse into one pair; a split-tender transaction produces one pair per method; two unrelated non-POS receipts stay two pairs.

One more idea does a lot of work here: absent is not zero. A day, revision, or fact written before this change carries no mix field at all. That absence means "unknown", and on an immutable accepted report it means something stronger — "read the frozen close-backed evidence, and do not try to reconstruct me."

Before and after

Before

  • Payments received: payment-allocation report facts, whole labelled week, live.
  • Payment mix: completed Daily Closes only, scheduled included dates only, frozen at close.
  • A method correction moved money between methods in the POS domain but emitted a zero-magnitude correction fact carrying no method information, so reporting could not see it.

After

One cash receipt now travels a single rail end to end:

  1. Allocation. A recorded inbound paymentAllocation is written as it always was.
  2. Fact. The existing emitter attaches four optional dimensions to the payment fact it already wrote: normalized method, participation identity, gross mix value, and (on a correction only) the method the value moves off.
  3. Day. The fold accumulates value per method and a net count per (identity, method) pair, then publishes a mix only if the rows sum exactly to that day's paymentsCollectedMinor.
  4. Week. Each lane's days are summed and re-checked against that lane's own received total. Acceptance freezes the same arithmetic from cutoff-bounded facts.
  5. Read. Both lanes are combined at read time, because the Payments figure beside the mix covers the whole labelled range.

An approved cash-to-card correction travels the same rail: the correction fact keeps the receipt's participation identity and carries a signed move from cash to card, dated to the original allocation's business time so it lands on the day the payment was received.

How the counting actually works

The state is deliberately not a set. It is a net count per pair:

{ participationId: "txn-1", method: "cash", net: 2 }

A receipt adds one to its pair. A method correction subtracts one from the old pair and adds one to the new. A pair with a positive net is exactly one tender use.

Why a net count and not add-then-remove? Because the correction fact is dated to the original allocation's business time, so it ties with the receipt it corrects in the fold's sort order. With set membership, whether cash or card survived would depend on which id happened to sort first. With commutative deltas, both orders land on the same answer — which is also what lets the incremental open-day path and the authoritative refold agree without sharing an execution order.

Publication is then all-or-nothing. derivePaymentMix refuses when evidence was broken, when any received value could not be attributed to a method, when the participation cap is exceeded, or when a value is not a safe integer. The final gate is arithmetic: if the rows do not sum to exactly the frame's paymentsCollectedMinor, the answer is unavailable. There is no partial state, because a breakdown that contradicts the number beside it is worse than no breakdown.

Failure boundaries

Three behaviours are easy to get backwards and are worth stating explicitly.

Gross mix follows the receipt, not the allocation's later fate. An inbound allocation that is later voided still contributes its gross method value on the day it was received, because paymentsCollectedMinor counts that receipt either way. Withholding the mix value would leave the day unable to reconcile to its own total. Reversals and refunds move settlement, never gross mix. This one was found by the verifier after the emitter had already shipped the opposite rule.

An unknown is not a change. A lane that goes from complete to unavailable, or a legacy baseline that never had a mix, is unknown — and nobody amends an accepted report because a fact stopped being provable. Only a complete mix is hashed into the weekly truth fingerprint, and the amendment gate additionally requires both sides complete and different.

Reseed does not replay a correction. Purge-then-rebuild reads each allocation's persisted method, which is already its post-correction final state. Replaying the correction's audit history would take the value off the method it actually ends in.

What changed, and what deliberately did not

Changed

  • Four optional dimensions on the existing payment report fact; fingerprint version 3.
  • Day fold publishes a mix plus the bounded participation state behind it; fold version 6, so already-folded days are refreshed by the existing repair.
  • Weekly current, accepted baseline, and amendment carry a per-lane mix; the mix joins weekly truth fingerprinting.
  • Reports and the weekly manager email select and explain the effective revision's mix.
  • The verifier recomputes method values and use counts independently from the source ledger.
  • The approved POS method correction fails atomically when its reclassification fact cannot be recorded.

Deliberately not changed

  • No new table, worker, index, repair queue, taxonomy registry, rollout framework, or UI component.
  • No backfill or rewrite of existing facts, accepted reports, or the sealed Wigclub correction.
  • No refund-method mix, net settlement, processor fees, disputes, or chargebacks.
  • Public reads stay projection-only; no paymentAllocation, reportFact, POS, or Daily Close read was added to a client-facing query.
  • The automatic weekly email stays baseline-only and never consumes amendment or current truth.
  • Payments totals keep their existing meaning: an unclassifiable method leaves them untouched and withholds only the breakdown.

  1. The rendered mix covered only the included lane while the total printed beside it covered the whole labelled range.
  2. An accepted read carrying an amendment showed the baseline's mix beside amendment totals.

Guidance for next time

When a report counts things, name the thing being counted. If a count is derived from per-row evidence, write down what one unit of the count actually is before writing arithmetic. "Count the rows" is a decision, usually the wrong one, and it is easy to make by accident.

Prefer commutative deltas over set mutation whenever an incremental path and a batch path must agree, or whenever two contributions can share a timestamp. Order-independence bought correctness here for free.

Give every published breakdown a reconciliation target and refuse to publish when it misses. Withholding is cheap; a plausible-looking breakdown that contradicts the number above it costs trust.

Treat an absent optional field as unknown and, on immutable records, as positive authority to read the frozen evidence. Reading absence as zero is how a rollout quietly rewrites history.

Build the independent verifier even when the fold looks obviously right. The one on this branch found a real disagreement between the emitter and the census about voided receipts, after the emitter had shipped.

Operationally: fold version 6 refolds otherwise-clean days through the existing repair, so lanes containing an unrepaired day read unavailable until it drains. Stores whose payment methods fall outside cash, card, and mobile_money will persistently read unavailable until their source data is normalized — which is the honest answer, not a defect.

Comprehension quiz

Ten questions. Eight correct to pass.

  1. Why did the weekly Payment mix disagree with the Payments received total printed above it?

    1. The mix used a different currency conversion.
    2. The mix aggregated completed Daily Closes, so it excluded open days and outside-schedule payments that Payments received included.
    3. The mix was computed on a stale cache.
    4. Refunds were subtracted from one figure but not the other.

    Payments received had already moved onto payment-allocation facts covering the whole labelled week, while the mix still needed a completed close to exist at all. The two sections were describing different scopes.

  2. What is the participation identity for an allocation attached to a POS transaction?

    1. The allocation's own id.
    2. The register session id.
    3. The POS transaction id, so several same-method allocations on one transaction count as one tender use.
    4. The customer profile id.

    Daily Close counts the transaction. Using the transaction id as the participation identity is what makes the new count agree with buildPaymentTotals.

  3. A single POS transaction is paid with two separate cash allocations of 20 and 10. What does the mix report for cash?

    1. Value 30, two tender uses.
    2. Value 30, one tender use.
    3. Value 10, one tender use.
    4. Value 30, and the day is marked unavailable.

    Value is additive so both allocations count in full, but they share one participation identity and method, so the pair contributes a single use.

  4. Why does the participation state store a net count per pair instead of adding and removing set members?

    1. To reduce the size of the stored document.
    2. Because sets are not serializable in Convex.
    3. Because a method correction is dated to the original allocation's business time and can tie with the receipt it corrects, so the result must not depend on fold order.
    4. To allow negative tender-use counts to be displayed.

    Commutative deltas make the fold order-independent, which is also what lets the incremental open-day path and the authoritative refold reach the same answer without sharing an execution order.

  5. A day's method rows sum to 9,900 but its paymentsCollectedMinor is 10,000. What is published?

    1. The rows, with a rounding disclaimer.
    2. The rows, plus an "other" row of 100.
    3. Nothing — the mix is unavailable, because a complete mix must reconcile exactly.
    4. The rows, scaled proportionally up to 10,000.

    There is deliberately no partial state. A breakdown that does not add up to the total beside it is worse than no breakdown at all.

  6. An inbound cash allocation is received on Monday and voided on Tuesday. What happens to Monday's cash mix value?

    1. It is removed, because the payment was reversed.
    2. It stays, because gross mix follows the receipt and Monday's paymentsCollectedMinor counts that receipt either way.
    3. It moves to Tuesday.
    4. Monday's mix becomes unavailable.

    Reversals move settlement, not gross receipts by method. Removing the value would leave Monday unable to reconcile to its own total — a disagreement the independent verifier actually caught.

  7. An accepted weekly baseline has no paymentMix field at all. How is that read?

    1. As an empty mix with zero rows.
    2. As a signal to recompute the mix from current facts.
    3. As legacy authority: read the frozen closeEvidence.payments and do not reconstruct it.
    4. As a validation error that blocks the read.

    Absent means unknown, and on an immutable accepted record it is positive authority to use the frozen close-backed evidence rather than permission to rewrite history.

  8. A week's mix goes from complete to unavailable because one contributing day lost its method evidence. Should this raise an amendment on the accepted baseline?

    1. Yes, any change to the stored mix is an amendment.
    2. No — an amendment claims the week moved, and a fact that stopped being provable did not move anything.
    3. Yes, but only if the totals also changed.
    4. No, because accepted baselines can never be amended.

    Only a complete mix is hashed into the weekly truth fingerprint, and the amendment gate requires both sides complete and different, so an unknown never masquerades as changed truth.

  9. Why must a full reseed avoid replaying an approved method correction from audit history?

    1. Because corrections are not stored durably.
    2. Because reseed runs before corrections are applied.
    3. Because the rebuilt allocation already carries its post-correction final method, so replaying the move would take the value off the method it actually ends in.
    4. Because replaying would violate the fact fingerprint.

    Purge-then-rebuild reads persisted state, which is already final. The correction's history stays audit-only during reseed.

  10. Why does the read layer combine both the included and outside-schedule lanes before rendering?

    1. To reduce the number of stored fields.
    2. Because the outside-schedule lane is otherwise discarded.
    3. Because the Payments received figure printed beside the mix covers the whole labelled date range, so the mix must cover the same frame to reconcile.
    4. Because acceptance only freezes one lane.

    Stored documents keep the lanes separate as evidence. The combination is a read-time conclusion, matching how the headline total is derived.
