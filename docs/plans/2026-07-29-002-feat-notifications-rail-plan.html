Implementation Plan

Centralized admin notifications rail

Type: feat · Status: active · Created: 2026-07-29 · Source: docs/plans/2026-07-29-002-feat-notifications-rail-plan.md (canonical)

Build a platform notifications rail — intent ledger, code-owned kind registry, subscription-based audience resolution, and a leased delivery ledger drained by immediate dispatch plus a safety-net sweeper — then port the three ad hoc admin email flows (register closeout, EOD daily manager report, POS terminal health) onto it. Future communications become one registry entry plus one template.

Problem & Requirements

Admin emails are bolted onto call sites: three flows hand-roll recipient loops over a hardcoded ADMIN_EMAILS constant, duplicate the MailerSend fetch, and invent per-flow dedupe via marker fields patched onto domain rows. Register closeout alerts are lost forever on one failed send; nothing sends outside prod; there is no store- or role-based routing.

  • R1 Domain code emits intents; no knowledge of channels, recipients, templates, transport.
  • R2 New communication = registry entry + template only.
  • R3 Audience from notificationSubscription data (org × optional store × category × channel); ADMIN_EMAILS fallback fires only when an org has zero subscription rows for the category — an empty filtered match (all disabled, or scoped to another store) suppresses the intent instead, so disabling every subscription in a category does silence it.
  • R4 Ledgered deliveries: lease tokens, a bounded per-dispatch batch (MAX_DELIVERIES_PER_DISPATCH) so a serial send loop finishes inside the action time limit, attempt caps, backoff, provider idempotency keys, percent-encoded dedupe-key components.
  • R5 Hybrid dispatch: immediate runAfter(0) for every kind (no urgency tiering) + one sweeper cron.
  • R6 Render at send time from fresh data; unsendable payloads suppress.
  • R7 Environment gate lives in transport; full pipeline runs everywhere.
  • R8 Terminal delivery failure records an operationalEvent.
  • R9 Three flows ported; legacy markers, admin loops, ledger writers retired. Cutover guards turned out to be three lanes, not two: POS closeout markers (U7) plus an EOD action-required read of the legacy automationNotificationDelivery ledger (U8); EOD applied/prepared stays unguarded.
  • R10 In-app channel schema-supported but stubbed.

Scope Boundaries

  • No subscription-management UI (seeded via internal mutation).
  • No customer-facing email or WhatsApp porting.
  • Manual explicit-recipient report actions stay outside the rail.
  • ADMIN_EMAILS is not deleted (fallback + new-order admin email).
  • Category granularity only; no per-kind overrides yet.
Deferred follow-up: in-app inbox UI reading readAt; porting remaining admin-ish emails; subscriptions admin surface.

Key Technical Decisions

  • Hybrid dispatch (immediate + sweeper) over sweeper-only — variance alerts need near-real-time. (user-confirmed)
  • Render-at-send over snapshot-at-emit — retries reflect current data; payload queries double as sendability checks. (user-confirmed)
  • Per-category subscriptions (cash_controls, eod, system_health). (user-confirmed)
  • Stage gate in transport — staging exercises the pipeline; non-prod redirects to NOTIFICATIONS_DEV_RECIPIENT or records the delivery as suppressed, never a false sent. (user-confirmed)
  • Terminal failures record operational events; in-app stubbed. (user-confirmed)
  • Reserving a delivery is leasing it: rows born in_flight with a lease token; no pending delivery state.
  • Timeouts classify retryable (not outcome_unknown) because sends are idempotency-keyed by delivery id.
  • Rail is separate from operationalEvent, not a projection of it.

Design Shape

Directional guidance for review, not implementation specification.

emit(kind, subject, payload) inside the domain mutation → intent row (no-op on dedupeKey hit) → unconditional runAfter(0) dispatch → reserve mutation leases one delivery per recipient × channel, at most one batch per pass (re-scheduling itself for the remainder) with the lease sized to that batch → registry prepareEmail loads fresh payload and renders the existing template (null ⇒ suppress; throw ⇒ retry with backoff) → transport sends with Idempotency-Key: deliveryId and 15s timeout → lease-guarded completion (sent / retryable with backoff / terminal + operational event / suppressed). A sweeper (every 5 minutes in prod, 60 minutes elsewhere) recovers expired leases, due retries, and undispatched intents, with independent per-phase budgets and abandonment of an intent once it has sat unreserved for longer than INTENT_ABANDON_AFTER_MS (6h, wall-clock — not a pickup count); requeueAbandonedIntent is the dashboard-only recovery path.

New module: packages/athena-webapp/convex/notifications/ — deliveryPolicy (pure), registry (4 kinds), transport, emit, dispatch, sweeper, seed; tables in convex/schemas/notifications.ts.

System-Wide Impact

  • Three mutation call sites switch from scheduling send actions to emitting intents; one new cron; new notification_delivery_failed and register_closeout_notification_skipped operational event types.
  • Send failures become ledgered delivery states with retries instead of throws inside fire-and-forget actions.
  • Legacy marker fields stop being written but stay in schema; automationNotificationDelivery becomes read-only legacy.
  • Unchanged: payload queries, templates, subjects, EOD outcome policy, POS sync ingestion semantics.
