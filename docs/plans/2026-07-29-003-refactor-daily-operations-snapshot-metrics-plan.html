Problem and target

The weekly companion query currently builds seven visible dates and one comparison boundary. Each date can read transactions, adjustments, expenses, and Daily Close rows: up to 32 indexed queries and roughly 6,400 capped rows.

Target: one bounded close-window read, then no mutable financial-source reads for dates with an effective completed and structurally usable frozen snapshot.

Daily Operations stays a read-only aggregate. EOD Review remains the close owner; Reports remains amended financial truth.

Authority rule: resolve within each operating date. Store-global isCurrent cannot identify the authoritative historical revision.

Key decisions

DecisionWhy
Frozen snapshot for finalized datesMatches EOD History semantics and stops mutable-source drift.
Strict v2 snapshot eligibilityMetadata must identify the requested store day and remain within one hour of request-derived boundaries, with a 23–25 hour duration for DST transitions; source entries must exactly match the frozen metadata, and absent or mis-bucketed money cannot become authoritative.
One contiguous close-range readThe seven dates plus prior Saturday form one bounded eight-date window.
Live fallback retainedOpen, reopened, legacy-snapshot, malformed, and ambiguous dates keep current correctness; legacy lifecycle rows with valid v2 snapshots remain eligible.
Allowlisted metric projectionPrevents close-only carry-over and variance data from changing the weekly contract.
Unique, consistent date-local authorityDuplicate terminal rows or broken revision links cannot safely select frozen financial truth.
Whole-window fallback at row 201Exactly 200 candidates is complete; the extra row proves truncation, so no frozen financial authority is trusted.

Implementation units

U1 · Characterize eligibility and read behavior

Instrument the existing in-memory query harness and pin snapshot authority, lifecycle resolution, fallback, redaction, and serialized metric shape before production changes.

Primary file: packages/athena-webapp/convex/operations/dailyOperations.test.ts

Proof: tests execute compound-index ordering and record table, index name, predicates, terminal operation, and limits—not merely equal output.

U2 · Route weekly analytics through frozen closes

Bulk-load close candidates, resolve authority per date, project usable frozen summaries, and invoke the existing live builder only for fallback dates.

Primary files: dailyOperations.ts and its focused backend tests.

Proof: the normal path uses 1 + 3k metric-source queries for k fallback dates; capped windows discard snapshot authority and recover through the established path.

U3 · Preserve refresh and client contracts

Apply the same decision to selected/prior refresh metrics, retain redaction and cache merge semantics, and capture the boundary in Athena's read-amplification learning.

Primary files: backend refresh tests, optional frontend characterization, and the existing performance solution note.

Proof: no public arguments or response fields change.

Verification strategy

  • Snapshot values win over deliberately conflicting live rows.
  • Active completed → reopen → reclose moves authority frozen → live → replacement frozen.
  • Historical automation works with isCurrent: false.
  • Malformed, incomplete, unsupported, or ambiguous evidence falls back live.
  • Seven dates and prior boundary share identical selection logic.
  • Full-admin, POS-only, timezone, today-refresh, and client merge behavior remain stable.
  • Table/index observers prove finalized dates avoid POS, adjustment, and expense reads.
  • Normal-path cost is 1 + 3k; cap-triggered recovery is measured and reported separately.
  • A pre-rollout sample establishes usable-snapshot coverage and representative close-document size.
  • Matching 24-hour and 72-hour production windows compare bytes per call, errors, and p50/p95 latency.
