Repair the existing POS telemetry rails so unexpected frontend failures are remotely diagnosable without changing cashier behavior or adding another observability system.

Summary and problem frame

What surfaced

M Supplies Register 1 showed “The drawer could not open locally,” but the native IndexedDB failure was flattened before any remotely accessible event was recorded.

The audit also found route coverage gaps, console-only handled failures, drain-time scope assignment, warning-dominated inspection, invisible telemetry-rail degradation, and unbounded server retention.

What changes

Reuse the bounded offline buffer, Convex ingest/dedupe, runtime heartbeat, and Terminal Health panel. Add occurrence-time scope, finite failure classifications, safe legacy compatibility, exact handled seams, terminal/error filtering, and 30-day local/server retention.

Core posture: telemetry remains best effort and evidentiary. It never becomes register authority, blocks a command, changes operator copy, or participates in recovery.

Scope boundaries

In scope

  • All production /pos/** routes and early/render/browser failures.
  • Drawer/native-storage evidence and exact audited handled seams.
  • Immutable store scope and clearly client-reported terminal/session correlation.
  • Finite v2 diagnostics, legacy rollout compatibility, rail-health gauges, terminal filtering, and retention.

Explicitly out

  • The underlying ledger purge/drawer reconciliation fix.
  • External SDKs, a new event table/transport, logger replacement, alerting, grouping, or sampling.
  • Raw payloads, arbitrary thrown text, public source maps, or exact-once cross-tab machinery.
  • Broader non-POS frontend telemetry.

Primary risks and controls

Replay and attribution

One oldest eligible scope per wakeup, order-preserving prefixes, per-scope backoff, and removal only after accepted + duplicates === sent.

Capture noise

One code-first expected-outcome classifier is shared by bootstrap, route boundary, and application sink. Unknown failures report; typed expected outcomes do not.

Privacy and rollout

Finite validators prohibit open-ended v2 text. Old clients are accepted only through a destructive legacy normalizer, and old stored raw fields never return to the UI.

Fixture and rail safety

Fixture resolution happens before any host/store hook. Telemetry failures become heartbeat facts, never recursive events or POS failures.

Verification strategy

  • Inject IndexedDB AbortError during drawer opening: unchanged operator copy, one safely classified event, correct store/client-reported terminal scope, no ledger/business text.
  • Prove offline/reload/reconnect, mixed stores/terminals, full and partial acknowledgements, replay dedupe, per-scope backoff, and concurrent-tab best-effort behavior.
  • Prove v1/v2 local decoding, old-client/new-server ingestion, unsafe legacy-field destruction, mixed stored-row reads, and 30-day boundary behavior.
  • Prove every POS route is structurally covered; fixture and expected auth/session/offline/conflict outcomes remain silent.
  • Using a production build and Terminal Health only, identify the actionable category, flow/operation, build, route ID, and terminal/session correlation for the drawer error and a generic runtime/render failure.
  • Run focused frontend/Convex suites, Convex audits, operation-admission checks, typecheck/build, Graphify rebuild, then pr:athena as merge-ready authority.
Completion bar: remotely visible is insufficient. If finite classifications and production source identifiers do not let support diagnose both representative failures, strengthen the closed classification set before U4 completes. Private symbolication remains deferred unless that still proves insufficient.
