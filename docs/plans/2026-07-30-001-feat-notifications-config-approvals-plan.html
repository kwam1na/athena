Summary & Problem Frame

Give operators a product surface to configure who receives admin notifications, and put approval requests on the notifications rail. Two workstreams:

  • Settings surface — a NotificationsView on the store configuration page manages notificationSubscription rows per category, backed by the rail’s first public Convex functions.
  • Approval emails — a new approvals.request_created kind emails subscribed managers when an approval request needing asynchronous manager approval is created, with per-requestType template differentiation and suppression for requests already decided.

The rail (PR #710) centralized delivery but left audience config dashboard-only and shipped no UI; async approval requests today notify nobody. Requests created and decided in the same flow by a present manager need no notification — the pending ones do, and “pending row created” is exactly the discriminator the code already provides.

Scope Boundaries

In scope

  • Four category cards (cash_controls, eod, system_health, new approvals): list, add, enable/disable, remove recipients
  • Member picker (managers first) + free-form email entry
  • Three-state semantics UI: fallback active / active recipients / silenced
  • approvals.request_created kind + ApprovalRequestPending template + shared insert helper wrapping all eight insert sites

Out of scope / deferred

  • In-app channel and inbox UI (still stubbed)
  • Store-scoped subscription rows (org-wide only in v1)
  • Dispatch delay, digest, batching (ship as-is, user-confirmed)
  • Manager-role auto-sync (recipients stay explicit rows; a one-time manager seed at rollout is in scope in U5)
  • Admin-side variance-review notification gap (pre-existing; follow-up)
  • Any change to existing kinds, dedupe keys, or PR #710 cutover guards
Sharp semantics the UI must teach: zero rows for a category → hardcoded ADMIN_EMAILS fallback; first row added → fallback stops entirely; rows exist but all disabled → category is silenced (fallback does not re-arm). Remove-last and disable-last look similar but have opposite outcomes — each gets distinct confirmation copy.

High-Level Design (directional, not implementation spec)

Backend flow: domain mutation → insertApprovalRequestWithCtx (skips variance_review) → emitNotificationWithCtx with dedupe = request id → dispatchIntent at 0 delay → prepareEmail re-reads the request → still pending: descriptor-driven ApprovalRequestPending render to the approvals audience; decided/deleted: null → suppressed.

Frontend flow: NotificationsView (configuration page, full_admin) → bounded list query per category + member-picker query → add/toggle/remove mutations (admission rail, full_admin server check, demo guards, dedupe/cap/format integrity) → rows consumed unchanged by dispatch’s resolveRecipients.

System-Wide Impact

  • Interaction graph: six domain command paths gain an in-transaction emit; dispatch/sweeper unchanged; configuration page gains its first non-store.config view.
  • Error propagation: emit failures would fail domain transactions — mitigated by schema-first ordering (U1) and idempotent dedupe; null-vs-throw keeps suppression and transient faults separate.
  • State lifecycle: subscription rows outlive membership (deferred badge); fast-resolved approvals end as one suppressed intent each, bounded by dedupe.
  • Unchanged invariants: existing kinds, dedupe keys, cutover guards, transport, delivery policy, sweeper, and fallback semantics are untouched — the UI only makes the semantics visible.
