Align weekly payment mix with live payments

Add the smallest missing payment-method and participation contribution to Athena's existing report fact, then carry it through the day, week, query, and email rails already in production.

Goal and boundary

Payment mix will use the same full-frame payment facts as Payments received and represent gross receipts before refunds. POS tender uses match Daily Close by counting each distinct transaction and normalized method pair once; non-POS payments fall back to allocation identity. New accepted reports freeze that evidence; legacy accepted and corrected reports keep their existing close-backed mix.

Constraint: no new table, worker, queue, taxonomy registry, rollout framework, endpoint, UI component, or interaction.

Implementation units

U1 · Existing payment facts

Add normalized method and a stable participation identity in the central allocation emitter, then retain that identity through the existing approved POS correction fact. Preserve v1/v2 facts; full reseed rebuilds final allocation state without replaying the method move twice.

U2 · Existing day fold

Sum every allocation's value while counting distinct identity-method pairs through incremental ingest and authoritative refold.

U3 · Existing weekly lifecycle

Compose current days, freeze cutoff facts at acceptance, and include mix in the existing amendment fingerprint.

U4 · Existing presentation

Select the effective stored revision and reuse the current Reports panel and weekly email rendering.

U5 · Existing verification

Extend the allocation census with the same transaction-method participation rule and use current allowlists and stale-fold repair; never touch accepted history.

Complexity removed from the prior draft

  • No payment-method taxonomy schema or service.
  • No pending envelope, outbox, scheduler, or correction-repair worker.
  • No participation ledger or changes across every payment caller; the central emitter derives the stable identity from existing allocation fields.
  • No normalization, mix-contract, or taxonomy version stack.
  • No three-stage feature-gate framework or new alert/classification system.
  • No independent normalization implementation, correction audit replay system, or new history payload branch.
  • No “Show all methods” UI or additional component.

Focused verification

  • Payment fact replay, legacy fingerprint compatibility, refunds/voids, and approved correction rollback.
  • Incremental/refold parity, exact reconciliation to Payments received, and Daily Close-aligned transaction-method use counts.
  • Current, accepted, amendment, legacy accepted, and corrected-preview selection.
  • Allocation verifier comparison and accepted-record immutability during existing refold repair.
