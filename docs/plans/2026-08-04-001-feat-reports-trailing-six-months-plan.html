Adding a trailing six-month period to Reports

Three parts ship together: a new Trailing 6 months window, drill-down reach raised to match it, and the SKU mix chart routed by span onto the bounded resumable snapshot lifecycle that Units moved uses, for the multi-day ranges that need it.

The span ceiling is 184 days, not 183. The window is calendar-month aligned, and the longest six calendar months (Mar–Aug, May–Oct, Jul–Dec, Aug–Jan) span 184 inclusive days. A 183-day ceiling would fail only on those windows — an intermittent, date-dependent bug that reads as a random production failure rather than an off-by-one.

Mix is span-routed — this is the headline design change. Mix is ambient: it fires on every workspace visit and every day click, so it cannot inherit movement's on-demand model. Selections of ≤2 days stay on the synchronous reader forever, provably under the 5,000-row cap because folds bound reportSkuDay at 2,000 rows per day (2 × 2,000 < 5,000). Only multi-day ranges use the async snapshot lifecycle. This kills ambient request volume at the source instead of tuning budgets around it.

Presets are decoupled from the window enum. ReportDateRangeField maps over an explicit preset list, not the raw enum, so a window can exist without a preset button appearing before every surface it reaches is ready. R3 holds at every unit boundary: presets decouple in U1, the enum/tab/snapshots land together in U2, and the six-month preset is appended last in U7.

Key technical decisions

DecisionRationale
Ceiling is 184 days, not 183Six calendar months span up to 184 inclusive days. A 183 ceiling fails only on those windows — a date-dependent bug that looks random in production. Documented at the constant with the arithmetic.
Route mix by span at the clientSpans of ≤2 days are provably under the 5,000-row cap (2,000 rows/day fold bound), so single-day selection — the dominant interaction — stays synchronous forever and never touches async admission. Multi-day ranges use the snapshot lifecycle.
Accept a calm pending state on multi-day first computationAfter each day folds, the default range's revision vector changes and the first visit mints a new snapshot. Dedupe makes every subsequent visit instant; a warm-ahead scheme is deferred, not needed.
Mix has no ranking phaseMix only ever shows top 5 + Other — no numbered pages, no ordinal addressing. Accumulate into child rows with a units-sold sort key, accumulate totals and SKU count on the header, and read top 5 via the sort-key index at read time. Phases: queued → aggregating → completed.
Per-surface ceilings during rolloutRaising one shared span constant would widen the synchronous mix reader past what it can serve. Ceilings are named per surface in U1 and applied per surface in U5/U7.
Decouple presets and tabs from the window enum's landingThe enum drives both presets and tabs. U1 introduces an explicit preset list (the current four); the enum, tab, and snapshots land together in U2; the six-month preset is appended only in U7, once every surface it reaches serves 184.
Generalize the lifecycle over kind before adding a third consumerCopy-pasting the movement lifecycle would triple the fencing, admission, cleanup, and backstop logic and guarantee divergence. Extract the kind-generic seams first, then add mix as configuration.
Sibling child table, not a reused movement tableThe movement child table's field names encode signed movement semantics. A sibling table reuses the index pattern with honest names.
Admission budget keyed by kind, sized for ambient use, no migrationA third consumer must not eat Units moved's budget. Buckets are 10-minute fixed windows, so old rows age out within one window of the key change — no migration machinery needed.
No fold-version bumpCertified provenance is already stamped at fold version 3 across production history. Verified as a U4 precondition, not assumed.
Mix totals are header state; Other is derivedThe Other bucket has no natural durable row. Header totals let the reader derive Other as total minus visible.
The overview backfill computes; no empty-preferenceSingletons refresh only for dirty-day stores, so a quiet store may never be rewritten. With the scan constant widened and the backfill routed through it, the read-time backfill can compute the six-month fields correctly — so it does. Short-history stores show partial totals, exactly as Trailing 30 and Trailing 3 months already do; no special understatement guard.
comparisonFor() gains an explicit case and a defensive fallbackToday's fallback silently yields the three-month comparison for any unrecognized window — a wrong number, not a visible error.

Generalized range lifecycle

custom_summary→ sku_movement→ sku_mix

Three request kinds now share one kind-generic machinery: admission (kind-keyed), fencing, scheduling, backstop, cleanup, and sanitized errors. Kind-specific behavior stays behind a small per-kind configuration — source projection, child row shape, totals struct, phase set (mix omits ranking entirely: queued → aggregating → completed, with top 5 read via the sort-key index), and constants.

Implementation units

U1 · Vocabulary, ceilings, preset decoupling

Define the six-month calendar math and named per-surface ceilings, and decouple the range-picker presets from the window enum — without changing any surface's behavior yet.

U2 · Six-month overview window

Land the window end to end on the overview: enum value, label, tab, snapshots, comparison, and a backfill that computes for quiet stores the sweeper never touches.

U3 · Generalize the range lifecycle over kind

Extract the movement lifecycle's kind-generic seams so a third request kind can be added as configuration, with movement behavior provably unchanged.

U4 · Async SKU mix snapshot backend (no rank)

Compute complete SKU mix for any admitted multi-day period as a bounded resumable snapshot with no ranking phase, opening by verifying the no-fold-bump premise.

U5 · Span-routed SKU mix surface

Route mix by span — synchronous for ≤2-day selections, snapshot lifecycle for multi-day — preserving the settled context that also feeds the Units moved sheet.

U6 · Shared-demo parity

Serve the new window and both mix paths in demo mode within the fixture's existing 21-day horizon, matching the established Trailing 3 months convention.

U7 · Drill-down reach and preset enablement

Raise the days table, SKU detail, and Units moved to the 184-day ceiling, then append the six-month preset last, once every surface it reaches serves the span.

U8 · Focused validation, build, and Graphify refresh

Run the focused suites named by U1–U7, require a clean production app build, and rebuild Graphify; the merge gate and PR are explicitly deferred.

Where this could go quietly wrong

  • Quiet-store overview backfill — solved by computing, not guarding. Singletons refresh only for dirty-day stores, so a quiet store's singleton may never be rewritten by the sweeper. The read-time backfill is that store's only source of the new fields; it now computes the six-month values via the widened shared scan constant rather than relying on an empty-preference or understatement guard, and short-history stores simply show partial totals, matching the existing convention.
  • Ambient usage and the daily pending state. Mix is ambient rather than on-demand, so after each day folds, the default multi-day range's revision vector changes and the first visit that day mints a new snapshot before dedupe makes every later visit instant. This designed pending state must read as calm and intentional, not as breakage — it is bounded (a short aggregation, a handful of worker batches), and a warm-ahead scheme that would eliminate it entirely is deferred as a named follow-up rather than built now.

The demo-horizon risk from the earlier draft is resolved: the fixture's 21-day horizon is retained as-is, and the six-month demo window renders from the same 21 days the three-month window already does — an established convention, not a gap.
